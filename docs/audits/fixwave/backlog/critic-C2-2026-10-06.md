## Owner decisions (with recommendations)

1. **Identity linking (F249-01, F249-03).** Options: (a) build verified linking. An authenticated web user starts a
   link, a one-time code goes out through the target channel, the reply binds it, and the action is audited and can be
   revoked. Reuse the TRG-36 `slack_identity_links` design. (b) Remove `link_identity` and document that principals are
   per channel. **Recommendation: (a)**, scheduled together with the deferred channel work (channels are parked
   by the owner). Add the cross-channel e2e test then.
2. **Data-classification gate (F250-01/02/03).** Options: (a) carry out AP10-T10: classify recalled memory, knowledge
   and handoffs before prompts, gated by `DATA_CLASSIFICATION`. (b) Treat AP10-T10 as superseded by guardrails_v2 and
   the sanitization layers: delete `redaction.py`, the unread flag and `state_context.py` (with its now-dead siblings
   `cache_bridge`, `cache_policy`, `knowledge_policy`, `memory_policy`, `session_memory`), and keep the classifier for
   few-shot. **Recommendation: (b).** The regex classifier is too coarse to gate every prompt: any `ddd-dd-dddd`
   becomes PHI and any phone number becomes PII. The live screening layers already cover outputs, logs and ingestion.
   Update the AP10 plan's status note when this is decided.
3. **Domain role templates (F250-04).** Options: (a) delete the module and its tests. (b) Ship
   `POST /auth/roles/from-template` with permissions only. (c) Build an ABAC evaluator first. **Recommendation: (a)**
   for now. Shipping templates whose names promise conditions ("assigned matters only", "client's own matters") that
   nothing enforces would grant broader access than the role name says.
