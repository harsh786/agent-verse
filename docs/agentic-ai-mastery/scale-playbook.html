Scale playbook

Deployment topology and the numbers at 10, 10k, and 10M goals/day.

Orientation

Everything in this book changes character at scale. A pattern that is elegant at 10 goals/day is a cost incident at 10M; a control that is thorough is a bottleneck; a shortcut that is harmless becomes the outage. This chapter is the playbook for what changes, and when, presented as three regimes — 10, 10k, and 10M goals per day — because the right architecture is different at each.

The single most useful framing: at every scale the binding constraint moves. At small scale it is capability (can it do the task at all); at medium scale it is reliability and cost (does it stay up and stay affordable); at large scale it is isolation and tail behaviour (does one tenant's spike hurt another, and what happens at the p99). Design for the constraint you have, and know which one comes next.

The playbook

01Deployment topology#

ShippedTopologyImpl8/10Criticality9/10

The physical shape: API replicas, a worker fleet split by plan queue, Postgres with pgvector, Redis for state and messaging, and the optional full stack (pgbouncer, Keycloak, object store, observability).

Mechanism

The minimum production topology: stateless API replicas behind a load balancer, a Celery worker fleet with pools per plan queue, Postgres+pgvector as the datastore, and Redis for pub/sub, cache, locks, and checkpoints. The full stack adds pgbouncer (connection pooling), Keycloak (identity), an object store (artifacts, screenshots), an observability stack (OTel collector, tracing backend), a search backend, and mail. Workers and API are stateless because state lives in Postgres and Redis — so both scale horizontally.

In AgentVerse

  • infra/docker-compose.ymlthe full stack (postgres, redis, pgbouncer, keycloak, celery worker+beat, minio, mailpit, otel, jaeger, searxng, frontend)
  • app/main.pythe API app (stateless, replica-safe)
  • app/scaling/celery_app.pythe worker fleet
  • app/core/pools.pyconnection pooling

Worked example

minimum prod       API ×3 · workers (per-queue pools) · Postgres+pgvector · Redis
full stack adds    pgbouncer · Keycloak · MinIO · OTel+Jaeger · SearXNG · mail
scaling            add API replicas for request load; add workers per queue
                   for goal load; both stateless, state in Postgres/Redis

At production scale

Statelessness is the property that makes horizontal scaling work — because agent state lives in Redis checkpoints and Postgres, any worker can pick up any goal and any replica can serve any request. pgbouncer becomes essential once worker count grows, or connection exhaustion caps you before compute does. The full stack's components map to chapters throughout this book — each is infrastructure for a capability, not optional decoration.

Failure modes

  • Stateful workers. Losing horizontal scalability.
  • No connection pooling. Connection exhaustion under fan-out.
  • One worker pool. No per-plan isolation.

Choose it when

  • Any production deployment.

02The 10/day regime: get it right#

ShippedRegimeImpl8/10Criticality6/10

At small scale the constraint is capability, not scale — a single process, in-memory services, one queue and one database are fine, and the effort belongs in correctness, not distribution.

Mechanism

At tens of goals a day, run the in-memory service path (the pre-swap phase of chapter 19), a single worker, one Postgres, and optionally one Redis. Skip per-plan queues, sharding, and read replicas — they solve problems you do not have. Spend the effort on getting the agent loop, the patterns, the retrieval, and the guardrails right, because at this scale a wrong answer matters more than a slow one.

In AgentVerse

  • app/main.pycreate_app(manage_pools=False) — the in-memory path (chapter 19)
  • app/providers/fake.pyno keys needed to develop
  • infra/docker-compose.ymlpostgres + redis is the minimum (per CLAUDE.md)

Worked example

a pilot deployment
 single API + worker, one Postgres, one Redis
 in-memory services, real providers from env keys
 no per-plan queues, no sharding, no replicas
 all effort on: does the agent do the task correctly?

At production scale

The mistake at this regime is premature distribution — building sharding and multi-region for a pilot that serves ten goals a day. The correctness work (patterns, retrieval, guardrails, evals) transfers to every later regime; the distribution work does not exist yet as a need. Build the capability right, and add scale machinery when the constraint actually moves.

Failure modes

  • Premature distribution. Complexity solving non-problems.
  • Neglecting correctness. A fast wrong answer.

Choose it when

  • Pilots, early products, internal tools.

03The 10k/day regime: reliability and cost#

ShippedRegimeImpl8/10Criticality9/10

The constraint becomes staying up and staying affordable — the DB/Redis-backed swap, per-plan queues, breakers, idempotency, budgets, and caches all become load-bearing here.

Mechanism

At thousands of goals a day, real tenants and real money arrive. The DB/Redis-backed service path (the lifespan swap of chapter 19) is now essential for cross-replica state; per-plan queues (chapter 20) isolate tenants; circuit breakers (chapter 28) handle provider flakiness; idempotency (chapter 28) makes the constant retries safe; Redis-backed budgets (chapter 13) keep cost accurate across replicas; and caches (chapter 29) become the dominant cost lever. This is where the platform's reliability and cost machinery earns its place.

In AgentVerse

  • app/main.pythe lifespan swap to DB/Redis-backed services (chapter 19)
  • app/scaling/celery_app.pyper-plan queues (chapter 20)
  • app/reliability/*, app/governance/cost.pybreakers, idempotency, budgets (chapters 28, 13)
  • app/rag/semantic_cache.py, app/mcp/tool_cache.pycaches (chapter 29)

Worked example

growth to 10k/day
 enable the DB/Redis swap → cross-replica state, durable checkpoints
 split queues by plan → the enterprise SLA survives a free-tier backfill
 breakers + idempotency → provider flakiness and retries stop hurting
 budgets + caches → cost per goal understood and controlled
the machinery that was optional at 10/day is load-bearing here

At production scale

This is the regime most production platforms live in, and the one where the reliability and cost chapters of this book pay off. The failure mode is arriving here with the 10/day architecture — in-memory services that lose state on restart, one queue that lets one tenant starve another, no idempotency so retries double-charge. The transition is not one change but the activation of a dozen mechanisms that were dormant.

Failure modes

  • 10/day architecture at 10k. State loss, noisy neighbours, double-charges.
  • No cost controls. A surprise invoice.
  • No breakers. Provider outages becoming yours.

Choose it when

  • Real tenants, real money, thousands of goals a day.

04The 10M/day regime: isolation and the tail#

PartialRegimeImpl6/10Criticality8/10

At the largest scale the constraint is isolation and tail behaviour — bulkheads, backpressure, sharding, read replicas, and regional residency, with the p99 (not the mean) as the number that matters.

Mechanism

At millions of goals a day, the constraints are one tenant's spike not hurting another (bulkheads and backpressure, chapter 28), the database not being a single bottleneck (sharding by tenant, read replicas for retrieval), and the tail latency being acceptable (the p99, since at this volume the tail is a large absolute number of unhappy users). Regional residency (chapter 30) becomes a topology concern — data and compute pinned per region. Much of this — cross-region active-active, tenant sharding — is where the platform's current implementation thins out, which the rating reflects.

In AgentVerse

  • app/reliability/bulkhead.py, app/qos/backpressure.pyisolation under load (chapter 28)
  • app/core/pools.pyconnection pooling (pgbouncer)
  • app/db/rls.pytenant isolation that sharding would build on
  • app/lifecycle/*residency for regional topology (chapter 30)

Worked example

at 10M/day the numbers that matter
 p99 latency, not mean — the tail is millions of requests
 per-tenant bulkheads — one tenant's spike is invisible to others
 sharding by tenant + read replicas — the DB is not one bottleneck
 regional topology — EU data and compute stay in the EU
this regime's machinery is where the platform is thinnest (see the rating)

At production scale

Rated 6 on implementation deliberately: bulkheads, backpressure, and RLS-based isolation exist, but tenant sharding, cross-region active-active, and the operational maturity for 10M/day are where the platform would need investment. The honest position is that the architecture is sound to this regime's door — stateless workers, per-plan queues, Redis-backed coordination — but the last mile (sharding, multi-region, p99 engineering) is future work, which is exactly the kind of gap this manual is meant to name.

Failure modes

  • Optimising the mean. A p99 that is unusable for millions.
  • Single database. The bottleneck at the top.
  • No regional topology. Residency and latency both failing.

Choose it when

  • Genuinely large scale — and expect to build the last mile.

What is missing here

  • Tenant sharding. RLS isolates logically; physical sharding of the datastore by tenant for the largest scale is future work.
  • Cross-region active-active. Regional residency is enforced; multi-region failover and active-active operation are not built.
  • p99 engineering. Latency is measured per percentile (chapter 10) but systematic tail-latency reduction is thin.
  • Load-test harness at scale. No documented harness for validating the 10M/day regime before reaching it.
