Simulation, red team, golden datasets, readiness gates, replay.

Orientation

You cannot test an agent the way you test a function, because its output is non-deterministic and its actions touch real systems. This chapter is how you gain confidence anyway: simulate before you execute, attack before an attacker does, measure against golden data, gate on readiness, and replay what happened.

The unifying principle is prove it in a sandbox before it touches production. Every technique here is a way to exercise an agent's behaviour — under mock tools, adversarial inputs, or replayed history — without the cost of a real mistake, so that when it does act for real, it has already been shown to behave.

Testing and certification

01Simulation and mock-tool sandboxes#

PartialTestingImpl7/10Criticality8/10

Run an agent against mock tools that return realistic results but have no real effects — so a goal that would file a return or send a payment can be exercised end-to-end, safely, thousands of times.

Mechanism

A simulation environment provides mock implementations of tools that return plausible results without side effects. An agent runs its full loop — plan, execute, verify — against these, so you observe its behaviour, its tool choices, and its failures without touching a real system. This is the substrate for evals (chapter 10), for certifying code-capable strategies (chapter 25), and for testing goals that are too dangerous to run for real during development.

In AgentVerse

  • app/enterprise/simulation.pythe mock-tool sandbox
  • app/sandbox_runtime/simulation_runner.py, sandbox_trace.pyrunning and tracing simulations
  • app/testing/harness.pythe test harness
  • app/api/simulation · frontend features/simulationthe surface

Worked example

test a "file GST amendment" goal
 mock tools: gst.fetch_filed returns a realistic filed return; gst.file_return
   records the call but files nothing
 the agent runs its full loop → observe: correct plan? right tools? gate hit?
 run 500 variations → measure behaviour distribution
no real filing, no real risk, full-loop confidence

At production scale

Simulation is what lets you develop and test dangerous goals at all — you cannot iterate on a payment-filing agent by filing real payments. It is also the engine under offline evals and strategy certification. The one risk is mock fidelity: mocks that diverge from real tool behaviour pass in simulation and fail in production, so mocks must be kept realistic and cross-checked against live behaviour periodically.

Failure modes

  • Unrealistic mocks. Passing simulation, failing live.
  • Simulation only for happy paths. Untested failure behaviour.

Choose it when

  • Any dangerous goal, and as the substrate for evals and certification.

02Red teaming#

ShippedSecurityImpl8/10Criticality10/10

Attack the agent before an attacker does: a growing corpus of injection, exfiltration, jailbreak, and abuse attempts, replayed on every change, with zero tolerance for a new pass.

Mechanism

A red-team corpus of adversarial cases — direct and indirect injection, encoded payloads, exfiltration attempts, dangerous-command generation, jailbreaks, cross-tenant probing — each asserting the control that should stop it. It runs as a safety eval (chapter 10) on every prompt, model, and guardrail change. The corpus only grows: every real incident and near-miss becomes a permanent case, so the platform can never regress on an attack it has seen.

In AgentVerse

  • app/enterprise/red_team.py, red_team_corpus.pythe red-team engine and corpus
  • app/evals/safety_score.pysafety scoring (chapter 10)
  • app/intelligence/indirect_injection.py, encoding_attacks.pythe detectors under test (chapter 12)
  • app/api/red-team · frontend features/red-teamthe operator surface

Worked example

red-team run on a prompt change
 190 cases across 8 attack categories
 189 blocked by the asserted control · 1 new pass (indirect injection)
 → BLOCKED: zero tolerance → the change cannot ship until fixed
the one that got through becomes a permanent regression case

At production scale

Red teaming is the safety net that makes fast iteration safe — prompt changes are the most common cause of safety regressions, and running the corpus on every change catches them before they ship. The ratchet is the point: the corpus never shrinks, so the platform's security monotonically improves. Asserting the specific control (not just the outcome) tells you not only that an attack was blocked but by what, so a regression is diagnosable. Full treatment in chapter 10.

Failure modes

  • Stale corpus. Yesterday's attacks only.
  • Tolerance for a new pass. One relaxed case becoming policy.
  • Testing only direct injection. Missing the harder indirect vector.

Choose it when

  • Always, before any external exposure.

03Golden datasets and regression gates#

PartialTestingImpl7/10Criticality8/10

A curated set of cases with known-good outcomes, built from real production runs, against which every change is measured — and a gate that blocks a change that regresses a protected dimension.

Mechanism

Golden datasets are curated cases (inputs plus expected outcomes or rubrics) drawn from real production — especially failures, which become permanent regression cases (chapter 10). A regression baseline records the incumbent's scores; a regression gate compares a candidate and blocks on a regression beyond tolerance in a protected dimension (safety and grounding at zero tolerance). This is the mechanism that makes rapid iteration safe: nothing ships that regresses what mattered.

In AgentVerse

  • app/api/golden_datasets.py, app/evals/dataset_builder.pycurated sets, built from production
  • app/evals/regression_baseline.py, regression_gate.pybaseline and gate
  • app/evals/certification_policy.pywhat must pass (chapter 10)

Worked example

golden set: 420 cases, half from real failures
 candidate prompt change → run the set
 goal 0.89 (was 0.87) · grounding 0.82 (was 0.82) · safety 0.98 (was 1.00)
 → BLOCKED on safety (zero tolerance) → fix or named override
the failures that built this set can never recur silently

At production scale

Golden datasets built from real failures are worth far more than synthetic ones — they encode the actual ways the system has been wrong, and the gate ensures it is never wrong that way again. The discipline is to feed every production failure back into the set (chapter 10's online-to-offline bridge), so the safety net tightens over time. Keep safety and grounding at zero tolerance; everything else can trade.

Failure modes

  • Synthetic-only sets. Easier than reality, flattering every change.
  • No gate. Regressions found by customers.
  • Auto-updating baseline. Drift with nothing to compare against.

Choose it when

  • Before the first automated change ships.

04Readiness gates, certification, and replay#

PartialOperationsImpl7/10Criticality8/10

Before anything serves production traffic it must pass a readiness gate and be certified against evidence; after it runs, replay lets you reconstruct exactly what happened for debugging or audit.

Mechanism

A readiness gate refuses to serve if a required control or dependency is unavailable (chapter 28). Certification binds a version to eval evidence — this agent, strategy, or connector passed these suites at these scores, approved by this person (chapter 10) — and uncertified configurations stay in the lab. Replay reconstructs a past goal from its recorded events and prompt recipes (chapter 11), so an incident is reconstruction, not archaeology, and a fix can be tested against the exact failing run.

In AgentVerse

  • app/runtime_readiness/readiness_gate.py, dependency_health.pyreadiness
  • app/orchestration/strategy_certification.py, app/rag/certification.py, app/mcp/certification.pycertification (chapter 10)
  • app/api/replay.py, app/coordination/replay.pyreplay
  • app/observability/runtime_decision_trace.pythe record replay reconstructs from (chapter 11)

Worked example

promote agent fin-ops@v13
 readiness gate: all required controls available? → yes
 certification: passed goal/retrieval/grounding/safety suites, approved → yes
 → serves production
incident on an earlier run: replay g-8891 from its events + prompt recipes
 → reproduce exactly → test the fix against the real failing case

At production scale

Certification is how you safely offer a large catalogue of agents, strategies, and connectors — each proven against evidence before it serves real tenants, and certificates expiring on model changes (chapter 10). Replay is the incident-response superpower: with recorded events and prompt recipes (stored, not full prompts, for cost and privacy — chapter 8), you reconstruct any run exactly and test a fix against it, turning speculative debugging into deterministic reproduction.

Failure modes

  • Uncertified paths reachable. The gate bypassable.
  • Certificates without expiry. Outliving the models they were measured against.
  • Replay impossible. Mutable sources or missing recipes.

Choose it when

  • Any multi-configuration platform, and before any incident.

What is missing here

  • Chaos and fault injection. Reliability primitives (chapter 28) exist; systematic fault injection to verify they hold together under failure is thin.
  • Mock-fidelity monitoring. Simulation mocks can drift from real tool behaviour with no continuous cross-check.
  • Automated red-team generation. The corpus grows from incidents; a generator that produces novel attacks to probe for unknown weaknesses is future work.
  • Property-based testing for agents. Cases are enumerated; testing invariants ("never calls a forbidden tool") across generated inputs is not first-class.
