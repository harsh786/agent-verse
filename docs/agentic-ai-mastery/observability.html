Observability

Logs, metrics, traces, decision traces, and the incident playbook.

Orientation

An agent is a distributed system that also makes non-deterministic decisions, which means it needs everything ordinary observability provides — logs, metrics, traces — plus a layer ordinary systems lack: a record of why the agent decided what it decided. When a goal costs $14 or takes an unexpected action, the question is never "which service was slow" but "why did the planner choose that, what did it retrieve, what did the verifier see". That is a decision trace, and it is the difference between debugging an agent and guessing about one.

The organising principle is one correlation id, many linked traces: a goal id ties together its logs, its metrics, its decision trace, its RAG traces, its cost breakdown, and its audit entries, so any one question is one query rather than a cross-reference across six systems.

The signals

01Structured logging#

ShippedSignalImpl9/10Criticality9/10

Every log line is a queryable event with the goal id, tenant, and step — never a free-text string — so "show me everything that happened in goal g-8891" is one filter.

Mechanism

A logger produces structured records with consistent fields: correlation id, tenant, agent, goal, step, level, and event-specific data. Sensitive values are redacted at the logging boundary, not hoped to be absent. The logger is one of the most-connected nodes in the whole system precisely because everything logs through it.

In AgentVerse

  • app/observability/logging.pyget_logger() — the structured logger (a top hub node, 575 edges)
  • app/tenancy/context.pycontext fields injected into every line
  • app/data_classification/redaction.pyredaction at the log boundary

Worked example

{"ts":"...", "level":"info", "corr":"g-8891", "tenant":"acme",
 "agent":"fin-ops", "step":3, "event":"tool_call",
 "tool":"gst.fetch_filed", "risk":"read", "ms":180}
query: corr="g-8891" → the whole goal's timeline, ordered, in one view

At production scale

Structured-first is not optional at scale: grepping free text across a fleet does not work, and the redaction-at-the-boundary discipline is what keeps customer data out of a log that a hundred engineers can read. Sample verbose events; keep errors and decisions at full fidelity.

Failure modes

  • Free-text logs. Ungreppable at scale.
  • PII in logs. Redact at the boundary, not by convention.
  • Missing correlation id. Events that cannot be joined.

Choose it when

  • Always.

02Metrics#

ShippedSignalImpl8/10Criticality9/10

The numbers that go on a dashboard and drive alerts: goals per minute, success rate, iterations, cost, latency percentiles, tool success — labelled by tenant, agent, and goal class.

Mechanism

Counters, gauges and histograms emitted at every meaningful event, with labels that let you slice by the dimensions that matter. The agent-specific metrics — iterations per goal, stall-detection rate, pattern set used, delegation rate — are as important as the infrastructure ones, because they are the leading indicators of cost and quality regressions.

In AgentVerse

  • app/observability/metrics.pymetric definitions and emission
  • app/observability/health.pyhealth metrics
  • app/scaling/tasks.pyper-stage counters

Worked example

agent_goals_total{tenant,agent,status}
agent_iterations{quantile="0.99"}          → cost regression detector
rag_strategy_delegations_total{from,to}    → a capability broke
ingestion_quality_drops_total{reason}      → a parser regressed
approval_queue_depth{tenant}               → an unserviced backlog

At production scale

The three agent metrics that belong on the main dashboard: p99 iterations (cost), stall-detection rate (broken retrieval or tools), and approval queue depth (an outage that pages nobody). Slice everything by goal class — aggregates hide the regression in one slice that moved thirty points.

Failure modes

  • Aggregate-only. Regressions hidden in slices.
  • Missing agent metrics. Infra green, agents misbehaving.
  • Label explosion. Per-goal-id labels blowing up cardinality.

Choose it when

  • Always.

03Distributed tracing#

ShippedSignalImpl8/10Criticality8/10

Spans across the whole request — API, queue, worker, model calls, tool calls, database — so latency is attributable to a stage rather than guessed.

Mechanism

OpenTelemetry spans propagate the trace context from the API through the queue into the worker and down each model and tool call. The trace shows where wall-clock actually went — usually a tool round-trip or a serial chain of model calls, rarely the place people assume — and exports to a backend like Jaeger.

In AgentVerse

  • app/observability/tracing.pyOTel setup and propagation
  • app/workflow/otel.pyworkflow-step spans
  • app/observability/model_trace.pyper-model-call spans
  • app/ingestion/pipeline.pya span per ingestion stage

Worked example

trace for goal g-8891 (total 41s)
 api.submit            12ms
 queue wait            1.2s   ← queue depth on the enterprise queue
 worker.plan           2.9s
 worker.execute
   tool gst.fetch      8.1s   ← the real cost, one slow connector
   tool invoices.query 0.3s
 worker.verify         1.8s
attributes the 41s precisely; the fix is the connector, not the model

At production scale

Trace context must survive the queue hop, or the worker's spans float detached from the request — the single most common tracing gap in agent systems, because the Celery boundary is where propagation is easy to drop. Sample traces (1–5%) plus all errors keeps the backend affordable.

Failure modes

  • Context lost at the queue. Detached worker spans.
  • Model/tool calls not spanned. The interesting part invisible.

Choose it when

  • Any multi-service or async execution — so all of them.

04Runtime decision traces#

ShippedSignalImpl8/10Criticality10/10

The agent-specific signal: a record of every decision the runtime made — which pattern, which model, which tools, which policy constraints — with the reason for each.

Mechanism

Each decision point records its inputs, its choice, and its reason: the classifier's output, the assembled pattern set and why, the model selected per role, the policy constraints applied, the routing decision. This is what turns "the agent did something weird" into "the classifier scored this expert, so the assembler added ToT and self-consistency, which is why it cost $4". Without it, agent behaviour is a black box that invites the useless conclusion "use a bigger model".

In AgentVerse

  • app/observability/runtime_decision_trace.pythe decision trace
  • app/orchestration/decision_trace.pySelectionDecision — orchestration choices
  • app/observability/pattern_trace.pywhich patterns ran
  • app/policy_runtime/policy_trace.pyPolicyTrace — policy decisions
  • app/explainability_runtime/decision_explainer.pyhuman-readable explanation

Worked example

decision trace g-8891
 classify   complexity=expert domain=analytical risk=high conf=0.88
 assemble   +CoT +reflection +self_refine +self_consistency +ToT +hitl
            reason: expert(HIGH) + analytical(HIGH) + risk=high(CRITICAL)
 models     planner=large executor=large verifier=mid
 policy     denied admin.*, gated write_high, cost ceiling $8
 route      agent fin-ops (connector match + 96% history)
"why did this cost $4?" → the six reasoning patterns, and here is the rule
for each

At production scale

The decision trace is the highest-value observability investment specific to agents. It converts cost and behaviour investigations from speculation into lookups, and it is what the explainability surface reads to answer an operator's or a regulator's "why". Make every decision record its reason — an unexplained choice is a debugging dead end.

Failure modes

  • Choices without reasons. You see what, not why.
  • Decisions not recorded. The black box returns.

Choose it when

  • Any agent whose behaviour or cost you will ever need to explain.

05RAG traces and cost breakdown#

ShippedSignalImpl8/10Criticality8/10

Two specialised traces: retrieval (strategy, filters, candidates, scores, delegation) and cost (tokens and spend per model, tool, and phase) — the two questions asked most after "why is it wrong" and "why is it expensive".

Mechanism

The RAG trace records each retrieval leg with its scores and any delegation, so a retrieval failure is diagnosable as recall, precision, or coverage (chapter 6). The cost breakdown attributes every token and every metered call to a component, so a cost spike points at a section — usually tool schemas or an expensive reasoning pattern — rather than at a vague "the model".

In AgentVerse

  • app/observability/rag_trace.pyretrieval trace
  • app/rag/agentic/rag_trace.pyagentic retrieval trace
  • app/observability/cost_breakdown.py, cost_breakdown_api.pycost attribution
  • app/observability/model_trace.pyper-call model usage

Worked example

RAG trace  strategy=hybrid→rerank · filters{policies} · 312→50→8 · scores
           0.94..0.41 · no delegation
cost break planner $0.06 · executor $0.21 (schemas 38%) · verifier $0.05
           embeddings $0.002 · tools $0.06 · total $0.38
two lookups answer "why wrong" (recall/precision/coverage) and "why
expensive" (which component)

At production scale

These two traces close most agent investigations. The cost breakdown in particular ends the recurring argument about model choice by showing that tool schemas, not the model, are 38% of the executor spend — a fixable, non-model problem. Surface both to tenants for their own goals; cost transparency changes behaviour.

Failure modes

  • Traces without scores. What was retrieved, not why.
  • Cost without attribution. A total nobody can act on.

Choose it when

  • Any retrieval-augmented or cost-sensitive agent.

06Goal events, SSE, and worker events#

ShippedDeliveryImpl9/10Criticality8/10

The live view: every step of a goal streams to the frontend as it happens, over Redis pub/sub and Server-Sent Events, so an operator watches execution rather than polling for a result.

Mechanism

The agent emits events at every transition — planned, executing, tool called, verified, waiting on approval, completed. These publish to a per-goal Redis channel; a subscriber bridges Celery workers to the API process, and the API streams them to the browser over SSE. The same events feed observability, so the live view and the historical record are the same data.

In AgentVerse

  • app/services/goal_service.pysubmit_goal, subscribe_events, the Celery→pub/sub bridge
  • app/services/goal_events.py, event_store.pyevent definitions and store
  • app/scaling/tasks.pyappend_submitted_goal_event, run_goal
  • agent-verse-frontend/src/lib/sse/useGoalStream.tsthe browser subscriber

Worked example

browser subscribes to goal g-8891
 ← {type:"planned", steps:5}
 ← {type:"executing", step:1}
 ← {type:"tool_call", tool:"gst.fetch_filed"}
 ← {type:"waiting_human", step:4, reason:"filing approval"}
 [hours later, after approval]
 ← {type:"completed", result:...}
the worker died and resumed between step 1 and step 4; the stream is
continuous because events flow through Redis, not the worker's memory

At production scale

Routing events through Redis pub/sub rather than a direct worker-to-browser connection is what makes the live view survive worker restarts and work across replicas — the browser is connected to the API, not to the worker that happens to be running the goal. This is the same mechanism that makes durable HITL possible.

Failure modes

  • Events tied to worker lifetime. The stream dies when the worker does.
  • No replay from the store. A reconnecting client missing what it did not see live.

Choose it when

  • Any goal a human wants to watch.

07SLOs and alerting#

PartialOperationsImpl7/10Criticality8/10

Define what "healthy" means per goal class and alert on the deviations that matter — including the agent-specific ones that infrastructure monitoring will never catch.

Mechanism

An SLO tracker measures against targets — success rate, latency percentile, grounding rate, cost per goal — and an alert router sends deviations to the right channel with the right severity. The alerts that matter most are agent-specific: a grounding-rate drop (a corpus regression), a stall-rate spike (broken retrieval or tools), an approval backlog (a silent outage), a delegation-rate jump (a broken capability).

In AgentVerse

  • app/observability/slo_tracker.pySLO tracking
  • app/observability/alert_router.pyrouting and severity
  • app/api/sla.py, public_status.pySLA and status surfaces
  • app/voice/alerts.pyvoice alerting

Worked example

SLOs (goal class "chat answer")
 success ≥ 0.95 · grounding ≥ 0.85 · p95 ≤ 4s · cost ≤ $0.05
alert  grounding 0.85 → 0.71 over 3 days
       → severity high → #agent-oncall
       → decision trace shows the "vendor-contracts" collection re-chunked
         with fixed@v1 → root cause in minutes

At production scale

Grounding rate is the best early-warning signal an agent platform has: it is cheap to compute on every answer (chapter 18) and it drops hours before users complain when a corpus or retrieval path regresses. Alert on it. And watch the approval queue — a backlog there is an outage that no infrastructure alert will ever fire on.

Failure modes

  • Infra-only SLOs. Green dashboards, unhappy users.
  • Alert fatigue. Thresholds so tight nobody reads them.
  • No grounding alert. The fastest signal, unused.

Choose it when

  • Any production deployment with users who notice.

08Audit correlation and replay#

ShippedOperationsImpl8/10Criticality8/10

Tie the observability signals to the audit trail by the same id, and be able to replay a goal from its recorded events — so an incident investigation is reconstruction, not archaeology.

Mechanism

The goal id links the decision trace, the RAG traces, the cost breakdown, and the audit entries, so an investigation moves seamlessly from "what was approved" (audit) to "why was it proposed" (decision trace) to "what did it retrieve" (RAG trace). Replay reconstructs a goal from its event stream and prompt recipes, letting you re-run it against a fix or step through exactly what happened.

In AgentVerse

  • app/api/replay.pygoal replay
  • app/coordination/replay.pycoordination replay
  • app/governance/audit_v3.pythe audit entries keyed by goal
  • app/provenance/claim_trace.pyclaim-level provenance

Worked example

investigation: "why was a ₹418k filing submitted?"
 audit       approved by j.iyer at 16:41, argument hash matches execution
 decision    plan proposed the filing; verifier passed against the filed
             return; consensus required (risk=critical) and reached
 RAG trace   the recomputed total came from chunk [2], filed record
 replay      re-run the goal with the same fixtures to confirm
one id, four signals, a complete answer

At production scale

The correlation is what makes incident response fast. Without it, an investigation is a manual join across systems that takes hours and often ends inconclusively. Store prompt recipes rather than full prompts (chapter 8) so replay is possible without a storage or privacy problem.

Failure modes

  • Different ids per system. No join.
  • Mutable sources. A re-chunked collection making replay impossible.

Choose it when

  • Before your first incident.

09Debugging and incident workflows#

PartialOperationsImpl7/10Criticality9/10

A repeatable playbook: from symptom to signal to root cause to fix, using the traces rather than reasoning about the model — because "use a bigger model" is the answer you reach when you cannot see.

Mechanism

The workflow follows the signals. A quality complaint → RAG trace (recall/precision/coverage) → the right fix (chunking, reranking, or ingestion). A cost spike → cost breakdown → the component (tool schemas, a reasoning pattern, iterations). A wrong action → decision trace + audit → the rule or the missed gate. A latency regression → distributed trace → the slow stage. Each symptom has a signal that localises it, and the discipline is to look before theorising.

In AgentVerse

  • app/observability/*the signals the playbook uses
  • app/api/observability.py, insights.pythe operator surfaces
  • app/explainability_runtime/*decision, profile, and source explainers
  • RUNBOOK.mdthe operational runbook

Incident playbook

SymptomFirst signalLikely root cause
Wrong answers risingRAG trace + groundingCorpus/chunking regression, or a broken sync
Cost spikeCost breakdownTool schemas, a pattern, or iteration blowout
Latency regressionDistributed traceA slow connector or serial model chain
Unexpected actionDecision trace + auditMisclassification or a missed gate
Goals stuckApproval queue depthUnserviced HITL backlog
Stall-rate spikeMetrics + RAG traceRetrieval returning nothing, or a dead tool

At production scale

The playbook exists to prevent the two worst incident outcomes: a fix aimed at the wrong layer (changing the prompt for a retrieval failure) and the reflexive "use a bigger model" that costs more and fixes nothing. Every symptom in the table has a signal that localises it in minutes — the investment is having built the signals before you needed them.

Failure modes

  • Theorising before looking. Fixes aimed at the wrong layer.
  • No playbook. Every incident debugged from scratch.
  • Signals that do not exist yet. Building observability during the incident.

Choose it when

  • Any production system that gets paged.

What is missing here

  • Automated root-cause suggestion. The signals exist; nothing correlates a symptom to a likely cause automatically the way the playbook does manually.
  • Trajectory diffing. No tool to show what changed between a working and a failing run of the same goal beyond the final result.
  • Tenant-facing observability. Rich internal signals; a thinner story for letting a tenant debug their own agents' behaviour and cost.
  • Cost-anomaly detection. Cost is attributed but a per-tenant spend anomaly detector is not wired to alerting.
