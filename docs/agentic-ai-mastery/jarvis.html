Jervis (JARVIS) console

The operator cockpit: design tokens, live streams, human control.

Orientation

"Jervis" — the JARVIS-style console — is the operator's cockpit: the React frontend through which a human submits goals, watches them execute live, approves gated actions, inspects memory and traces, and steers the fleet. It is named for the Iron Man AI because the design language is deliberately that — a dark, instrument-panel aesthetic with a boot sequence, live telemetry, and spring-based motion — but the substance is a serious piece of information design over a complex backend.

The reason it earns a chapter: an agent platform is only as governable as its console makes it. Every control in the safety and governance chapters (HITL approval, emergency stop, policy, budgets, audit) is only real if a human can see it and act on it in time. The console is where the abstract controls become operable, and its design decisions — a shared design-token system, live SSE streams, human-in-the-loop surfaces — are architecture, not decoration.

The console

01The design-token system#

ShippedDesign systemImpl8/10Criticality6/10

One source of truth for colour, motion, and spacing — the electric-cyan-on-slate JARVIS palette expressed as tokens, so 60+ feature pages look like one product rather than sixty.

Mechanism

Design tokens define the palette (electric #00D4FF, semantic emerald/amber/rose/violet, a five-level surface hierarchy, text tiers), spring-motion presets (never duration/ease), and glow tiers, synced with CSS variables. Every page imports the tokens rather than hardcoding values, so a palette change is one edit. The JARVISPageShell wraps each page with consistent entrance motion, spacing, and accessibility (aria-live, focus management, reduced-motion).

In AgentVerse

  • agent-verse-frontend/src/lib/design/tokens.tscolours, shadows, tw helpers, spec-aligned token map
  • agent-verse-frontend/src/lib/design/motion.tsspring presets
  • agent-verse-frontend/src/components/ui/JARVISPageShell.tsxthe page wrapper
  • agent-verse-frontend/src/components/ui/JARVISBootScreen.tsxthe startup sequence

Worked example

tokens   electric #00D4FF · surfaces #020408→#2D3748 · text #F1F5F9/#94A3B8
motion   SPRING_PAGE {stiffness 280, damping 26} — springs, never durations
shell    every page: blur-in entrance, staggered children, aria-live region,
         useReducedMotion fallback
change the accent once in tokens.ts → the whole console updates

At production scale

A token system is what keeps a large, fast-moving frontend coherent — the alternative is sixty pages that drift apart as different people build them. The accessibility built into the shell (reduced-motion, focus, aria-live) is not optional for a console operators use all day, and baking it into the wrapper means every new page inherits it rather than re-implementing it. (This manual's own design borrows the same electric accent, honouring the project's existing system.)

Failure modes

  • Hardcoded colours. Pages that drift from the system.
  • Duration-based motion. The inconsistent feel springs avoid.
  • Accessibility per-page. Inconsistent, often forgotten.

Choose it when

  • Any frontend beyond a handful of pages.

02Live goal execution view#

ShippedLive viewImpl9/10Criticality9/10

The heart of the console: watch a goal plan, call tools, and verify in real time over SSE — so an operator sees what the agent is doing, not just its final answer.

Mechanism

The goal detail page subscribes to the goal's SSE stream (chapter 11) and renders each event as it arrives: the plan appearing, steps executing, tool calls, verifier verdicts, replans, and completion. Because events flow through Redis pub/sub, the view is continuous even across worker restarts, and a reconnecting client can resume. This is the surface that makes agent execution legible rather than a black box that returns a result minutes later.

In AgentVerse

  • agent-verse-frontend/src/features/goals/GoalDetailPage.tsxthe live view
  • agent-verse-frontend/src/lib/sse/useGoalStream.tsthe SSE hook
  • agent-verse-frontend/src/features/goals/adaptiveResult.tsadaptive result rendering per connector
  • app/services/goal_service.pythe backend event source

Worked example

operator opens goal g-8891
 live: "planned (5 steps)" → "executing step 1" → "tool: gst.fetch_filed"
       → "waiting for your approval: file amendment" → [operator approves]
       → "executing step 4" → "verified" → "completed"
the operator watched the agent work and approved the one action that
needed a human — the whole point of the console

At production scale

The live view is what turns "the AI did something" into "I watched the AI do it and approved the risky step". It is the difference between a system operators trust and one they fear. The SSE-over-Redis design (chapter 11) is what makes it robust: the operator is connected to the API, not to the worker, so the view survives the fleet churn that is constant in production.

Failure modes

  • Result-only view. No visibility into execution.
  • SSE without reconnect. A dropped stream losing the live view.
  • No adaptive rendering. Raw JSON where a rendered result belongs.

Choose it when

  • Any goal a human should be able to watch or steer.

03Human-in-the-loop surfaces#

ShippedControlImpl9/10Criticality10/10

Where the abstract HITL gate becomes a button: a queue of pending approvals, each showing the proposed action, its arguments, and the evidence — enough to decide without reading the transcript.

Mechanism

The approval surface renders the HITL queue (chapter 1): each pending request shows the action, its exact arguments, why it was flagged, and the supporting evidence. Approving or denying resumes or fails the goal; the decision is recorded and the argument hash is compared at execution. A badge surfaces pending approvals across the console so nothing waits unseen. The same surface handles clarification requests — the agent asking a question rather than proposing an action.

In AgentVerse

  • agent-verse-frontend/src/features/approvals/the approval surface
  • agent-verse-frontend/src/components/ui/PendingApprovalsBadge.tsxthe always-visible badge
  • agent-verse-frontend/src/features/chat/chat + HITL surface
  • app/governance/hitl.pythe backend gateway
  • app/collaboration_runtime/clarification.pyclarification requests

Worked example

approval card
  action    file GSTR-1 amendment
  arguments period 2026-03, total ₹418,200, GSTIN 27AAAPZ…
  reason    write_high + regulated domain
  evidence  [the recomputed total, the filed return, the diff]
  [Approve]  [Deny]  [Ask a question]
badge shows "3 pending" across every page so none is missed

At production scale

The approval UX is where governance succeeds or fails operationally. Design it for the phone, because approval latency dominates gated-goal time (chapter 1); show enough to decide without opening the run; and make the pending badge impossible to ignore, because an unserviced approval queue is a silent outage (chapter 11). This surface is the concrete form of the platform's most important safety control.

Failure modes

  • Too little context. Forcing the approver to open the whole run.
  • Hidden queue. Approvals waiting unseen.
  • Desktop-only design. Approvers who are never at a desk.

Choose it when

  • Any platform with gated actions.

04Governance and emergency controls#

ShippedControlImpl8/10Criticality10/10

The operator's steering wheel and brake: policy management, budget dashboards, the audit trail, and an emergency stop that can halt a tenant's agents at once.

Mechanism

The governance page exposes the controls from chapter 13 as an interface: view and edit policies (with changes propagating fleet-wide via Redis, chapter 20), watch budgets and spend, read the hash-chained audit trail, and — critically — an emergency stop that halts execution for a tenant or the fleet when something is going wrong. The emergency stop is the control you hope never to use and must be able to reach instantly.

In AgentVerse

  • agent-verse-frontend/src/features/governance/policy, e-stop, budgets
  • agent-verse-frontend/src/features/audit/the audit trail view
  • agent-verse-frontend/src/features/security/, rbac/, compliance/security surfaces
  • agent-verse-frontend/src/lib/api/client.tsgovernanceApi
  • app/governance/*, app/policy_runtime/*the backend controls

Worked example

incident: a connector is returning bad data and agents are acting on it
 operator → governance page → emergency stop for tenant acme
 → all running goals pause, no new goals start
 → operator disables the connector (policy change propagates in seconds)
 → resumes
the audit trail records the stop, who, when, and why

At production scale

An emergency stop is the control that makes autonomous agents deployable at all — the ability to halt everything instantly is what lets you grant autonomy in the first place. Policy changes propagating in seconds (not on next deploy) is what makes the console a real steering wheel rather than a status display. These surfaces are the operational face of chapters 12–14.

Failure modes

  • No emergency stop. Nothing to pull when it goes wrong.
  • Policy changes needing a deploy. Too slow to matter in an incident.
  • Audit not surfaced. No operator view of what happened.

Choose it when

  • Any platform with autonomous or high-risk agents.

05Memory, agent, and observability inspection#

PartialInspectionImpl7/10Criticality7/10

The console makes the invisible visible: browse an agent's memory, watch its autonomy and reputation, and inspect the decision, RAG, and cost traces that explain its behaviour.

Mechanism

Inspection surfaces render the internal state the earlier chapters describe: a memory browser shows what an agent remembers and lets an operator review or quarantine (chapter 3); an autonomy control sets the tier (chapter 22); observability pages render the decision, RAG, and cost traces (chapter 11) so "why did it do that / cost that" is answerable in the UI, not just in logs. This is where the platform's observability becomes an operator tool rather than an engineer's query.

In AgentVerse

  • agent-verse-frontend/src/components/agent/MemoryBrowser.tsx, AutonomyControl.tsx, DiscoveryPanel.tsxagent inspection
  • agent-verse-frontend/src/features/observability/, eval/, eval-suites/traces and evals
  • agent-verse-frontend/src/features/memory/, knowledge/, knowledge-graph/memory and knowledge
  • agent-verse-frontend/src/components/org/OrgChart.tsx, KanbanBoard.tsxorg visualisation

Worked example

an agent behaves oddly
 operator → memory browser → finds a suspicious lesson → quarantines it
 → observability → decision trace shows the classifier scored it expert,
   so six reasoning patterns ran → explains the cost
 → autonomy control → drops the agent to supervised until reviewed
all in the console, no log queries

At production scale

Inspection surfaces are what let operators — not just engineers — run the platform. A memory browser that lets an operator quarantine a poisoned lesson, an autonomy control that lets them dial back a misbehaving agent, and trace views that explain cost and behaviour turn the rich internal state of the backend into something a human can actually steer. This is the payoff of building observability and memory as first-class, inspectable subsystems.

Failure modes

  • State only in logs. Operators dependent on engineers.
  • Read-only inspection. Seeing a problem but unable to act on it.

Choose it when

  • Operators, not just engineers, need to run the platform.

06The builder, lab, and playground#

PartialAuthoringImpl7/10Criticality6/10

Where humans create and test agents: a natural-language builder, a workflow canvas, and a playground to trial an agent before it touches production.

Mechanism

The builder turns a description into an agent configuration via the meta-agent (chapter 9), validated against real capabilities. The workflow builder is a visual canvas for composing deterministic workflows (chapter 20 templates). The lab and playground let an operator run an agent against test inputs, see the full trace, and iterate before promoting it — the authoring counterpart to the certification gate (chapter 10).

In AgentVerse

  • agent-verse-frontend/src/features/builder/, lab/, playground/authoring and testing
  • agent-verse-frontend/src/features/workflow-builder/, workflow-engine/visual workflow canvas
  • agent-verse-frontend/src/features/templates/, marketplace/starting from templates
  • app/api/builder.py, lab.pythe backend surfaces

Worked example

builder: "an agent that reconciles vendor invoices monthly"
 → meta-agent proposes config → validated against acme's tools/collections
 → operator opens it in the lab → runs against last month's data
 → inspects the full trace → adjusts the threshold → certifies → promotes
create, test, and gate before a single real invoice is touched

At production scale

The builder and playground are what let non-engineers create agents safely — the meta-agent proposes, the human reviews, the lab tests, and certification gates. The workflow canvas serves the deterministic end of the spectrum where a fixed process is preferable to an autonomous agent. Together they make the platform authorable without making it dangerous, provided the certification gate is real.

Failure modes

  • Promote without testing. An agent reaching production untested.
  • Generated config auto-activated. No human review (chapter 9).

Choose it when

  • Non-engineers create agents, or workflows need visual authoring.

What is missing here

  • Mobile-first approval. The approval surface exists, but a genuinely mobile approval experience (the phone is where approvers are) is thinner than the desktop console.
  • Operator-facing cost attribution. Traces are rich; a tenant-facing "where your spend goes" breakdown per goal class is less developed (chapter 11).
  • In-console trajectory diffing. No UI to compare a working and a failing run of the same goal side by side.
  • Collaborative steering. The WebSocket collaboration layer exists; multi-operator steering of the same goal with presence and conflict handling is early.
