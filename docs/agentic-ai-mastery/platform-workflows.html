Orientation

This chapter is the spine that the rest of the book hangs on: the twenty-two steps a goal actually takes, from an HTTP request to a streamed result. Every subsystem you have met — retrieval, memory, guardrails, routing, audit — appears here as a station on one line. If you understand this flow, you understand how the pieces compose; if you are debugging, this is the map that tells you where to look.

The one structural idea to hold onto is the two-phase service wiring: the app is built once with in-memory services, then a lifespan upgrades them to DB- and Redis-backed versions. Most "works in tests but not in prod" bugs live in the gap between those two phases.

The twenty-two steps

01App startup and two-phase service wiring#

ShippedLifecycleImpl9/10Criticality10/10

The app is assembled once with in-memory services, then a lifespan swaps them for DB- and Redis-backed versions and re-hydrates state — the single most important thing to understand about the platform's behaviour.

Mechanism

create_app() constructs every service (tenant, goal, knowledge, MCP, cost, rate limiter…) in an in-memory form and binds them to app.state, then includes ~25 routers. When manage_pools=True, the FastAPI lifespan starts connection pools, swaps the in-memory services for DB/Redis-backed ones, re-hydrates state from Postgres, and re-wires auth, SSE, cost control, and the MCP client. Dependency resolution reads from app.state dynamically, so the swap takes effect without breaking already-registered middleware.

In AgentVerse

  • app/main.pycreate_app() (a hub node, 183 edges) and the lifespan
  • app/bootstrap/services.py, routers.pyservice and router assembly
  • app/core/pools.pyConnectionPools
  • app/db/session.pyget_session_factory()

Worked example

tests            create_app(manage_pools=False)
                 → in-memory services, no DB, deterministic FakeProvider
production       create_app() + lifespan(manage_pools=True)
                 → in-memory services built first
                 → pools start → services swapped to DB/Redis-backed
                 → sync_from_db() re-hydrates tenants, agents, schedules
                 → real providers resolved from env keys
the swap is why a bug can be invisible in tests and appear only in prod

At production scale

When something works in tests but not in production (or vice versa), this swap is the first suspect: the in-memory path and the DB-backed path are different implementations of the same interface, and behaviour that depends on persistence, cross-replica state, or real providers only exists on one side. Knowing the two phases exist turns a baffling bug into a targeted one.

Failure modes

  • State not re-hydrated. A service swapped but its data not loaded.
  • Middleware bound to the old service. The swap not taking effect.
  • Test-only behaviour. Relying on the in-memory path's quirks.

Choose it when

  • Understanding, debugging, or extending the platform — always start here.

02Steps 1–2: submission and tenant authentication#

ShippedStepImpl9/10Criticality10/10

A goal arrives over HTTP; middleware authenticates it, establishes the immutable tenant context, and sets the RLS boundary before any business logic runs.

Mechanism

The request hits POST /goals. Tenant middleware authenticates (API key or JWT), resolves the tenant, checks the key's scope and IP allowlist, and constructs the TenantContext. The database session sets app.tenant_id so RLS applies to everything that follows. Only then does the request reach the goal endpoint.

In AgentVerse

  • app/api/goals.pythe submit endpoint
  • app/tenancy/middleware.pyTenantMiddleware
  • app/tenancy/context.pyTenantContext
  • app/auth/scope_enforcement.py, ip_allowlist.pykey checks
  • app/db/rls.pythe boundary set per request

Worked example

POST /goals {goal:"reconcile March payouts"}  Authorization: Bearer ak_...
 middleware  key valid, scope goals:submit ok, IP in allowlist
             → TenantContext(acme, plan=enterprise)
 session     SET LOCAL app.tenant_id = 'acme'
 endpoint    now runs, everything it touches is tenant-scoped

At production scale

Authentication and scope establish the outermost two scopes (chapter 14) before the goal exists as a record — so an unauthorised or out-of-scope request never creates state. The RLS boundary being set here, at the session level, is what makes every downstream query safe by default. Full treatment in chapters 13–14.

Failure modes

  • Context not propagated to the worker. The goal runs without its tenant.
  • Scope checked after record creation. State for a request that should have been rejected.

Choose it when

  • Always — this is the front door.

03Steps 3–5: record, budget, queue, worker#

ShippedStepImpl9/10Criticality9/10

GoalService creates the record and checks the budget, enqueues the goal on the tenant's plan queue, and a Celery worker acquires a lock and builds the agent graph.

Mechanism

GoalService writes a GoalRecord, checks the tenant and goal budget, and enqueues onto a per-plan queue (goals.free … goals.enterprise) so an enterprise tenant is not stuck behind a free tenant's backlog. A worker picks it up, acquires a distributed lock (one worker per goal), and constructs the AgentGraph with the goal's runtime profile and model clients.

In AgentVerse

  • app/services/goal_service.pysubmit_goal, GoalRecord
  • app/services/goal_queue.pyenqueue_goal
  • app/scaling/celery_app.pyPLAN_QUEUE_MAP — per-plan routing
  • app/scaling/tasks.pyrun_goal, append_submitted_goal_event
  • app/reliability/distributed_lock.pyone worker per goal

Worked example

GoalService  record g-8891 · tenant budget ok · goal budget $8
enqueue      → goals.enterprise queue
worker-4     acquires lock lock:goal:g-8891 (worker-7 would skip)
             builds AgentGraph(runtime_profile, model clients, checkpointer)

At production scale

Per-plan queues are how the platform avoids noisy-neighbour effects — the single most important scaling decision for a multi-tenant agent system, because one tenant's batch of 10,000 goals must not delay another's interactive one. The lock prevents the duplicate-execution bug that otherwise appears under retries and rebalancing. Full treatment in chapters 20 and 32.

Failure modes

  • Shared queue. Noisy-neighbour delays.
  • No lock. A goal running twice on two workers.
  • Budget checked after enqueue. Work scheduled that cannot be paid for.

Choose it when

  • Any multi-tenant async execution.

04Steps 6–11: the agent loop#

ShippedStepImpl9/10Criticality10/10

Initialize, retrieve, plan, execute, verify — the LangGraph state machine from chapter 1, running with real tools, real credentials, and real approval gates, looping to replan or completing.

Mechanism

The graph runs the loop: initialize loads context and checks budget; retrieve runs RAG before planning; plan produces a validated plan; execute calls tools through MCP with vault credentials, guardrails, and HITL gates; verify checks against evidence and routes to complete, replan, max-iter, waiting-human, or rag-remediate. State is checkpointed after each node, so the goal survives a worker restart mid-loop.

In AgentVerse

  • app/agent/graph.pyAgentGraph — the state machine
  • app/agent/nodes/*.pyone mixin per node
  • app/mcp/client.pyMCPClient.call_tool — tool dispatch
  • app/providers/vault.pycredential resolution at call time
  • app/governance/hitl.pyapproval gates

Worked example

6 initialize  tenant ctx, agent config, budget check
7 retrieve    4 chunks from the runbook collection (chapters 2, 6)
8 plan        [fetch filed, recompute, diff, file*, notify]  (*gated)
9 execute     step 1 → MCP call, vault resolves the GST credential
              step 4 → write_high → HITL → waiting_human (checkpointed)
              [resume after approval]
10 verify     totals match the filed return → complete
11 (or replan on failure, bounded by max_iterations)

At production scale

This is the product. Every earlier chapter — patterns, retrieval, memory, prompts, guardrails, routing — converges here into the running loop. The checkpointing is what makes it operable: workers are cattle, a deploy mid-goal is not an outage, and a HITL pause costs nothing because the worker is released. Full treatment in chapter 1.

Failure modes

  • Non-serializable state. Checkpointing fails, resume impossible.
  • Credentials in state. A secret in the checkpoint.
  • Unbounded loop. No iteration cap (chapter 1).

Choose it when

  • Always. This is the core.

05Tool discovery and execution through MCP#

ShippedStepImpl9/10Criticality9/10

Tools live behind the Model Context Protocol: the registry lists what a tenant has, the client executes calls with circuit breaking and stale-cache fallback, and credentials are resolved from the vault so the model never sees them.

Mechanism

The MCP registry holds per-tenant connectors; tools/list discovers available tools; call_tool executes one, delegating to an inner implementation wrapped in a circuit breaker. On an open circuit it can serve a stale cached result before raising. Credentials are resolved from the vault at call time and injected into the request, never placed in the prompt. Results are sanitized and wrapped as untrusted before returning to the loop.

In AgentVerse

  • app/mcp/registry.pyper-tenant connector registry
  • app/mcp/client.pycall_tool, _call_tool_impl, CircuitBreakerOpenError, stale-cache fallback
  • app/mcp/tool_cache.pyToolResultCache
  • app/mcp/oauth.pyPKCE OAuth for connectors
  • app/providers/vault.pycredential resolution
  • app/mcp/servers/325 built-in server modules

Worked example

execute step "fetch filed GSTR-1"
 registry     gst connector present for acme
 vault        resolves the GST API token (model never sees it)
 call_tool    gst.fetch_filed(period, gstin)
              breaker closed → _call_tool_impl → result
              [if breaker open] → serve stale cached result or raise
 result       sanitized, wrapped untrusted, returned to the loop

At production scale

MCP is the architecture decision that makes tools safe and per-tenant: each connector is its own process, so a misbehaving integration cannot take the agent down, and the tool surface is configuration rather than compiled in. The stale-cache fallback is a thoughtful touch — a read tool whose provider is down can still answer from cache rather than failing the goal. Full treatment in chapter 20.

Failure modes

  • Credentials in the prompt. Exfiltration surface.
  • No breaker on the connector. A dead tool taking down goals.
  • Unsanitized tool output. Injection vector.

Choose it when

  • Any agent that calls external tools.

06Steps 12–14: memory, eval, and event emission#

ShippedStepImpl9/10Criticality9/10

On completion (or failure), the platform writes memory, scores the goal, and emits the final events — the closing stations that turn a finished run into learning, measurement, and a delivered result.

Mechanism

Goal completion fans out into memory writes — episodic, procedural, execution, long-term, and on failure reflexion (chapter 3). The eval layer scores the run across dimensions (chapter 10). Throughout and at the end, events publish to the goal's Redis channel, bridged to the API and streamed to the browser over SSE (chapter 11). The outcome persists to Postgres and the LangGraph checkpoint.

In AgentVerse

  • app/memory/*the tier writes on completion
  • app/agent/reflexion_wirer.pylesson extraction on failure
  • app/evals/runtime_scorecard.py, goal_score.pyscoring
  • app/services/goal_service.pyevent emission, Celery→pub/sub bridge
  • agent-verse-frontend/src/lib/sse/useGoalStream.tsthe browser receiver

Worked example

goal g-8891 completes
 memory   execution (all steps), episodic (this run), procedural (if a
          stable method emerged), long-term (durable facts learned)
 eval     goal 0.91 · grounding 0.88 · cost $0.42 · latency 41s
 events   {type:"completed", result, citations} → Redis → SSE → browser
 persist  outcome to Postgres, final checkpoint retained

At production scale

The closing steps are what make the platform improve rather than merely run: memory turns this goal into context for the next, eval turns it into a measurement, and events turn it into a live experience. Skipping any of them leaves a platform that works today and does not get better — or one whose users cannot see what it is doing.

Failure modes

  • Memory write failure swallowed. Learning silently lost.
  • Events tied to worker lifetime. The stream dying with the worker.
  • Eval skipped on failure. The most informative runs unmeasured.

Choose it when

  • Any goal you want to learn from, measure, or show.

07The frontend SSE/WebSocket path and the SDK/Action boundary#

ShippedBoundaryImpl8/10Criticality7/10

The same events reach a browser over SSE, a collaboration client over WebSocket, and CI over the SDK and GitHub Action — one backend, several front doors, one event model.

Mechanism

The React frontend subscribes to a goal's SSE stream for live execution and to a WebSocket for collaboration. The Python and TypeScript SDKs submit a goal and poll or stream its result. The GitHub Action wraps the SDK to submit a goal from CI and await it. All of them speak the same OpenAPI contract published by the backend, so the backend is the single source of truth and the clients are thin.

In AgentVerse

  • agent-verse-frontend/src/lib/sse/useGoalStream.tsSSE
  • agent-verse-frontend/src/lib/ws/useCollabSocket.tscollaboration WebSocket
  • agent-verse-frontend/src/lib/api/client.tsHTTP client
  • app/api/goals.pythe endpoints all clients consume
  • scripts/export_openapi.pythe contract the clients are generated against

Worked example

same goal, three front doors
 browser   POST /goals → SSE stream → live step-by-step view
 CI        GitHub Action → SDK → submit → await → pass/fail the build
 script    SDK client → submit → poll → result
all consume the same OpenAPI contract; the backend does not know or care
which client called

At production scale

A single backend contract with thin clients is what keeps five deployable projects in sync: the backend publishes OpenAPI, the SDKs are generated or checked against it, and a backend change that breaks a client is caught at contract level. The Action is just the SDK in a Docker entrypoint — the smallest possible front door, which is the right size for CI. (The SDKs themselves are out of scope for this manual, per the brief; here they matter only as consumers of the same event model.)

Failure modes

  • Contract drift. Clients and backend disagreeing after a change.
  • SSE without reconnect. A dropped stream losing the live view.

Choose it when

  • Any platform with more than one kind of client.

What is missing here

  • A single end-to-end trace view. The signals exist per station; a one-screen "here is the whole goal from submit to SSE" view would speed onboarding and debugging.
  • Warm-start for the two-phase swap. The in-memory-then-DB swap re-hydrates on every start; a faster warm path would cut cold-start latency.
  • Backpressure from loop to queue. The queue routes by plan but does not yet shed load based on downstream worker saturation (chapter 28).
