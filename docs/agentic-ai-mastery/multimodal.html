Orientation

Multimodal is not one capability — it is the discipline of turning every non-text modality into something the rest of the platform can retrieve, reason over, and cite. The recurring move is extract to text plus keep the original by reference: a screenshot becomes a description plus OCR plus a stored image; audio becomes a timestamped transcript; a table becomes a structure plus a summary. Text is the lingua franca, and the original is the evidence.

The chapter is organised by modality because each has a different extraction path, a different cost profile, and a different privacy risk — images and screenshots being the most likely to carry personal data, video the most expensive per minute, tables the most likely to produce confidently wrong numbers.

The modalities

01Text — the baseline#

ShippedModalityImpl9/10Criticality9/10

Everything reduces to text, so the text path is the one every other modality is measured against: chunk, embed, retrieve, cite.

Mechanism

The native path (chapters 4–8): parse to structured text, chunk by strategy, embed, index in vector and lexical form, retrieve, and cite by stable chunk id. Other modalities succeed to the extent they produce text of comparable quality — a good caption or transcript is one that retrieves and cites as well as authored prose.

In AgentVerse

  • app/ingestion/pipeline.pythe shared pipeline
  • app/rag/store.pythe shared index
  • app/multimodal/pipeline.pyrouting modalities into it

Worked example

a PDF report yields native text (body) + OCR text (scanned appendix) +
captions (diagrams) + table structures — all four become chunks in the
same collection, retrievable together

At production scale

Keeping every modality's output in one text index is what lets a single query span a diagram, a table, and a paragraph. The alternative — a separate store per modality — makes cross-modal retrieval a join nobody wants to maintain.

Failure modes

  • Modality silos. Separate indexes that cannot be searched together.

Choose it when

  • Always. It is the target every extractor aims at.

02PDF and document layout#

ShippedModalityImpl8/10Criticality9/10

The multimodal workhorse: digital text, scanned images, and hybrids in one format, each needing a different path, with layout reconstruction deciding whether the output is usable.

Mechanism

Detect the sub-case per page (chapter 5), reconstruct reading order from geometry, route scanned pages to OCR, extract tables as structures, and keep page numbers for citation. A single report often exercises all three sub-cases at once, which is why per-page handling matters.

In AgentVerse

  • app/ingestion/parsers/pdf_parser.py, chunkers/pdf_layout.pyextraction and layout chunking
  • app/ocr/engine.pythe scanned-page path
  • app/multimodal/pipeline.pyper-page routing

Worked example

84-page report: prose (columns reordered) + financial tables (structured)
+ a scanned appendix (OCR) → one document, correct reading order, tables
intact, citations to page numbers

At production scale

PDFs are the majority of enterprise multimodal volume and the majority of the bugs. Measure extracted-characters-per-page as a health signal; a drop means a parser or upstream change. Full treatment in chapter 5.

Failure modes

  • Column interleaving. Unusable text.
  • Missed scanned pages. Silent content loss.

Choose it when

  • Any enterprise corpus.

03Images#

PartialModalityImpl7/10Criticality6/10

Three extractions — OCR for embedded text, a vision caption for what it depicts, and the surrounding context — with the original stored and classified as sensitive by default.

Mechanism

Route by content: photos and diagrams get a vision caption, screenshots and scans get OCR, charts benefit from both. The text (caption plus OCR) is embedded; the image is stored by reference and linked to the chunk. Cache by image hash — the same logo appears in thousands of documents.

In AgentVerse

  • app/ingestion/parsers/vision_parser.pyvision captioning
  • app/perception/multimodal.pyperception-side analysis
  • app/multimodal/models.pymultimodal asset model
  • app/ocr/engine.pythe OCR path

Worked example

architecture diagram → OCR labels [API GW, auth, payments, pgbouncer]
                     + caption "request flow: gateway → auth/payments → DB"
                     + surrounding section text
"what sits between payments and the DB?" → answerable from the caption+OCR

At production scale

Vision captioning is metered per image, so gate it: caption images users query, skip decorative assets, cache by hash. Images hide personal data — classify originals as sensitive and never put a raw screenshot in a prompt without redaction. Full treatment in chapter 5.

Failure modes

  • Captioning everything. 4,000 copies of the letterhead.
  • OCR on photos. Garbage text.

Choose it when

  • Documents carry meaning in images.

04Screenshots and browser DOM#

PartialModalityImpl7/10Criticality6/10

For agents that operate a UI, prefer the DOM (structured, cheap) and fall back to screenshots (vision, expensive) — and never carry either forward across steps unnecessarily.

Mechanism

The page analyzer extracts an accessibility/DOM summary first; only when that is opaque (a canvas app, an image-based UI) does it escalate to a vision description or the raw screenshot. Successful selectors are remembered (visual memory, chapter 3), so subsequent runs replay cheaply. Screenshots are redacted before any prompt use and stored with short retention.

In AgentVerse

  • app/perception/page_analyzer.pyDOM + visual analysis
  • app/perception/browser_agent.pythe browsing agent
  • app/rpa/artifacts.pyscreenshots by reference
  • app/rpa/session.pyremembered selectors

Worked example

step "submit the form"
 DOM summary → form#filing with named inputs → act on structure (420 tok)
 only if opaque → vision description (900 tok) → screenshot (1,400 tok)
escalate on failure, not by default

At production scale

DOM-first is the cost story for RPA: it turns most steps into cheap deterministic actions and reserves vision for genuinely visual pages. Carrying screenshots across steps is the most common way RPA cost per goal triples. Full treatment in chapters 8 (visual injection) and the RPA sections of chapter 5.

Failure modes

  • Pixels first. Expensive and less reliable than the DOM.
  • Screenshot accumulation. Cost blowout.

Choose it when

  • UI automation where the DOM is insufficient.

05Audio and video#

PartialModalityImpl7/10Criticality6/10

Transcribe to timestamped text; for video, add sampled keyframes and scene boundaries — the timestamps are the feature, because they let a citation point at a moment.

Mechanism

Audio: STT produces text plus word/segment timing and speaker labels; chunk on time windows with overlap. Video: transcribe the audio, detect scenes, sample a keyframe per scene, caption or OCR those frames, and chunk by scene so each chunk has words and visual context aligned on one timeline.

In AgentVerse

  • app/ingestion/parsers/audio_parser.py, video_parser.pyextraction
  • app/ingestion/chunkers/timestamp.py, scene.pychunking
  • app/voice/stt_engine.pytranscription

Worked example

demo video → scene 4 (3:40–5:10): speech "configure the retry policy" +
frame OCR "Retry: 3, Backoff: exponential" → chunk answers "default backoff?"
from the frame the audio never stated

At production scale

Transcription is priced per minute and video per frame; gate both by value and sample frames sparsely (one per scene). Recordings are among the most regulated data you hold — consent, retention, residency all apply. Full treatment in chapters 5 and 26.

Failure modes

  • No timestamps. A wall of text, uncitable.
  • Frame flood. One per second is 1,800 vision calls per 30 min.

Choose it when

  • Calls, meetings, and recordings hold knowledge.

06Tables#

PartialModalityImpl7/10Criticality8/10

Structure, not prose: every chunk of a table carries its header, and large tables are summarised and queried rather than embedded row by row.

Mechanism

Small tables serialise to one chunk with the header; large tables split into row groups with the header repeated, plus a summary chunk; very large tables are indexed as schema plus sample and answered with code execution (chapter 25). A header separated from its values is the cause of most confidently wrong numeric answers.

In AgentVerse

  • app/ingestion/chunkers/table.pytable chunking
  • app/ingestion/parsers/excel_parser.py, csv_parser.pyextraction
  • app/tools/code_interpreter.pythe query path for large tables

Worked example

revenue table → each row group keeps "Region | Q1 | Q2 | Q3" header
+ summary "FY24 revenue by region, INR lakhs, 12 regions"
large transactions.csv → schema + sample, then code execution for
"failed over ₹10k in March"

At production scale

Header preservation is an invariant to test. For anything above a few hundred rows, schema-plus-execution is cheaper and more accurate than embedding rows. Full treatment in chapters 5 and 17.

Failure modes

  • Headers dropped. Numbers without labels.
  • Row-per-vector. Expensive and useless.

Choose it when

  • Documents or data with tables that matter.

07Extracted spans and visual context in planning#

PartialStructureImpl7/10Criticality7/10

Extraction produces not just text but located spans — a field on an invoice, a label in a diagram, a moment in a call — which the agent can reason over and, when planning, see visually.

Mechanism

An extracted span carries its value, its type, and its location (bounding box, page, timestamp, DOM path), so a downstream step can act on a specific field rather than searching prose. In planning, a vision-capable model can be given the visual context directly — a screenshot of the page it is about to operate, or the diagram it is reasoning about — turning "describe then act" into "see then act" where the DOM is insufficient.

In AgentVerse

  • app/multimodal/models.pyextracted span model
  • app/ocr/models.pyOCR spans with locations
  • app/perception/multimodal.pyvisual context for the agent
  • app/perception/page_analyzer.pylocated page elements

Worked example

invoice OCR → spans {invoice_no@(x,y,p1), total@(x,y,p1), due_date@(x,y,p1)}
the agent acts on span.total directly, and the location lets a human
verify by opening the original at that box

At production scale

Located spans are what make multimodal output verifiable: a human can jump from the extracted value to its exact position in the original, which is essential for document AI that has to be right (chapter 21). Visual context in planning is powerful but expensive — reserve it for the cases the DOM cannot cover.

Failure modes

  • Spans without locations. Values you cannot verify against the original.
  • Vision in planning by default. Cost without need.

Choose it when

  • Field-level extraction or UI operation where verification matters.

08Asset ingestion jobs#

PartialInfrastructureImpl7/10Criticality7/10

Multimodal extraction is heavy, bursty, and separately scaled — large files, GPU-ish workloads, per-asset metering — so it runs as its own job class, not inline with the agent loop.

Mechanism

Asset processing (OCR, transcription, captioning, frame sampling) is dispatched as background jobs with their own queue, concurrency limits, and retry/DLQ handling. Originals are stored in object storage by reference; extracted text and spans flow into the standard pipeline. The separation matters because asset work is CPU/GPU-bound and bursty while the agent loop is IO-bound — mixing them makes both scale badly.

In AgentVerse

  • app/multimodal/pipeline.pyasset processing pipeline
  • app/ingestion/modality_pipeline.pymodality routing
  • app/rpa/artifacts.py, app/services/result_artifacts.pyartifact storage
  • app/scaling/tasks.pythe job runners

Worked example

tenant uploads 400 scanned PDFs
 → asset queue (separate from goal queue)
 → OCR jobs, bounded concurrency, per-asset metering, DLQ on failure
 → extracted text → standard ingestion pipeline → searchable
the agent workload is unaffected by the backfill

At production scale

Give asset processing its own queue and its own scaling. A batch of video transcriptions must not starve interactive goals of workers, and asset work's cost profile (per-minute, per-frame, per-page) is different enough that it needs its own budget and its own alarms.

Failure modes

  • Inline extraction. A large upload stalling the agent loop.
  • Shared queue. Backfill starving interactive work.

Choose it when

  • Any real volume of non-text assets.

09Multimodal limitations and future work#

PartialRealityImpl6/10Criticality6/10

The honest boundary: extraction loses information, cross-modal reasoning is shallow, and some modalities (native audio understanding, video reasoning) are still caption-and-transcribe rather than true multimodal inference.

Mechanism

The extract-to-text approach is pragmatic and lossy. A caption cannot capture everything in an image; a transcript loses tone; a table summary loses the long tail. True multimodal models that reason over pixels and audio directly would close some of this gap, but they are more expensive, harder to cite, and harder to govern — so the platform's production path is text extraction, with native multimodal reserved for the narrow cases where it clearly wins.

In AgentVerse

  • app/perception/multimodal.pywhere native vision is used when available
  • app/multimodal/pipeline.pythe extraction-based production path
  • app/embedding/router.pythe multimodal-embedding seam (rated thin, chapter 7)

Worked example

what works well   OCR, transcription, document layout, table structure
what is shallow   cross-modal reasoning ("does this chart match this text?")
what is future    native audio understanding, video reasoning, joint
                  multimodal embeddings (caption-then-embed today)

At production scale

The extraction approach is the right default because it is cheap, citable, and governable. Native multimodal is worth adopting only where the extraction loses something the use case depends on — visual search, document-understanding tasks where layout is the meaning. Name the limitation to users rather than implying capability the system does not have.

Failure modes

  • Overclaiming. Implying visual reasoning the system does by captioning.
  • Extraction loss unmeasured. No sense of what the caption dropped.

Choose it when

  • Set expectations honestly; adopt native multimodal only where extraction demonstrably falls short.

What is missing here

  • Native joint multimodal embeddings. The production path is caption-then-embed; true image/text joint retrieval is a thin seam (chapter 7).
  • Image-region chunking. Images are handled whole rather than split into semantically distinct regions.
  • Cross-modal grounding. No equivalent of the deterministic grounding check for claims derived from a chart or a screenshot (chapter 18).
  • Extraction-loss measurement. Nothing quantifies what a caption or summary dropped relative to the original.
