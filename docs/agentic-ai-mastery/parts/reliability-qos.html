Orientation

Reliability primitives appeared throughout the book as they were needed; this chapter assembles them as a system and adds the quality-of-service layer on top. The distinction: reliability keeps the platform correct under failure (idempotency, rollback, breakers); QoS keeps it fair and responsive under load (priority, backpressure, bulkheads, degraded mode).

The unifying idea is graceful degradation under both failure and load. A production agent platform never has the luxury of a clean environment — providers flap, tenants stampede, connectors die — so every primitive here answers "how do we stay correct and fair when something is wrong", and the answer is never "fall over" and never "silently do less without saying so".

Reliability and QoS

Failure classification and recovery policy

Not all failures are equal: classify each — transient, rate-limited, auth, missing-input, invalid-plan, permanent — and map the class to a response, because retrying an auth failure is as wrong as escalating a timeout.

Mechanism

A failure classifier maps an error to a class; a recovery policy maps the class to an action; a retry strategy selector picks the backoff shape; an escalation policy decides when a human is involved. This is the recovery subsystem introduced in chapter 1, presented here as the platform's central failure-handling brain — every subsystem's failures flow through the same classification so responses are consistent.

In AgentVerse

  • app/recovery/failure_classifier.py, recovery_policy.pyclassify → respond
  • app/recovery/retry_strategy_selector.py, escalation_policy.pybackoff and escalation

Worked example

failure                    class          response
timeout / 5xx              transient      retry, exp backoff + jitter
429                        rate-limited   retry after window; shed if repeated
403 / 401                  auth           no retry → escalate
"missing account id"       missing-input  clarification to a human
"step precondition false"  invalid-plan   replan with the failure as context
"unsupported operation"    permanent      fail; roll back side effects

At production scale

Consistent classification is what keeps failure handling sane across dozens of subsystems — the same timeout means the same thing whether it came from a tool, an embedder, or a database. The recovery trace is the audit of what was attempted, which is essential when a goal took nine iterations to fail: you can see it retried a permanent error four times because it was misclassified. Full treatment in chapter 1.

Failure modes

  • Misclassification. Retrying the permanent, escalating the transient.
  • Uniform retry. The same backoff for every failure class.

Choose it when

  • Always. Failure is the normal case in distributed systems.

Idempotency and deduplication

In a system that retries constantly, safety means a repeated operation has the same effect as a single one — an idempotency key per write, dedup of repeated requests, so a retry never double-charges.

Mechanism

Every write carries an idempotency key derived from goal + step + argument hash, so the target (or the platform) recognises a retried call as the same call and does not repeat the side effect. Deduplication catches repeated requests earlier — the same goal submitted twice, the same webhook delivered twice — and returns the prior result. Together they make at-least-once delivery safe, which is the only delivery guarantee a distributed system can cheaply offer.

In AgentVerse

  • app/reliability/idempotency.pyidempotency keys
  • app/reliability/dedup.py, app/services/dedup.py, app/gateway/dedup_scheduler.pydeduplication
  • app/reliability/goal_lifecycle.pylifecycle state that dedup keys off

Worked example

goal retried after a worker crash mid-step-4 (create invoice)
 step 4's idempotency key = hash(goal, step 4, invoice args)
 the ERP recognises the key → returns the already-created invoice
 → the customer is billed once, not twice
without idempotency, the retry creates a second invoice

At production scale

Idempotency is non-negotiable for any agent that writes, because retries are constant — a worker crash, a timeout, a rebalance all trigger them. The key must be derived deterministically from the operation, not generated fresh, or the retry looks like a new operation. This is the primitive that lets you use at-least-once delivery (cheap and reliable) instead of exactly-once (expensive and often impossible).

Failure modes

  • Retry without idempotency. Duplicate side effects.
  • Non-deterministic keys. Retries not recognised as repeats.
  • Dedup window too short. A late retry treated as new.

Choose it when

  • Any write-capable agent — so any production agent.

Bulkheads and circuit breakers

Two isolation primitives: bulkheads cap per-tenant concurrency so one cannot starve the fleet, and breakers stop calling a failing dependency so its outage does not become yours.

Mechanism

A bulkhead is a concurrency ceiling per tenant (and per resource pool) — a fan-out that would exhaust the workers or connections queues instead. A circuit breaker fronts each flaky dependency: after repeated failures it opens and fails fast (or serves stale) until a probe confirms recovery. Breaker state is shared across replicas via Redis, so the whole fleet learns a dependency is down rather than each node discovering it independently.

  • app/reliability/bulkhead.pyper-tenant concurrency

  • app/providers/circuit_breaker.pyprovider breakers (chapter 16)

Worked example

bulkhead   acme capped at 50 concurrent tool calls → a 200-way fan-out
           queues; other tenants keep their capacity
breaker    the CRM connector fails 5× → open (shared via Redis, whole fleet
           stops calling it) → 60s later a probe → recovered → close

At production scale

The bulkhead is the ceiling that no amount of agent spawning (chapter 1) or trigger firing (chapter 27) can breach — it is what makes multi-tenancy survivable under load. Cross-replica breaker state is the detail that matters: without it, a hundred replicas each hammer a dead provider a hundred times before giving up. Together they turn "one thing is broken" into "one thing is isolated".

Failure modes

  • No bulkhead. One tenant's fan-out starving all.
  • Per-replica breakers. The fleet not learning collectively.
  • No stale fallback. A read failing when a cached answer would do.

Choose it when

  • Any multi-tenant system with external dependencies.

Priority, backpressure, and queue policy

Under load, decide what runs now, what waits, and what is shed — priority for what matters, backpressure to slow intake before the system tips over, and a queue policy that is fair by design.

Mechanism

A QoS layer over the queue: priority policy ranks work (an interactive goal over a batch one, a paying tenant's over a free one); backpressure signals upstream to slow down when the system is saturated, rather than accepting work it cannot serve; a queue policy governs fairness so no class is starved. A scheduler applies these. The goal is to degrade predictably under load — the right work still runs, the rest waits or is shed with a clear signal.

In AgentVerse

  • app/qos/priority_policy.py, queue_policy.py, scheduler.pypriority, fairness, scheduling
  • app/qos/backpressure.py, qos_trace.pybackpressure and its trace
  • app/scaling/priority_queue.py, celery_app.pythe queues it governs (chapter 20)

Worked example

load spike: 10,000 goals arrive in a minute
 priority: interactive + enterprise goals run first
 backpressure: intake slows, upstream told to retry later (not silently dropped)
 fairness: free tier still gets its guaranteed share, not zero
 result: predictable degradation — the important work is unaffected

At production scale

Backpressure is the primitive that separates a system that degrades gracefully from one that collapses: accepting work faster than you can serve it just moves the failure downstream and makes it worse. Priority is how you honour SLAs under contention — the enterprise tenant you promised 4-second latency should not queue behind a free tenant's backfill (chapter 20). QoS is where fairness stops being an aspiration and becomes a policy.

Failure modes

  • No backpressure. Accepting more than you can serve, then collapsing.
  • Priority without fairness. Low-priority work starved entirely.
  • Silent shedding. Dropping work without telling the caller.

Choose it when

  • Any system that experiences load spikes — so any real one.

Degraded mode and readiness gates

When a dependency is down, run with less rather than failing entirely — lexical search without the embedder, deterministic guardrails without the toxicity model — and refuse to serve only what genuinely cannot run safely.

Mechanism

A degraded-mode policy defines what the platform does when a dependency is unavailable: fall back to the lexical retrieval path if the embedder is down (chapter 7), run deterministic guardrails if the toxicity model is down (chapter 12), delegate to a ready RAG strategy if one is unavailable (chapter 2). A readiness gate refuses to serve only what cannot run safely in degraded mode — a fail-closed control (chapter 12) must not degrade to fail-open. Dependency health drives both.

Worked example

embedder provider down
 degraded mode: retrieval falls back to BM25 + trigram, flagged degraded
 guardrails: deterministic checks still run; toxicity model unavailable →
   for high-risk channels, BLOCK (never fail-open)
 status page: "semantic search degraded" — announced, not silent
 readiness gate: refuses only the operations that cannot run safely

At production scale

Degraded mode is the difference between a partial outage and a total one — most of the platform keeps working when one dependency fails, and the reduction is announced rather than silent. The one inviolable rule: fail-closed controls never degrade to fail-open. A toxicity model being down is a reason to run stricter deterministic checks, never a reason to skip safety. Announce degradation on the status page so users know why quality changed.

Failure modes

  • All-or-nothing. One dependency down taking everything down.
  • Fail-closed degrading to fail-open. Skipping safety when a model is down.
  • Silent degradation. Users blaming the product.

Choose it when

  • Any platform with external dependencies that can fail independently.

What is missing here

  • Adaptive concurrency limits. Bulkheads are configured, not learned from observed latency and error rates under load.
  • Chaos testing. The primitives exist; systematic fault injection to verify they work together under failure is thin (chapter 31).
  • Cross-region failover. Degraded mode handles dependency failure; regional failover for the datastores themselves is future work (chapter 32).
  • Predictive backpressure. Backpressure reacts to saturation; anticipating a spike from leading indicators would smooth degradation.
