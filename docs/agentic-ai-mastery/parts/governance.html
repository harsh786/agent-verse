Orientation

Guardrails stop unsafe actions. Governance answers a different set of questions: who is allowed to do what, who pays, who approved it, and can you prove all of it afterwards. It is the layer that makes an agent platform sellable to a regulated enterprise, and it is enforced in three places — the application, the database, and an append-only audit trail — because a control that exists in only one of them is a control someone will eventually route around.

The organising idea is defence in depth through independent enforcement: tenant isolation is checked in app code and in Postgres row-level security; a budget is checked in the app and recorded in Redis for cross-replica accuracy; every consequential action is both gated and written to a tamper-evident log.

The controls

Tenant isolation

Every row belongs to a tenant, and the boundary is enforced in two independent places: app code that filters by tenant, and a database that refuses to return another tenant's rows regardless of what the query asks for.

Mechanism

A TenantContext — an immutable, per-request identity — flows through the whole request. App code scopes every query by its tenant id. Underneath, Postgres row-level security policies filter rows by a session variable (app.tenant_id) set with SET LOCAL inside the transaction, so even a query that forgot its tenant filter returns nothing from other tenants. The two layers are independent by design: RLS is the backstop for the app bug that will eventually happen.

In AgentVerse

  • app/tenancy/context.pyTenantContext — the immutable per-request identity (a top-10 hub node)
  • app/db/rls.pysqlalchemy_rls_context() — SET LOCAL app.tenant_id per transaction
  • app/tenancy/middleware.pyTenantMiddleware — establishes the context from the API key
  • app/tenancy/sub_tenants.pynested tenancy
  • app/tenancy/store.pytenant records

Worked example

request with API key for tenant acme
 middleware  → TenantContext(tenant_id="acme", plan="enterprise", ...)
 transaction → SET LOCAL app.tenant_id = 'acme'
 query       SELECT * FROM goals WHERE status = 'running'
             (developer forgot the tenant filter)
 RLS policy  rewrites to ... AND tenant_id = current_setting('app.tenant_id')
 result      only acme's running goals — the bug did not leak

At production scale

The single most important test in the whole platform asserts that a request in tenant A can never return a tenant B row — through the API, through retrieval, through memory recall, through the cache. Cross-tenant leakage is the incident that ends contracts, and the reason RLS exists is that app-code discipline alone is not enough at the scale of hundreds of queries written by dozens of people.

Watch for the paths that bypass RLS: raw connections, admin tooling, background jobs that use a system session. Each is a legitimate exception and each is where the next leak will come from.

Failure modes

  • App-only isolation. One forgotten filter is a leak.
  • RLS bypassed by system sessions. Background jobs that see everything — scope them explicitly.
  • Shared caches without tenant keys. The cache becomes the leak.
  • Context not propagated to async work. A spawned task losing its tenant.

Choose it when

  • Any multi-tenant system. Both layers, from day one.

API key scopes

A key is not all-or-nothing: each carries a scope limiting which operations it can perform, so a compromised read key cannot write and a CI key cannot touch billing.

Mechanism

Each API key is bound to a tenant and a set of scopes — read goals, submit goals, manage agents, admin — plus optional constraints like an IP allowlist and an expiry. Scope is checked before the request reaches the business logic, and it is the narrowest of the authorisation layers: it bounds what the credential can do before RBAC even considers who the user is.

  • app/auth/scope_enforcement.pyscope checks
  • app/auth/scope_seeder.pydefault scopes
  • app/tenancy/tenant_users.py, rbac.pykey-to-role binding
  • app/auth/ip_allowlist.pyIP constraints per key
  • app/auth/goal_tokens.pyscoped, short-lived tokens for a single goal

Worked example

key ak_ci_… (CI pipeline)
 scopes      [goals:submit, goals:read]  · IP allowlist [CI egress range]
 submit goal → allowed
 delete agent → DENIED (no agents:admin scope)
 request from a laptop → DENIED (IP not in allowlist)

goal token gt_… (issued for one goal, expires in 1h)
 scope       exactly the tools that goal needs, nothing else

At production scale

Goal tokens are the underused idea here: a short-lived, narrowly-scoped credential issued per goal means a leaked token grants access to one goal's tool set for one hour, not the tenant's whole surface. Combined with an IP allowlist, it turns key compromise from a breach into an inconvenience.

Failure modes

  • God keys. One key with every scope, used everywhere.
  • No expiry. Keys that outlive the person who created them.
  • Scope checked after side effects. Authorisation that runs too late.

Choose it when

  • Any API with more than one kind of caller.

RBAC and the permission matrix

Roles map to permissions, users and keys map to roles, and the effective permission set is computed by expanding a role hierarchy — so access is describable, auditable, and changeable in one place.

Mechanism

A role (tenant_admin, org_admin, org_member, org_viewer, approver, billing_admin) carries a set of permissions; roles form a hierarchy so higher roles inherit lower ones. A user or key holds roles, and the effective permission set is the union after hierarchy expansion. Custom roles let a tenant define its own, and temporary elevation grants a permission for a bounded window with an audit record.

In AgentVerse

  • app/tenancy/rbac.pyeffective_roles() — hierarchy expansion
  • app/tenancy/tenant_users.pyTenantRole enum
  • app/auth/custom_roles.pytenant-defined roles
  • app/auth/temp_elevation.pybounded privilege elevation
  • app/auth/permission_cache.pycached decisions with TTL
  • app/governance/permissions.pythe permission matrix

Worked example

user j.iyer  roles [org_member, approver]
 org_member → [goals:submit, goals:read, agents:read]
 approver   → [approvals:act]
 effective  = union → can submit/read goals, read agents, act on approvals
             cannot create agents (needs org_admin) or view billing

temp elevation: granted agents:admin for 2h to run a migration
 → recorded: who granted, why, expiry → auto-revoked, audited

At production scale

The permission decision is on the hot path of every request, so it is cached with a short TTL — and the cache is the thing that bites you when a revocation does not take effect for thirty seconds. Make the TTL a conscious choice, and invalidate on role change for anything security-critical. Temporary elevation with an audit record is how you handle "I need admin just for this" without permanent scope creep.

Failure modes

  • Permission sprawl. Everyone accumulating roles until the matrix is meaningless.
  • Stale cache after revocation. Access that outlives its removal.
  • Permanent elevation. "Temporary" admin that was never revoked.

Choose it when

  • More than a couple of users per tenant, or any role distinction.

The policy engine

Compile a goal's context into a set of runtime constraints — which tools are allowed, what requires approval, the cost ceiling, what is denied — evaluated deterministically and propagated across replicas in seconds.

Mechanism

The compiler takes the goal's runtime profile (tenant, plan, risk, domain, compliance regime) and produces RuntimeConstraints: allowed and denied tools, approval requirements, cost and iteration limits, data-class restrictions. The computation is deterministic and shares its dimension logic so the same inputs always produce the same constraints, and a policy trace records every dimension, its value, and why. Changes propagate through Redis pub/sub, so a rule edit takes effect fleet-wide without a deploy.

In AgentVerse

  • app/policy_runtime/compiler.pyPolicyCompiler.compile() → RuntimeConstraints
  • app/policy_runtime/constraint_model.pyRuntimeConstraints
  • app/policy_runtime/runtime_enforcer.pyenforcement at runtime
  • app/policy_runtime/policy_trace.pyPolicyTrace — per-goal decision audit
  • app/governance/policies.py, policy_rules.pythe policy definitions + Redis pub/sub propagation
  • app/security_runtime/policy_bundle_selector.pyselecting the right bundle

Worked example

goal profile  tenant=acme plan=enterprise risk=high domain=finance
              compliance=[SOC2, DPDP]

compiled constraints
 allowed tools    finance.* invoices.* gst.* notify.slack
 denied tools     admin.* infra.* (not in scope for this domain)
 approvals        any write_high, any external notification
 cost ceiling     $8.00
 max iterations   25
 data classes     may not place 'restricted' data in tool args
policy trace: each line above with its source rule and reason

At production scale

Deterministic compilation plus a policy trace is what lets you answer a regulator's "why was this allowed?" with a document rather than a shrug. Redis propagation matters operationally: when you discover a tool is dangerous, you disable it fleet-wide in seconds, not at the next release — which is the difference between an incident and a near-miss.

Failure modes

  • Non-deterministic policy. The same goal allowed on one replica, denied on another.
  • No trace. Decisions that cannot be explained.
  • Propagation lag. A disabled tool still callable for minutes.
  • Policy that can loosen safety. Optimisation rules removing an approval — the append-only safety rule (chapter 1) exists to prevent this.

Choose it when

  • Any deployment where different goals need different rules — which is any real one.

Cost control and budget enforcement

Every goal and every tenant has a budget, checked before each model and tool call, backed by Redis so the accounting is accurate across replicas — a goal cannot overspend by racing itself on two workers.

Mechanism

Cost accumulates in Redis keyed by goal and tenant, so a check-and-increment is atomic across the fleet. Before each metered operation the controller checks the remaining budget; over the limit, the goal pauses or fails rather than continuing. Budgets exist at several scopes — per goal, per tenant per period, per plan — and the tightest binding wins. Cross-replica accuracy is the whole point: an app-local counter lets a goal running on two workers spend twice its budget.

In AgentVerse

  • app/governance/cost.pyRedisCostController, get_cost_tier(), the pre-call check
  • app/governance/pricing.pythe price table
  • app/intelligence/cost_tracker.pyper-run accumulation
  • app/tenancy/limits.py, limits_v2.pyper-plan limits
  • app/tenancy/billing.pytenant accounting

Worked example

goal budget $5.00, running on worker-3
 before executor call: spent $4.80 + estimated $0.35 = $5.15 > $5.00
 → BLOCK the call → goal pauses at "budget exceeded", not silently over
tenant budget $2,000/month, at $1,900
 → new goals warned at 90%, blocked at 100% (except allowlisted critical)
Redis atomicity: two workers on the same goal cannot both pass the check

At production scale

Redis-backed budgets are the difference between a cost model and a cost hope. The check is on the hot path, so it must be a single atomic operation, not a read-then-write. And it must include tool and compute cost, not just model tokens — in tool-heavy or code-execution workloads, model tokens are frequently the minority of spend.

Attribute sub-agent spend to the parent goal, or multi-agent goals appear cheap and your per-goal costs do not reconcile with the provider invoice.

Failure modes

  • App-local counters. Overspend by racing across replicas.
  • Post-hoc accounting. Finding out you overspent after the fact.
  • Model-tokens-only. Missing tool and compute cost.
  • No sub-agent attribution. Costs that do not add up.

Choose it when

  • Always. Unbudgeted agents are how a platform gets a surprise invoice.

The audit trail

An append-only, hash-chained record of every consequential action — tamper-evident, so a modified or deleted entry breaks the chain and is detectable.

Mechanism

Each audit entry includes the actor, action, target, tenant, timestamp, and a hash of the entry plus the previous entry's hash — a chain. Altering or removing any entry breaks every subsequent hash, so tampering is detectable even by someone with database write access. A background flusher batches writes for throughput without losing the ordering the chain depends on, and entries can be exported to WORM storage and to SIEM systems.

In AgentVerse

  • app/governance/audit_v3.pyAuditV3 — hash-chained append-only, _hash_dict(), AuditFlusher, system_session()
  • app/governance/audit.py, audit_v2.pyearlier audit implementations
  • app/governance/siem_adapters.pyexport to SIEM
  • app/provenance/export.pyWORM export
  • app/workflow/audit_middleware.pyaudit for workflow steps

Worked example

entry n     {actor:"j.iyer", action:"approve", target:"goal:g-8891",
             detail:"filing amendment, ₹418,200", ts:..., 
             prev_hash:"7c1f...", hash:"9a02..."}
entry n+1   {..., prev_hash:"9a02...", hash:"b41d..."}

tamper attempt: someone edits entry n's detail
 → entry n's hash no longer matches its content
 → and every entry after it now has a wrong prev_hash
 → chain verification fails at exactly entry n → tampering located

At production scale

The hash chain is what lets you say "this log has not been altered" rather than "we don't think anyone changed it". For regulated deployments that distinction is the difference between an audit that passes and one that does not. Export to WORM storage and SIEM so the record survives even a full compromise of the primary database, and batch writes carefully — throughput matters, but never at the cost of the ordering the chain depends on.

Failure modes

  • Mutable audit. A log you can edit is not evidence.
  • Gaps. Actions that bypass the audit path.
  • Chain broken by batching bugs. Out-of-order writes that break verification legitimately.
  • Audit only in the primary DB. Lost with it.

Choose it when

  • Any action a regulator, auditor, or customer might ask about — so most of them.

Compliance controls and bundles

Regulatory regimes — GDPR, DPDP, SOC2, PCI, HIPAA — are pre-configured as bundles that set policy, redaction, retention, and audit requirements together, so a tenant selects a regime rather than assembling a hundred settings.

Mechanism

A compliance bundle is a coherent set of controls: which data classes must be redacted, retention periods, residency requirements, consent handling, audit granularity, and approval requirements. Selecting a bundle configures the policy engine, the redaction layer, the retention policy, and the audit level in one act — and the bundle is versioned, so a change to a regime's interpretation is a bundle update, not a scramble across subsystems.

In AgentVerse

  • app/governance/compliance_bundles.pythe bundles
  • app/enterprise/compliance.py, compliance_v2.pycompliance controls
  • app/api/dpdp.pyDPDP data-subject rights
  • app/lifecycle/retention_policy.py, legal_hold_policy.pyretention and hold
  • app/governance/legal_holds.pylegal holds that suspend deletion

Worked example

tenant selects "HIPAA" bundle
 → redaction: PHI classes always redacted before external calls
 → retention: 6 years, with legal-hold override
 → residency: US only; connectors outside the region blocked
 → audit: full detail on every access to PHI-classed data
 → approvals: any disclosure of PHI requires a named approver
one selection, five subsystems configured consistently

At production scale

Bundles are what make multi-regime, multi-tenant compliance tractable. The alternative — configuring each control per tenant — guarantees that some tenant is misconfigured, and the one that is will be the one audited. Version the bundles and record which version a tenant is on, so when a regime's requirements change you know exactly who needs re-configuring.

Failure modes

  • Per-setting configuration. Inconsistent controls, inevitable gaps.
  • Unversioned bundles. No way to track who is on which interpretation.
  • Bundle selected but not enforced. A regime chosen in the UI that does not reach the policy engine.

Choose it when

  • Any regulated tenant, and before you sign the first one.

Approval workflows and chains

Some actions need more than one signature. Approval chains route a request through an ordered set of approvers, each recorded, with escalation and expiry.

Mechanism

A chain defines an ordered sequence of required approvers (or roles), optionally with conditions — a ₹10,000 refund needs a manager, a ₹1,000,000 refund needs the finance director too. Each step is durable (the request waits, it does not block), recorded, and subject to escalation if an approver does not respond within a window. The chain composes with the HITL gateway: the gate triggers the chain, the chain gathers the signatures.

In AgentVerse

  • app/org/approval_chain.pyApprovalChain
  • app/governance/hitl.pythe gateway that triggers it
  • app/recovery/escalation_policy.pyescalation on no-response
  • app/collaboration_runtime/human_decision_trace.pythe record
  • app/integrations/email/approval_sender.py, app/gateway/channels/*how approvals reach people

Worked example

action: refund ₹1,200,000
chain  1 team lead        → approved 14:05
       2 finance manager  → approved 14:40
       3 finance director → no response by 18:00
                          → escalated to deputy director → approved 18:20
each step recorded; the refund executes only after step 3 completes;
the executed amount is hashed against the approved amount

At production scale

Chains are where governance meets human latency, so the escalation and expiry behaviour matters as much as the chain itself: a request stuck on an unavailable approver is an outage nobody gets paged for. Define what happens on timeout explicitly, and make chain depth proportional to the stakes — a two-signature chain for routine actions trains everyone to rubber-stamp.

Failure modes

  • Chains too long for the stakes. Approval fatigue.
  • No escalation. Stuck on an unavailable approver.
  • Approve-then-substitute. Hash the approved action against the executed one.

Choose it when

  • High-value or regulated actions needing more than one signature.

Tool risk classification

Every tool is classified by what it can do — read, write-low, write-high, destructive — and that class drives whether it needs approval, whether it needs a compensating action registered, and how it is audited.

Mechanism

Classification combines the connector and the operation: github.get_issue is read, github.create_issue is write-low, github.delete_repo is destructive. Some connectors use token-based classifiers preserved for backward compatibility; most use substring matching over the breadth of real MCP tool names. The class then drives policy: destructive tools require approval and a registered inverse, write-high tools require approval, reads flow freely.

In AgentVerse

  • app/agent/tool_risk.pyclassify_tool_risk() — read/write_low/write_high/destructive
  • app/tool_runtime/tool_policy.pyclass → policy
  • app/reliability/tool_inverses.pycompensating actions for reversible risk
  • app/governance/policies.pythe rules that consume the class

Worked example

tool                     class         policy
crm.get_contact         read          allowed, standard audit
crm.update_contact      write_low     allowed, detailed audit
crm.bulk_delete         destructive   approval + inverse required + full audit
stripe.create_refund    write_high    approval + full audit
db.execute("DROP ...")  destructive   approval + no inverse → HITL mandatory

At production scale

The pairing that matters is irreversible ⇒ approved: a destructive tool with no registered inverse must go through a human, because there is no automated way to undo it. Classification also needs to be conservative on unknown tools — a newly-connected MCP server's tools should default to a higher risk class until reviewed, not flow freely.

Failure modes

  • Unknown tools default to read. A new connector's destructive tool flowing freely.
  • Name-based misclassification. "update" that actually deletes.
  • Destructive without inverse or gate. Irreversible and unapproved.

Choose it when

  • Any agent with write-capable tools.

Enterprise controls

The features that appear on a security questionnaire: SSO/SAML/SCIM, MFA, IP allowlists, data residency, break-glass access, and legal holds — each unglamorous and each a deal-breaker if absent.

Mechanism

Identity federation (SAML, OIDC via Keycloak) and user provisioning (SCIM) so enterprises manage access in their own IdP; MFA for sensitive operations; IP allowlists per key and per tenant; data residency enforced at the connector and storage layer; break-glass access for emergencies that requires elevated approval and generates a prominent audit record; and legal holds that suspend deletion for named subjects or matters.

Worked example

enterprise onboarding
 SSO      SAML to the customer's Okta → users authenticate there
 SCIM     provisioning/deprovisioning driven by their IdP → a departed
          employee loses access automatically

At production scale

These are the controls that gate enterprise sales, and the one most often underestimated is SCIM deprovisioning — automatic access removal when someone leaves is both a security requirement and the thing a customer's own auditor checks first. Break-glass is the honest acknowledgement that emergencies happen: better a controlled, audited, two-approval path than an undocumented back door someone builds under pressure.

Failure modes

  • No SCIM deprovisioning. Departed employees retaining access.
  • Break-glass without audit. An emergency path that becomes a routine bypass.
  • Residency enforced only in storage. A connector that egresses data out of region.

Choose it when

  • Selling to enterprises. These are table stakes, not differentiators.

What is missing here

  • Continuous access review. Roles and scopes are granted but there is no periodic attestation flow ("confirm these 12 people still need admin").
  • Policy simulation at tenant scale. The guardrail engine has simulate mode; the policy engine has no equivalent "what would this rule change block across all goals" preview.
  • Audit analytics. The trail is tamper-evident but there is no built-in anomaly detection over it ("this approver approved 200 refunds in an hour").
  • Cross-tenant policy templates. Compliance bundles are shared, but tenant-authored policies cannot be templated and shared with governance review.
