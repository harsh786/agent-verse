Orientation

A prompt in a production agent is not a string someone wrote. It is the output of a compiler: sources of context are gathered, ranked, capped, budgeted, labelled with trust levels, given citation ids, and rendered into a role-specific template with an output contract attached.

That framing matters because it makes the prompt an artifact you can version, diff, test, cost and attribute. "The agent gave a bad answer" becomes answerable: you can look at exactly what it was given, which source each token came from, and what was cut to make room.

Assembling context

Context assembly as a pipeline

Seven ordered steps turn a pile of candidate context into a rendered prompt, and every step records what it did — so the prompt is reproducible and its cost attributable.

Mechanism

Rerank the candidates by relevance policy; cap each source so none dominates; fit the survivors to a token budget with per-section allocations; assign stable citation ids; gather everything into one context bundle; render per-role prompts from that bundle; return a result that carries both the prompts and the composition. The last part is what makes the pipeline debuggable — the result says how many tokens came from where.

Separating bundle from render is the design decision that pays off: the same assembled context produces the planner's prompt, the executor's prompt and the verifier's prompt without re-doing any of the expensive work.

At production scale

Log the composition for every call and you can answer the three questions that come up constantly: why did this cost so much, why was that document not used, and what changed between the run that worked and the run that did not. Without it, prompt debugging is archaeology.

Assembly is also the natural cost-control point: it is the last place you can cheaply decide not to spend 4,000 tokens on marginal context.

Failure modes

  • Ad-hoc string building. Prompts assembled at call sites; no budget, no caps, no composition record.
  • Budget applied after rendering. Truncation cuts the output contract or the citations.
  • Re-assembling per role. Three times the work for the same context.

Choose it when

  • Any agent with more than one context source or more than one model role.

Context budget

Allocate the window before you fill it: a fixed reserve for the response, fixed allocations for system and task, and the remainder distributed across evidence sources by priority.

Mechanism

Compute the budget from the model's window minus a response reserve, then allocate by section rather than filling greedily. Greedy filling is the classic mistake: retrieved chunks arrive first, consume everything, and the tool output that actually answers the question gets truncated.

Allocations should be proportions with floors — evidence gets 60% but memory never gets less than 200 tokens if memory exists — and the budget must be computed in real tokens from the model's tokeniser, not estimated from characters.

At production scale

Tool schemas are the section everyone underestimates — 34 tools with full JSON schemas can be 8,000 tokens on every single call, which is both the largest cost line and a measurable accuracy drag. Narrowing the tool list is usually the highest-value budget action available.

Long-context models do not remove the need for this. They remove the hard failure and keep the cost, which is worse, because the waste becomes invisible.

Failure modes

  • Greedy filling. The important section gets what is left.
  • Estimated tokens. Off by 3× on code and JSON; requests fail at the provider.
  • No response reserve. The model runs out of room mid-answer.
  • Silent truncation. Cut without a marker, so the model reasons over a fragment believing it is whole.

Choose it when

  • Always. This is the difference between predictable and mysterious prompt behaviour.

Rerank policy and source caps

Rank everything together, then cap per source — so a verbose tool output or an enthusiastic memory recall cannot crowd out the documents that hold the answer.

Mechanism

Two stages that are easy to conflate. Reranking orders candidates by relevance regardless of origin. Capping then enforces a maximum share per source, because relevance scores are not comparable across sources and because different sources have different trust levels. A memory can be the most semantically similar item in the pool and still deserve at most 10% of the window.

At production scale

Caps are the control that keeps a multi-source agent stable as sources are added. Every new context source — a new memory tier, a new tool, a graph — otherwise silently reduces the evidence share, and answer quality drifts down for reasons nobody can attribute.

Failure modes

  • No caps. One verbose source dominating.
  • Caps before ranking. You cap away the best item in a source before comparing it.
  • Uniform caps. Trust differs by source; the caps should too.

Choose it when

  • More than one context source.

Citation ids in the prompt

Every evidence item enters the prompt with an id the model is required to use — which is the only way a citation in the output can be verified rather than believed.

Mechanism

The citation manager assigns short ids across all sources in one namespace, records the mapping from id to chunk/memory/graph-edge, and the output contract requires the model to cite those ids and only those ids. Afterwards, a verifier checks each cited id exists and that the claim it supports is actually supported.

The alternative — asking the model to "include sources" — produces plausible references to documents that do not exist, which is worse than no citations because it manufactures confidence.

  • Id reuse across calls. [1] meaning different things in one conversation.
  • Unverified citations shipped. Trust manufactured, not earned.

Per-role prompts

System prompt injection

The platform-authored layer: role, hard rules, refusal conditions, output contract. It is assembled from policy rather than typed by a developer, and nothing downstream can override it.

Mechanism

Composed from several sources at runtime: the base role for this model position, the tenant's policy bundle, the compliance profile, and the selected skill's instructions. Because it is assembled from policy objects, changing "agents must refuse to send external email without approval" is a policy edit rather than a prompt edit, and it applies everywhere at once.

The invariant: system content is platform-authored. Tenant text, retrieved text and tool output never enter this layer, no matter how authoritative they claim to be.

At production scale

Assembling the system layer from policy is what makes multi-tenant, multi-regime deployment tractable. The alternative — a per-tenant prompt fork — becomes unmaintainable at about the fifth tenant and untestable at about the tenth.

Version it. When behaviour changes, the first question is which system-prompt version produced it, and that must be answerable from the run record.

Failure modes

  • Tenant text in the system layer. A tenant-configurable "custom instruction" that can disable a guardrail.
  • Unversioned prompts. Behaviour changes with no diff to point at.
  • Prompt bloat. Every past incident adding a sentence until the layer is 3,000 tokens of accumulated caution.

Choose it when

  • Always. And keep it policy-derived rather than hand-maintained.

Planner prompt construction

The planner's job is a validated plan, so its prompt carries goal, retrieved context, lessons, available capabilities, and constraints — and demands a machine-checkable structure back.

Mechanism

Contents, in order of importance: the goal; the constraints (iteration cap, budget, autonomy mode, which actions require approval); available capabilities described at the right altitude — capability names and one-line purposes, not full JSON schemas, because the planner chooses what and the executor chooses how; retrieved context; relevant lessons from reflexion memory; and the previous plan plus failure feedback if this is a replan.

The output contract is a structured plan with a success criterion per step, which the plan verifier can validate before anything executes.

At production scale

Give the planner capability names, not tool schemas. Full schemas for 30 tools cost thousands of tokens and make plans worse, because the planner starts writing argument-level detail it has no information to get right. The executor sees the schema for the one tool it is about to call.

Always include the constraints. A planner that does not know the iteration cap or the approval rules produces plans that cannot be executed, and every such plan costs a full replan.

Failure modes

  • Schema flooding. Thousands of tokens of tool definitions in the planning call.
  • Missing constraints. Unexecutable plans.
  • No success criteria. The verifier has nothing to check against.
  • Unbounded plan length. Twelve steps for a two-step job.

Choose it when

  • Any plan-and-execute agent.

Executor prompt construction

Narrow and concrete: one step, the tools that step could plausibly need with full schemas, the results of prior steps it depends on, and a strict call format.

Mechanism

The executor's prompt is deliberately the opposite of the planner's: fewer capabilities, more detail per capability. The tool selector narrows the offered list first — by skill, by step intent, by tenant connector availability — and only then are full schemas injected. Prior step outputs are included by dependency, not wholesale, and untrusted tool output from previous turns is fenced in the untrusted layer.

At production scale

Tool-list length is the dominant driver of both executor cost and executor accuracy. Narrowing 34 tools to 2–9 typically halves the prompt and measurably improves selection — the selector pays for itself several times over.

Never include a tool the tenant is not permitted to call, even "for context". The model will eventually try it, and you will have built a prompt-level permission bypass.

Failure modes

  • All tools always. Expensive and less accurate.
  • Prior outputs wholesale. The window fills with irrelevant history.
  • Unfenced tool output. The injection vector.
  • Loose call format. Unparseable responses and repair loops.

Choose it when

  • Any tool-calling agent.

Verifier prompt construction

The verifier must be able to fail. Give it the success criterion, the evidence, and an output contract that makes "not satisfied" as easy to express as "satisfied".

Mechanism

Contents: the step or goal, its explicit success criterion, the actual result and the evidence behind it, and a rubric. Deliberately excluded: the agent's reasoning about why it thinks it succeeded. A verifier shown the actor's justification tends to agree with it, which is the failure mode that makes verification decorative.

The output contract asks for a verdict, a reason, a confidence, and — on failure — a specific diagnosis usable by the replanner. Vague failures produce vague replans.

At production scale

Two habits keep verification real. Run a deterministic grounding check before the model call — if the claimed number does not appear in any tool output, you do not need a model to know something is wrong. And calibrate: measure the verifier against labelled outcomes, because a verifier that passes 99% of steps has stopped being a control.

Failure modes

  • Actor's reasoning included. The verifier agrees with it.
  • No explicit criterion. "Did it work?" is unanswerable.
  • Failure without diagnosis. The replanner learns nothing.
  • Uncalibrated leniency. Verification theatre.

Choose it when

  • Always. The verifier is the only node with the authority to end a run.

What goes in, and how

Tool schema injection

Tool definitions are usually the largest and most wasteful part of a prompt. Narrow the list, describe rather than dump, and never offer a tool the caller cannot use.

Mechanism

Three decisions. Which tools: narrowed by skill selection, step intent, and tenant connector availability. How much detail: names and purposes for planning, full schemas only for the executor. How rendered: consistent, compact, with required arguments and enums explicit — enums in particular prevent a whole class of argument hallucination.

The offered list is also a security boundary. A tool present in the prompt will eventually be called; availability in the prompt must exactly match permission at dispatch.

  • Offering unauthorised tools. A prompt-level permission bypass.
  • Missing enums and formats. Invented argument values.
  • Inconsistent rendering. The model learns one shape and then sees another.

RAG context injection

Retrieved chunks enter as labelled, cited, ordered evidence — with the source named, the freshness visible, and the instruction that the answer must come from them.

Mechanism

Each chunk is rendered with its citation id, its source (document and section), and where it matters its date. Ordering is not cosmetic: models attend more reliably to the beginning and end of a long context, so the strongest evidence belongs first, with the next-strongest last. Where the retrieval returned nothing above the confidence floor, the prompt should say so explicitly rather than presenting weak chunks as evidence.

At production scale

Surfacing document age in the prompt and in the answer is one of the cheapest trust features available. Stale wiki content is the most common source of confidently wrong answers, and a model told a document is three years old will usually hedge appropriately.

Failure modes

  • Unlabelled chunks. The model cannot cite what it cannot identify.
  • Weak evidence presented as strong. Below-threshold chunks included silently.
  • Middle burial. The key chunk placed in the least-attended position.
  • No "not found" path. The model answers from whatever it was given.

Choose it when

  • Any retrieval-augmented call.

Memory injection

Memory enters capped, labelled as inference rather than evidence, and with its applicability reason — because it is the system's own claim about the world, not a document.

Mechanism

Recalled memories arrive with a score, a provenance status (verified, missing, disputed) and an applicability reason. All three should be visible in the prompt: the model should know that a memory is a prior inference, how confident the system is, and why it was considered relevant. Cap the section tightly — 5–10% of the budget — because memory competes with evidence and evidence should usually win.

Visual context injection

Screenshots and page state for agents that operate a UI — expensive in tokens, essential for RPA, and the most likely context to contain personal data.

Mechanism

Three representations, in increasing cost: an accessibility or DOM summary (cheap, structured, usually sufficient), a text description of the screen produced by a vision model, and the image itself passed to a vision-capable model. The rule is to escalate only on failure: try structure, then description, then pixels.

A screenshot must pass a redaction step before it enters a prompt, and it should never be retained in context longer than the step that needed it.

Feedback and failure injection

On a replan, the previous plan and the specific verifier failure are the most valuable context available — and the least likely to be included correctly.

Mechanism

Include the previous plan (or its relevant portion), the exact verifier verdict and diagnosis, and any reflection produced from it. Include only the last one or two, not the whole history — an accumulating list of failures fills the window and gives the planner no signal about which failure matters now.

Where the same failure has repeated, say so explicitly: "this approach failed twice with the same error" is a much stronger instruction than two copies of the error.

Output contracts

Specify the response shape and validate it — then repair or retry rather than parsing prose with regular expressions.

Mechanism

The contract is built alongside the prompt: a schema for the expected response, rendered into the prompt as an explicit requirement and used afterwards to validate. Failed validation triggers a bounded repair — a second call quoting the schema violation — before falling back to a lenient parse. Native structured-output or tool-calling modes should be used where the provider offers them, since they enforce the shape at generation time rather than after.

Prompt lifecycle and safety

Prompt compression

When the assembled context exceeds the budget, compress deliberately — drop, truncate with markers, or summarise — in a priority order you chose in advance.

Mechanism

An ordered ladder, cheapest and least lossy first: drop below-threshold evidence; truncate verbose tool outputs keeping head and tail with an explicit marker; summarise older conversation turns; drop lower-ranked memories; and only then compress evidence itself. The system layer and the output contract are never compressed.

Every compression must leave a trace in the prompt ("[truncated 3,200 tokens]") so the model knows it is reasoning over a fragment, and in the composition log so you know afterwards.

never touched: system layer, output contract, top-5 evidence

At production scale

Compression frequency is a design signal. If most calls need it, the problem is upstream — too many tools offered, too many candidates retrieved, too much history carried — and fixing that is cheaper than compressing on every call.

Failure modes

  • Silent truncation. The model does not know it is missing something.
  • Compressing the contract. Unparseable output.
  • Summarising the answer away. The critical detail lost in a digest.
  • Unordered dropping. Whatever happened to be last gets cut.

Choose it when

  • Any variable-length context — so always, as a safety net.

Prompt variants and selection

Prompts are versioned artifacts with variants, selected per tenant or goal class and compared on measured outcomes rather than opinion.

Mechanism

Each role's prompt has a registry of variants with ids. A selector chooses one per call — by tenant configuration, goal class, or experiment assignment — and the choice is recorded on the run so outcomes can be attributed. That record is what turns prompt engineering from taste into measurement.

At production scale

Recording the variant id on the run is the whole trick. Without it you cannot compare, cannot roll back with confidence, and cannot explain why last month's numbers differ. With it, prompt changes become ordinary software changes with measurable effects.

Failure modes

  • Unversioned prompts. Silent behaviour changes.
  • Variant not recorded. Uncomparable outcomes.
  • Too many live variants. Nothing reaches significance.
  • Optimising the wrong metric. Pass rate up, false-pass rate up too.

Choose it when

  • As soon as prompts are load-bearing — which is immediately.

Prompt safety and injection resistance

Structural defence, not persuasion: layer the prompt by trust, fence untrusted content, never let data become instructions, and validate what comes back regardless.

Mechanism

Five structural rules, each of which holds even when the model is fooled:

  1. Layer by authority. System, task, evidence, untrusted — in that order, never reorderable by content.
  2. Fence untrusted content explicitly with delimiters and a statement that it is data.
  3. Never interpolate untrusted text into the system layer, including via a tenant-configurable "custom instruction" field.
  4. Do not let content name tools. Tool selection comes from the registry, and a tool name appearing in retrieved text is not a tool call.
  5. Validate the output. A model persuaded to emit an unauthorised call still has to get past name validation, argument validation, risk classification and the approval gate.

Prompt-level defences reduce the frequency of successful injection; the validation layers are what make it non-catastrophic. Both are required.

At production scale

Assume the model will occasionally be fooled and design so that being fooled is not sufficient. Every serious agent incident in the industry has the same shape: a persuasive instruction reached a privileged layer, or an unvalidated call reached a real system. The prompt structure prevents the first; the validation chain prevents the second.

Alarm on injection-detection rate per source. It is one of the few genuinely high-signal security metrics available, and it tells you which connector is being used as an attack path.

Failure modes

  • Untrusted text in the system layer. The root cause of most real incidents.
  • Trusting the fence alone. Fences help; they are not a boundary.
  • Tool names from content. Never resolve a tool from text the model read.
  • No output validation. One persuasive document becomes a privileged action.

Choose it when

  • Always. Structure first, detection second, validation always.

Prompt reproducibility

Record enough to rebuild any prompt exactly: variant ids, context item ids, budget decisions, model and parameters — because "what did it actually see?" is the first question in every investigation.

Mechanism

Store the prompt's recipe rather than the prompt itself: the variant id per role, the ordered list of context item ids with their token counts, the budget allocations and any compression applied, the model and its parameters, and a hash of the fully rendered prompt. The recipe is small, contains no duplicated content, and lets you reconstruct the prompt from immutable sources — with the hash proving the reconstruction matches.

The memory contract's as_of field exists for the same reason: recall is reproducible at a point in time.

At production scale

Storing full prompts for every call is expensive and often contains personal data; storing recipes is cheap and privacy-preserving, and it is what you actually need. Keep full prompts only for sampled traffic and for failures, with the same retention rules as any other content.

Failure modes

  • No recipe. Investigations become guesswork.
  • Mutable sources. A chunk edited in place makes the recipe unreconstructable — this is why supersede-not-overwrite matters.
  • Full prompts retained forever. A compliance problem with a storage bill attached.

Choose it when

  • Before your first production incident.

What is missing here

  • Prompt-level cost attribution in the product. The composition is logged, but there is no per-section cost breakdown surfaced to tenants ("your tool schemas cost 38% of your spend").
  • Automatic context-window packing. Allocation is policy-driven; nothing solves the packing problem optimally against a value estimate per item.
  • Visual context budgeting. Text sections have caps and compression; image context does not participate in the same budget discipline.
  • Prompt regression tests as a gate. Variants are measurable, but there is no required "this prompt change must not regress these 50 cases" check in the release path.
  • Cross-role prompt consistency checks. Nothing detects that the planner and verifier have drifted into different definitions of success.
