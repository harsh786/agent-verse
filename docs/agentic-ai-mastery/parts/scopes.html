Orientation

A scope is a boundary that answers "which of these am I allowed to touch?" The platform has nine of them, nested, and the discipline that makes multi-tenancy safe is that every data access and every action is filtered by the full stack of scopes before it happens — not checked afterwards, not enforced by the prompt, and never by a single layer alone.

This chapter is short because the individual scopes appear throughout the book. Its job is to show them as one system: how they nest, how a request is narrowed by each in turn, and what specific leak each one prevents. The recurring rule — filter before you fetch, at every scope — is the whole of data-leakage prevention.

The nine scopes

Tenant scope

The outermost boundary: everything belongs to exactly one tenant, and the boundary is enforced in app code and independently in the database.

Mechanism

The immutable TenantContext flows through every request; app queries filter by it and Postgres RLS enforces it with SET LOCAL app.tenant_id. Every other scope lives inside this one — an agent, a collection, a memory all belong to a tenant first.

In AgentVerse

  • app/tenancy/context.pyTenantContext
  • app/db/rls.pythe database enforcement
  • app/tenancy/middleware.pyestablishing it per request

Prevents

tenant A's goal retrieves tenant B's documents
 → blocked in app (query scoped by tenant_id)
 → AND blocked in DB (RLS rewrites the query)
the leak requires BOTH layers to fail simultaneously

At production scale

This is the boundary whose failure ends contracts. The test that asserts a tenant-A request can never return a tenant-B row — through API, retrieval, memory, and cache — is the most important test in the codebase. Full treatment in chapter 13.

Failure modes

  • System sessions bypassing RLS. Background jobs seeing all tenants.
  • Caches without a tenant key. The cache becomes the leak.

Choose it when

  • Always. It is the foundation.

API key scope

Within a tenant, a key is limited to specific operations — so a leaked read key cannot write and a CI key cannot reach billing.

Mechanism

Each key carries a scope set (read, submit, admin, billing…), an optional IP allowlist, and an expiry, checked before the request reaches business logic. Goal tokens narrow this further to a single goal's tool set for a bounded time.

In AgentVerse

  • app/auth/scope_enforcement.pythe check
  • app/auth/goal_tokens.pyper-goal scoped tokens
  • app/auth/ip_allowlist.pyIP constraints

Prevents

a leaked read-only key attempts to submit a goal → DENIED
a valid key used from an unexpected network → DENIED (IP allowlist)
a goal token used after its goal completes → DENIED (expired)

At production scale

Goal tokens turn key compromise from a breach into an inconvenience. Full treatment in chapter 13.

Failure modes

  • God keys. Every scope, everywhere.
  • No expiry. Keys outliving their purpose.

Choose it when

  • More than one kind of caller.

Agent scope

Each agent has its own tools, collections, memory, and identity — so one agent cannot reach another's connectors or recall another's memories.

Mechanism

An agent configuration binds an allowed tool set, accessible collections, a memory namespace, and an identity (its own credentials for the systems it operates). A spawned sub-agent inherits a narrowed version — never a wider one (chapter 1).

In AgentVerse

  • app/db/models/agent.pyAgent — the configuration
  • app/auth/agent_identity.py, agent_credentials.py, agent_manifest.pyper-agent identity and credentials
  • app/agent/tool_context.pythe agent's permitted tool view

Prevents

support-agent tries to call the finance connector → not in its tool set
support-agent recalls fin-ops-agent's memories → different memory namespace
a spawned child requests a tool the parent lacked → DENIED (monotonic)

At production scale

Per-agent identity is what makes "which agent did this?" answerable at the connector — each agent authenticates to external systems as itself, so the external system's own logs attribute correctly too.

Failure modes

  • Shared credentials. All agents authenticating as one identity, unattributable.
  • Widening inheritance. A child with more than its parent.

Choose it when

  • More than one agent per tenant.

Knowledge collection scope

Retrieval is authorised per collection before any similarity is computed — an agent searches only the collections it is permitted, and a user only what their role allows.

Mechanism

A collection carries an access rule (roles, or an explicit allowlist). The retrieval gateway resolves which collections the current principal may search before retrieval, so restricted content is never scored, never ranked, never logged. Federated search fans out only to authorised collections.

In AgentVerse

  • app/rag/gateway.pySQLCollectionAuthorizer
  • app/knowledge/federated_search.pyper-source authorisation before fan-out
  • app/org/knowledge_access.pyrole/department gating

Prevents

an analyst searches "salary" → the HR collection is not in their authorised
set → those chunks are never scored or returned
authorisation happens BEFORE retrieval, not as a post-filter — the
restricted content never enters the pipeline

At production scale

Filter-before-fetch is the rule. A post-filter means the restricted rows were read, ranked, and possibly logged — a leak waiting for a logging bug. Full treatment in chapters 4 and 6.

Failure modes

  • Post-filtering. The classic leak shape.
  • Default-open collections. Created outside the normal path.

Choose it when

  • Any collection with access restrictions — which is most.

Connector scope

Which external systems an agent can reach, with which credentials — the boundary between the agent and the outside world.

Mechanism

Connectors are registered per tenant with credentials held in the vault, never in config or prompt. An agent's tool set determines which connectors it can invoke, and the vault resolves the credential at call time so the model never sees it. A connector's scope also bounds what it can do in the external system — read-only OAuth scopes where the agent only needs to read.

In AgentVerse

  • app/mcp/registry.pyper-tenant connector registry
  • app/providers/vault.pyencrypted credential resolution
  • app/mcp/oauth.pyPKCE OAuth with scoped grants
  • app/rpa/credential_injector.pycredentials injected without model exposure

Prevents

an agent with a read-only GitHub connector attempts a write
 → the OAuth grant itself lacks write scope → the external system refuses
credentials never appear in the prompt, so injection cannot exfiltrate them

At production scale

Request the narrowest external scope the agent needs. A read-only grant means even a fully compromised agent cannot write to the customer's GitHub — the boundary is enforced by the third party, not just by you.

Failure modes

  • Over-broad OAuth grants. Write access the agent never needed.
  • Credentials in prompt or config. Exfiltration surface.

Choose it when

  • Any external integration.

Tool scope

The exact set of tools available to a goal — narrowed from the tenant's catalogue by agent, skill, policy, and step — and the offered set must equal the permitted set.

Mechanism

Tool availability is progressively narrowed: the tenant has a catalogue, the agent a subset, the skill a further subset, the policy engine may deny specific tools, and the step's intent narrows again. The critical invariant: a tool visible in the prompt must be one the goal is permitted to call, because the model will eventually try everything it can see.

In AgentVerse

  • app/agent/tool_selector.pynarrowing
  • app/agent/tool_context.pythe permitted view
  • app/tool_runtime/tool_policy.pypolicy-level tool rules
  • app/agent/tool_calls.pyvalidate_tool_name() — the backstop

Prevents

tenant catalogue      34 tools
 → agent allowlist    12
 → skill narrows      6
 → policy denies      admin.* → 5
 → step intent        2 offered to the model
a tool the model invents or a denied tool it names → validate_tool_name
rejects it before dispatch (chapters 1, 18)

At production scale

The offered-equals-permitted invariant is a security boundary, not a UX nicety. Offering a tool "for context" that the goal cannot use is a prompt-level permission bypass waiting to be exercised.

Failure modes

  • Offering unauthorised tools. The bypass.
  • Resolving a tool name from content. Never — only from the registry.

Choose it when

  • Any tool-calling agent.

Memory scope

Memory is addressed by a tuple — tenant, department, agent, goal, collection, source — and recall is filtered by it and by data classification before scoring.

Mechanism

Every memory row carries its scope; the recall request carries the allowed data classes and the principal's scope. Candidates are filtered to the intersection before any similarity is computed, so a memory outside scope is never a candidate — regardless of how well it would have matched.

In AgentVerse

  • app/memory/contracts.pyMemoryRecallRequest.allowed_data_classes
  • app/state_runtime/memory_policy.pyper-runtime policy
  • app/memory/dept_memory.pydepartment-scoped memory
  • app/db/rls.pythe database backstop

Prevents

support-bot recall (class ≤ internal, dept support)
 candidate memories filtered to tenant=acme AND dept IN {support, tenant-wide}
   AND class IN {public, internal} AND lifecycle=active
 → 412 rows excluded before scoring (other tenants, HR, restricted)
memory is recalled silently into prompts, so a scope gap is a silent leak

At production scale

Memory is the most dangerous scope to get wrong because it is recalled into prompts without a human seeing it — a leak may only surface in a customer's output. Filter-then-score is mandatory. Full treatment in chapter 3.

Failure modes

  • Filter-after-score. The rows were already read.
  • Scope in the prompt. "Only use acme's memories" is not enforcement.

Choose it when

  • Any cross-goal memory.

Policy scope

Which policy bundle and constraints apply to a goal — determined by tenant, plan, domain, and compliance regime, and inviolable downward: safety constraints can only be added, never removed.

Mechanism

The policy engine selects a bundle from the goal's context and compiles it into constraints. Policy scope determines which rules a goal is subject to, and the append-only safety rule (chapter 1) means a narrower-scoped optimisation can never strip a broader-scoped safety requirement.

In AgentVerse

  • app/security_runtime/policy_bundle_selector.pybundle selection
  • app/policy_runtime/compiler.pycompilation to constraints
  • app/governance/compliance_bundles.pythe regime bundles

Prevents

a HIPAA-tenant goal → HIPAA bundle applies regardless of agent config
an optimisation rule tries to drop an approval gate the risk rule added
 → DENIED: safety_patterns is append-only

At production scale

Policy scope is what guarantees a regulated goal always gets its regime's controls, no matter how it was configured or routed. The append-only safety invariant is the single most valuable line in the policy system. Full treatment in chapter 13.

Failure modes

  • Wrong bundle selected. A regulated goal on default rules.
  • Removable safety. An optimisation loosening a control.

Choose it when

  • Any deployment with differing rules per goal.

Runtime context scope

The innermost boundary: what this specific goal, right now, may touch — the intersection of every enclosing scope, materialised as a runtime profile the loop enforces at every step.

Mechanism

At goal start, the platform computes a runtime profile: the effective tool set, collections, memory scope, constraints, budget, and autonomy mode for this goal — the intersection of tenant, key, agent, policy, and request. Every node in the loop reads from it, so a step cannot exceed what the profile allows even if the model asks. It is the concrete, per-goal realisation of all the abstract scopes above.

  • app/orchestration/runtime_profile.py, runtime_profile_builder.pybuilding the profile
  • app/core/runtime_profiles.py, runtime_flags.pyprofile definitions and flags
  • app/state_runtime/state_context.pythe runtime state context
  • app/explainability_runtime/runtime_profile_explainer.pyexplaining what the goal may do and why

Prevents

goal g-8891 runtime profile (computed at start)
 tools     [invoices.query, gst.fetch_filed, gst.file_return*]  (*gated)
 collections [acme/finance-policies]  memory [acme/finance/*]
 budget $8 · max_iter 25 · autonomy supervised
any step attempting a tool or collection outside this → rejected by the loop

At production scale

The runtime profile is where all nine scopes become one enforceable object. Its explainer answers the question every operator eventually asks — "what is this goal actually allowed to do, and why?" — from the computed profile rather than from a mental model of five interacting systems.

Failure modes

  • Profile not enforced per step. Computed once, ignored later.
  • Stale profile. Not recomputed when scopes change mid-goal.

Choose it when

  • Always. It is how the scopes are actually enforced.

How scopes compose to prevent leakage

Safety comes from the intersection: a request must satisfy every scope, and each narrows what the previous allowed. A gap in one scope is caught by the others — but only if each is enforced before the data is fetched.

Mechanism

The scopes are AND-ed, never OR-ed. A goal reaches a piece of data only if the tenant owns it, the key permits the operation, the agent is allowed the collection, the collection's access rule admits the principal, the policy does not deny it, and the runtime profile includes it. Because each is enforced independently — and tenant scope is enforced twice, in app and database — a single missed check is not a breach. The failure mode to fear is the same gap appearing in every layer, which is why the layers use different mechanisms.

In AgentVerse

  • app/orchestration/runtime_profile_builder.pywhere the intersection is computed
  • app/db/rls.pythe independent database enforcement
  • app/explainability_runtime/decision_explainer.pyexplaining a scope decision

Worked example

request: agent support-bot, user analyst, goal "salary bands by team"
 tenant     acme ✓
 key scope  goals:submit ✓
 agent      support-bot's collections: [support-kb, product-docs]
            → HR collection NOT in the agent's set ✗
result  denied at the agent scope; even if that check had a bug,
        the collection's own access rule excludes analysts, and
        RLS scopes to the tenant — three independent barriers

At production scale

Defence in depth is not redundancy for its own sake — it is the acknowledgement that in a system with hundreds of access paths written by dozens of people, one of them will forget a check. The scopes compose so that one forgotten check is a bug, not an incident. Test the composition, not just each scope: assert that a request failing any one scope is denied.

Failure modes

  • OR instead of AND. Satisfying one scope granting access.
  • Same gap in every layer. Why the layers use different mechanisms.
  • A path that skips the profile. Admin tooling, raw queries, background jobs.

Choose it when

  • Always. This is the model, not a feature.

What is missing here

  • A scope-composition test harness. Each scope is tested; a systematic "cross-product of scope violations is denied" suite would be stronger.
  • Runtime-profile diffing. No tooling to show how a goal's effective profile changed between two runs or two config versions.
  • Scope for outbound data. Scopes govern what a goal can read; there is less structure around what it may send where, beyond the exfil guard.
