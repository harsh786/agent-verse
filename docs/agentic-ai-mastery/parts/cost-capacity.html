Orientation

An agent has unit economics, and if you do not understand them you will discover them on an invoice. The cost of a goal is not a mystery — it decomposes cleanly — and the levers to reduce it are known and ordered. This chapter is the economics of running agents at scale: what a goal costs, why, and how to make those numbers survive growth.

The core formula is worth memorising: cost per goal ≈ iterations × (tokens per iteration × price) + tool cost + compute cost. Every optimisation targets one factor, and they must be attacked in the right order, because the tempting lever (a cheaper model) is usually not the biggest one (fewer iterations, fewer tokens).

Cost and capacity

The unit economics of a goal

Cost per goal decomposes into iterations, tokens per iteration, price, tool cost, and compute — measure each, attribute it (including sub-agents), and you can explain and control the bill.

Mechanism

The cost tracker accumulates real spend per run across every component and attributes it to the goal, including descendants of spawned agents. The breakdown by component (planner, executor, verifier, embeddings, reranker, tools, code execution) is what makes cost actionable — "this goal cost $0.42" is not useful; "51% of it was executor tokens, 38% of which were tool schemas" points at the fix.

the breakdown says: narrow the tool schemas first — biggest, easiest win

At production scale

Attribute descendant spend to the parent, or multi-agent goals look cheap and your per-goal costs do not reconcile with the provider invoice — the moment finance stops trusting the numbers. Publish cost per goal class to the teams that own those goals; visibility changes behaviour faster than any optimiser. The breakdown is what turns the recurring "just use a bigger model" argument into a specific, non-model fix.

Failure modes

  • Unattributed sub-agent spend. Costs that do not reconcile.
  • Total without breakdown. A number nobody can act on.
  • Model tokens only. Missing tool and compute cost.

Choose it when

  • From the first production goal.

The cost levers, in order

Attack cost in the order that pays: iterations first (better planning, lessons, stall detection), then tokens (narrow schemas, tighter retrieval, caching), then price (per-role routing) — never price first.

Mechanism

The levers, ordered by impact and by how quality-neutral they are. Iterations: better planning, recalled lessons, stall detection, and cheap replans cut the multiplier that dominates cost. Tokens per iteration: narrowing tool schemas (often 30–40% of the prompt), tighter retrieval, prompt compression, and caching. Price: per-role model routing, shadow-tested downgrades. Starting with price risks quality for the smallest gain; starting with iterations and tokens is usually quality-neutral or positive.

At production scale

The order matters because the levers interact: narrowing tool schemas cuts tokens and improves selection accuracy and thereby reduces iterations — one change, three factors. Model downgrades, the most tempting lever, come last and only after shadow testing (chapter 16) confirms quality holds. Report every optimisation with its quality delta; a cost win that lowers success is a loss.

Failure modes

  • Price first. Quality risk for the smallest gain.
  • Cost without quality. Optimising a proxy.
  • Caching personalised answers. A correctness bug sold as a saving.

Choose it when

  • As soon as volume is real.

Capacity planning under variance

Agent workloads have enormous variance — a 200ms lookup and a four-hour audit run on the same platform — so capacity is planned against a distribution of goal shapes, not a single mean.

Mechanism

Because per-goal graph assembly (chapter 1) makes cost and duration vary by orders of magnitude, capacity planning uses the distribution: p50, p95, p99 of iterations, tokens, and duration per goal class, plus the mix of classes. Provision workers per plan queue (chapter 20) to meet each tier's SLA at its p95, and use autoscaling metrics that reflect agent work (queue depth, in-flight goals) rather than CPU alone.

At production scale

Planning against the mean is the classic capacity mistake for agents — the mean is meaningless when the distribution spans four orders of magnitude. Provision for the p95 of each class on its own queue, and scale on queue depth: an agent worker waiting on a slow tool shows low CPU while being fully occupied, so CPU-based autoscaling under-provisions exactly when you need capacity.

Failure modes

  • Planning against the mean. Under-provisioned for the tail.
  • CPU-based autoscaling. Blind to IO-bound agent work.
  • One pool for all classes. The audit starving the lookups.

Choose it when

  • Any workload with variance — which agent workloads always have.

The economics of caching

Caching is the highest-return cost lever on repetitive workloads — semantic cache on retrieval, tool-result cache, embedding cache — but each has a correctness boundary that, crossed, turns a saving into a bug.

Mechanism

Three caches with three risk profiles. The semantic cache (chapter 2) serves a repeated question's answer by embedding match — highest return on FAQ/support, but a loose threshold serves the wrong answer. The tool-result cache serves a repeated read — safe for idempotent reads, wrong for anything time-sensitive. The embedding cache (chapter 7) serves a repeated text's vector — safe as long as the model is in the key. Each must be tenant-scoped and invalidated on the underlying change.

support workload

At production scale

On repetitive workloads (support, FAQ) semantic caching commonly removes 25–40% of pipeline executions — the single largest cost reduction available. But the correctness boundaries are unforgiving: a cross-tenant cache hit is a data leak, a stale cache after ingest is a wrong answer, and a cached personalised answer is a privacy bug. Tune hit-rate against these risks deliberately (chapter 2's semantic cache concept).

Failure modes

  • Cross-tenant hit. A data leak.
  • Stale after ingest. A wrong answer served fast.
  • Cached personalised content. A privacy bug.

Choose it when

  • Repetitive query distributions — the common case in support and FAQ.

What is missing here

  • Predictive cost estimation. Cost is measured after the fact and plans are estimated (chapter 1), but a learned per-goal-class cost predictor for admission control is thin.
  • Cost-anomaly detection. Spend is attributed but a per-tenant anomaly alarm is not wired (chapter 11).
  • Autoscaling on agent-native signals. Queue-depth scaling exists; a richer model using goal-class mix and predicted duration is future work.
  • Spot/preemptible execution. No use of cheaper preemptible capacity for interruptible batch goals, which the checkpointing (chapter 1) would make safe.
