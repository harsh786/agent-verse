Orientation

"Memory" in an agent platform is not one thing. It is at least seven stores with different lifetimes, different trust levels, different write triggers and different failure modes, and the only reason to keep them separate is that each answers a different question:

KindAnswersLifetimeWritten by
executionWhat happened in this goal?One goalEvery step
reflexionWhat did we learn from failing?Until supersededTerminal failure
long_termWhat is durably true here?Months–yearsExtraction from successes
episodicWhat happened that time?Weeks–monthsGoal completion
proceduralHow do we do this here?Until the process changesValidated repetition
knowledge_graphHow do these things relate?With the graphEntity extraction
prospectiveWhat must we do later?Until the moment arrivesIntention capture

Every one of them is an injection surface and a compliance surface. Memory is the only part of an agent platform that writes its own future prompts, which makes it the only part where a single poisoned row can change behaviour indefinitely — and the part a data subject can demand you delete.

The contract, the tiers, and the flows

The canonical memory contract

One record type, one write request, one recall request, one feedback record — so all seven tiers share scoping, classification, provenance, scoring and retention instead of each reinventing them.

Mechanism

A MemoryRecord carries far more than content: tenant, kind, a safe_summary (capped, the part that may enter a prompt), content_ref (the full payload by reference), evidence_refs, data classification, confidence, lifecycle_state, version, the embedding model and its dimension, outcome and effectiveness scores, recall/helpful/harmful counters, expiry, retention policy id, and an idempotency key.

Three design decisions worth stealing: scores are integers scaled to 10,000, so ranking is exactly reproducible with no float drift; the summary and the payload are separate fields, so a prompt can never accidentally carry the whole blob; and the embedding model and dimension are stored on the row, so a model migration is detectable per record rather than a corpus-wide guess.

In AgentVerse

  • app/memory/contracts.pyMemoryRecord, MemoryWriteRequest, MemoryRecallRequest, MemoryRecallHit, MemoryFeedback; MemoryKind (7), LifecycleState (5), Classification (4)
  • app/memory/repository.pywrite(), recall ranking, poison quarantine
  • app/memory/postgres_repository.pydurable implementation + sensitive redaction
  • app/memory/backfill.pyidempotent backfill for rows written before the contract

Models are frozen with extra="forbid": a memory row cannot be mutated in place, and an unexpected field is an error rather than silent data.

Worked example

MemoryWriteRequest
  tenant_id       t_acme
  memory_kind     procedural
  content         "Vendor reports: pull the CSV export, not the API — the
                   API omits credit notes."
  source_goal_id  g-8891      source_execution_id  x-3
  evidence_refs   ("step:4:tool_result", "chunk:invoices/notes.md#2")
  classification  internal
  confidence      7200            (0.72 on a 10,000 scale)
  idempotency_key sha256(tenant|kind|content|goal)
  retention_policy_id  standard-365d

LifecycleState: active → disputed → quarantined → expired → deleted

At production scale

The idempotency key is what keeps memory from bloating: a goal that retries three times writes one row, not three. Without it, a flapping connector generates thousands of near-identical "lessons" and recall quality collapses within a week.

evidence_refs is the field that makes memory defensible. When an agent asserts something surprising, you can walk from the memory to the exact tool result and chunk that produced it. Memories without evidence should be recallable only at low confidence, if at all.

Failure modes

  • Unbounded summaries. Without a length cap, one memory eats the context budget.
  • Float scores. Ranking that varies between runs makes eval impossible.
  • Missing dimension. Change the embedder and every recall silently mismatches (chapter 7).
  • Mutable rows. In-place edits destroy the audit trail; version instead.

Choose it when

  • You have more than one memory tier, more than one tenant, or any retention obligation.

Current run context (working memory)

What the agent is holding right now: the goal, the plan, the last few observations, the scratchpad — bounded by the context window and compacted as it fills.

Mechanism

Working memory is the only tier with a hard physical limit, so its discipline is eviction, not storage. Three techniques, applied in order: truncate tool outputs on write (keep the head and tail, store the whole thing as an artifact), summarise older turns into a running digest, and externalise anything reusable to a durable tier so it can be recalled by relevance instead of carried by position.

  • app/memory/working_memory.pythe tier
  • app/state_runtime/session_memory.pysession-scoped context
  • app/agent/prompt_compressor.pycompression before the call
  • app/context/context_budget.py, prompt_budget.pythe budget that decides what survives
  • app/coordination/group_chat/compaction.pycompaction for multi-agent transcripts

Worked example

iteration 6, budget 32k tokens
  goal + plan               1.2k   keep whole (never evict)
  retrieved chunks          8.0k   keep top-ranked within budget
  steps 1-3 observations    —      compacted to a 400-token digest
  steps 4-5 observations    3.1k   keep verbatim (recent)
  verifier feedback         0.3k   keep last only
  memory recall             1.5k   capped at 5% of budget
  tool schemas              4.0k   narrowed to 9 tools by the selector
total                      18.5k   headroom for the response

At production scale

Context is the most expensive resource in the system, and working memory is where it is wasted. The three biggest wins, in order: narrow the tool schemas (often 30–40% of the prompt), truncate tool outputs aggressively, and compact old turns instead of carrying them. Long-context models make this feel unnecessary right up until the invoice arrives — cost scales with tokens whether or not the window allows them.

Failure modes

  • Silent truncation of the answer. The critical tool output gets cut. Truncate with a marker and keep the tail as well as the head.
  • Lost-in-the-middle. Content in the centre of a long prompt is under-used. Put the most important evidence first and last.
  • Compaction drift. Repeated summarisation loses specifics. Summarise from the original, not from the previous summary, where possible.

Choose it when

  • Always. This is the tier you cannot opt out of.

Agent state

The serialisable, checkpointed record of where the run is — distinct from what it knows. State is control-flow memory: plan, step index, iteration, status, accumulated cost.

Mechanism

A typed object persisted after each node transition, keyed by a thread id. It must contain everything needed to resume and nothing that cannot be serialised — no open connections, no live provider clients. The checkpointer is pluggable so the same code runs against Redis in production and memory in tests.

The rule that keeps this honest: if a value affects control flow, it belongs in state; if it is merely useful context, it belongs in working memory and can be re-derived.

  • app/state_runtime/state_context.pyruntime state context

Worked example

checkpoint after verify, iteration 2
{ goal_id: g-8891, thread: t_acme:g-8891,
  plan: [5 steps], step_index: 3, iteration: 2,
  step_status: [done, done, done, running, pending],
  verifier_feedback: "step 3 returned no rows for APAC",
  cost_accum_usd: 0.83, autonomy_mode: supervised,
  waiting_on: null }

worker killed at 14:02 → new worker loads this → resumes at step 4

At production scale

Checkpoint size is the metric to watch. Every node transition writes it, so a state object that grows with tool output turns into the dominant cost of a long run and a source of Redis pressure. Keep payloads out of state and store references.

Resumability is also a safety property: a poison goal that crashes workers can be stopped by refusing to resume its checkpoint, without restarting the fleet.

Failure modes

  • Unserialisable state. Someone stores a client object; checkpointing fails at 3 a.m.
  • State bloat. Megabyte checkpoints written a dozen times per goal.
  • Version skew. A deploy changes the state shape and old checkpoints cannot load. Version the schema and migrate or discard explicitly.

Choose it when

  • Any agent that runs longer than one request, on any infrastructure that can restart.

Execution memory

Every step's inputs, outputs and verdicts for the current goal — the reason a replan does not re-execute work that already succeeded.

Mechanism

Keyed by goal and step, it stores what each step did and what came back. Two uses: replan reads it to skip completed work, and rollback reads it to know what needs compensating. It is also the raw material from which episodic and long-term memories are later extracted.

In AgentVerse

  • app/memory/execution.pythe tier
  • app/reliability/rollback.pyreads it to build the compensation list
  • app/services/result_artifacts.pylarge outputs stored by reference
  • app/plan_runtime/plan_trace.pythe plan-side view of the same history

Worked example

goal g-8891
 step 1  github.list_runs      → run 8891           ✓ (cached in exec memory)
 step 2  github.get_logs       → 2.1MB → artifact a-77, digest kept   ✓
 step 3  jira.create_issue     → PROJ-1180          ✓  inverse: delete
 step 4  confluence.update     → 403                ✗

replan  reuses 1-3 from execution memory (0 tokens, 0 API calls)
rollback reads step 3's inverse and undoes it

At production scale

This tier is the single largest cost saving on multi-iteration goals: without it, a failure at step 7 costs seven steps on every retry. With it, cost per replan is roughly one step. Store big outputs as artifacts and keep only a digest plus a summary in memory, or the tier becomes the thing that fills your database.

Failure modes

  • Stale reuse. Reusing a read from 40 minutes ago when the world has changed. Attach freshness requirements per step type.
  • Unbounded growth. Every byte of every tool output retained. Truncate and reference.
  • Missing inverses. Rollback cannot compensate what was not recorded.

Choose it when

  • Any agent that can replan, retry, or roll back — which is any production agent.

Episodic memory

"What happened that time" — a compact record of a completed goal, retrievable by similarity so a new goal can see how the last one like it went.

Mechanism

On goal completion, distil the run into an episode: goal text, approach taken, outcome, notable surprises, cost, duration. Embed the goal text for similarity recall. At plan time for a new goal, recall the most similar episodes and show the planner what worked and what did not.

The difference from reflexion memory is that episodes record successes too, and the difference from long-term memory is that an episode is a specific event, not a generalised fact.

In AgentVerse

  • app/memory/episodic.pythe store
  • app/memory/salience.pywhich episodes are worth keeping
  • app/memory/consolidation.py, app/memory_v2/consolidation.pyepisodes → generalised memories
  • app/scaling/memory_tasks.pythe background jobs that do it

Worked example

episode e-441
  goal      "reconcile March payouts"
  approach  CSV export → recompute → diff → file
  outcome   success, 6 iterations, $1.20, 14 min
  surprise  "the API omitted credit notes; CSV did not"

new goal "reconcile April payouts"  (similarity 0.94)
  planner sees e-441 → plans the CSV route immediately
  result 2 iterations, $0.40

At production scale

Episodic recall is what makes recurring work cheap. It also grows without limit if every goal writes an episode, so gate on salience: keep the surprising, the expensive, and the failed; drop the routine successes that resemble a hundred others. Consolidation should run as a scheduled job that folds similar episodes into one generalised memory and expires the originals.

Failure modes

  • Episode flood. Ten thousand near-identical rows drown recall. Salience gate plus dedup by embedding.
  • Wrong-lesson transfer. A similar-looking goal with a different constraint. Include the constraints in the episode, and let the planner judge applicability.
  • PII in episodes. Goal text often contains customer data. Classify and redact on write.

Choose it when

  • Similar goals recur for the same tenant.
  • Skip if every goal is genuinely novel.

Long-term (semantic) memory

Durable facts about this tenant's world — extracted from runs, not asserted by a user: "invoices are approved by the finance lead", "the staging cluster is eu-west-2".

Mechanism

An extractor reads completed runs and proposes typed candidates; each candidate must carry evidence references and a confidence. Only candidates above threshold with real evidence are promoted to long-term rows. Recall is by semantic similarity plus confidence floor.

This is the tier people mean by "the agent remembers our setup". Its value is proportional to how strictly you gate writes — a long-term store full of guesses is worse than an empty one, because the guesses look authoritative in a prompt.

  • app/memory/long_term.pythe store

Worked example

candidates from 40 runs
  "finance lead approves invoices > $10k"   conf 8800  evidence 6 runs  → PROMOTE
  "the CFO prefers PDF summaries"           conf 4100  evidence 1 run   → hold
  "prod database is in eu-west-2"            conf 9500  evidence 12 runs → PROMOTE
recall for a new invoicing goal returns the two promoted facts, not the guess

At production scale

Require corroboration. A fact seen once is an observation; a fact seen in six independent runs is knowledge. Making the promotion rule explicit (n ≥ 2, evidence present, confidence ≥ threshold) turns this tier from a liability into an asset, and gives you something to point at when a memory turns out to be wrong.

Long-term memory is also the tier most likely to appear in a data-subject access request. Keep the classification and retention policy on every row.

Failure modes

  • Promoting guesses. Confidence without evidence.
  • Contradictions. Two facts that cannot both be true. Mark as disputed and stop recalling both until resolved.
  • Silent staleness. The approver left the company. Re-confirm on use, and decay.

Choose it when

  • Agents operate in a stable environment with durable facts worth learning.
  • Avoid where the environment changes faster than facts can be corroborated.

Procedural memory

Not facts but methods: the validated sequence that works here, learned from repetition and checked before it is trusted.

Mechanism

When the same sequence of steps succeeds repeatedly for a goal class, it is a candidate procedure. A validator checks it before storage — are the steps still valid, do the tools still exist, does it still satisfy policy? — because a stored procedure is executed, not merely read, which makes it far more dangerous than a stored fact.

At the extreme this becomes a skill: a named, parameterised, reusable capability (see Voyager skills below).

In AgentVerse

  • app/memory/procedural.pythe store
  • app/memory/procedural_validator.pyvalidation before trust
  • app/skills_runtime/executor.py, models.pyprocedures as executable skills
  • app/agent/skill_selector.pyselecting the right procedure for a goal

Worked example

observed 9× for goal class "monthly vendor report"
  1 export CSV   2 recompute   3 diff   4 draft   5 route for approval
validate  all 5 tools exist · step 5 still requires approval · no policy change
store     procedure p-12, confidence 9100
next run  planner starts from p-12 instead of planning from scratch
          (2 fewer iterations, ~$0.55 saved per run)

At production scale

Procedural memory is where agent platforms start to resemble automation platforms — and where the governance question sharpens: a learned procedure is code nobody reviewed. Version procedures, require re-validation on tool or policy change, and never let a procedure carry its own approval exemption.

Failure modes

  • Fossilised process. The procedure encodes a workaround for a bug that was fixed. Expire and re-derive.
  • Tool drift. A step references a tool that no longer exists — caught by validation, not at runtime.
  • Policy bypass. A procedure that skips a gate. Safety patterns must be re-applied at execution, never inherited from the stored procedure.

Choose it when

  • Goals repeat with a stable method.
  • Avoid where the method should be re-derived each time because the environment shifts.

Reflexion memory

The failure ledger: one durable lesson per terminal failure, classified and recalled for similar future goals.

Mechanism

On terminal failure, extract a single actionable lesson and a failure class, then store with the goal fingerprint. Recall at plan time for matching fingerprints. Covered as a pattern in chapter 1; here it is a store with the same contract as every other tier — which is what gives it classification, decay, quarantine and feedback for free.

In AgentVerse

  • app/memory/reflexion.pylearn() → MemoryWriteRequest
  • app/state_runtime/reflexion_store.pydurable store
  • app/agent/reflexion_wirer.pythe wiring at failure time

Worked example

failure  "GSTR-1 filing rejected: invalid HSN code"
lesson   "validate HSN codes against the master list before filing"
class    validation_error       confidence 8000
recall   any future filing goal for this tenant
effect   plans now include a validation step; rejection rate 11% → 2%

At production scale

Watch the ratio of lessons to failures. Near 1:1 means you are storing noise; a healthy system deduplicates so that recurring failures reinforce one lesson's confidence rather than creating new rows. Feedback closes the loop: a lesson that is recalled and does not help should lose effectiveness score and eventually stop being recalled.

Failure modes

  • Superstition. A lesson from a coincidence. Require evidence and corroboration.
  • Negative spiral. Lessons that make the agent overly cautious. Track whether lessons improve success rate, not just whether they are recalled.
  • Poisoning. Induced failures to plant lessons — see memory safety below.

Choose it when

  • Failures are systematic and the same agent will meet them again.

Prospective memory

Remembering to do something later — the intention store, and the tier almost no agent framework has.

Mechanism

An agent notices during a run that something must happen in the future — follow up in a week, check whether the fix held, renew before expiry — and writes an intention with a trigger condition. Something outside the run must then fire it, which is why this tier only makes sense on a platform with schedules and triggers.

Conceptually it is the bridge between memory and time: without it, an agent's helpfulness ends when the goal ends.

In AgentVerse

  • app/memory/prospective.pythe store
  • app/triggers/store.py, nl_scheduler.pythe mechanism that can fire an intention
  • app/triggers/consumers/memory.pymemory-driven trigger consumption
  • app/scaling/tasks.pyfire_due_schedules

Rated 6 for implementation: the store exists and triggers exist, but the end-to-end "agent sets its own reminder and something reliably fires it" path is thinner than the other tiers.

Worked example

during a run  "certificate for api.acme.com expires 2026-11-04"
intention     { when: 2026-10-21, goal: "renew api.acme.com certificate",
                because: "expires in 14 days", evidence: step 3 output }
2026-10-21    trigger fires → new goal submitted → renewal handled

At production scale

Prospective memory needs the same governance as any scheduled action: an intention is a future write, so it must carry the authorisation context that will be needed when it fires, and it must expire if it becomes irrelevant. Un-expired intentions are how you get an agent doing something in six months that nobody remembers asking for.

Failure modes

  • Orphaned intentions. Fired after the context is gone. Re-validate on fire.
  • Duplicate intentions. Three runs each set the same reminder. Dedupe by condition.
  • Stale authorisation. The user who authorised it has left. Re-check permissions at fire time, never at write time only.

Choose it when

  • Work has natural follow-ups: renewals, verifications, deadlines.
  • Skip until you have reliable triggers — an intention nothing fires is a lie.

Knowledge-graph memory

Memory as a graph rather than a list — entities the agent has learned about and the relations between them, queryable by structure.

Mechanism

Facts learned during runs are written as nodes and edges instead of prose rows, so they can be traversed. "Who owns the payments service?" becomes a one-hop lookup rather than a similarity search over sentences. It shares the graph machinery with graph RAG (chapter 4) but its writes come from agent experience, not from ingested documents.

In AgentVerse

  • app/memory/knowledge_graph_memory.pythe tier
  • app/state_runtime/kg_query_engine.pyquery at runtime
  • app/knowledge_graph/store.pythe shared store

Worked example

learned over 30 runs
  (service:payments) —owned_by→ (team:fin-platform)
  (team:fin-platform) —on_call→ (rota:fin-oncall)
  (service:payments) —depends_on→ (vendor:razorpay)

"who do I page for a payments outage?"  → 2 hops, no embedding search

At production scale

Graph memory is the right shape for organisational knowledge — ownership, dependencies, escalation — which is exactly the knowledge that is never written down. Entity resolution is the whole game: without it you accumulate five nodes for one team. Budget a resolution pass and an alias table.

Failure modes

  • Fragmented entities. Resolution failure makes the graph useless.
  • Unsourced edges. Every edge should cite the run that produced it.
  • Access leakage. A graph makes the org chart trivially extractable — gate traversal by role.

Choose it when

  • The knowledge worth keeping is relational.
  • Skip if your durable facts are independent statements.

Tool reliability memory

The agent's own record of which tools actually work — success rate, latency, typical failure — used to prefer the reliable path and to avoid the flaky one.

Mechanism

Every tool call updates per-tool statistics scoped to tenant and connector: attempts, successes, p50/p95 latency, recent error classes. Planning and tool selection read it: two tools that can do the job are not equivalent if one fails 40% of the time. It also feeds the circuit breaker and the tool ranker.

In AgentVerse

  • app/memory/tool_reliability.pythe store
  • app/tool_runtime/tool_score.py, tool_ranker.pyranking by measured reliability
  • app/tool_runtime/tool_trust_store.pytrust state per tool
  • app/reliability/redis_circuit_breaker.pythe automatic response to a failing tool

Worked example

tenant acme, last 30 days
  vendor-api.get_invoices    attempts 412  success 62%  p95 8.1s
  vendor-csv.export          attempts 88   success 99%  p95 1.4s
planner  prefers vendor-csv.export for the same intent
breaker  vendor-api opened twice this week; ranked below CSV automatically

At production scale

This is one of the cheapest quality wins available: it requires no LLM, it is pure telemetry, and it directly prevents the most common agent failure — repeatedly calling a broken tool. Scope it per tenant, because a connector healthy for one customer is often broken for another (their credentials, their network, their quota).

Failure modes

  • Stale statistics. A tool fixed last week still ranked last. Use a decaying window.
  • Cold start. A new tool with no history ranked below a mediocre known one. Reserve exploration.
  • Global aggregation. Mixing tenants hides tenant-specific breakage.

Choose it when

  • You have more than a handful of tools, or any third-party connector.

Skill memory (Voyager-style)

The agent writes and keeps reusable capabilities, so its competence grows without retraining — and so does the review burden.

Mechanism

When a novel task is solved, generalise the solution into a named, parameterised skill and store it with its trigger hints. Later goals retrieve skills by matching those hints, which both narrows the tool list and supplies pre-compressed instructions. The important property: a skill is executable, so its lifecycle needs versioning and validation, not just storage.

In AgentVerse

  • app/memory/voyager_skills.pythe skill library
  • app/agent/patterns/voyager.pythe accumulating pattern
  • app/agent/skill_selector.pyselection by trigger-hint embedding; narrows allowed_tools
  • app/skills_runtime/executor.pyexecution
  • app/db/models/skill.pypersistence

Worked example

skill "reconcile_settlement(provider, month)"
  triggers  ["reconcile", "settlement", "payout", provider names]
  tools     [csv_export, compute, diff, file_amendment]
  steps     the validated 5-step procedure
selecting it drops the offered tool list 34 → 4 and the system prompt by 2.1k
tokens — skills usually reduce total context rather than adding to it

At production scale

Skills are the most promising and least mature idea in this chapter. The token-reduction argument is real and immediate; the growth-of-capability argument requires governance that mostly does not exist yet — nobody has a good answer for reviewing a thousand machine-written skills. Start with skills as a context-narrowing device and treat autonomous skill creation as opt-in.

Failure modes

  • Unreviewed executable memory. The core risk. Require validation and, for write-capable skills, human approval before first use.
  • Skill rot. Encodes an API that changed. Version and re-validate.
  • Over-triggering. Broad hints select the wrong skill. Keep hints specific.

Choose it when

  • You want context reduction from curated skills.
  • Avoid autonomous skill creation with write tools until you have a review process.

Department & organisational memory

Memory scoped to a team rather than an agent — so finance's agents share what finance knows, and engineering's do not see it.

Mechanism

A scope between tenant and agent. Department memory is written by any agent in the department and recalled by all of them, which makes shared context possible without making it global. It is the memory counterpart to the org model in chapter 22: departments, roles, and autonomy tiers.

In AgentVerse

  • app/memory/dept_memory.pydepartment-scoped store
  • app/org/context_engine.py, org_learning.pyorg-level context and learning
  • app/org/knowledge_access.pywho may read what

Worked example

  "quarter close freezes writes from the 28th"
  "the CFO wants variance explanations over 5%"

At production scale

Department scope is what most enterprises actually want, and it is usually missing — frameworks give you global or per-agent and nothing in between. The operational benefit is that a new agent in the department is useful immediately, because the context is not locked in another agent's history.

Failure modes

  • Scope creep. Department memories promoted to tenant-wide "because it is useful". That is how HR context ends up in an engineering prompt.
  • Orphaned scope. A department is reorganised; its memory has no owner.

Choose it when

  • Multiple agents serve one business function and share context.

RPA & visual memory

What the browser-driving agent has seen: screenshots, DOM snapshots, and the selector that worked last time on this page.

Mechanism

Automation against a UI is brittle because pages change. Visual memory keeps per-page artifacts — screenshot, DOM digest, the successful selector or coordinate — so the next run tries what worked before and only falls back to vision-based analysis when it fails. That turns most runs into cheap replays and reserves expensive perception for genuine change.

At production scale

Screenshots are the heaviest data in the platform and the most likely to contain personal data — someone's name, address and account number, rendered. Store them by reference with a short retention window, classify them as sensitive by default, and never put a raw screenshot into a prompt without a redaction pass.

Failure modes

  • Stale selectors. Detect and re-learn rather than retrying blindly.
  • Storage blowout. Screenshots per step per run. Sample, compress, expire.
  • PII in artifacts. Treat as restricted data with a real retention policy.

Choose it when

  • Agents drive UIs repeatedly against the same pages.
  • Not needed when an API exists — use it instead.

Memory scoping

Every memory row is addressed by a tuple — tenant, department, agent, goal, collection, source — and recall is filtered by that tuple before scoring, never after.

Mechanism

Scope is a hard boundary enforced at the store, plus data classification enforced at recall. The recall request carries allowed_data_classes, so a caller operating at internal level cannot receive a restricted memory even if it is the best semantic match. In the database, row-level security adds a second, independent enforcement layer.

The ordering matters: filter, then score. Scoring first and filtering after means the wrong rows were already read, ranked, and possibly logged.

recall for agent support-bot (tenant acme, dept support, class ≤ internal)

At production scale

A cross-tenant memory leak is the worst bug this system can have, because memory is recalled into prompts silently and the leak may only surface in a customer's output. Defence in depth is not optional: application-level scope filters, database RLS, and a test suite that asserts a tenant-B row can never appear in a tenant-A recall.

as_of on the recall request is a subtle but valuable feature: it makes recall reproducible for eval and for audit — you can ask what the agent would have remembered last Tuesday.

Failure modes

  • Filter-after-score. The classic leak shape.
  • Scope in the prompt. "Only use memories for tenant X" is not enforcement.
  • Global caches. A memory embedding cache without the tenant in the key.

Choose it when

  • Always, from the first memory row you write.

Scored recall

Similarity alone ranks memory badly. Combine semantic score with recency, measured outcome, and measured effectiveness — then cut to a token budget.

Mechanism

Four factors per candidate: semantic (does it match the query), recency (how fresh), outcome (did goals that used it succeed), effectiveness (was it marked helpful when used). The final score is a weighted combination, all integers on a 10,000 scale for reproducibility. Each hit also carries an applicability_reason and a provenance_status of verified / missing / disputed — so the prompt can carry why a memory was included and how much to trust it.

At production scale

Effectiveness scoring is the difference between memory that improves and memory that accumulates. It requires the feedback loop below to actually be wired — most systems store memories and never record whether they helped, which means bad memories rank forever on semantic similarity alone.

Cap memory's share of the context budget (5–10% is a reasonable start). Memory competes with evidence, and evidence should usually win.

Failure modes

  • Recency dominance. Yesterday's noise outranks last quarter's hard-won lesson.
  • No provenance signal. A disputed memory presented with the same authority as a verified one.
  • Budget crowding. Twelve memories, no room for documents.

Choose it when

  • You have more memories than fit in a prompt — which happens in the first week.

Memory feedback & effectiveness

After a goal ends, record for each recalled memory whether it was used, whether it helped, and whether it hurt — and let those counters change future ranking.

Mechanism

A feedback record per (memory, execution) pair: was_used, was_helpful, was_harmful, an outcome score, and a reason. Helpful and harmful are mutually exclusive by validator, which prevents the meaningless "both" state that makes aggregate statistics useless. Counters on the record update, effectiveness score moves, and memories that consistently fail to help sink below the recall floor and eventually expire.

At production scale

Attribution is the hard part: with six memories in a prompt and a successful goal, which one helped? Two workable approaches — ask the verifier to name the memories it relied on, and run occasional ablations where a memory is withheld to measure its contribution. Neither is perfect; both beat storing memories forever with no signal.

Failure modes

  • No feedback wired. The most common state, and it silently disables memory improvement.
  • Attribution error. Credit to the wrong memory. Prefer explicit citation.
  • Feedback loops. A memory that causes success only because it was recalled — measure against a control.

Choose it when

  • You intend memory to get better rather than merely bigger.

Memory safety: poisoning, quarantine, redaction

Memory is the only store that writes future prompts, so a poisoned row is a persistent compromise — quarantine on write, redact sensitive content, and never recall a suspicious row.

Mechanism

The attack: get the agent to store attacker-authored text as a lesson, and every future goal reads it. Defence in four layers:

  1. Provenance requirement. A memory needs evidence references from actual execution; text that arrived from a retrieved document or tool output cannot become a lesson on its own.
  2. Quarantine on write. Suspicious content — imperative instructions, tool names, credential-shaped strings — lands in lifecycle_state=quarantined and is never recalled.
  3. Redaction. Sensitive spans are removed before persistence, so a secret never becomes a memory in the first place.
  4. Recall-time treatment. Memory enters the prompt as untrusted data, clearly framed, never as system instruction.

At production scale

Treat memory writes with the same suspicion as user input, because they frequently are user input one hop removed. The specific rule that prevents most of this: a memory may only be created from the agent's own execution evidence, never from retrieved content alone.

Alarm on quarantine rate. A rise means someone is probing, and it is one of the few high-signal security metrics an agent platform has.

Failure modes

  • Summarisation laundering. The injection survives because it was paraphrased. Scan the summary too, not just the source.
  • Quarantine without review. Rows pile up unexamined; the attack goes unnoticed.
  • Redaction after embedding. The secret is already in the vector. Redact first.

Choose it when

  • Always, before you enable any cross-goal memory.

Retention, decay, and deletion

Memory that never expires is a compliance liability and a quality problem — every row carries a retention policy, a lifecycle state, and a real deletion path.

Mechanism

Five lifecycle states — active, quarantined, disputed, expired, deleted — plus expires_at and retention_policy_id on every record. Consolidation folds many similar memories into one and expires the originals; decay lowers confidence with age unless reinforced; deletion must be real, cascade to embeddings and caches, and be provable.

The state that matters most legally is deleted as distinct from expired: expiry is housekeeping, deletion is an obligation, and the two need different guarantees.

At production scale

Deletion is much harder than it looks, because a memory's content has usually been copied into embeddings, caches, artifacts, logs and possibly a summary of a summary. Design the fan-out on day one; retrofitting a deletion cascade across seven stores is a quarter of work.

Legal hold is the correct exception mechanism — it must be able to suspend deletion for specific subjects or matters, and its own application must be audited.

Failure modes

  • Orphaned embeddings. The row is gone; the vector still retrieves.
  • Cached content. A deleted memory served from a semantic cache.
  • Infinite retention by default. Every row keeps forever because nobody set a policy.
  • Deletion during hold. Destroying evidence under legal hold is worse than keeping it.

Choose it when

  • Always. Any system storing memory about people needs this before it stores the first row.

What is missing here

  • Contradiction detection at write time. The disputed state exists, but nothing systematically detects that a new memory contradicts an existing one; today it surfaces when an agent behaves oddly.
  • Memory attribution. Feedback exists, but attributing a goal's success to a specific recalled memory is still approximate. Counterfactual ablation would give a real signal.
  • Cross-tenant learning with privacy. Every tenant learns alone. Federated or differentially-private aggregation of lessons across tenants is the obvious value left on the table, and the obvious risk.
  • Prospective memory end-to-end. The store exists; the reliable "agent sets a reminder, platform fires it, authorisation re-checked" path is thin.
  • Skill review workflow. Machine-written skills accumulate with no review queue, no diff view, and no approval record.
