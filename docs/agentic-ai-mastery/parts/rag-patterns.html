Orientation

Retrieval-augmented generation is one idea — put the right text in the prompt — with fifteen architectures built on top because "the right text" is hard. Each named pattern is an answer to a specific way that naive retrieval fails: the query does not look like the answer (HyDE), one query is not enough (fusion, multi-query), the retrieved chunks are wrong (corrective), the model does not know it needs more (FLARE), the answer spans documents (multi-hop, graph), the corpus is too big to embed usefully (RAPTOR), or the model should decide for itself (agentic).

AgentVerse treats this as a typed vocabulary rather than a pile of scripts. Eighteen strategies live in one enum; every execution produces the same result shape with per-leg traces and citations; and a gateway decides which strategies are actually runnable right now given the tenant's configured capabilities, falling back rather than failing.

The patterns

The retrieval contract

Before any pattern, agree on a shape: a request names a strategy and collections, a result carries chunks, per-leg traces and citations, and unknown or unavailable strategies raise typed errors rather than silently degrading.

Mechanism

One enum (RAGStrategy, 18 members) is the public vocabulary. Historical names are resolved through an alias map — fusion_rag → fusion, graph_rag → graph — so callers, stored agent configs and templates written a year ago keep working without the enum growing duplicates. Two error types separate two very different situations: UnknownRAGStrategyError (caller typo — a bug) and UnavailableRAGStrategyError (known strategy, missing capability — an operational state).

Every execution returns the same canonical result: chunks, one RAGRetrievalLeg per retrieval operation, and RAGCitation records with chunk id, score and source.

In AgentVerse

  • app/rag/contracts.pyRAGStrategy, RAG_STRATEGY_ALIASES, resolve_rag_strategy(), RAGExecutionRequest/Result, RAGStrategyTrace, RAGCitation, RAGRetrievalLeg
  • app/rag/catalogue.pyRAG_CAPABILITY_CATALOGUE — what each strategy needs
  • app/rag/gateway.pyRetrievalGateway.execute(), execute_core_strategy()
  • app/rag_platform/retriever.pyRAGRetriever — synthesis layer over the gateway

Ten of the eighteen are DIRECT_CORE_RAG_STRATEGIES, executed by the gateway core; the rest are agentic patterns with their own runtimes.

Worked example

request  {query:"why did payouts fail on the 14th?",
          strategy:"corrective_rag", collections:["runbooks","incidents"], k:8}
resolve  alias corrective_rag → RAGStrategy.CORRECTIVE
authz    both collections belong to tenant acme        → ok
ready?   needs grader LLM + fallback search            → ok
result   {chunks:[…8], legs:[{strategy:corrective, query:…, ms:180, n:24},
                             {strategy:hybrid,     query:…, ms:95,  n:8}],
          citations:[{chunk_id:…, score:0.81, source:"runbooks/payouts.md"}]}

At production scale

The contract is what makes retrieval improvable. Because every strategy emits the same legs, you can compare corrective against hybrid on the same queries, attribute cost per strategy, and alarm on "strategy X now returns zero candidates" without instrumenting each implementation separately.

It is also what keeps an 18-strategy system maintainable at all. Without a shared result shape, each pattern grows its own half-compatible dictionary and the eval harness becomes untestable.

Failure modes

  • Alias sprawl. Every rename adds an alias forever. Keep the map small and deprecate loudly.
  • Leaky results. A pattern returning its own bespoke shape breaks tracing. Normalise at the gateway, as _normalize_engine_results() does.
  • Silent degradation. Falling back without recording it. The delegation must appear in the trace, or your eval numbers describe a strategy that never ran.

Choose it when

  • You have more than two retrieval strategies, or intend to.
  • Retrieval quality is something you plan to measure.

Basic RAG

Embed the query, take the top-k nearest chunks, put them in the prompt. Everything else in this chapter is a repair to a specific failure of this baseline — which is why you should always keep it as the control in your evals.

Mechanism

Index time: split documents into chunks, embed each, store the vector with metadata. Query time: embed the query with the same model, cosine-search for top-k, sort by score, format into the prompt with source labels.

Three parameters do most of the work: chunk size, k, and whether you include neighbouring chunks. Tuning those beats switching strategies more often than anyone admits.

  • app/rag/engine.pyRetrievalResult, strategy execution errors
  • app/rag/indexing.pyRAGIndexingPipeline, RAGIndexRecord
  • app/agent/nodes/rag_mixin.pythe retrieval node in the agent graph

Worked example

query   "what is our refund window?"
embed   1536-d vector
search  top 5 by cosine over tenant acme's "policies" collection
 0.89  policies/returns.md#3   "Refunds accepted within 30 days…"
 0.71  policies/returns.md#4   "Exceptions for damaged goods…"
 0.55  policies/shipping.md#2  ← borderline, still included at k=5
prompt  chunks + question, answer must cite chunk ids

At production scale

Naive RAG is right for a surprising share of production traffic — FAQ, policy lookup, "what does the doc say" — and it is the cheapest thing in the chapter. The engineering discipline is to measure before upgrading: run the fancy strategy and the baseline on the same 200 queries and look at the delta. In many corpora it is under two points, and the naive path is a tenth of the cost.

Failure modes

  • Vocabulary mismatch. User says "reimbursement", corpus says "refund" — hybrid fixes this.
  • Chunk boundary loss. The answer straddles two chunks; neither scores well. Parent-child or sentence-window retrieval fixes it.
  • Top-k tyranny. Fixed k returns junk on narrow corpora and truncates on broad ones. Use a score floor as well as a count.
  • Stale index. The document changed; the embedding did not.

Choose it when

  • Questions map to passages, the corpus is clean, and latency matters.
  • Always as the eval baseline.
  • Not for relationship questions, aggregation, or anything spanning documents.

Hybrid RAG

Run semantic and lexical search together and merge — because embeddings are good at meaning and terrible at exact tokens like INV-2024-8891, while keyword search is the reverse.

Mechanism

Three retrievers, one merge. Vector similarity handles paraphrase; BM25 handles term importance and rare exact terms; trigram similarity handles typos and partial identifiers. Scores from different scales cannot simply be added, so the merge either normalises per-retriever or — better — uses rank fusion, which ignores absolute scores altogether.

The store implements this twice on purpose: an in-memory fast path that is always available, and a Postgres path that pushes the work into the database where the data lives.

In AgentVerse

  • app/rag/store.pyhybrid_search() (in-memory fast path) and hybrid_search_db() — cosine + trigram + BM25 → HybridSearchResult
  • app/rag/bm25.pyBM25Retriever
  • app/rag/engine.pyhybrid_search / rerank_results wiring
  • app/rag/cross_encoder.pyCrossEncoderReranker on top of the merge

Worked example

query "INV-2024-8891 disputed by Northwind"

vector top3   0.62 invoices/policy.md      (semantic: disputes)
              0.58 invoices/northwind.md
              0.55 support/disputes.md
bm25 top3     8.9  invoices/INV-2024-8891.pdf   ← exact ID, vector missed it
              4.1  invoices/northwind.md
trigram       0.91 invoices/INV-2024-8891.pdf

fused         1 INV-2024-8891.pdf   2 northwind.md   3 policy.md

At production scale

Hybrid is the correct default for enterprise corpora, and the reason is identifiers: invoice numbers, ticket keys, SKUs, error codes, employee IDs. Pure vector search fails these consistently and the failure is invisible in aggregate metrics because it affects a minority of queries — the minority that matters most to the user typing an exact ID.

Push the merge into Postgres when the corpus is large. Pulling 500 candidates per retriever into Python to merge them costs more in serialisation than the query did.

Failure modes

  • Score incomparability. Adding a cosine 0.6 to a BM25 8.9 is meaningless. Use rank fusion or per-retriever normalisation.
  • Lexical dominance. BM25 overwhelms on keyword-stuffed documents. Cap each retriever's contribution.
  • Double counting. The same chunk from two retrievers appearing twice. Deduplicate on chunk id before ranking.

Choose it when

  • Almost always. This should be your default rather than pure vector search.
  • Skip only when the corpus has no identifiers, codes, or proper nouns — which is rare.

Fusion RAG

Generate several rewrites of the question, retrieve for each, and combine the ranked lists with reciprocal rank fusion — coverage insurance against a single unlucky phrasing.

Mechanism

An LLM produces n query variants (typically 3–5) emphasising different aspects. Each is retrieved independently. Results merge by RRF: each document scores Σ 1/(k + rank_i) with k≈60, so a document ranked 2nd in three lists beats one ranked 1st in a single list. RRF needs no score calibration, which is exactly why it is the standard merge for heterogeneous retrievers.

Worked example

original  "why are payouts delayed?"
variants  1 "payout settlement delay causes"
          2 "bank transfer processing time SLA"
          3 "failed payout retry behaviour"

doc                     r1  r2  r3   RRF
payouts-runbook.md       1   4   2   0.0480   ← wins on consistency
bank-sla.md              -   1   -   0.0164
retry-policy.md          5   -   1   0.0325

At production scale

Cost is one LLM call plus n retrievals — cheap if retrieval is cheap, expensive if each retrieval involves a reranker. Run the n retrievals concurrently; done serially, fusion turns a 200ms retrieval into a second.

The measurable benefit is recall on ambiguous questions. If your eval shows the answer was in the corpus but not in the context, fusion is the first thing to try — before any exotic pattern.

Failure modes

  • Variant collapse. Three near-identical rewrites. Require lexical diversity or different aspects.
  • Drifted variants. A rewrite that answers a different question, poisoning the pool. Keep the original query as one of the legs, always.
  • Context overflow. More coverage means more chunks. Fusion must be followed by a rerank and a budget cut, not fed straight to the model.

Choose it when

  • Queries are ambiguous or use vocabulary the corpus does not.
  • Recall matters more than latency.
  • Avoid for exact-lookup queries — you are paying to rephrase a question that was already precise.

HyDE — hypothetical document embeddings

Ask the model to write the answer it expects, embed that, and search with it — because an answer-shaped vector matches answer-shaped chunks better than a question-shaped one does.

Mechanism

Questions and passages occupy different regions of embedding space: "what is our refund window?" is lexically and structurally unlike "Refunds are accepted within 30 days of delivery." HyDE closes the gap by generating a plausible passage first — factual accuracy of the hypothetical does not matter, only that it looks like the target text — then retrieving with its embedding.

In AgentVerse

  • RAGStrategy.HYDE in app/rag/contracts.pya direct core strategy
  • app/rag/gateway.pyexecute_core_strategy() dispatch
  • app/rag/agentic/llm_query_transformer.pythe generation step

Worked example

question     "how do I rotate the signing key?"
hypothetical "To rotate the signing key, generate a new keypair with
              openssl, upload the public half to the JWKS endpoint, wait
              for the cache TTL to expire, then retire the old key."
embed        the hypothetical, not the question
retrieved    runbooks/key-rotation.md#2  0.91   (question alone: 0.63)

At production scale

HyDE adds one small-model call per query — a real latency cost on an interactive path, negligible on a background goal. Use a cheap fast model for the hypothetical; quality of that text barely matters. Cache hypotheticals by normalised query, since repeated questions are common.

It helps most on corpora of declarative prose (docs, policies, wikis) and helps least on conversational or transactional corpora where passages already look like questions.

Failure modes

  • Confident fiction. The hypothetical invents terminology absent from the corpus and drags retrieval away. Retrieve with both the hypothetical and the original.
  • Latency on chat. An extra call in front of every message is felt.
  • Domain drift. On specialised corpora the model's guess is wrong-shaped; measure before adopting.

Choose it when

  • Questions are short and the corpus is long-form prose.
  • You see high recall failure with low query/passage similarity.
  • Skip on latency-critical chat, or where hybrid already solves it.

Corrective RAG (CRAG)

Grade the retrieved chunks before generating: if they are good, proceed; if ambiguous, refine the query and retry; if bad, go somewhere else entirely — the pattern that stops the model answering from irrelevant context.

Mechanism

A lightweight grader scores each retrieved chunk for relevance to the question, producing one of three verdicts:

  • Correct — enough good chunks; generate.
  • Ambiguous — some signal; decompose or rewrite the query and retrieve again, then generate from the union.
  • Incorrect — nothing relevant; discard the context entirely and fall back to another source (web, a different collection) or answer "not found".

The critical behaviour is the third branch. Most RAG failures are not retrieval failures — they are generation failures on top of bad retrieval that nobody checked.

  • app/rag/agentic/fallback_chain.pyFallbackChain — ordered alternatives
  • app/agent/graph.pyrag_remediate node — the agent-level version of the same idea

The assembler adds corrective_rag for analytical goals at high or critical risk.

Worked example

query    "what is the penalty for late GSTR-1 filing?"
retrieve 5 chunks from "tax-policies"
grade    0.2 0.1 0.3 0.1 0.2   → INCORRECT (all below 0.5)
action   discard context, fall back to the statutory-text collection
retry    3 chunks scoring 0.88 0.81 0.77 → CORRECT
answer   grounded, cites the statute, not the internal summary
without CRAG: a confident answer from an outdated internal summary

At production scale

CRAG is the highest-value quality pattern in this chapter for regulated work, because "answered confidently from the wrong document" is the failure mode that produces incidents. The grader can be a small model or a cross-encoder — do not use the generation model, it is expensive and biased toward finding its own context useful.

Track the three verdict rates as a metric. A rising INCORRECT rate is an ingestion problem, not a retrieval problem, and it is often the first sign that a connector stopped syncing.

Failure modes

  • Grader miscalibration. Too strict throws away good context; too lenient makes the pattern a no-op. Calibrate the threshold on labelled pairs.
  • Fallback loops. Every source graded incorrect, forever. Bound the chain and end at an honest "I could not find this".
  • Cost doubling. Grading every chunk on every query. Grade the top-k only.

Choose it when

  • Wrong answers are expensive and the corpus has gaps.
  • You have multiple sources to fall back to.
  • Skip on a small curated corpus where retrieval is reliably good.

Self-RAG

Let the model decide whether to retrieve at all, then critique its own output for support and usefulness — retrieval on demand rather than retrieval by default.

Mechanism

Reflection tokens at three decision points: retrieve? (is external knowledge needed for this span), relevant? (is what came back useful), supported? (does the generated claim follow from the evidence). Unsupported spans trigger regeneration or citation removal.

The under-appreciated win is the first decision. A large share of turns — greetings, arithmetic, formatting, reasoning over what is already in context — do not need retrieval, and skipping it saves both latency and the risk of dragging in irrelevant context.

  • app/rag/agentic/patterns/self_rag.pythe pattern
  • app/rag/agentic/retrieval_policy.pywhen retrieval is warranted
  • app/agent/grounding.pythe support check, deterministic then LLM
  • app/intelligence/nli_checker.pyentailment checking for supported/not-supported

Worked example

turn 1  "hi, can you help with invoices?"      retrieve? NO   (0 tokens spent)
turn 2  "what's our late fee policy?"          retrieve? YES  → 4 chunks
        relevant? 3 of 4                       → drop one
        draft: "Late fees are 1.5% monthly and waived for enterprise plans."
        supported? clause 1 YES  clause 2 NO   → regenerate without clause 2
final   "Late fees are 1.5% monthly. I found no policy on enterprise waivers."

At production scale

In a chat product, retrieve-on-demand typically removes 30–50% of retrieval calls, which shows up directly in p50 latency and embedding spend. The support check is the more important half for safety: it is where "the model added a plausible clause nobody wrote" gets caught.

Implement the support check deterministically first (does the entity, number, or quoted string appear in the evidence?) and only escalate to an NLI model for the spans that fail — an order of magnitude cheaper than checking everything with a model.

Failure modes

  • Overconfident skip. The model decides it knows, and it does not. Bias the policy toward retrieving on any factual claim about tenant data.
  • Self-assessment bias. The generator judging its own support is lenient. Use a separate checker.
  • Latency spikes. Reflection adds turns. Bound the number of regenerations.

Choose it when

  • Conversational workloads where many turns need no retrieval.
  • Grounding must be enforced per claim, not per answer.
  • Skip in pipelines where every request is by definition a knowledge request.

Speculative RAG

A small fast model drafts several answers from different chunk subsets; a large model only verifies and picks — moving most of the token volume to the cheap model.

Mechanism

Partition the retrieved set into diverse subsets. A small model drafts one answer per subset, in parallel, each with its own rationale. The large model then reads the drafts plus rationales — far fewer tokens than reading all chunks — and selects or merges. Borrowed from speculative decoding: generate cheaply, verify expensively, keep the verifier's quality.

In AgentVerse

  • app/rag/agentic/patterns/speculative.pythe pattern
  • app/ai_router/model_orchestrator.pydrafter/verifier model pair selection
  • app/providers/base.pyprovider-neutral completion so drafter and verifier can be different vendors

Worked example

retrieved  12 chunks → 3 subsets of 4 (diverse by source)
drafts     small model × 3, parallel, ~600 tokens each
verify     large model reads 3 drafts + rationales (1.8k tokens)
           vs reading all 12 chunks (9k tokens)
cost       ~55% lower, quality within noise of the direct large-model answer
latency    drafting is parallel → wall-clock roughly unchanged

At production scale

Worth it when context is large and the verifier is expensive — long-document QA over 20+ chunks. Not worth the complexity below ~8 chunks, where the large model can just read everything. Its real constraint is operational: you now depend on two models being healthy, which the router and circuit breaker must handle (chapter 16).

Failure modes

  • Weak drafter. All drafts wrong; the verifier picks the least wrong. Floor the drafter quality.
  • Subset partitioning loses the answer. The critical chunk lands alone in a weak subset. Overlap subsets slightly.
  • Verifier laziness. Picks the longest draft. Force it to cite which chunks support its choice.

Choose it when

  • Long context, expensive verifier, cost matters more than architectural simplicity.
  • Avoid for short-context questions or when a single model is already fast enough.

FLARE — forward-looking active retrieval

Retrieve during generation: when the next sentence the model is about to write has low token confidence, pause, retrieve for that specific claim, and continue.

Mechanism

Generate a provisional next sentence. Inspect confidence — token log-probs where available, otherwise a proxy such as hedging language or an explicit self-assessment. If confidence is below threshold, form a query from that sentence (masking the uncertain spans), retrieve, and regenerate the sentence with the new evidence. Repeat until the answer is complete.

This is the only pattern here that couples retrieval to generation position rather than to the question, which is why it is the right tool for long documents where different paragraphs need different sources.

In AgentVerse

  • app/rag/agentic/patterns/flare.pythe pattern
  • app/rag/agentic/search_directive_parser.pyturns an uncertain span into a search directive
  • app/rag/agentic/citation_threader.pykeeps citations attached to the spans they support

The assembler adds flare when the goal requires web knowledge or is time-sensitive — the case where the model's parametric knowledge is most likely to be stale mid-answer.

Worked example

writing a vendor report…
para 1  company background            confidence high  → no retrieval
para 2  "Their Series C was led by…"  confidence LOW   → retrieve
        query "Northwind Series C lead investor round size"
        → regenerate: "Their $40M Series C (Mar 2024) was led by Acme Ventures."
para 3  contract terms                confidence high  → no retrieval
total   3 retrievals for a 9-paragraph report, each targeted

At production scale

FLARE shines on long-form generation — reports, briefs, documentation — and is wasteful on short answers, where one upfront retrieval covers everything. The practical blocker is confidence signal quality: many hosted APIs do not expose log-probs, and the textual proxies are noticeably worse. Budget the number of mid-generation retrievals per document, or a hedging model will retrieve on every sentence.

Failure modes

  • No confidence signal. Without log-probs the trigger is unreliable — measure before relying on it.
  • Retrieval thrash. Every sentence triggers. Cap retrievals per generation.
  • Incoherence. Regenerated sentences contradict earlier ones. Re-read the prefix when regenerating.

Choose it when

  • Long outputs whose paragraphs need different evidence.
  • Confidence signal is available and calibrated.
  • Skip for short answers and interactive chat.

RAPTOR — hierarchical summary retrieval

Cluster chunks, summarise each cluster, cluster the summaries, and repeat — then retrieve from every level, so a question can match a detail or a theme.

Mechanism

At index time: embed leaf chunks, cluster them, generate a summary per cluster, embed the summaries as new nodes, repeat until one root remains. At query time, search across all levels at once. A specific question matches a leaf; "what are the main themes across these 400 documents" matches a mid-level summary that no single chunk could answer.

In AgentVerse

  • app/rag/agentic/patterns/raptor.pythe pattern
  • app/rag/indexing.pywhere hierarchical records are built and stored
  • app/knowledge_graph/community_detection.pythe graph analogue: communities as a summary layer

The assembler adds raptor for analytical goals of complex or expert complexity.

Worked example

L0  1,240 chunks from 3 years of incident reports
L1  86 clusters → "database connection exhaustion incidents (14)" …
L2  9 clusters  → "infrastructure capacity failures" …
L3  1 root      → "reliability history 2023-2026"

"what recurring failure modes should the roadmap address?"
  → matches L2 summaries, not any single incident
  → answer cites the summaries and drills into 3 exemplar L0 chunks

At production scale

All the cost is at index time — one LLM call per cluster, at every level. On a 100k-chunk corpus that is a real bill, and it must be re-run incrementally as documents change or the tree goes stale. Budget it as a batch job, and only build RAPTOR for collections that actually receive thematic questions; for lookup-style collections it is wasted money.

Failure modes

  • Summary drift. Summaries of summaries lose the specifics that make an answer useful. Always return leaf evidence alongside a summary hit.
  • Stale tree. New documents are not in the hierarchy. Rebuild affected branches on ingest.
  • Cluster garbage. Poor clustering yields incoherent summaries. Validate cluster cohesion before summarising.

Choose it when

  • Large corpora, thematic or comparative questions, stable content.
  • Avoid on fast-changing corpora or where every question is a lookup.

Agentic RAG

Give the agent retrieval as a tool rather than a pipeline stage: it decides what to search for, reads the results, and searches again until it can answer.

Mechanism

Retrieval becomes one or more tools the executor can call — search a collection, list collections, fetch a document by id, follow a citation. The agent's loop supplies the control flow, so decomposition, reformulation and stopping are decisions made with the evidence in hand rather than guessed in advance.

This subsumes several patterns: multi-hop happens naturally, corrective happens when the agent judges results poor, fusion happens when it issues several queries. The trade is predictability — each goal's retrieval cost is now variable.

  • app/rag/agentic/citation_threader.pycarries citations through multiple hops

Worked example

goal "did we ever ship the fix for the duplicate-charge bug?"
 search incidents "duplicate charge"          → INC-4471 (Mar)
 search jira      "INC-4471"                  → PROJ-1180 "fix duplicate charge"
 search github    "PROJ-1180"                 → PR #3312, merged, but reverted
 search github    "revert 3312"               → revert PR #3340, no re-land
 gap check        "no evidence of a re-landed fix"
 answer  "No. PR #3312 was merged 12 Mar and reverted 14 Mar; no
          subsequent fix references PROJ-1180." + 4 citations

At production scale

Agentic RAG is how you answer questions that span systems, and it is the pattern most likely to blow a latency budget: each hop is a retrieval plus a model call. Cap hops explicitly (3–5), run independent searches concurrently, and cache aggressively — agents re-issue similar queries constantly within one goal.

Give the agent a source inventory rather than raw access. Knowing which collections exist, what they contain and how fresh they are turns blind flailing into targeted search, and it is the single biggest quality lever for this pattern.

Failure modes

  • Search spirals. Endless reformulation. Hop caps and stall detection.
  • Context accumulation. Every hop's results retained until the window overflows. Summarise between hops.
  • Lost citations. After four hops nobody can say where a fact came from. Thread citations through every hop.
  • Cost variance. One goal costs $0.05, another $4. Budget per goal, not per query.

Choose it when

  • Questions span sources and the path is unknown in advance.
  • Thoroughness beats latency.
  • Avoid on interactive chat with a tight latency budget.

Multi-hop retrieval

Answer questions whose evidence is chained: retrieve, extract the bridge entity, use it to retrieve again — the query at hop two cannot be written before hop one returns.

Mechanism

Detect a multi-hop question (it references an entity by description rather than name), retrieve for the first hop, extract the bridging entity from the results, construct the second query, and repeat. Each hop's evidence is kept so the final answer can cite the whole chain.

Two implementations: iterative retrieval in the RAG layer, and graph traversal when the entities and relations are already extracted into a knowledge graph — the second is far cheaper when it applies.

In AgentVerse

  • RAGStrategy.MULTI_HOP in app/rag/contracts.pycore strategy
  • app/knowledge_graph/multi_hop.pygraph-based multi-hop reasoner
  • app/rag/agentic/query_reformulator.pybuilding hop n+1's query
  • app/rag/agentic/citation_threader.pychain-of-evidence citations

Worked example

question "what SLA applies to the vendor who runs our payment gateway?"
hop 1  retrieve "payment gateway vendor"  → "Razorpay (contract C-2291)"
hop 2  retrieve "C-2291 SLA"              → "99.95% uptime, 4h P1 response"
answer with both citations; a single-hop search for "payment gateway SLA"
returns the internal SLA of the wrong system

At production scale

Latency is the constraint — hops are inherently serial. Two hops is usually the sweet spot; beyond three, error compounds and users have given up waiting. If your workload is dominated by multi-hop questions, build the knowledge graph and traverse it instead: a two-hop graph query is milliseconds against a second or more of iterative retrieval.

Failure modes

  • Wrong bridge entity. Hop 1 extracts the wrong name; everything after is confidently wrong. Verify the entity before hopping.
  • Hop explosion. Ambiguous entities fan out. Cap the branching factor.
  • Lost provenance. The final answer cites only hop 2. Cite the chain.

Choose it when

  • Questions reference entities indirectly.
  • Evidence genuinely lives in different documents.
  • Avoid when a graph already encodes the relationship — traverse it.

Graph-augmented RAG

When the question is about relationships rather than passages, retrieve a subgraph instead of chunks — vectors are good at similarity and structurally blind to "who reports to whom".

Mechanism

At ingest, extract entities and relations into a tenant-scoped graph. At query time, resolve the question's entities to nodes, traverse to a bounded depth, and serialise the resulting subgraph — plus the source chunks that produced each edge — into the prompt. Community detection over the graph gives the same thematic layer RAPTOR builds over text.

In AgentVerse

  • app/knowledge_graph/extractor.pyEntityExtractor — entities and relations from chunks
  • app/knowledge_graph/models.pyGraphNode, GraphEdge
  • app/knowledge_graph/store.pyKnowledgeGraphStore (tenant-scoped)
  • app/knowledge_graph/community_detection.pyclusters as summary nodes
  • app/knowledge_graph/access_control.pyGraphAccessControl — role-gated traversal
  • app/knowledge_graph/ingestion_hook.pyKGIngestionHook — graph built as a side effect of ingestion
  • app/state_runtime/kg_query_engine.pyquery engine used at runtime

Worked example

question "which customers are affected if the Frankfurt region goes down?"

vector search  returns the DR runbook. Useless — it does not list customers.
graph traversal
  (region:Frankfurt) ←hosted_in— (cluster:eu-1) ←runs— (service:checkout)
                                        ↑used_by
                          (tenant:Northwind), (tenant:Contoso), … 23 more
answer  the 23 tenants, with the edge that connects each, each edge citing
        the config document it was extracted from

At production scale

Graph RAG has a real cost: extraction is an LLM call per chunk at ingest, and graph quality is entirely determined by entity resolution — "Acme Corp", "ACME", and "Acme Corporation" must become one node or the graph is decoration. Budget for a resolution pass and expect to maintain an alias table.

Access control is not optional. A graph is a very efficient way to leak an org chart, so traversal must be filtered by role and tenant at the store, not after the results come back.

Failure modes

  • Entity fragmentation. Five nodes for one company. Resolution and aliasing.
  • Hallucinated relations. The extractor invents an edge. Require every edge to cite its source chunk, and score edge confidence.
  • Traversal explosion. Depth 4 from a hub node returns half the graph. Bound depth and degree.
  • Staleness. Relations that ended. Version edges with validity intervals where the domain needs it.

Choose it when

  • Questions are about connections, impact, lineage, or org structure.
  • Entities are well defined and resolvable.
  • Avoid for prose-comprehension questions — the graph loses the nuance the text carries.

Federated retrieval

Search across many collections — or many stores — at once, then merge, with per-source authorisation applied before anything is combined.

Mechanism

Fan out the query to every authorised source concurrently, apply per-source limits, then merge with rank fusion because the sources' scores are not comparable. Two properties matter more than the merge algorithm: authorisation is evaluated per source before dispatch, and a slow or failing source degrades the result rather than failing the query.

In AgentVerse

  • app/knowledge/federated_search.pythe fan-out and merge
  • app/api/knowledge.pyfederated_search_endpoint()
  • app/rag/gateway.pySQLCollectionAuthorizer — collection-level authorisation

Worked example

query across 6 collections for user u-77 (role: analyst)
  policies      authorised   142ms   8 hits
  incidents     authorised    98ms   5 hits
  hr-records    DENIED (role) —      excluded before dispatch
  contracts     authorised   2.1s    TIMEOUT → degraded, flagged in response
  wiki          authorised   115ms   6 hits
  code          authorised   210ms   3 hits
merged by RRF; response says which sources were skipped and why

At production scale

Federation is where a partial result is better than an error, but only if the user is told. Return the source list with per-source status; an answer silently missing the contracts collection is worse than no answer, because nobody knows to check.

Per-source timeouts must be shorter than the overall budget, and repeated timeouts should trip a breaker so a sick source stops being queried at all.

Failure modes

  • Authorisation after merge. Filtering results the user should never have seen is a leak waiting for a bug. Filter before dispatch.
  • Slowest-source latency. One slow store sets the response time. Timeout and degrade.
  • Silent gaps. Report source status in the payload.

Choose it when

  • Knowledge is genuinely spread across collections or stores with different permissions.
  • Unnecessary when one collection holds the answer — you are paying fan-out cost for nothing.

Web-augmented retrieval

Reach outside the corpus for knowledge that is newer than it — and treat everything that comes back as hostile input.

Mechanism

A search tool queries the open web (or a self-hosted meta-search), pages are fetched, stripped to text, and injected as clearly-labelled untrusted context. Three controls are mandatory: SSRF protection on every fetch, an injection scan on the retrieved text, and provenance so the answer's citations point at URLs the user can check.

In AgentVerse

  • app/rag/agentic/patterns/web_augmented.pythe pattern
  • app/tools/web_search.pythe search tool
  • app/net/ssrf_guard.pyblocks internal addresses and redirect tricks
  • app/agent/exfil_guard.pycheck_tool_output_for_injection, wrap_tool_output_as_untrusted
  • app/ingestion/connectors/web_crawl_connector.pythe ingest-time equivalent

The assembler switches on web_auto_activate when the goal requires web knowledge or is real-time sensitive.

Worked example

goal   "is the CVE in our nginx version exploitable?"
kb     nginx 1.24.0 in the infra collection
web    search "CVE-2025-… nginx 1.24 exploitability"
fetch  3 pages   → ssrf guard: all public, no redirects to 169.254.x
scan   page 2 contains "SYSTEM: ignore prior instructions" → quarantined
answer from pages 1 and 3, cited by URL, marked as external evidence

At production scale

The web is the largest prompt-injection surface an agent has. Treat every fetched page as attacker content: never let it name a tool, never let it be summarised into memory without a scan, and never let it override tenant policy. Rate-limit and cache aggressively; search APIs are metered and agents are enthusiastic.

Enterprise deployments frequently need a self-hosted meta-search rather than a public API, for both egress control and data-residency reasons.

Failure modes

  • Indirect prompt injection. The main event. Scan, wrap, and never trust.
  • SSRF. A URL pointing at the metadata service. Guard every fetch, including redirects.
  • Source quality. A content farm outranks the vendor's docs. Prefer allowlisted domains for factual claims.
  • Cost drift. Metered search on every goal. Gate on the classifier's requires_web.

Choose it when

  • The answer is newer than your corpus, or genuinely outside it.
  • You have SSRF and injection controls already in place.
  • Avoid in regulated flows unless the domain allowlist is explicit and approved.

Memory-augmented RAG

Retrieve from what this tenant's agents have learned — past runs, lessons, preferences, tool reliability — not just from documents.

Mechanism

Memory tiers are retrievable stores with the same interface as a document collection, but different trust and lifecycle rules. At context assembly, memory recall runs alongside document retrieval and the results compete for the same token budget, with memory usually capped as a fraction of it.

The difference from document RAG is provenance: a document is evidence, a memory is a claim the system made about itself. It must be scoped, decayed, and treated as lower-trust than a source document.

In AgentVerse

  • app/memory/repository.pyrecall ranking, poison quarantine
  • app/memory/long_term.py, episodic.py, procedural.pythe tiers
  • app/memory/knowledge_graph_memory.pymemory as graph
  • app/memory/salience.pywhat deserves to be remembered
  • app/context/context_pipeline.pywhere memory and documents are merged under one budget

Chapter 3 covers the tiers in full; here the point is that memory is a retrieval source.

Worked example

goal "prepare the monthly vendor report"
documents  6 chunks: this month's invoices, the template
memory
  procedural  "vendor reports use the two-page format, not the deck"
  episodic    "last month Contoso's numbers came from the CSV, not the API"
  reliability "vendor-api tool: 62% success in the last 30 days"
plan  changes as a result: pull the CSV first, skip the flaky API

At production scale

Memory recall is what makes an agent feel like it has been working here for a year. It is also the highest-risk retrieval source, because memory is written by the system itself and can be poisoned via an earlier goal. Cap memory at a modest share of the context budget, scope it hard, and log which memories entered a prompt — when an agent starts behaving strangely, that log is the first place to look.

Failure modes

  • Poisoned memory. An attacker-shaped lesson recalled forever. Quarantine on write, validate on read.
  • Stale preferences. A preference from a departed employee. Decay and re-confirm.
  • Budget crowding. Memory pushing out the actual evidence. Hard cap.

Choose it when

  • Agents run repeatedly for the same tenant and context carries over.
  • Skip for stateless one-shot tasks — the recall cost buys nothing.

Code RAG

Retrieving code is a different problem: chunk on syntax not sentences, embed with a code-aware model, and return the symbol's definition plus its callers, not a window of characters.

Mechanism

Four changes to the standard pipeline. Chunking follows the AST — one function, class or method per chunk, with the enclosing signature preserved as context. Embedding uses a model trained on code, where identifier structure carries meaning. Metadata carries language, path, symbol name, and imports. Retrieval can follow structure: definition, references, tests, and the surrounding module.

In AgentVerse

  • app/ingestion/chunkers/ast_chunker.pysyntax-aware chunking
  • app/embedding/router.pyroutes code content to a code embedding model
  • app/ingestion/connectors/github_connector.py, gitlab_connector.pysource acquisition
  • app/knowledge/ingestors/github_ingestor.pyrepository ingestion
  • app/ingestion/repository_security.pysecret scanning before indexing

Purposeful example

query "where do we validate webhook signatures?"

prose chunking  returns 400-char windows spanning two functions — unusable
ast chunking    returns verify_signature() whole, with its decorator,
                its module imports, and the 3 call sites
plus            the test file that exercises it (linked by symbol metadata)

At production scale

Two non-negotiables. Scan for secrets before indexing — a repository index is a very efficient way to make a leaked key searchable by every agent in the tenant. And index by commit, so retrieval can be pinned to the revision an agent is reasoning about; answering questions about `main` using a six-month-old index produces confident nonsense.

Embedding dimension and model choice differ from prose; keep code in its own collection so the index is homogeneous (chapter 7).

Failure modes

  • Prose chunkers on code. The single most common mistake — semantically meaningless chunks.
  • Missing context. A function without its imports or class is not runnable knowledge. Include the enclosing signature.
  • Secrets indexed. Scan first, always.
  • Index drift. Re-index on merge, not on a weekly cron.

Choose it when

  • Agents answer questions about, or modify, a codebase.
  • Do not reuse your document pipeline for code and hope.

ColBERT and late interaction

Instead of one vector per chunk, keep one per token and score by summing each query token's best match — much finer-grained matching, at a large index cost.

Mechanism

Single-vector retrieval compresses a whole passage into one point, which blurs specifics. Late interaction keeps token-level vectors and computes MaxSim: for each query token, the maximum similarity against any document token, summed. The result approaches cross-encoder quality at a fraction of the query-time cost — but the index is one or two orders of magnitude larger.

In AgentVerse

  • app/rag/agentic/patterns/colbert.pythe pattern
  • app/rag/gateway.pyprobe_colbert_readiness() — the gateway refuses to promise what is not indexed
  • app/rag/cross_encoder.pythe alternative: rerank a small candidate set instead

Readiness probing is the interesting detail — ColBERT is only offered when its index actually exists, otherwise the gateway delegates to a ready strategy.

Worked example

query "refund window for damaged goods"
single-vector  matches the general refunds passage (0.71)
late interaction
  "refund"  → best match in passage A (0.9), B (0.8)
  "window"  → A (0.4), B (0.9)
  "damaged" → A (0.2), B (0.95)   ← the distinguishing token
  MaxSim sum: B wins clearly; single-vector had them nearly tied

At production scale

The honest recommendation: try bi-encoder retrieval plus a cross-encoder rerank of the top 50 first. It usually gets most of the quality at a fraction of the storage, and it is far easier to operate. Reach for ColBERT when your corpus is large, queries are long and specific, and rerank latency has become the bottleneck.

Failure modes

  • Index size shock. 10–100× the vector storage. Plan capacity before enabling.
  • Half-built index. Enabled for a collection that was never indexed — which is exactly what the readiness probe prevents.
  • Re-index cost. Model changes mean re-embedding every token.

Choose it when

  • Precision on long, specific queries matters and you can afford the index.
  • Start with cross-encoder reranking instead.

RAFT — retrieval-aware fine-tuning

Train the model to use retrieved context correctly, including ignoring distractor documents — the only pattern here that changes the model rather than the pipeline.

Mechanism

Build training data where each example contains the question, the golden document, and distractors, with the target answer citing only the golden one. The model learns to read selectively rather than to summarise everything it is given. It is the counter to a real failure mode: models that dutifully incorporate irrelevant retrieved text because it was in the prompt.

In AgentVerse

  • app/rag/raft.pyRAFTService
  • app/rag/raft_repository.pydataset persistence
  • app/db/models/raft.pystored artifacts
  • app/rag/gateway.pychecks for a completed RAFT model before offering the strategy
  • app/api/training_export.pyexporting training sets

Present as a service and dataset pipeline; the fine-tune itself happens outside the platform, which is why the gateway must check whether a completed model exists.

Worked example

training example
  question    "what is the escalation path for a P1?"
  golden      runbooks/oncall.md#4
  distractors runbooks/oncall.md#9, policies/hr-escalation.md#2
  target      answer citing only #4, explicitly ignoring the HR document
after tuning: distractor incorporation drops from 23% to 6% on the eval set

At production scale

RAFT is for organisations with a stable domain, a labelled corpus, and enough volume to amortise a fine-tune — and it fights the platform's vendor-neutrality, since a tuned model is a lock-in. In practice most teams get more from better retrieval and a distractor-resistant prompt than from tuning. Keep the dataset pipeline regardless: those examples are also your eval set.

Failure modes

  • Overfitting to the corpus. The model becomes brittle when documents change.
  • Stale tuned model. Domain moves, model does not. Version and re-eval.
  • Provider lock-in. Your fallback provider does not have your tune.

Choose it when

  • Stable domain, high volume, measured distractor problem.
  • Not before you have exhausted retrieval and prompt fixes.

Modular RAG

Treat retrieval as a pipeline of swappable modules — rewrite, retrieve, rerank, filter, compress, generate — and let a tenant or a goal compose its own arrangement.

Mechanism

Each stage is an interface with several implementations. A pipeline is a validated list of stages; validation rejects arrangements that cannot work (rerank before retrieve, compress with no budget). The named patterns in this chapter then become presets over the same module set, which is what keeps eighteen strategies from being eighteen codebases.

In AgentVerse

  • app/rag/modular.pymodules(), validate_modular_pipeline()
  • app/rag/agentic/patterns/modular.pythe runtime, including _fallback()
  • app/rag_platform/query_planner.pyplans which modules to run
  • app/rag/certification.pycertifies a pipeline as fit to serve

Worked example

tenant "legal" pipeline
  rewrite:    legal_terminology_expander
  retrieve:   hybrid(k=40)
  rerank:     cross_encoder(top=10)
  filter:     jurisdiction == tenant.jurisdiction
  compress:   citation_preserving(budget=6k)
  generate:   with_mandatory_citations

validation: passes. the same modules with rerank before retrieve → rejected

At production scale

Modularity is how a platform serves tenants with genuinely different retrieval needs without forking. The cost is a combinatorial test surface — which is why pipelines need certification and a fallback: if a custom arrangement fails at runtime, fall back to a known-good preset rather than failing the goal.

Failure modes

  • Invalid compositions. Caught by validation, not at 3 a.m.
  • Untested combinations. Certify pipelines against an eval set before allowing them in production.
  • Debug difficulty. Six stages, one bad result. Per-stage traces are mandatory.

Choose it when

  • Different tenants or domains need materially different retrieval.
  • Overkill for a single-domain product — use presets.

Adaptive RAG & retrieval strategy selection

Classify the query, then pick the cheapest strategy that can answer it — no retrieval for chit-chat, hybrid for lookups, agentic for research.

Mechanism

A classifier assigns the query to a complexity band, and a policy maps band to strategy. The policy is a table, not a model, so it is auditable and adjustable:

Query typeStrategyTypical cost
No knowledge needednone0
Single-fact lookuphybrid1×
Ambiguous phrasingfusion or HyDE2–3×
Accuracy-criticalcorrective2–4×
Relationship questiongraph1–2×
Multi-source researchagentic5–20×

In AgentVerse

  • app/rag/agentic/patterns/adaptive.pythe pattern
  • app/rag/agentic/retrieval_policy.pythe policy table
  • app/agent/pattern_assembler.pygoal-level RAG pattern selection
  • app/rag_platform/query_planner.pyquery-level planning

Worked example

"thanks!"                              → none        $0.000
"what's the refund window?"            → hybrid      $0.002
"how do our refund terms compare
 to what we promised Contoso?"         → agentic     $0.140
same endpoint, same tenant, 70× cost difference — decided by the classifier

At production scale

Adaptive selection is the difference between a RAG bill that scales with traffic and one that scales with your most expensive strategy. In a mixed workload, routing away from the heavy strategies on the 80% of trivial queries typically cuts total retrieval spend by more than half.

Log the chosen strategy with every request. Without that label you cannot compute cost or quality per strategy, and you are tuning blind.

Failure modes

  • Under-classification. A research question routed to hybrid returns a shallow answer that looks fine. Sample and audit.
  • Classifier cost. Do not use a large model to decide whether to use a large model.
  • Policy rot. Re-tune the table as strategies and prices change.

Choose it when

  • Query mix is heterogeneous — which it always is in a real product.
  • Skip only if every query is genuinely the same shape.

Strategy readiness & delegation

A strategy you cannot run is not an error to throw at the user — the gateway checks capability facts and delegates to the best ready alternative, recording the substitution.

Mechanism

Each strategy declares its requirements in a capability catalogue: an embedder, a built ColBERT index, a reachable reranker, a populated graph, an enabled web tool, a completed RAFT model. At request time the gateway gathers readiness facts about the current tenant and deployment, evaluates the requested strategy against them, and either runs it or picks a delegation candidate that is ready. The substitution appears in the trace.

This is what turns eighteen strategies from a fragility into a resilience feature: the system degrades along a defined ladder instead of failing.

In AgentVerse

  • app/rag/catalogue.pyRAG_CAPABILITY_CATALOGUE, DELEGATION_CANDIDATES
  • app/rag/gateway.pyreadiness(), readiness_context(), ReadinessFact, probe_colbert_readiness()
  • app/rag/readiness.pythe readiness model
  • app/rag/contracts.pyUnavailableRAGStrategyError for the cases that cannot degrade
  • app/runtime_readiness/degraded_mode_policy.pythe platform-wide equivalent

Worked example

requested   colbert
facts       embedder ok · colbert index MISSING for collection "wiki"
delegate    colbert → hybrid + cross_encoder   (nearest ready capability)
trace       {requested:"colbert", executed:"hybrid+rerank",
             reason:"colbert index not built for collection wiki"}
user sees   an answer; the operator sees a build-the-index task

At production scale

Readiness is the difference between a multi-strategy platform and a demo. Tenants enable features at different times, indexes get rebuilt, providers go down — and none of that should turn into a user-facing error. Expose readiness on a status endpoint so support can answer "why is this tenant's search worse today" in one look.

Alarm on delegation rate. A spike means a capability broke, and it will otherwise be invisible because every request still succeeds.

Failure modes

  • Silent degradation. Delegation with no trace and no metric — your evals then measure a strategy that never ran.
  • Delegation cascades. A → B → C. Bound the chain, then fail honestly.
  • Stale facts. Cached readiness that no longer holds. TTL the cache.

Choose it when

  • More than one strategy, or any capability that can be absent per tenant.

Semantic caching

Two users ask the same question in different words — serve the second from cache by matching embeddings rather than strings.

Mechanism

Embed the incoming query, search the cache of previous query embeddings, and if the nearest neighbour is above a similarity threshold, return its stored answer. The threshold is the whole design: too low and you serve the wrong answer confidently, too high and you never hit. Cache keys must include tenant, collection set, and any filter — a cached answer scoped wrongly is a data leak, not a performance win.

Two layers in practice: cache the retrieval result (safe, high hit rate) and cache the final generation (bigger saving, needs a stricter threshold and shorter TTL).

Worked example

q1  "how long do I have to return an item?"     MISS → full pipeline, $0.004
q2  "what's the return window?"                 sim 0.94 → HIT, $0.00002
q3  "what's the return window for Contoso?"     sim 0.88 → MISS (below 0.92)
                                                 — correctly, the answer differs
key = hash(tenant, collections, filters, normalised query embedding)

At production scale

On support and FAQ workloads a semantic cache commonly removes 25–40% of pipeline executions, which is the largest single cost reduction available in RAG. Two rules keep it safe: never share a cache across tenants, and invalidate on ingestion — a cached answer from before this morning's document update is a correctness bug that no user will report.

Failure modes

  • Threshold too loose. "Refund policy" answered with "return policy". Tune against labelled near-miss pairs.
  • Cross-tenant hit. Catastrophic. Tenant must be part of the key, enforced in code.
  • Stale after ingest. Invalidate by collection version.
  • Personalised answers cached. Never cache anything containing user-specific data.

Choose it when

  • Query distribution is repetitive — support, FAQ, internal help.
  • Avoid where answers are personalised or the corpus changes hourly.

What is missing here

  • Learned strategy selection. Adaptive RAG uses a hand-written policy table. The obvious upgrade is a bandit trained on measured answer quality per strategy per query class.
  • Retrieval evaluation in the live path. Offline retrieval evals exist (chapter 10), but there is no continuous online estimate of retrieval precision per collection to drive automatic strategy changes.
  • Cross-encoder distillation. Nothing distils the reranker's judgements back into the bi-encoder, which is the standard way to make cheap retrieval better over time.
  • Query-time index selection. The system picks a strategy but not an index — no mechanism to choose between a fresh small index and a large stale one under latency pressure.
