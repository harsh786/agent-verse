Orientation

Retrieval patterns (chapter 2) assume something to retrieve from. This chapter is that something: the object model — collection, document, chunk, metadata, citation — the two index shapes that make it searchable, and the graph that makes relationships answerable.

The object model looks trivial and is where most production RAG problems actually live. A chunk with no stable id cannot be cited. A document with no source reference cannot be re-synced. A collection with no authorisation boundary is a data-leak vector. Get these five nouns right and the interesting patterns become easy; get them wrong and no amount of clever retrieval saves you.

The object model

Knowledge collections

A collection is the unit of authorisation, configuration and lifecycle — not a folder. Which chunks an agent can see, which embedding model was used, and what happens on deletion are all collection-level facts.

Mechanism

A collection binds: a tenant, an access rule, an embedding model and dimension, a chunking strategy, a retention policy, and a set of sources that sync into it. Because the embedding model is fixed per collection, the index stays homogeneous — which is the property that makes vector search meaningful at all (chapter 7).

The practical design rule: split collections by who may read them and by what kind of content they hold, not by topic. Mixing code and prose in one collection breaks embedding quality; mixing HR and engineering breaks access control.

Worked example

collection  acme/policies
  embedding    text-embedding-3-large @ 3072
  chunking     markdown_heading, 800 tokens, 80 overlap
  access       roles [employee, analyst, admin]
  retention    7 years (regulatory)
  sources      confluence:space=POL, s3:bucket/policies/

collection  acme/code-monorepo
  embedding    code-embedding model @ 1536      ← different index entirely
  chunking     ast_chunker
  access       roles [engineer]
  retention    90 days rolling

At production scale

Collection count grows faster than anyone plans for — per team, per product, per compliance regime. Two things must be cheap: creating one (so nobody stuffs unrelated content into an existing collection) and enumerating what an agent may search (so retrieval can fan out safely). Cache the authorisation decision per (principal, collection) with a short TTL; it is on the hot path of every retrieval.

Failure modes

  • Mixed-model collections. Two embedding models in one index — scores are incomparable and results are quietly wrong.
  • Collection sprawl. Hundreds of near-duplicates; retrieval fans out over everything.
  • Authorisation drift. A collection created outside the normal path with default-open access.

Choose it when

  • Always — a single global namespace fails on the first access-control requirement.

Documents

The unit of ingestion and of identity: a document has a stable id, a content hash, a source reference, and a version — which together are what make re-sync, dedup and deletion possible.

Mechanism

A document is the thing a connector fetched: a PDF, a Confluence page, a Jira issue, a source file. It carries provenance (which source, which external id, which revision), a content hash for idempotency, and the metadata that will be copied onto every chunk. Re-ingesting a document with an unchanged hash is a no-op; with a changed hash it supersedes the previous version and its chunks are replaced, not appended.

Worked example

document
  doc_id      acme:confluence:POL-118
  source_ref  confluence://space/POL/page/118?version=7
  hash        sha256:9f2c…
  metadata    {space:POL, author:"r.iyer", updated:2026-08-02,
               labels:[policy, refunds], classification:internal}
re-sync at 03:00  → hash unchanged → skipped at stage 3, 0 embedding calls
edit at 11:20     → hash changes   → version 8, chunks replaced, citations
                                      to old chunk ids resolve to superseded

At production scale

Content hashing at stage 3 — before parsing and embedding — is the single largest cost control in ingestion. Most connectors re-deliver most documents on every sync; without the hash gate you pay to embed an unchanged corpus nightly.

Keep the external revision alongside your own version. When a user says "the answer is out of date", the first question is which revision was indexed, and only provenance can answer it.

Failure modes

  • Unstable ids. A connector that generates a new id per sync creates duplicates forever.
  • Hash over the wrong bytes. Hashing a rendering that includes a timestamp makes every document look changed.
  • Append instead of replace. Old and new chunks both retrievable; the model sees a contradiction.

Choose it when

  • Always. Without document identity you cannot re-sync, dedup, or delete.

Chunks

The atom of the whole system: what gets embedded, scored, budgeted, cited and deleted. Every quality argument about RAG is ultimately an argument about chunk boundaries.

Mechanism

A chunk is a span of a document with a stable id, its text, an embedding, inherited document metadata, structural position (heading path, page, line range, symbol name), and optionally a parent reference. The id must be stable across re-ingestion for the same content, or citations rot.

Chunking strategy is a per-collection decision covered in full in chapter 17; the object model requirement is simply that a chunk knows where it came from precisely enough to be quoted.

Worked example

chunk
  chunk_id   acme:confluence:POL-118#h2-refunds#0
  text       "Refunds are accepted within 30 days of delivery…"
  position   {heading_path:["Policies","Refunds"], page:null, order:3}
  parent     acme:confluence:POL-118#h2-refunds
  metadata   inherited from the document + {tokens:412, lang:en}
  embedding  3072-d, model text-embedding-3-large

retrieval returns the child (precise match) but the prompt receives the
parent (full section) — better answers, same precision

At production scale

Chunk count, not document count, is your capacity unit: a 10k-document corpus at 40 chunks per document is 400k vectors, and that number drives index size, memory, and re-embedding cost. Track it per collection and alarm on unexpected growth — a chunker misconfiguration can 10× it overnight.

Deduplicating chunks (stage 11) matters more than it sounds. Boilerplate headers, footers and legal notices repeat across thousands of documents; without dedup they dominate retrieval for generic queries.

Failure modes

  • Unstable chunk ids. Every re-ingest invalidates every citation.
  • Chunks without position. A citation you cannot follow is not a citation.
  • Boilerplate flood. The same footer retrieved for everything.
  • Orphaned vectors. Chunk deleted, embedding retained — it still comes back in search.

Choose it when

  • Always. The only question is how you cut them (chapter 17).

Metadata

The fields you can filter on before you ever compute a similarity — and therefore the cheapest precision improvement available, as well as the enforcement point for jurisdiction and sensitivity.

Mechanism

Document metadata is copied onto chunks at ingestion so filters apply at the index level. Four categories, each earning its keep differently:

  • Provenance — source, external id, revision, ingested-at.
  • Structural — heading path, page, section, symbol.
  • Semantic — labels, author, product, language, dates.
  • Governance — classification, jurisdiction, retention policy, legal-hold flag.

Governance metadata is not decoration: it is what lets a retrieval filter enforce "this tenant's EU users may only see EU-resident documents" as a pre-filter rather than a hopeful post-check.

  • app/rag/contextual_enricher.pyadds derived context to chunks at stage 9

Worked example

query "notice period" for a user in the German entity
naive     top hits are the US handbook (better written, more chunks)
filtered  metadata.jurisdiction == "DE" applied as a pre-filter
          → 14 candidates instead of 900 → correct answer, faster query
governance the US chunks were never scored, never logged, never returned

At production scale

Metadata filtering routinely beats better embeddings. Narrowing 900 candidates to 14 with a jurisdiction filter improves both precision and latency more than any reranker would, at zero model cost.

Index the filter fields. A metadata filter that forces a sequential scan turns a 20ms query into 900ms, and it will be blamed on "the vector database being slow".

Failure modes

  • Metadata loss at parse. The parser returns text and drops everything else — the most common ingestion bug.
  • Inconsistent vocabularies. DE, de-DE, Germany in the same field.
  • Over-filtering. Filters so narrow nothing matches; retrieval returns empty and the agent replans forever.
  • Unindexed filters. Correct results, unacceptable latency.

Choose it when

  • Always, and design the vocabulary before ingesting a million documents with the wrong one.

Citations

A citation is a machine-checkable claim that a specific span of output is supported by a specific chunk — the difference between an answer a user can verify and one they must believe.

Mechanism

Three requirements make citations real rather than cosmetic. They must be resolvable — chunk id → document → source URL a human can open. They must be verifiable — a checker can confirm the cited chunk actually supports the claim. And they must be threaded — carried through multi-hop retrieval, synthesis and summarisation rather than lost at the first transformation.

Citation management is therefore a pipeline component, not a prompt instruction. Asking a model to "include citations" produces plausible-looking references to chunks that do not exist.

   the window [2], and enterprise contracts may override both [3]."

At production scale

Citations are the primary hallucination control that users can actually see, and the primary reason regulated teams accept agent output at all. Two operational rules: verify before display (an unverified citation is worse than none, because it manufactures trust), and keep citation ids stable so a screenshot from three months ago still resolves.

Measure citation precision — the share of citations that genuinely support their claim — as a first-class quality metric alongside answer accuracy (chapter 10).

Failure modes

  • Fabricated references. The model invents a plausible id. Only emit citations the pipeline assigned.
  • Citation drift. Citation attached to the wrong sentence after a rewrite.
  • Broken resolution. The chunk was re-ingested with a new id and the link 404s.
  • Citation theatre. Every sentence cited, none verified.

Choose it when

  • Any output a human relies on, and every regulated flow.
  • Never ship "citations" you do not verify.

KnowledgeStore behaviour

One component owns the index: writes chunks, runs hybrid search two ways (in-memory fast path and pushed-down SQL), expands parent citations, and serves precomputed indexes.

Mechanism

The store exposes a small surface with a deliberate duality. hybrid_search() is an in-memory path that combines cosine similarity, trigram scoring and BM25 — always available, no database required, which is what makes tests and single-node deployments simple. hybrid_search_db() pushes the same computation into Postgres, where the data already is, for production scale. A precomputed-index path serves collections whose vectors are prepared offline.

It also owns parent citation expansion: retrieval matched a child chunk, but the citation and the prompt should reference the parent section.

  • app/rag/evaluation.pystore-level retrieval evaluation

The in-memory/DB swap at startup is the same two-phase wiring pattern the whole platform uses (chapter 19) — and it is why "works in tests, differs in prod" bugs cluster here.

Worked example

dev / tests      KnowledgeStore (in-memory)
                 hybrid_search: python cosine + trigram + BM25 over 2k chunks
                 ~8ms, zero dependencies

production       KnowledgeStore (DB-backed, swapped in lifespan)
                 hybrid_search_db: one SQL statement, pgvector + tsvector +
                 pg_trgm, LIMIT 50, ~22ms over 1.2M chunks
identical result shape → the same retrieval code runs in both

At production scale

Push search into the database. Fetching candidates into the application to rank them costs more in serialisation than the query itself, and it breaks as soon as the corpus outgrows one process's memory. The in-memory path should stay a genuine fast path — small collections, tests, degraded mode — not the production route.

Keep the two implementations behaviourally identical and test them against the same fixtures. Divergence here produces the worst class of bug: correct in CI, subtly wrong for customers.

Failure modes

  • Path divergence. The two implementations rank differently.
  • Missing tenant filter on one path. A leak that tests never see.
  • Unbounded candidate fetch. No LIMIT, and one query reads the collection.

Choose it when

  • Always; the duality is worth it, but only with shared tests.

Vector index

Approximate nearest-neighbour search over embeddings, in the same database as the metadata — which is the decision that makes filtered vector search a single query instead of two systems and a join.

Mechanism

Embeddings live in a pgvector column with an ANN index (HNSW or IVFFlat). The index type is a real trade: HNSW gives better recall and query speed at higher build cost and memory; IVFFlat builds fast and is cheaper but needs list tuning and degrades on updates. Distance metric must match how the embedding model was trained — cosine for most, inner product for some — and mixing them silently degrades ranking.

The reason to keep vectors in Postgres rather than a dedicated vector database: filters, joins, transactions and row-level security come for free, and RLS is how tenant isolation is enforced at the storage layer.

Worked example

SELECT chunk_id, content, 1 - (embedding <=> $1) AS score
FROM chunks
WHERE tenant_id = current_setting('app.tenant_id')      -- RLS also enforces
  AND collection_id = ANY($2)
  AND metadata->>'jurisdiction' = 'DE'                  -- pre-filter
ORDER BY embedding <=> $1
LIMIT 50;

one statement: tenant isolation + collection scope + metadata filter + ANN

At production scale

Three numbers to know for your corpus: index build time (HNSW on a million vectors is minutes to hours), memory footprint (the index wants to be resident), and recall at your ef_search setting. Tune recall explicitly — the default parameters of most ANN indexes trade away more recall than teams realise, and it shows up as "the answer was in the corpus but not in the context".

Rebuilds are the operational hazard: a dimension change or a model change means a full re-embed and re-index, which must be done online with a shadow index unless you can afford downtime (chapter 7).

Failure modes

  • Dimension mismatch. A query vector of the wrong size — either an error or, worse, a silently meaningless result.
  • Metric mismatch. Cosine index queried with L2.
  • Filter-then-ANN vs ANN-then-filter. Filtering after the ANN limit returns fewer rows than requested, sometimes zero.
  • Index bloat after churn. Heavy update workloads need periodic maintenance.

Choose it when

  • Any semantic retrieval. The question is not whether but where it lives — and next to your metadata is usually the right answer.

Lexical indexes: full-text, trigram, BM25

Three different keyword mechanisms with three different jobs — stemmed full-text for natural language, trigram for typos and partial identifiers, BM25 for term-importance ranking.

Mechanism

Full-text search tokenises and stems with a language configuration, then matches on lexemes — good for prose, blind to typos. Trigram similarity compares three-character sequences, so "invocie" still finds "invoice" and INV-2024 matches INV-2024-8891. BM25 is a ranking function: term frequency saturating, inverse document frequency, length normalisation — the reason a rare term in a short document ranks above a common term in a long one.

In AgentVerse

  • app/rag/bm25.pyBM25Retriever
  • app/rag/store.py_trigram_score(), FTS in the DB path
  • app/db/migrations/tsvector columns, GIN and pg_trgm indexes

Worked example

query "recieve payment confirmation"     (typo, and stemmed forms differ)

FTS      'receive' & 'payment' & 'confirm'  → misses "recieve" entirely
trigram  0.78 similarity to "receive payment confirmation" → hit
BM25     ranks the payments runbook above the 40-page handbook that
         mentions "payment" 200 times, because of length normalisation

At production scale

Language configuration matters more than teams expect: an English stemmer on German content produces poor matches, and a multi-tenant platform will have both. Store the language on the document and pick the configuration per row.

Trigram indexes are large and writes are slower — enable them where identifiers matter (invoices, tickets, SKUs, code) rather than globally.

Failure modes

  • Wrong language config. Silent quality loss.
  • Missing GIN index. Full-text search that sequential-scans.
  • BM25 on the wrong corpus statistics. IDF computed globally instead of per collection skews ranking.

Choose it when

  • Alongside vectors, always. Lexical search is not a legacy fallback; it is half of hybrid.

The knowledge graph

Nodes, edges, and where they come from

A tenant-scoped property graph built as a side effect of ingestion: entities become nodes, relations become edges, and every edge remembers the chunk it was extracted from.

Mechanism

An extractor reads each chunk and proposes typed entities and relations. Nodes carry a type, a canonical name, aliases and properties; edges carry a relation type, a confidence, and the source chunk id. The graph is built incrementally as documents arrive rather than as a separate batch job, which keeps it as fresh as the corpus.

Extraction quality is dominated by two things: a constrained schema (a fixed set of entity and relation types beats open-ended extraction) and entity resolution (below).

  • app/knowledge_graph/ingestion_hook.pyKGIngestionHook — graph built during ingestion

  • app/db/models/knowledge_graph.pypersistence
  • app/api/knowledge_graph.pythe API surface, including export

Worked example

chunk  "The payments service is maintained by the fin-platform team and
        depends on Razorpay under contract C-2291."

nodes  (service:payments) (team:fin-platform) (vendor:Razorpay)
       (contract:C-2291)
edges  payments —maintained_by→ fin-platform     conf 0.93  src chunk#12
       payments —depends_on→    Razorpay          conf 0.88  src chunk#12
       Razorpay —governed_by→   C-2291            conf 0.81  src chunk#12

At production scale

Extraction is an LLM call per chunk, so the graph costs roughly what embedding costs, again. Build it selectively: collections where relationship questions are common (architecture, contracts, org data), not the whole corpus. Store edge confidence and use it — low-confidence edges should be visible in exploration but excluded from answers.

Failure modes

  • Schema-free extraction. Ten relation types meaning the same thing. Constrain the schema.
  • Hallucinated edges. Require the source chunk and sample-audit edges.
  • Graph and corpus divergence. Documents updated, edges not. Rebuild affected subgraphs on re-ingest.

Choose it when

  • Users ask about relationships, ownership, dependency, or impact.
  • Skip for corpora that are purely narrative.

Entity resolution

The step that decides whether your graph is knowledge or noise: merging "Acme Corp", "ACME", "Acme Corporation" and "acme-corp" into one node.

Mechanism

A cascade, cheapest first: exact match on a canonical key, then normalised string match (case, punctuation, legal suffixes), then alias table lookup, then embedding similarity above a threshold, then — only for the remainder — an LLM adjudication. Every merge should be recorded so it can be undone, because a wrong merge is worse than a missed one: it fuses two real entities into a fiction.

Worked example

observed   "Acme Corp"  "ACME"  "Acme Corporation"  "acme-corp"  "Acme Inc"
resolution normalise → strip suffixes → "acme" for the first four
           "Acme Inc" → embedding 0.91 but LEGAL SUFFIX DIFFERS
           → held for review: Acme Inc may be a different legal entity
result     one node with 4 aliases + 1 pending review, not 5 nodes

At production scale

Entity resolution is where knowledge-graph projects succeed or quietly fail. Two rules from practice: maintain an explicit alias table that humans can edit (it is the highest-leverage manual data in the system), and never auto-merge across a legal-entity or tenant boundary.

Failure modes

  • Fragmentation. Five nodes, no traversal works.
  • Over-merging. Two subsidiaries fused; answers become wrong in a way that is hard to detect.
  • Unreviewable merges. No log, no undo.

Choose it when

  • Any graph. Skipping it does not save time; it moves the cost to every query.

Community detection

Cluster the graph into densely-connected groups and summarise each — the graph's answer to "what are the themes here", and the structure that makes a large graph navigable.

Mechanism

Run a modularity-based clustering algorithm over the edges to find communities, then generate a summary per community from its member nodes and their source chunks. Global questions are answered from community summaries; specific questions drill into nodes. It is structurally the same idea as RAPTOR (chapter 2) applied to a graph instead of text.

  • app/knowledge_graph/community_detection.pythe detector

Worked example

At production scale

Communities are most useful as a navigation device for humans and agents alike — a map of a graph too large to read. Summaries go stale, so regenerate on significant graph change rather than on a fixed schedule, and always keep the drill-down path to real nodes so a summary is never the only evidence.

Failure modes

  • Unstable communities. Small graph changes reshuffle everything; summaries churn.
  • Hub distortion. One highly-connected node dominates and communities become meaningless.
  • Stale summaries. Regenerate on change.

Choose it when

  • The graph is large and users ask thematic questions.
  • Unnecessary on a small graph you can traverse directly.

The graph retrieval path

Resolve the question's entities to nodes, traverse to bounded depth under an access filter, then return the subgraph and the chunks that produced each edge.

Mechanism

Four steps. Anchor: map question entities to node ids (this is entity resolution again, at query time). Traverse: expand along permitted relation types to a depth and degree bound. Filter: apply role and tenant access to nodes and edges during traversal, not after. Serialise: render the subgraph compactly for the prompt, attaching the source chunk for each edge so the answer can cite documents rather than the graph.

The last point is what keeps graph answers auditable: the graph is an index over the corpus, and the corpus is the evidence.

In AgentVerse

  • app/knowledge_graph/multi_hop.pythe multi-hop reasoner
  • app/knowledge_graph/access_control.pyGraphAccessControl — role-gated traversal
  • app/state_runtime/kg_query_engine.pyruntime query engine
  • app/rag/agentic/patterns/graph.pygraph as a RAG strategy

Worked example

question "if Razorpay is down, which teams are affected?"
anchor    "Razorpay" → (vendor:Razorpay)
traverse  depth 2, relations {depends_on⁻¹, maintained_by}
          → payments, payouts, refunds services
          → fin-platform, treasury teams
filter    caller role=engineer → treasury contract nodes excluded
serialise 7 nodes, 9 edges, each edge citing its source chunk
answer    two teams, with the dependency chain and 6 document citations

At production scale

Bound the traversal hard. A depth-4 expansion from a hub node returns a large fraction of the graph and produces a prompt nobody can use. Depth 2 with a degree cap answers most real questions.

Graph queries are milliseconds where iterative retrieval is seconds — if your workload is dominated by relationship questions, the graph is not a luxury, it is the performance fix.

Failure modes

  • Anchor failure. The entity is not in the graph, so the answer is empty even though the corpus contains it. Fall back to vector search.
  • Traversal explosion. Bound depth and degree.
  • Post-filtering. Access applied after traversal means restricted nodes were read.

Choose it when

  • The question is structural. Otherwise use vectors.

Graph retrieval versus vector retrieval

Vectors answer "what does the corpus say about X"; graphs answer "how is X connected to Y". Choosing wrongly is the most common architectural mistake in knowledge systems.

Mechanism

Use the shape of the question, not the shape of the data:

Question shapeUseWhy
"What is our refund policy?"Vector / hybridAnswer is a passage
"Summarise this contract"VectorNeeds the prose, not the structure
"Who owns service X?"GraphA single relation
"What breaks if X fails?"GraphTransitive closure
"Which vendors appear in both contracts?"GraphSet intersection over entities
"How did our policy change over time?"Vector + metadata filterVersioned prose
"What themes recur in incidents?"RAPTOR or communitiesAggregation
"Everything about vendor X"BothGraph for scope, vectors for content

The general rule: graphs are an index, not a knowledge base. They tell you what to read; the chunks are what you read.

In AgentVerse

Both are strategies in the same vocabulary (RAGStrategy.GRAPH versus HYBRID), selected by app/rag/agentic/retrieval_policy.py and by the pattern assembler. Because they share the result contract, an agent can use graph retrieval to scope and vector retrieval to read within one goal — which is usually the best answer.

Worked example

"prepare a risk brief on our payment vendors"
graph    scope: 3 vendors, 5 contracts, 2 services, 4 owning teams
vector   read: the risk clauses in those 5 contracts, the incident write-ups
                for those 2 services
result   a brief that is both complete (graph found everything) and
         substantive (vectors supplied the text) with citations to documents

At production scale

The failure to watch for is a team building a graph because graphs are interesting, then discovering that 90% of their questions are passage questions. Instrument question shapes before investing: if relationship questions are under a fifth of traffic, hybrid retrieval plus good metadata will serve you better than an extraction pipeline you have to maintain.

Failure modes

  • Graph for prose questions. Structurally correct, substantively empty answers.
  • Vectors for structural questions. Confident answers that miss two thirds of the affected systems.
  • Two disconnected systems. A graph that cannot cite chunks is unauditable.

Choose it when

  • Every time you design a knowledge feature. Ask what shape the question is.

How graph, RAG, memory and agents compose

Four sources of context with four different trust levels, merged under one token budget with per-source caps — the composition is where a platform is won or lost.

Mechanism

At context assembly time, four kinds of material compete for the same window:

SourceTrustTypical capVerifiable?
Retrieved chunksHigh — a document said it50–70%Yes, cite the chunk
Graph subgraphMedium — extracted, may be wrong10–20%Via the edge's source chunk
MemoryLower — the system inferred it5–10%Via evidence refs
Tool outputFresh but untrusted10–25%Yes, but wrap as untrusted

Per-source caps prevent the failure where one source crowds out the others — usually memory or a verbose tool output eliminating the evidence the answer needed.

At production scale

Log the composition of every prompt: how many tokens came from each source, and which ids. When answer quality drops, the composition log tells you whether retrieval degraded, memory crowded in, or a tool started returning verbose junk. Without it you are guessing at a system with four moving parts.

Failure modes

  • Uncapped sources. One source eats the window.
  • Mixed trust, uniform presentation. The model treats an inferred memory as authoritative as a contract clause. Label sources in the prompt.
  • Citation namespace collisions. Two sources both using "[1]".

Choose it when

  • As soon as you have more than one context source — which is immediately.

Freshness, sync state and readiness

A collection has an operational state — last synced, documents pending, index built, embedder available — and retrieval quality is a direct function of it.

Mechanism

Per source: a cursor (where the last sync stopped), a last-success timestamp, a failure count, and a dead-letter queue for documents that could not be processed. Per collection: chunk count, index build state, embedding model, and readiness facts the retrieval gateway consults before promising a strategy.

Making this visible is what converts "the AI is wrong" into "the Confluence connector has been failing for six days".

At production scale

Alarm on sync staleness per source, not on ingestion errors in aggregate. A connector that fails silently is indistinguishable from a corpus that has nothing to say — and users experience it as the agent getting dumber. The DLQ needs an owner and a retry path, or it becomes a graveyard.

Jitter the schedules. Fifty sources all syncing at 03:00 is a self-inflicted thundering herd against both your database and the upstream APIs.

Failure modes

  • Silent sync failure. The most damaging knowledge bug there is.
  • Cursor loss. Full re-sync of a large source, and a large bill.
  • Unattended DLQ. Documents that never make it in, with nobody looking.
  • Readiness not surfaced. Support cannot explain degraded quality.

Choose it when

  • Any scheduled ingestion — that is, any real knowledge base.

What is missing here

  • A dedicated entity-resolution service. Canonicalisation exists inside the extractor; a reviewable merge log, an editable alias table and a resolution API do not.
  • Temporal graph edges. Relations have no validity interval, so "who owned this last quarter" cannot be answered from the graph.
  • Citation stability guarantees. Chunk ids are stable by convention rather than by contract; a formal supersede/redirect record would keep old citations resolvable.
  • Cross-collection deduplication. The same document ingested into two collections is embedded twice and retrieved twice.
  • Knowledge quality scoring per collection. Readiness says whether a strategy can run, not whether the corpus is any good — no continuous coverage or contradiction metric.
