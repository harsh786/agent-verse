Orientation

Ingestion is the least glamorous and most consequential subsystem in an agent platform. Every retrieval quality problem, every "the AI doesn't know about X", every compliance incident involving a document that should never have been indexed — all of it originates here.

The design that survives production is a single pipeline with explicit numbered stages, the same for every source and every format, where the format-specific work is isolated to one stage (parse) and the strategy-specific work to another (chunk). AgentVerse runs thirteen stages, and the ordering encodes hard rules: idempotency before any paid work, PII detection before the embedder ever sees the text, quality gating before storage.

Pipeline and sources

The 13-stage pipeline

One code path for every document from every source: receive, validate, hash, classify, parse, redact, quality-gate, chunk, enrich, embed, dedup, index, emit.

Mechanism

Each stage is small, individually observable, and can drop or skip a document with a recorded reason. The stage boundaries are chosen so that expensive and irreversible work happens as late as possible: quota check first (free), hash third (cheap, prevents everything downstream), parse fifth (moderate), embed tenth (paid, external), index twelfth (durable).

Four platform rules are enforced structurally rather than by convention: content hashing for idempotency at 3; PII detection and redaction before the embedder at 6; an OTel span plus a metric counter at every stage; and one correlation id carried through all thirteen.

Worked example

doc  contract.pdf, 4.2MB, from s3://acme-legal/

1  receive       tenant quota 12GB/40GB              ok
2  validate      4.2MB < 50MB limit                  ok
3  hash          sha256:c19a… new                    proceed
4  classify      application/pdf, has text layer     → pdf parser
5  parse         38 pages → 91k chars + layout
6  PII           4 emails, 1 IBAN → redacted, flags recorded
7  quality       score 0.86 ≥ 0.40 min               ok
8  chunk         pdf_layout strategy → 142 chunks
9  enrich        + heading path, page no, doc summary
10 embed         142 vectors, 1 batched provider call
11 dedup         6 boilerplate chunks dropped → 136
12 index         136 rows + vectors + tsvector
13 emit          knowledge.updated → SSE → the UI count ticks up

At production scale

Per-stage metrics are what make ingestion operable. The three most valuable: skip rate at stage 3 (should be high on re-syncs — if it is near zero your hashing is broken), drop rate at stage 7 (a spike means a parser regressed), and stage-10 latency (the external dependency that will eventually be your bottleneck).

Batch the embed stage. One call with 142 texts instead of 142 calls is the difference between minutes and hours on a large corpus, and most providers price it identically.

Failure modes

  • Wrong stage order. Embedding before redaction sends raw PII to a third party — a reportable incident, not a bug.
  • Silent stage failure. A stage that swallows an exception and returns empty text produces indexed documents with no content.
  • Unbounded documents. A 2GB PDF that OOMs the worker; stage 2 exists for that.
  • Partial indexing. A crash between 10 and 12 leaves paid embeddings unindexed — make 12 idempotent and re-runnable.

Choose it when

  • Always. Ad-hoc per-format scripts are how ingestion becomes unmaintainable.

Source configuration and connectors

A connector's job is narrow and precise: given a cursor, return the documents that changed since it — nothing about parsing, chunking or embedding.

Mechanism

Every connector implements the same contract, centred on get_delta(cursor). That single method shape is what makes forty-plus integrations maintainable: incremental sync, resumption, and backfill are all the same operation with a different starting cursor. Credentials come from the vault, never from the source config. Connectors are registered in a registry so sources are configuration, not code.

The catalogue spans six families: SaaS apps (Jira, Confluence, Slack, Notion, Salesforce, HubSpot, Zendesk, ServiceNow, Teams, Discord, PagerDuty, Sentry), object stores (S3, GCS, Azure Blob, MinIO, SharePoint, Drive), databases and warehouses (Postgres, MySQL, MongoDB, Snowflake, BigQuery, ClickHouse, DuckDB, Elasticsearch, Neo4j, InfluxDB), streams (Kafka, Kinesis, Pub/Sub, MQTT), the open web (crawl, RSS, arXiv, YouTube), and email (IMAP).

At production scale

Commit the cursor after the pipeline succeeds, not after fetching. Committing early loses documents on a crash; committing late re-processes a few, which the hash gate makes nearly free. That asymmetry is why at-least-once with idempotency is the right design here.

Every connector will eventually rate-limit you. Per-source concurrency limits and respect for Retry-After belong in the base connector, not in each implementation.

Failure modes

  • Cursor semantics mismatch. A source whose "updated_after" is not monotonic silently skips documents.
  • Credential expiry. Sync fails for days; nobody notices without staleness alarms.
  • Full re-sync on cursor loss. Expensive and slow; keep cursors durable and backed up.
  • Permission over-fetch. A connector with admin scope ingesting documents the tenant's users may not see.

Choose it when

  • Any recurring source. One-off uploads can go straight to the pipeline.

Scheduled sync: locks, jitter, cursors, backoff

The distributed-systems half of ingestion — due-source dispatch, one worker per source at a time, periodic cursor commits, exponential backoff, and a dead-letter queue.

Mechanism

A tracker finds sources whose next-run time has passed. Each acquires a Redis lock so two workers cannot sync one source concurrently (the classic cause of duplicate ingestion). Schedules are jittered so fifty sources do not fire simultaneously. Long syncs commit the cursor periodically — every hundred documents — so a failure at document 9,000 does not restart from zero. Failures back off exponentially and eventually land in a DLQ with the classified reason.

Worked example

       s3-legal: lock acquired by worker-4
                 14,200 documents; cursor committed at 100, 200, …
                 fails at 9,340 (S3 throttle)

       3 documents exceed retries → DLQ with reason=parse_error
       confluence-POL: lock held by worker-1, worker-7 skips (no duplicate)

At production scale

Ingestion is bursty and competes with the agent workload for the same database and the same embedding quota. Give it its own queue and its own concurrency ceiling, or a nightly backfill will degrade interactive goals. The DLQ needs a named owner and a review cadence; unattended, it is where knowledge silently goes missing.

Failure modes

  • Missing lock. Two workers, duplicate documents, doubled embedding spend.
  • Thundering herd. Unjittered schedules taking out the database at 03:00.
  • Poison document. One document crashes the worker repeatedly and blocks the source — classify, DLQ, and move on.
  • Retry without backoff. Turning an upstream hiccup into an outage.

Choose it when

  • Any source that syncs on a schedule — which is nearly all of them.

Content classification

Decide what a document actually is — by sniffing bytes, not by trusting the filename or the declared MIME type — because the parser choice depends on it.

Mechanism

Three signals in order of trust: magic bytes (a PDF starts %PDF-), structural probes (does this "PDF" have a text layer or is it scanned images?), and only then extension and declared type. The output is a content type plus attributes that steer downstream choices: has-text-layer, is-scanned, language, encoding, and whether it looks like code.

Sniffing is a security control as well as a routing decision: a file named report.pdf that is actually an HTML document with a script payload should be handled as what it is.

  • app/ingestion/content_classifier.pysniffing and attributes (stage 4)
  • app/ocr/classifier.pyDocumentClassifier — document kind for OCR routing (invoice, ID, statement)
  • app/ingestion/modality_pipeline.pyroutes by modality

Two different classifiers, deliberately: one answers "what format is this file", the other "what kind of business document is this" (chapter 21).

Worked example

scan-0041.pdf
  magic bytes  %PDF-1.7                      → pdf
  text layer   0 extractable characters      → scanned
  route        pdf → OCR path, not text parse
  attributes   {pages:3, scanned:true, dpi:300}

notes.txt
  magic bytes  none
  content      "{\"invoices\":[…" → actually JSON
  route        json parser, not text parser

At production scale

Misclassification is silent and expensive: a scanned PDF sent down the text path produces a document with no content, which indexes successfully and answers nothing. Assert non-empty extracted text as a pipeline invariant and route empties to OCR or the DLQ rather than indexing them.

Failure modes

  • Trusting extensions. The most common source of empty documents.
  • Missing the scanned case. Text-layer probing is not optional for real-world PDFs.
  • Encoding guesswork. Latin-1 read as UTF-8 produces mojibake that embeds meaninglessly.

Choose it when

  • Always. Never trust the filename.

Parser selection

A registry maps content type to parser, every parser returns the same structure, and one bad parser cannot take down the pipeline.

Mechanism

Parsers implement a common interface: bytes plus attributes in, structured text plus metadata plus elements (tables, images, code blocks) out. The registry resolves by content type with a fallback chain — try the specialised parser, then a generic one, then the DLQ. Because the interface is uniform, adding a format is one file and one registration, and the pipeline never grows a if content_type == … chain.

At production scale

Parsers are where third-party libraries crash on real-world files. Run parsing with a timeout and a memory cap, and treat a parser exception as a document-level failure, never a pipeline-level one. Keep a corpus of nasty real documents as a regression suite — every parser bug you fix should add a file to it.

Failure modes

  • Parser hangs. A malformed file that loops forever; timeouts are mandatory.
  • Metadata dropped. A parser that returns only text discards the structure chunking needs.
  • Silent empties. Success with zero characters — assert against it.

Choose it when

  • More than one format — so, immediately.

Formats

PDF ingestion

The hardest common format: a page-description language with no semantic structure, three distinct sub-cases (digital text, scanned images, hybrid), and tables that are just lines and glyphs.

Mechanism

Detect the sub-case first. Digital PDFs have an extractable text layer, but reading order is not guaranteed — multi-column layouts need geometric reconstruction from character positions. Scanned PDFs have no text and must go to OCR. Hybrid documents have both, page by page, and must be handled per page rather than per document.

Layout-aware extraction is what separates usable PDF ingestion from garbage: headers and footers identified and dropped, columns ordered correctly, tables extracted as structures, figure captions kept with their figures, page numbers preserved for citation.

Worked example

annual-report.pdf, 84 pages
 pages 1-2    cover + contents      → dropped (low information)
 pages 3-61   two-column prose      → column-ordered, headers/footers stripped

naive extraction on the same file interleaves the two columns line by line

At production scale

PDFs will be the majority of enterprise ingestion volume and the majority of your ingestion bugs. Budget for it: keep per-page metadata (a citation to "page 47" is worth far more than one to "the document"), handle hybrid documents per page, and measure extracted-characters-per-page as a health metric — a drop signals a parser or upstream change.

Tables are the highest-value and hardest part. A financial table flattened into prose is worse than absent, because it produces confidently wrong numbers.

Failure modes

  • Column interleaving. Text that is technically extracted and semantically ruined.
  • Missed scanned pages. A hybrid document treated as digital loses the appendix.
  • Table flattening. Rows and columns collapsed; numbers attach to the wrong labels.
  • Header/footer pollution. The same company name in every chunk dominates retrieval.

Choose it when

  • Any enterprise corpus. Invest here first — it has the highest ratio of quality gained to effort spent.

DOCX and Office formats

Structurally far kinder than PDF — real heading hierarchies, real tables, real comments — and the trap is ingesting the parts you should not: tracked changes, hidden text, and speaker notes.

Mechanism

Office files are zipped XML with explicit semantics, so extraction can recover a heading tree, tables as tables, footnotes, and comments. That makes heading-based chunking accurate rather than heuristic. The judgement calls are about inclusion: tracked changes and deleted text may be confidential or simply wrong; comments are often the most useful content in a draft; hidden slides and speaker notes frequently contain internal commentary never meant for wider circulation.

At production scale

Decide the inclusion policy explicitly and record it, because it is a governance question: an organisation may be perfectly happy indexing comments internally and horrified to find them surfacing in a customer-facing agent. Default to excluding tracked deletions and hidden content, and make inclusion an opt-in per collection.

Failure modes

  • Deleted text indexed. The agent quotes a clause the legal team removed.
  • Formulas as content. "=SUM(B2:B40)" retrieved as a number.
  • Merged-cell tables. Header/value misalignment.
  • Password-protected files. Fail clearly to the DLQ; do not index the error message.

Choose it when

  • Any corpus with authored documents — usually the highest-quality material you have.

Markdown and plain text

The easiest format and the one most worth chunking well, because the heading structure is already a semantic outline the author wrote for you.

Mechanism

Parse the heading hierarchy and use it directly as chunk boundaries, carrying the full heading path into chunk metadata. Preserve code fences intact — splitting a code block is always wrong — and keep tables and lists whole. For plain text with no structure, fall back to token-aware or semantic chunking.

At production scale

Markdown corpora (runbooks, wikis, docs sites, READMEs) are usually the highest-signal content in an organisation and the cheapest to ingest well. Heading paths in metadata double as navigation and as filter fields; they are worth preserving even when the chunker does not need them.

Failure modes

  • Split code fences. Half a command is worse than none.
  • Giant sections. One H2 with 8,000 tokens still needs sub-splitting.
  • Lost heading context. A chunk that says "run the second command" with no path.

Choose it when

  • Always available; start your knowledge base here.

HTML and web pages

Nine tenths of a web page is not content — navigation, cookie banners, footers, related links. Boilerplate removal is the whole job, and untrusted-input handling is the whole risk.

Mechanism

Extract the main content region (readability-style heuristics or explicit selectors), convert surviving structure to markdown-like text so headings and lists persist, resolve relative links, and strip scripts and styles. For crawling, respect robots directives, bound depth and page count, and stay within an allowlist for anything that feeds an agent's answer.

Everything fetched from the web is attacker-controlled input. It must be scanned for injection and labelled untrusted before it becomes a chunk or a memory.

At production scale

Web content changes and you will re-crawl. Hash the extracted content, not the raw HTML — otherwise a rotating ad slot or a timestamp makes every page look changed and you pay to re-embed the web weekly.

Keep external content in its own collection. Mixing authoritative internal docs with scraped pages in one collection makes it impossible to reason about trust at query time.

Failure modes

  • Boilerplate indexed. Cookie-banner text retrieved as policy.
  • SPA with no server HTML. Empty extraction; needs a rendering fetch (chapter 15).
  • Injection via page content. The main reason to keep this content labelled and scanned.
  • Crawl runaway. Bound depth, count and time.

Choose it when

  • Public knowledge matters and you accept the trust cost.
  • Avoid crawling as a substitute for a real integration.

Code ingestion

Chunk on the syntax tree, keep symbol metadata, index by revision, and scan for secrets before anything is stored.

Mechanism

Parse to an AST and emit one chunk per function, method or class, with the enclosing signature and module imports attached as context. Metadata carries language, path, symbol name, and revision. Secret scanning runs before indexing — an index is a search engine over your repository, and a leaked credential in git history becomes trivially findable by every agent in the tenant.

 chunk 2  class WebhookHandler                 + docstring
 chunk 3  def handle(self, event)              + enclosing class signature

At production scale

Index by revision and re-index on merge. An agent reasoning about main with a two-week-old index gives confidently stale answers about code that no longer exists, and it is very hard to debug because the answer looks plausible.

Keep code in its own collection with its own embedding model. Code and prose in one index degrade each other measurably.

Failure modes

  • Prose chunker on code. Meaningless chunks; the single most common mistake.
  • Secrets indexed. Scan first, always.
  • Vendored dependencies. 200k chunks of node_modules drowning your own code. Exclude aggressively.
  • Stale index. Re-index on merge, not weekly.

Choose it when

  • Agents answer questions about or modify code.

CSV, JSON, and columnar data

Rows are not prose. Either summarise the table into text worth embedding, or keep it as data and let the agent query it with code — but do not embed ten thousand rows one at a time.

Mechanism

Three viable strategies, chosen by shape. Schema + sample: embed a description of the table (columns, types, ranges, a few example rows) so the agent knows it exists and what it contains, then answer questions with code execution against the real file. Row grouping: for small tables, serialise groups of rows as labelled text. Path flattening: for JSON, emit path: value lines so nested structure survives embedding.

The anti-pattern is embedding each row separately: 50,000 near-identical vectors that answer "find me a row like this" and nothing else.

At production scale

The schema-plus-code-execution pattern is the correct default for tabular data and it is dramatically cheaper and more accurate than embedding rows. It also changes the security posture: the data stays in its store, and the agent gets a query capability rather than a copy.

For database connectors, sync summaries and schemas rather than table contents unless the table is genuinely small and genuinely textual.

Failure modes

  • Row-per-vector. Expensive, useless, and hard to undo.
  • Lost headers. Values with no column names.
  • Type loss. Dates and numbers as strings, so no comparison works.
  • Whole-warehouse ingestion. Ingest the schema, query the data.

Choose it when

  • Agents answer analytical questions — use schema plus execution.
  • Do not embed large tables row-wise.

Image ingestion

Three extractions per image, and you usually want all three: OCR for text in the image, a vision-model caption for what it depicts, and the surrounding document context.

Mechanism

Route by image content: photographs and diagrams get a vision-model description; screenshots and scans get OCR; charts benefit from both plus, ideally, data extraction. The caption or transcript is what gets embedded (text vectors are more useful than image vectors for most retrieval), while the image itself is stored as an artifact by reference and linked from the chunk.

  • OCR on photographs. Garbage text embedded as content.
  • Lost linkage. A caption with no reference back to the image or its page.

Choose it when

  • Documents carry meaning in diagrams, screenshots or scans.
  • Skip for decorative imagery.

Audio ingestion

Transcribe, then treat the transcript as a timestamped document — the timestamps are the feature, because they let a citation point at a moment.

Mechanism

Speech-to-text produces text plus word or segment timing, and ideally speaker labels. Chunk on timestamp windows with overlap, keep the time range in metadata, and preserve speaker attribution where diarisation is available. A citation then resolves to "call recording, 14:32–15:05", which is far more useful than "the recording".

At production scale

Transcription is priced per minute and is the dominant cost of audio ingestion, so gate it by value: transcribe customer calls and meetings, not every voicemail. Recordings are also among the most regulated data you will hold — consent, retention and residency all apply, and a transcript inherits every obligation of the recording.

Failure modes

  • No timestamps. A wall of text with no way to cite a moment.
  • Missing diarisation. Customer statements attributed to the rep.
  • Accent and jargon errors. Domain terms mangled; supply a vocabulary hint where the provider supports it.
  • Consent gaps. Ingesting a recording you had no right to process.

Choose it when

  • Calls and meetings hold knowledge nobody wrote down — which is most organisations.

Video ingestion

Audio track plus sampled frames plus scene boundaries — three streams that must stay aligned on a single timeline.

Mechanism

Extract and transcribe the audio, detect scene changes, sample a keyframe per scene, and caption or OCR those frames. Chunk by scene so that each chunk has both the words spoken and a description of what was on screen. On-screen text is often the highest-value content in a demo or a tutorial, and it exists only in the frames.

At production scale

Video is the most expensive modality per minute of content and usually the least queried — sample frames sparsely (one per scene, not one per second) and prefer existing captions when the source provides them. Where a video has an accompanying document, ingest the document first; it is almost always better value.

Failure modes

  • Frame flood. One frame per second at 30 minutes is 1,800 vision calls.
  • Timeline drift. Frames and transcript misaligned, so citations point at the wrong moment.
  • Ignored on-screen text. The actual answer, discarded.

Choose it when

  • Training material, demos, or recorded walkthroughs are the knowledge.
  • Skip when a written equivalent exists.

Email ingestion

Threads, not messages — plus quoted-reply explosion, attachments that are the real content, and the highest PII density of any source you will ingest.

Mechanism

Reconstruct threads from message ids and references, strip quoted history (or a ten-message thread indexes the first message ten times), extract and separately ingest attachments, and normalise the header metadata that makes email searchable: participants, dates, subject, direction. Signature blocks should be stripped for the same reason as boilerplate.

In AgentVerse

  • app/ingestion/parsers/email_parser.pyparsing, threading, quote stripping
  • app/ingestion/connectors/email_imap_connector.pyIMAP acquisition
  • app/integrations/email/imap_listener.pylive inbound mail
  • app/gateway/channels/email.pyemail as an interaction channel (chapter 27)

Worked example

thread "Re: Re: Re: Contract renewal" — 11 messages
 naive   11 documents, message 1 quoted 10 times → 10× duplicate content
 threaded 1 document with 11 turns, quotes stripped, participants normalised
 attachments  renewal-v3.pdf → ingested separately, linked to the thread
 PII      6 personal emails, 2 phone numbers → redacted at stage 6

At production schedule

Email is where ingestion meets privacy law hardest. Default to excluding personal mailboxes, ingest shared or role mailboxes only, apply the shortest defensible retention, and expect data-subject requests to hit this source first. The technical work is easy; the policy work is not, and it should precede the integration.

Failure modes

  • Quote duplication. Retrieval dominated by the same quoted paragraph.
  • Broken threading. Non-compliant clients that drop references.
  • Attachments ignored. The contract was the point, not the covering note.
  • Over-collection. Ingesting mailboxes you have no basis to process.

Choose it when

  • Shared mailboxes hold operational knowledge.
  • Avoid personal mailboxes without an explicit legal basis.

SaaS sources with real quirks

GitHub ingestion

Four different content types behind one API — code, pull requests, issues, and CI results — each wanting a different chunking and freshness policy.

Mechanism

Code is AST-chunked and indexed by revision. Pull requests are threaded discussions plus a diff — the review conversation is often more valuable than the code. Issues are threads. Releases and CI runs are events. Sync incrementally by updated_at, exclude vendored paths and generated files, and respect the API's rate limits, which are the practical constraint on large organisations.

  • app/ingestion/connectors/github_connector.pythe connector
  • app/knowledge/ingestors/github_ingestor.pyrepository-level ingestion
  • app/ingestion/repository_security.pysecret scanning
  • app/mcp/servers/GitHub also appears as an MCP tool surface for live actions

Note the distinction: ingestion makes the repository searchable; the MCP connector makes it actionable. Agents usually need both.

Worked example

            excluded: node_modules, dist, *.lock, generated/

At production scale

The PR discussion corpus is the most under-appreciated knowledge source in engineering organisations: it records why, which neither the code nor the docs contain. Ingest it.

Rate limits force prioritisation: sync default branches frequently, other branches rarely, and archived repositories once.

Failure modes

  • Vendored code flood. Dependencies outnumbering your source ten to one.
  • Secrets in history. Scan, and remember that history is searchable too.
  • Rate-limit exhaustion. One large org sync starving every other source.
  • Private-repo leakage. A connector with broad scope indexing repositories the collection's readers should not see.

Choose it when

  • Engineering agents, code questions, or change-history questions.

Jira ingestion

Issues are threads with custom fields, and the custom fields are where each organisation's real process lives — so a generic mapping loses the point.

Mechanism

Each issue becomes a document: summary and description as content, comments as thread turns, and fields — status, assignee, sprint, epic, labels, and the tenant's custom fields — as metadata. Links between issues (blocks, relates-to, duplicates) are relationship data, which is exactly what the knowledge graph wants. Sync incrementally with JQL on updated.

In AgentVerse

  • app/ingestion/connectors/jira_connector.pythe connector
  • app/knowledge/ingestors/jira_ingestor.pyissue ingestion

At production scale

Ticket corpora are large and mostly low-signal. Filter by project and recency rather than ingesting a decade of closed tickets.

  • Comment order lost. A thread that reads as contradictory.

Choose it when

  • Agents answer "what is the status of", "who is working on", or "why did we do this".

Confluence ingestion

A page tree with macros, restrictions and heavy staleness — the richest internal corpus most organisations have, and the one that most needs a freshness signal.

Mechanism

Pages become documents; the space and ancestor path become metadata (and natural filter fields); storage-format XML is converted to text with headings preserved. Macros need decisions: an included page should not be duplicated, a Jira macro should become a reference rather than text, a code macro should be preserved verbatim. Page restrictions must be read and honoured — Confluence permissions are per-page and do not follow the space.

At production scale

Wikis rot, and stale wiki content is the most common cause of confidently wrong agent answers. Ingest last_updated and use it: down-rank or flag content older than a threshold, and surface "this page was last updated 3 years ago" in the citation.   • Macro duplication. Included pages indexed many times.

Slack ingestion

High volume, low signal per message, and organised as threads inside channels — plus the strongest privacy expectations of any source, because people speak informally.

Mechanism

Threads, not messages, are the unit: a thread is a conversation with an outcome, a single message is usually noise. Channel selection is the main quality lever — support and incident channels are valuable, social channels are not. Resolve user and channel mentions to names, keep reactions as weak signal (a checkmark often marks the resolution), and exclude DMs and private channels by default.

At production scale

Slack is the highest-volume and lowest-density source in most organisations — millions of messages, thousands of useful threads. Be aggressive: allowlist channels rather than excluding them, require a thread length threshold, and prefer resolved threads. Browser and RPA extraction

The last resort that is sometimes the only resort: drive a real browser, log in, and read the screen — for systems with no API and no export.

Mechanism

A browser session authenticates with vault-held credentials, navigates to the target, and extracts either the DOM (preferred — structured and cheap) or a screenshot for vision analysis (fallback). Selectors that worked are remembered so subsequent runs replay rather than re-analyse. Everything about it is brittle, so it needs artifact capture on every step to be debuggable at all.

At production scale

  • Never when an API exists.

Quality, safety, and failure

PII detection and redaction

Stage 6, before the embedder, by design: raw personal data must never leave the boundary in an API call to a third-party embedding provider.

Mechanism

Detect with deterministic patterns first — emails, phone numbers, IBANs, card numbers with a Luhn check, national identifiers, API keys — then optionally a model pass for names and addresses that patterns cannot catch. Redact, tokenise, or drop depending on policy, and record what was found as metadata so the document's sensitivity is known even after redaction.

The stage ordering is the control. Detection after embedding is theatre: the data has already been transmitted, and a vector derived from personal data is itself personal data.

In AgentVerse

  • app/ingestion/pipeline.pystage 6, before stage 10
  • app/data_classification/classifier.pydetection and classification
  • app/data_classification/redaction.pyredaction
  • app/governance/compliance_bundles.pyper-regime configuration (GDPR, DPDP, HIPAA, PCI)
  • app/api/dpdp.pydata-subject request surface

Worked example

parsed text
  "Contact Priya Sharma (priya@northwind.example, +91 98765 43210)
   regarding invoice INV-2024-8891. Card ending 4242, IBAN DE89 3704…"

detected  email · phone · IBAN · PAN-shaped (Luhn ok) · person name
redacted  "Contact [PERSON] ([EMAIL], [PHONE]) regarding invoice
           INV-2024-8891. Card [CARD_REDACTED], IBAN [IBAN_REDACTED]."
kept      the invoice number — a business identifier, not personal data
metadata  {pii_types:[email,phone,iban,card,name], classification:confidential}

At production scale

Over-redaction destroys utility: redacting invoice numbers, order ids and product codes makes the corpus unsearchable for the queries users actually have. Tune the detectors on your own data, keep business identifiers, and treat the classification metadata as the primary output — it is what lets retrieval enforce sensitivity later.

Regime configuration belongs in one place. A healthcare tenant and an e-commerce tenant need different rules, and hardcoding either is how you end up non-compliant for the other.

Failure modes

  • Redaction after embedding. The incident this stage exists to prevent.
  • Over-redaction. A corpus of placeholders.
  • PII in metadata. Redacted from the body, retained in the author field.
  • PII in the vector. Re-embed after redaction, never before.

Choose it when

  • Always, and before your first external embedding call.

The quality gate

Score the extracted document and drop what is not worth indexing — because a corpus of navigation menus and empty templates degrades every query.

Mechanism

A composite score over cheap signals: extracted character count, ratio of alphabetic to symbol characters (catches OCR garbage), duplicate-line ratio (catches boilerplate), language detection confidence, and information density. Below a threshold the document is skipped with a recorded reason rather than indexed.

Skipping must be visible. A silently dropped document is indistinguishable from a missing integration when a user complains the agent does not know something.

In AgentVerse

  • app/ingestion/quality_checks.pyQualityChecker (stage 7)
  • app/ingestion/pipeline.pyskip with reason and metric

Worked example

doc A  template.docx      42 chars after extraction     score 0.08  DROP
doc B  scan-blurry.pdf     OCR: "ffi1 lIlI 0O"          score 0.11  DROP → OCR review
doc C  nav-page.html       92% duplicate lines           score 0.19  DROP
doc D  policy.pdf          dense prose, 41k chars        score 0.86  PASS
metrics: quality_drop_total{reason="low_density"} etc., per source

At production scale

Watch the drop rate per source as a regression detector. A parser change or an upstream template update shows up here first, as a sudden cliff in pass rate — long before anyone notices worse answers. Set the threshold empirically on a sample and revisit it; too strict and you lose short but valid documents like FAQ entries.

Failure modes

  • Threshold too strict. Legitimate short documents dropped.
  • Invisible drops. No metric, no reason, no way to explain a gap.
  • Wrong signal for the format. Code and tables score badly on prose density metrics — gate per content type.

Choose it when

  • Any corpus you do not fully control — which is any real corpus.

Deduplication and hashing

Two dedup layers: document-level content hashing at stage 3 to avoid paying for unchanged work, and chunk-level dedup at stage 11 to stop boilerplate dominating retrieval.

Mechanism

Document hash: SHA-256 over normalised extracted content. Unchanged means skip everything downstream, including the paid embedding call. Chunk dedup: hash each chunk and drop exact repeats within and across documents, so the standard legal footer is indexed once rather than nine thousand times. Near-duplicate detection (embedding similarity above a high threshold) catches the cases hashing misses, at higher cost.

In AgentVerse

  • app/ingestion/pipeline.pystage 3 content hash, stage 11 chunk dedup
  • app/services/dedup.py, app/reliability/dedup.pythe platform's dedup primitives
  • app/rag/store.pyindex-level uniqueness

Worked example

nightly re-sync, 14,200 documents
 stage 3   13,980 unchanged → skipped   (0 parse, 0 embed, 0 index)
            220 changed → full pipeline
 saving    ~98% of the nightly embedding bill

stage 11 on 220 documents → 9,400 chunks
 dropped  1,180 exact-duplicate chunks (footers, disclaimers, headers)
 indexed  8,220

At production scale

Hash the normalised content, not the raw bytes: a PDF regenerated with a new creation timestamp is byte-different and content-identical, and hashing bytes makes your entire corpus look changed every night. Getting this wrong is the most expensive ingestion mistake there is.

Keep the hash on the document row so re-sync is a single indexed lookup rather than a re-parse.

Failure modes

  • Hashing volatile bytes. Timestamps, generation ids, rotating asset urls.
  • No chunk dedup. Boilerplate wins every generic query.
  • Over-aggressive near-dedup. Two genuinely different contract versions collapsed into one.

Choose it when

  • Always, at both levels.

Contextual enrichment

Stage 9 adds what the chunk cannot know about itself — its document's subject, its position in the structure, a one-line summary — so a retrieved fragment carries its own context.

Mechanism

A chunk that reads "the limit is 30 days" is nearly useless in isolation. Enrichment prepends or attaches context: the document title, the heading path, and optionally a generated sentence situating the chunk in the document. Cheap enrichment is deterministic (titles, paths, dates); expensive enrichment is a model call per chunk and should be reserved for corpora where it measurably helps.

In AgentVerse

  • app/rag/contextual_enricher.pythe enricher
  • app/ingestion/pipeline.py_enrich() at stage 9
  • app/rag/late_chunker.pylate chunking — embed with full context, then split

Worked example

raw chunk     "The limit is 30 days from delivery."
enriched      "[Refund policy › Standard refunds] The limit is 30 days from
               delivery."  (document: Acme Customer Policy, updated 2026-08)
effect        retrieval for "refund window" now matches strongly;
              the model answering from this chunk cannot mistake which limit

At production scale

Deterministic enrichment — titles and heading paths — is nearly free and reliably improves both retrieval and answer quality. Model-generated per-chunk context costs one call per chunk, which on a million-chunk corpus is a serious line item; measure the gain on your own eval set before enabling it broadly. Late chunking is the middle path: embed with surrounding context, then split, so context influences the vector without a per-chunk model call.

Failure modes

  • Enrichment dominating the chunk. A 40-token chunk with 120 tokens of preamble retrieves on the preamble.
  • Wrong context. An incorrect heading path is worse than none.
  • Cost blowout. Per-chunk model calls at corpus scale.

Choose it when

  • Chunks are small or the corpus is deeply structured.
  • Skip model-based enrichment until you have measured it.

Failure handling and reprocessing

Every document that does not make it must be classified, queued, retryable, and visible — otherwise your knowledge base has holes nobody can see.

Mechanism

Classify the failure — transient (network, throttle), format (unsupported, corrupt), policy (too large, quota, restricted), or systemic (embedder down) — and respond accordingly: transient retries with backoff, format goes to the DLQ for review, policy is recorded and skipped, systemic pauses the whole source rather than burning through documents. Reprocessing must be possible after a parser fix, which means the raw document (or a reference to it) has to be retrievable.

At production scale

The DLQ is a product surface, not a log. Tenants should be able to see "6 documents from your S3 source could not be processed, and why", because they are the only people who can fix a password-protected file. Systems that hide this create the worst support conversations in the category — a user certain the document exists, and an agent certain it does not.

Failure modes

  • Silent drops. The defining failure of bad ingestion.
  • Infinite retries. A corrupt document retried forever, blocking the source.
  • No reprocess path. A parser fix that cannot be applied retroactively.
  • Systemic failure treated as per-document. Burning the whole corpus through a dead embedder.

Choose it when

  • Always. This is the difference between a knowledge base and a hope.

What is missing here

  • Ingestion-time contradiction detection. Nothing notices that a new document contradicts an indexed one, which is the root of most "the AI gave two different answers".
  • Corpus coverage measurement. There is no metric for "what fraction of the questions users ask is this corpus able to answer" — the gap that drives every knowledge roadmap.
  • Incremental re-chunking. Changing a chunking strategy means re-ingesting the collection; there is no way to re-chunk from stored parsed text without re-fetching.
  • Permission mirroring. Source-side ACLs (Confluence page restrictions, Jira project roles, SharePoint permissions) are honoured at ingest time but not continuously reconciled — a document that becomes restricted upstream stays indexed.
  • Agent-generated connectors as a first-class flow. The seam exists; the review, testing and promotion path for a connector an agent wrote does not.
