Orientation

Embeddings are the boring infrastructure that everything semantic rests on, and they have one property that makes them operationally unlike anything else in the platform: they are only comparable to embeddings from the same model. A vector is not data you can migrate — it is a measurement in a coordinate system that exists only inside one model version.

Everything difficult about embeddings follows from that: dimension policy, index compatibility, drift monitoring, and the re-embedding migration that nobody budgets for and everybody eventually performs.

The embedding subsystem

Provider abstraction

One interface for every embedding backend, so the model is configuration and the calling code never knows which vendor answered.

Mechanism

A typed request carries texts, a model identifier, and an input type (query versus document, which several models distinguish); the response carries vectors, the model actually used, the dimension, and token usage for cost accounting. Providers are resolved from environment configuration at startup, with a deterministic fake for tests and key-less environments.

Reporting the model and dimension in the response rather than assuming them from the request is what makes the rest of the subsystem honest — a provider that silently serves a different version is detectable.

EmbedRequest

At production scale

Vendor neutrality here is not idealism: embedding providers deprecate models, change pricing, and have outages, and your entire index is denominated in one of their models. The abstraction is what makes a migration a project rather than a rewrite.

The deterministic fake earns its keep daily — it lets the whole retrieval stack run in CI with no keys and no network, which is why tests can cover retrieval at all.

Failure modes

  • Leaky abstraction. Vendor-specific parameters reaching calling code, so switching means editing twenty files.
  • Assumed dimension. Hardcoding 1536 and discovering a provider returns 1024.
  • Ignored input type. Embedding queries as documents on models that distinguish them costs measurable recall.

Choose it when

  • Always. Even single-vendor deployments need it for testing.

Model registry

A catalogue of every embedding model the platform knows: dimension, max input, cost per million tokens, modality, and whether it is available in this deployment.

Mechanism

The registry answers questions the router and the policies need: how many dimensions does this model produce, what is its token limit, what does it cost, what content types does it handle, and is it currently reachable. Without a registry these facts get hardcoded at call sites and drift apart.

  • Stale entries. A deprecated model still offered; requests fail at the provider.
  • Missing limits. Silent truncation at the max input length.
  • Hardcoded dimensions elsewhere. The registry becomes advisory rather than authoritative.

Choose it when

  • More than one embedding model — which happens as soon as you index code.

Embedding router

Pick the model from the content and the context: code goes to a code model, prose to a text model, a free-tier tenant to the cheap model, an image to a multimodal one.

Mechanism

Inputs: content type, tenant plan, collection configuration, language, and the target index's existing dimension. Output: a model choice with a recorded reason. The hard constraint is the last input — if the collection's index is 1536-dimensional, the router cannot select a 3072-dimensional model regardless of what else it would prefer.

At production scale

Routing by plan is a real cost lever — the small text model is roughly a sixth the price of the large one and adequate for many collections — but it is a per-collection decision, not a per-chunk one. Switching models mid-collection produces an index whose vectors cannot be compared with each other.

Failure modes

  • Mid-collection model switch. The worst outcome in this chapter: an index of mutually incomparable vectors.
  • Query routed differently from documents. Search silently returns noise.
  • Unrecorded reason. Nobody can explain why one collection performs worse.

Choose it when

  • You index more than one content type or serve more than one plan tier.

Embedding orchestrator

The component that actually gets vectors: selects a model, batches the texts, retries and falls back on failure, and returns a result that names the model used.

Mechanism

Three operations. select() resolves the model against registry and dimension policy. embed_batch() groups texts into provider-sized batches — the single biggest throughput lever, since per-call overhead dominates on small texts. embed_with_fallback() handles provider failure by retrying, then trying an alternative model, but only one whose dimension matches the target index.

Worked example

142 chunks to embed, target index dim 3072

select        3-large (3072)  ✓ compatible
batch         142 → 2 calls of 96 and 46 (provider limit 96)
call 1        ok, 1.2s
call 2        429 rate limited → backoff 2s → ok
result        BatchEmbeddingResult{vectors:142, model:"3-large",
                                   dim:3072, tokens:58204, retries:1}

alternate scenario: provider down entirely
  fallback candidates: bge-m3 (1024) → REJECTED, dimension mismatch
  → the batch fails and goes to the DLQ, rather than corrupting the index

At production scale

Batching is not an optimisation, it is the difference between a corpus that ingests in an hour and one that takes a day. Beyond that, the orchestrator is where per-tenant embedding rate limits belong: one tenant's backfill must not exhaust the shared provider quota and stall every other tenant's ingestion.

The "fail rather than write incompatible vectors" rule is worth being strict about. A DLQ entry is recoverable; a mixed-dimension index is a re-ingestion.

Failure modes

  • Unbatched embedding. One call per chunk; 100× the wall-clock.
  • Fallback across dimensions. Index corruption dressed as resilience.
  • No per-tenant quota. A noisy backfill starves everyone.
  • Partial batch loss. Some vectors written, some not; make the write idempotent per chunk.

Choose it when

  • Any real ingestion volume.

Dimensions and index compatibility

Dimension is a hard contract between a model and an index. Mismatches are not degradations — they are either errors or, far worse, silently meaningless results.

Mechanism

A vector column has a fixed width. Writing a differently-sized vector fails; comparing vectors from two models of the same width succeeds numerically and means nothing. A dimension policy therefore has to enforce three rules: a collection has one model, a query must use that model, and a model change requires a new index rather than a new write path.

Some model families support dimension truncation (Matryoshka-style), where a 3072-dimensional model can emit 1024 usable dimensions. That is a legitimate way to trade quality for storage — but it must be recorded per row, because a truncated vector is a different measurement from a full one.

Worked example

collection acme/policies — index dim 3072, model 3-large

request to embed with 3-small (1536)
  → DimensionPolicy: INCOMPATIBLE. Options:
     a) use 3-large for this collection
     b) create a new collection with a 1536 index
     c) truncate 3-large to 1536 and re-embed the whole collection
  → never: write 1536 vectors into a 3072 index

the silent-failure version, which the policy prevents:
  two models that both emit 1024 dims, mixed in one index —
  cosine similarity computes fine and ranks randomly

At production scale

Store the model and dimension on every row. It costs a few bytes and it is the only way to detect that part of a collection was embedded with something else — which does happen, usually via a well-meaning backfill script.

Dimension choice is a storage decision too: 3072 floats per chunk is 12KB before indexing, so a million chunks is roughly 12GB of vectors plus index overhead. Truncation to 1024 is often the right call for large corpora with modest quality loss — but measure it rather than assuming.

Failure modes

  • Mixed models, same dimension. The silent killer.
  • Query/document model divergence. Retrieval returns plausible nonsense.
  • Untracked truncation. Half the collection at 1024, half at 3072-truncated-to-1024, with no record.

Choose it when

  • Always, from the first vector you write.

Text embeddings

The default case, with two details that matter more than model choice: query/document asymmetry, and normalisation.

Mechanism

Several model families are trained asymmetrically — documents and queries are embedded with different prefixes or input types, because a question and its answer are not the same kind of text. Using the document mode for queries measurably lowers recall, and it is invisible unless you test for it.

Normalisation matters for the distance metric: if vectors are L2-normalised, cosine similarity and inner product are equivalent and cheaper; if they are not, mixing metrics produces wrong ranking. Pick one convention and enforce it at write time.

  documents as "document", queries as "query"     recall@5  0.91

At production scale

Write a test that asserts the query path and the document path use the same model and the correct input types. It is a five-line test that prevents the most expensive class of silent regression in the retrieval stack.

Failure modes

  • Wrong input type. Silent recall loss.
  • Mixed normalisation. Some vectors normalised, some not.
  • Truncation at the token limit. Long chunks silently cut; the tail is never searchable.

Choose it when

  • The default for prose. Verify the asymmetry handling once and forget it.

Code embeddings

Code-trained models understand identifier structure, syntax and call relationships that a prose model reads as noise — and they need their own collection.

Mechanism

A prose model sees getUserById as an unusual word; a code model relates it to fetch_user, findUser and the concept of a lookup by identifier. Code models also tolerate the token density of source files better and often support longer inputs, which matters because a function is not divisible.

Because the model differs, the collection must differ: one index cannot hold vectors from two models.

At production scale

Worth the extra collection whenever agents work on code. The measurable gain is on identifier-shaped queries, which is what developers actually ask. Keep the revision in metadata so retrieval can be pinned to a commit.

  • Code in the prose collection. Both corpora get worse.
  • Mixed languages in one index. Usually fine, but measure if one language dominates.
  • Long files truncated. Respect the model's input limit at chunk time.

Choose it when

Multimodal embeddings

One vector space for text and images, so a text query can retrieve a picture — powerful where it applies, and often beaten by captioning plus text embedding.

Mechanism

A jointly-trained model maps images and text into a shared space, enabling cross-modal retrieval without an intermediate caption. The alternative — caption the image with a vision model, then embed the caption as text — is usually cheaper, more explainable and easier to debug, at the cost of losing detail the caption did not mention.

At production scale

  • Separate index sprawl. Joint embeddings need their own collection and their own dimension.
  • Caption blind spots. Details omitted from the caption are unsearchable.
  • Cost per image. Both routes are metered per asset.

Choose it when

  • Visual search is the product.
  • Otherwise caption and embed as text.

Embedding fallbacks

Providers fail, and the correct response depends on which side you are on: a query can degrade to lexical search, but an index write cannot degrade to a different model.

Mechanism

Two asymmetric paths. On the query side, if the embedder is unavailable, fall back to lexical retrieval (BM25 plus trigram) and mark the result as degraded — worse than hybrid, far better than an error. On the index side, only a dimension-compatible model may substitute; otherwise queue the work and retry, because writing incompatible vectors is unrecoverable.

A circuit breaker in front of the provider stops the retry storm and makes the degradation immediate rather than after thirty seconds of timeouts.

Worked example

embedding provider returns 503 for 90 seconds

query path    breaker opens after 5 failures
              → BM25 + trigram only, response flagged degraded
              → recall drops from 0.91 to ~0.68 — acceptable for 90s
index path    batches queued, not written
              → resume on breaker close, hash gate makes the retry cheap

At production scale

Surface the degradation. A user who is told "semantic search is temporarily unavailable, showing keyword results" behaves completely differently from one who silently gets worse answers and concludes the product is bad.

Self-hosted embedding models are a legitimate fallback tier for exactly this reason: they are slower and slightly worse, and they are yours.

Failure modes

  • Dimension-incompatible fallback. Index corruption.
  • Silent degradation. Users blame the product.
  • Retry storms. No breaker; the provider outage becomes your outage.

Choose it when

  • Always — the embedder is an external dependency on the hot path.

Tenant plan and cost constraints

Embedding is metered per token, and ingestion is bursty — so the plan tier has to bound both the model choice and the throughput.

Mechanism

Three controls. Model choice by plan (small model for free tiers). Throughput limits per tenant, so one backfill cannot consume the shared provider quota. And a spend ceiling that pauses ingestion rather than producing a surprise invoice. All three need the token counts from the provider response, which is why usage is part of the contract.

  • Plan enforced only at the API. Background jobs bypassing the check.

Drift detection

Providers update models without changing the name. Drift monitoring catches it by re-embedding fixed probe texts and comparing against their stored vectors.

Mechanism

Keep a set of probe texts whose vectors were stored at a known time. Periodically re-embed them and compute cosine similarity against the stored versions. Identical models produce near-1.0 similarity; anything materially lower means the model behind the name changed, and your index is now partly denominated in a different measurement. Severity grades the response: log, alert, or halt writes and schedule a re-embed.

Worked example

probe set: 50 fixed sentences, vectors stored 2026-04-01

weekly check
 2026-08-30   mean cosine vs stored 0.9998   → none
 2026-09-06   mean cosine vs stored 0.9421   → MODERATE
               provider changed the model behind the same name
 response     alert; freeze new writes to affected collections;
              schedule shadow re-embed; compare retrieval quality
              on the eval set before and after

At production scale

This is one of those controls nobody builds until it bites them. The failure it prevents is particularly nasty: retrieval quality degrades gradually as newly-embedded documents become incomparable with older ones, and nothing errors. Fifty probe texts checked weekly is a negligible cost for catching it.

Pin model versions explicitly wherever the provider allows it. Version pinning is the actual fix; drift monitoring is how you find out the pin was not honoured.

Failure modes

  • No monitoring. Silent, gradual quality loss.
  • Probes too few or too similar. Weak signal; use varied text.
  • Alert with no policy. A drift alarm nobody knows how to respond to.

Choose it when

  • Any hosted embedding provider — which is most deployments.

Re-embedding and migration

The migration everyone eventually performs: build a shadow index with the new model, validate it against evals, then cut over — never edit in place.

Mechanism

Four triggers: model deprecation, a materially better model, a dimension change, or detected drift. The procedure is the same each time and it is a dual-write pattern, not an update:

  1. Create a new index (new column or new collection) with the target dimension.
  2. Backfill in batches, tracking progress, with the hash gate preventing redundant work.
  3. Dual-write new documents to both indexes during the transition.
  4. Compare retrieval quality on a labelled set — old versus new, same queries.
  5. Cut queries over; keep the old index until confidence is established; then drop it.

Worked example

migrate acme/policies: 3-small (1536) → 3-large (3072)
 corpus     412k chunks · 168M tokens · ≈$22 · ≈6h at the throughput cap
 shadow     new 3072 column, backfill in 2k batches, resumable
 dual-write for 6 days while backfill runs

At production scale

Budget re-embedding as a recurring cost, not a one-off: over a few years you will do it more than once. The two things that make it survivable are per-row model tags (so you know what is migrated) and a labelled eval set (so cutover is a measurement, not a hope).

Never migrate without the comparison. A newer, more expensive model is not automatically better on your corpus, and the only way to know is to run both.

Failure modes

  • In-place re-embedding. No rollback, and a half-migrated index that ranks randomly.
  • No dual-write. Documents ingested during the migration are missing from one index.
  • Unvalidated cutover. A quality regression discovered by users.
  • Forgotten dependants. Semantic caches, memory embeddings and precomputed indexes that also need migrating.

Choose it when

  • Model deprecation, drift, or a measured quality opportunity. Plan it before you need it.

Embedding caches

The same text gets embedded over and over — repeated queries, boilerplate chunks, re-ingested documents. Cache by content hash and model.

Mechanism

Key on (normalised text hash, model, input type) and store the vector. Query-side caching is the highest-hit case in a chat product, where the same questions recur constantly. Document-side caching catches boilerplate and re-ingestion. The cache key must include the model, or a model change serves stale vectors from the old space.

At production scale

Query-side embedding cache hit rates of 30–50% are normal on support workloads, and each hit removes a network round trip from the user's latency path as well as a metered call. Keep the cache per tenant or key it with the tenant — embeddings themselves are not secret, but a shared cache is a shared side channel and not worth the argument.

Failure modes

  • Model not in the key. Stale vectors from a previous model.
  • No normalisation. Whitespace differences causing misses.
  • Unbounded growth. Cache every chunk forever; use TTL and size limits.

Choose it when

  • Repetitive query distribution, or boilerplate-heavy corpora — both are common.

Evaluating an embedding model

Benchmark rankings do not predict performance on your corpus. Measure recall on your own labelled queries before you commit an index to a model.

Mechanism

Take 100–200 real queries with known correct passages. For each candidate model, embed the corpus (or a representative sample), run the queries, and record recall@k, MRR, and the cost and latency. Include the incumbent as the control and a lexical-only baseline as the floor — occasionally the floor wins on a particular corpus, which is worth knowing before spending on vectors.

At production scale

This table is worth building once per corpus type, because the answer is genuinely corpus-dependent — domain jargon, document length and language mix all move it. Failure modes

  • Choosing by leaderboard. Public benchmarks are not your corpus.
  • Ignoring the lexical baseline. Sometimes you are paying for vectors you do not need.
  • Evaluating on synthetic queries. They are easier than real ones and flatter every model.

Choose it when

  • Before committing a corpus to a model, and before any migration.

What is missing here

  • A one-command model bake-off. The evaluation components exist but not the workflow that produces the comparison table above for a given collection.
  • Automated migration orchestration. The re-embedding policy describes what to do; a managed shadow-index-and-cutover job with progress and rollback is not there.
  • Native multimodal embedding. Routing seam present, production path is caption-then-embed.
  • Quantisation and compression. No support for int8 or binary quantisation, which is the standard way to cut vector storage 4–32× at modest recall cost.
  • Fine-tuned domain embeddings. No path to adapt an embedding model on tenant data, which is where the remaining recall usually lives.
