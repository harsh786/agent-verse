Orientation

An agent platform that does not improve is a depreciating asset: models change, corpora rot, connectors drift, and the workload shifts under you. Improvement is the closed loop that turns production signal into shipped change — and the only reason it works is that every link in the loop is a measurement rather than an opinion.

The loop has five links, and most teams are missing the last two: signal (evals and production telemetry) → diagnosis (which dimension is failing, and why) → candidate change (a new prompt, model, retrieval strategy, or memory) → experiment (control versus candidate on real traffic) → promotion or rollback (gated by a regression check).

The improvement loop

Eval-driven improvement

Change nothing without a measurement that would have caught the change being wrong. The eval set is the specification; the improvement is a hypothesis about it.

Mechanism

A runtime scorecard aggregates per-dimension scores across recent production runs and offline suites: goal success, grounding, tool relevance, safety, latency, cost. The improvement engine reads the scorecard, identifies the weakest dimension with enough volume to be meaningful, and proposes a change targeted at it. Every proposal names its target metric and its expected direction, so the experiment has a falsifiable prediction.

Worked example

scorecard, agent fin-ops, last 14 days (n=1,840 goals)
 goal success   0.87   ▲ baseline 0.85
 grounding      0.71   ▼ baseline 0.82   ← weakest, and moved
 tool relevance 0.93

 p95 latency    41s    ▲ 33s

diagnosis  grounding regression concentrated in goals touching the
           "vendor-contracts" collection (0.44 vs 0.79 elsewhere)
proposal   that collection was re-chunked with fixed@v1 on 08-24;
           re-chunk with heading@v3. Target: grounding ≥ 0.80.

At production scale

The scorecard has to be sliced — by agent, by goal class, by collection, by tenant cohort — or regressions hide in aggregates. The example above is the common shape: a metric that moved four points overall because one slice moved thirty-five.

Run the loop on a cadence with a named owner. Improvement machinery that exists but is never run is the most expensive kind of unused code, because it looks like the problem is solved.

Failure modes

  • Aggregate-only scorecards. Regressions invisible until they are large.
  • Chasing noise. Acting on a dimension with 40 samples.
  • Unfalsifiable proposals. "Improve the prompt" with no target metric.
  • No cadence. The loop runs once, at launch.

Choose it when

  • You have production traffic and intend to change anything.

Prompt optimizer

Generate prompt candidates automatically from failure cases, score them on a held-out set, and promote only what wins — prompt engineering as search rather than intuition.

Mechanism

Take the failing cases for a role, ask a model to propose prompt revisions that would have handled them, then evaluate each candidate on a held-out set that includes both the failures and a regression set of previously-passing cases. The regression set is the essential half: a candidate that fixes ten failures and breaks fifteen passes is a loss, and without the regression set it looks like a win.

At production scale

Automated prompt search finds real wins, and it also finds prompts that are longer, slower and over-fitted to the failure set. Score candidates on cost and latency alongside quality, and cap prompt growth — a 40% longer verifier prompt applied to every step is a material cost increase.

Failure modes

  • No regression set. Fixing one class by breaking another.
  • Prompt bloat. Every iteration adds a clause and never removes one.
  • Overfitting to few cases. Thirty failures is not a distribution.
  • Promotion without an experiment. Offline wins that do not hold in production.

Choose it when

  • You have a labelled failure set and a regression set.
  • Not before you have both.

Self-optimizer

The component that proposes and, within bounds, applies changes on its own — model routing, retrieval strategy, iteration caps — under explicit limits and with a rollback path.

Mechanism

A bounded autonomy contract: the optimizer may adjust parameters within a declared range (model tier within a plan's allowed set, retrieval strategy among certified ones, iteration cap within limits), must run each change as an experiment, and must roll back automatically on regression. Anything outside the range becomes a proposal for a human.

The distinction that keeps this safe: it tunes parameters, it does not rewrite policy. It can route a goal class to a cheaper model; it cannot switch off an approval gate.

 observation  goal class "ticket summary" — success 0.96 on the large model

At production scale

Bounded self-optimisation is genuinely valuable for cost: routing decisions are exactly the kind of parameter that benefits from continuous measurement and that humans never revisit. Keep the bounds narrow, keep every change in an audit log, and keep rollback one command away.

The failure to guard against is optimisation against a proxy: cost per goal falls beautifully if the agent stops trying, so cost changes must always be evaluated jointly with success.

Failure modes

  • Proxy optimisation. Cost down because quality down.
  • Unbounded autonomy. An optimizer that can change policy.
  • No rollback window. A change you cannot undo when the delayed effect appears.
  • Silent changes. Behaviour drifts with no audit trail.

Choose it when

  • Experiments, gates and audit are already working.
  • Never before them.

Lessons learned

The cheapest improvement mechanism there is: durable, scoped lessons extracted from failures, recalled at plan time — no retraining, no deployment.

Mechanism

Covered as a pattern in chapter 1 and a memory tier in chapter 3; here it is an improvement channel. Its properties as an improvement mechanism are unusual: it takes effect immediately, requires no release, is scoped per tenant, and degrades gracefully because a bad lesson can be quarantined. Its weakness is that it is invisible in code review — behaviour changes with no diff.

The discipline that makes it trustworthy: corroboration before promotion, effectiveness scoring after recall, and decay for lessons that stop helping.

Worked example

failure class "filing rejected: invalid HSN"  seen 4× in 9 days
lesson promoted (corroboration ≥ 2): validate HSN before filing
effect over the next 30 days
  filings attempted 214 · rejections 4 (1.9%) vs 11.2% before
  no deploy, no prompt change, no model change

At production scale

Because lessons change behaviour without a deploy, they need the same operational visibility as a release: a list of active lessons per agent, when each was promoted, and its measured effectiveness. The first time an agent behaves strangely and nobody can find a code change to blame, that list is what you will wish existed.

Failure modes

  • Invisible behaviour change. No inventory of active lessons.
  • Superstitions. Promotion without corroboration.
  • Unbounded accumulation. Hundreds of lessons, none decayed.

Choose it when

  • Failures repeat. Which they do.

Model selection improvement

Continuously re-measure which model is right for each role and goal class — the highest cost lever available, and the one that goes stale fastest.

Mechanism

Score each candidate model per role (planner, executor, verifier, judge) and per goal class on quality, latency and cost, then let the router use the measured table rather than a static configuration. Because new models arrive constantly and prices move, the table needs periodic refresh — a shadow-routing mode that scores a candidate on real traffic without serving its output is the cheapest way to keep it current.

At production scale

Verifiers and classifiers are where cheap models usually win, and where teams most often leave an expensive model running out of caution. Executors on complex tool work are where they usually lose. Measuring per role rather than globally typically finds a 40–70% cost reduction with no quality change.

Shadow routing is worth building. It lets you evaluate a new model on your real distribution in days rather than arguing about benchmarks.

Failure modes

  • Global model choice. One model for every role, chosen for the hardest case.
  • Stale table. Prices and models changed six months ago.
  • Quality judged by the incumbent. Circular evaluation.

Choose it when

  • Any deployment with real volume — this is usually the largest single cost win available.

Retrieval quality improvement

Most "the agent is wrong" reports are retrieval failures. Fixing retrieval is usually cheaper and more effective than any change to the loop.

Mechanism

Diagnose which of three failures occurred, because the fixes are unrelated. Recall failure: the answer is in the corpus but was not retrieved — fix chunking, widen candidates, add hybrid or fusion. Precision failure: retrieved but out-ranked — fix reranking or metadata filters. Coverage failure: not in the corpus at all — fix ingestion, which is a knowledge problem, not a retrieval one.

Distinguishing them requires labelled cases: for each failed answer, was the supporting passage present in the corpus, and was it in the candidate set?

Worked example

60 failed answers, triaged from traces
 recall failure     31   passage in corpus, not in top-200
                          → cause: fixed chunking split the section
                          → fix: heading chunker  → 27 of 31 resolved
 precision failure  14   passage retrieved at rank 40+
                          → fix: enable cross-encoder rerank → 12 resolved
 coverage failure   15   passage not in the corpus
                          → fix: the SharePoint source has been failing
                            for 11 days
one of these three is an ingestion incident, not a retrieval problem

At production scale

Build the triage into your support workflow: every "wrong answer" report should be classified into one of the three buckets before anyone touches a prompt. In most deployments the distribution is roughly half recall, a quarter precision, a quarter coverage — and only the middle quarter is what people usually try to fix.

Failure modes

  • Treating all failures as model failures. Prompt changes that cannot help.
  • No corpus-presence check. Cannot distinguish recall from coverage.
  • Fixing precision when recall is the problem. Reranking cannot recover what was never retrieved.

Choose it when

  • Any quality complaint about a retrieval-augmented agent — start here, not at the prompt.

Tool success feedback

Feed measured tool reliability back into selection and ranking, so the agent stops choosing the tool that fails 40% of the time.

Mechanism

Every tool call updates per-tenant statistics — success rate, latency, error classes — which feed the tool ranker, the trust store and the circuit breaker. Selection then prefers tools that work, and the planner can be told which capability is currently unreliable so it plans around it rather than through it.

This is pure telemetry: no model involved, immediate effect, and it fixes the most common visible failure (an agent retrying a broken integration).

Worked example

tenant acme, capability "fetch invoices"
 vendor-api.get_invoices   success 62%  p95 8.1s   trust 0.41
 vendor-csv.export         success 99%  p95 1.4s   trust 0.96
effect  ranker prefers CSV; planner told "vendor-api degraded"
result  goal success for invoice goals 0.79 → 0.94, no prompt change

At production scale

Scope statistics per tenant. A connector healthy for one customer is often broken for another — their credentials, their quota, their network — and a global average hides both. Use a decaying window so a tool fixed last week can recover its ranking.

Failure modes

  • Global averages. Tenant-specific breakage invisible.
  • No recovery path. A once-broken tool ranked last forever.
  • Cold start. New tools never chosen; reserve exploration.

Choose it when

  • More than a handful of tools, or any third-party integration.

Cost and latency optimisation

Both are measurable, both have a small number of dominant causes, and both improve without touching quality if you attack the right ones.

Mechanism

Cost per goal decomposes into iterations × tokens per iteration × price per token. Attack in that order: reduce iterations (better planning, lessons, stall detection), then tokens (narrow tool schemas, tighter retrieval, compression), then price (cheaper models per role). Latency decomposes into serial model calls, tool round-trips, and retrieval — attack with parallelism (waves), caching, and smaller models where quality allows.

Worked example

baseline  $0.42/goal · p95 41s

1 tool schema narrowing (34→9)      −$0.11  −6s
2 semantic cache on retrieval        −$0.06  −4s   (31% hit rate)
3 verifier model large→mid           −$0.09  −3s

At production scale

The order matters because the levers are not independent: narrowing tool schemas reduces tokens and improves selection accuracy, which reduces iterations. Starting with model downgrades — the most tempting lever — risks quality for the smallest gain.

Always report cost and quality together. A cost improvement with no quality number attached is not a result.

Failure modes

  • Cost without quality. Optimising the proxy.
  • Caching personalised answers. A correctness bug sold as an optimisation.
  • Parallelising dependent steps. Faster and wrong.
  • Optimising the wrong percentile. Mean latency fine, p99 unusable.

Choose it when

  • As soon as volume is real. These numbers only get harder to move later.

Regression detection and gates

A baseline plus a gate: every change is measured against the previous behaviour on a fixed set, and a material regression blocks promotion automatically.

Mechanism

Maintain a frozen baseline — a fixed eval set and the incumbent's scores on it. Any candidate change runs the same set and is compared per dimension with a tolerance. The gate blocks on regression beyond tolerance in any protected dimension (safety and grounding are usually zero-tolerance), and requires an explicit human override to proceed.

Refresh the baseline deliberately, not automatically: a baseline that updates on every promotion drifts until it no longer represents the behaviour anyone agreed to.

At production scale

The gate is what makes rapid iteration safe. Without it, an improvement programme reliably ships a regression within a few months and loses organisational trust — after which nobody is allowed to change anything, which is worse than never having optimised.

Keep safety and grounding at zero tolerance. Everything else can trade.

Failure modes

  • No gate. Regressions found by customers.
  • Auto-updating baseline. Slow drift with nothing to compare against.
  • Tolerance too loose. A gate that never blocks.
  • Silent overrides. Overrides must be named and recorded.

Choose it when

  • Before the first automated improvement ships.

Experiments

Control versus candidate on real traffic, with an assignment recorded on every run — the only way to know a change works on your distribution rather than your eval set.

Mechanism

An experiment specification names the kind of change (prompt, model, retrieval), the target key, and the control and candidate versions. Assignment is deterministic per unit (tenant, agent, or goal fingerprint) so a user does not oscillate between behaviours mid-conversation. The assignment is stamped on every run, which is what makes attribution possible afterwards.

Choose the assignment unit carefully: per-goal randomisation gives faster statistics; per-tenant assignment gives coherent user experience and is usually the right answer for anything a person notices.

ExperimentSpec
  kind             model
  target_key       role:verifier · goal_class:invoice_reconciliation
  control_version  large-A
  candidate_version mid-B
  assignment       per tenant, 15% candidate

At production scale

Two practical rules. Run few experiments at once — overlapping experiments on the same traffic make attribution impossible and neither reaches significance. And define the stopping rule in advance, including the guardrail that aborts on a safety regression, because "let it run a bit longer" is how a bad candidate serves a thousand more goals.

Failure modes

  • Unrecorded assignment. Results cannot be attributed.
  • Overlapping experiments. Confounded outcomes.
  • Per-goal assignment for user-visible behaviour. Inconsistent experience.
  • No stopping rule. Peeking until the numbers look good.

Choose it when

  • Any change whose effect you cannot fully measure offline — which is most of them.

Meta-agent: agents that configure agents

Turn a natural-language description into an agent configuration — role, tools, collections, patterns, models — and let the improvement loop tune it from there.

Mechanism

A planner-style model reads a description of the job ("handle vendor invoice reconciliation for the finance team") and emits a configuration: system prompt, tool allowlist, knowledge collections, pattern set, model tiers, and approval requirements. The output is a proposal, validated against what the tenant actually has (tools that exist, collections that are populated, plans that permit those models) and reviewed before activation.

Worked example

input  "an agent that reconciles vendor invoices against POs every month
        and flags mismatches over ₹5,000 for the finance lead"

proposal
  tools        invoices.query, po.query, notify.slack, gst.fetch_filed
  collections  acme/finance-policies, acme/vendor-contracts
  patterns     plan_execute + reflection + rollback
  models       planner mid · executor mid · verifier mid
  approvals    any write, and any flag notification over ₹5,000
  schedule     monthly, 2nd business day

review      finance lead approves with one edit (threshold ₹10,000)

At production scale

Meta-agents are excellent at producing a sensible starting configuration and poor at getting the approval and threshold details right — which are exactly the details that matter. Treat the output as a draft for review, always validate against real capabilities, and never let a generated configuration grant permissions the requester did not already have.

Failure modes

  • Hallucinated capabilities. Tools and collections that do not exist.
  • Over-permissive configuration. A generated allowlist wider than the requester's own access.
  • Unreviewed activation. An agent nobody approved acting on real systems.

Choose it when

  • Non-engineers need to create agents, with review.
  • Never auto-activate a generated configuration.

What is missing here

  • Learned pattern selection. The improvement loop can tune models and prompts but does not yet tune which agent patterns are used per goal class, which is where a lot of the remaining cost sits.
  • Counterfactual memory attribution. Ablating a recalled memory to measure its real contribution is not implemented.
  • Cross-tenant learning. Every tenant improves in isolation; privacy-preserving aggregation is the obvious unrealised value.
  • Automatic corpus-gap backlog. Coverage failures are detectable per query but do not roll up into a prioritised "documents you should ingest" list.
  • Improvement cost accounting. Nothing tracks what the improvement loop itself costs against the savings it produces.
