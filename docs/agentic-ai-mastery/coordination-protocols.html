Orientation

Chapter 1 covered the multi-agent patterns that run inside one goal. This chapter is about the coordination protocols underneath them — the durable, event-sourced machinery that lets agents negotiate, hand off, converge, and bid over time, with state that survives restarts and a transcript that can be replayed. These are the primitives that turn "several agents in a loop" into a governed multi-agent system.

The unifying design is event-sourced coordination: each protocol is a state machine whose transitions are recorded, so coordination is durable (survives a worker dying), auditable (every decision is in the ledger), and replayable (you can reconstruct exactly what happened). Each protocol below is one answer to "how do multiple agents agree on something".

The protocols

01The coordination substrate#

ShippedFoundationImpl8/10Criticality7/10

A shared service, contracts, store, and state machines that every coordination protocol builds on — event-sourced, tenant-scoped, and replayable.

Mechanism

The coordination service provides the common machinery: typed contracts for coordination messages, a durable store, state machines, streaming, an outbox for reliable delivery, and replay. Each protocol (magentic, group chat, swarm, auction…) is an adapter over this substrate, so they share persistence, audit, and cross-replica delivery rather than each reinventing it.

In AgentVerse

  • app/coordination/service.pyCoordinationService
  • app/coordination/contracts.py, store.py, state_machines.py, state_repository.pythe substrate
  • app/coordination/outbox.py, streaming.py, streams.pyreliable delivery + streaming
  • app/coordination/replay.py, read_models.pyreplay and projections
  • app/coordination/transcript/*the transcript service and projections

Worked example

a coordination session (any protocol)
 messages recorded as events in the store (tenant-scoped)
 state machine advances on each event
 outbox guarantees delivery across replicas
 transcript projection → a readable record → replayable for audit

At production scale

Event-sourcing coordination is what makes multi-agent systems debuggable at all. When a negotiation produces a strange outcome, the transcript is the only artifact that explains it, and replay lets you reconstruct it exactly. Building the substrate once means every protocol inherits durability and audit.

Failure modes

  • Coordination state in memory. Lost on restart, unauditable.
  • No transcript. Outcomes that cannot be explained.

Choose it when

  • Any durable multi-agent coordination.

02Magentic: ledger-driven orchestration#

PartialProtocolImpl7/10Criticality6/10

A supervisor protocol with a task ledger: the orchestrator tracks progress against a plan, detects stalls, evaluates progress, and replans — a durable, auditable version of the supervisor pattern.

Mechanism

Magentic maintains a ledger of the plan and its revisions. A progress evaluator judges whether the team is advancing; a stall detector catches lack of progress; a replan manager revises the plan (recording a ledger revision); a participant policy governs who acts; and human review can be inserted. It is the supervisor pattern (chapter 1) made durable and event-sourced.

In AgentVerse

  • app/coordination/magentic/adapter.pythe protocol adapter
  • app/coordination/magentic/progress_evaluator.py, stall_detector.pyprogress and stall
  • app/coordination/magentic/replan_manager.py, participant_policy.pyreplan and participation
  • app/coordination/magentic/human_review.py, models.pyhuman review
  • app/coordination/ledger/*LedgerRevision — the task ledger

Worked example

magentic session, goal "resolve the incident"
 ledger v1: [gather metrics, diff deploys, analyse queries, remediate]
 progress evaluator: steps 1-2 done, step 3 stalled (same result 3×)
 stall detector fires → replan manager → ledger v2 (new approach for step 3)
 all revisions recorded → replayable, auditable

At production scale

Magentic's value over the plain supervisor pattern is durability and the explicit stall/progress machinery — a long-running multi-agent goal survives restarts and cannot silently spin. The ledger is the audit artifact that explains why the plan changed. Reserve it for goals long or complex enough to justify the coordination overhead.

Failure modes

  • Weak progress signal. A stall not detected, or false stalls.
  • Unbounded replanning. Ledger revisions without a cap.

Choose it when

  • Long, complex multi-agent goals needing durable orchestration.

03Group chat#

PartialProtocolImpl7/10Criticality5/10

Multiple agents in a shared conversation, with a speaker policy deciding who talks next and compaction keeping the transcript within budget.

Mechanism

Agents share a conversation; a speaker policy (round-robin, or a selector that picks the most relevant next speaker) governs turn-taking, preventing the free-for-all that makes group chat incoherent. A state machine tracks the conversation; compaction summarises old turns so a long discussion stays within the context budget (chapter 8).

In AgentVerse

  • app/coordination/group_chat/adapter.py, state_machine.pythe protocol
  • app/coordination/group_chat/speaker_policy.pyturn-taking
  • app/coordination/group_chat/compaction.pytranscript compaction
  • app/api/coordination_group_chat.pythe API

Worked example

group chat: architect, security, cost agents discuss a design
 speaker policy: relevance-based → security speaks when risk is raised
 compaction: after 40 turns, older turns summarised to stay in budget
 outcome: a design with all three perspectives, in one transcript

At production scale

Group chat is useful for genuinely multi-perspective deliberation but expensive (every agent reads every turn) and prone to incoherence without a good speaker policy. The compaction is essential — an uncompacted group chat hits the context limit fast. Prefer a supervisor or debate protocol unless the value is specifically in the open conversation.

Failure modes

  • No speaker policy. Incoherent free-for-all.
  • No compaction. Context overflow.
  • Cost blowout. Every agent reading every turn.

Choose it when

  • Multi-perspective deliberation where the conversation itself is the value.

04Handoffs#

PartialProtocolImpl7/10Criticality6/10

An agent explicitly transfers control to another, with membership and a state machine governing the handoff — the "escalate to a specialist" pattern, made durable.

Mechanism

An agent decides a task belongs to another and hands off, passing a compact brief. Membership governs who can receive a handoff; a state machine tracks the transfer so control is never lost or duplicated. The receiving agent inherits the necessary context but not more than its scope allows (chapter 14).

In AgentVerse

  • app/coordination/handoffs/service.py, state_machine.pythe protocol
  • app/coordination/handoffs/membership.py, models.py, repository.pymembership and state
  • app/api/coordination_handoffs.pythe API

Worked example

support-agent handles a ticket → recognises it needs billing expertise
 → handoff to billing-agent with a brief (not the whole transcript)
 → state machine: control transferred, support-agent no longer acting
 → billing-agent resolves, control returns or closes

At production scale

Handoffs are the clean way to compose specialists without a supervisor overhead — each agent does what it is good at and passes on the rest. The state machine matters: without it, a handoff can leave control ambiguous (both agents acting) or lost (neither acting). Pass a brief, not the whole history, to keep the receiving agent's context focused.

Failure modes

  • Control ambiguity. Both or neither agent acting.
  • Context dump. The whole transcript handed over.
  • Handoff loops. Two agents bouncing a task.

Choose it when

  • Work moves cleanly between specialists.

05Swarm and mixture-of-agents#

PartialProtocolImpl6/10Criticality4/10

Two decentralised protocols: a swarm where agents claim work and converge via gossip, and mixture-of-agents where layers of agents refine a proposal with diversity and quorum.

Mechanism

Swarm: agents claim tasks from a shared pool, share state via gossip, and converge without a central coordinator — resilient but harder to reason about. Mixture-of-agents (MoA): several agents propose independently, then layers of aggregator agents refine, with a diversity policy ensuring the proposals differ and a quorum deciding acceptance. Both trade central control for parallelism or diversity.

In AgentVerse

  • app/coordination/swarm/*claims, convergence, gossip
  • app/coordination/moa/aggregator.py, layer_planner.py, diversity_policy.py, quorum.pyMoA aggregation
  • app/api/coordination_swarm.py, coordination_moa.pythe APIs

Worked example

MoA on a hard question
 layer 1: 4 agents propose independently (diversity policy enforces difference)
 layer 2: 2 aggregators refine the proposals
 quorum: accept when 2 of 2 agree → a stronger answer than any single agent
swarm on a large task pool: agents claim, gossip progress, converge

At production scale

Rated low on criticality because both are specialised: swarm suits large, parallelisable task pools where central coordination is a bottleneck; MoA suits hard questions where diverse refinement beats a single strong model. For most production work a supervisor or debate protocol is more predictable and cheaper. Use these where their specific shape — decentralisation or diverse aggregation — is genuinely needed.

Failure modes

  • Swarm non-convergence. Agents never agreeing.
  • MoA fake diversity. Proposals that agree because they are similar.
  • Cost. Many agents, high spend.

Choose it when

  • Large parallel pools (swarm) or hard questions needing diverse refinement (MoA).

06Auction-based allocation#

PartialProtocolImpl6/10Criticality4/10

Agents bid for tasks; a sealed-bid auction allocates work to the best-fit agent, with fairness and threat detection — a market mechanism for task assignment.

Mechanism

Tasks are auctioned; agents submit sealed bids reflecting their fit and capacity; an allocator assigns based on scoring, with a fairness policy preventing one agent from winning everything and threat detection catching manipulation. It is an alternative to the router (chapter 1) for task allocation — a market rather than a scorer — useful when agents have genuine capacity constraints.

In AgentVerse

  • app/coordination/auction/sealed_bids.py, allocator.py, scoring.pythe auction
  • app/coordination/auction/fairness.py, threat_detection.pyfairness and anti-manipulation
  • app/coordination/auction/state_machine.py, models.pystate
  • app/api/coordination_auction.pythe API

Worked example

task pool auctioned across a team
 agents bid (fit × available capacity)
 sealed bids → allocator assigns → fairness policy caps any one winner
 threat detection: an agent bidding to starve others → flagged

At production scale

Auctions are a specialised allocation mechanism — most task assignment is better served by the router's multi-signal scoring (chapter 1). Auctions earn their place when agents have real, differing capacity and a market clears it better than a central scorer. The fairness and threat-detection machinery signals the concern: any market invites gaming.

Failure modes

  • Bid gaming. Agents manipulating the market.
  • Unfair concentration. One agent winning everything.
  • Overhead. Auction cost exceeding the allocation benefit.

Choose it when

  • Agents have genuine capacity constraints a market clears well.

07CAMEL role-play and generative agents#

PartialProtocolImpl6/10Criticality4/10

Two more specialised protocols: CAMEL pairs a role-playing "user" and "assistant" agent to drive a task through inception prompting, and generative agents simulate personas with memory, observation, reflection, and a simulation clock.

Mechanism

CAMEL: two agents role-play (a task-giver and a task-doer) with an inception prompt setting up the collaboration, useful for autonomous task completion through dialogue, bounded by a termination condition. Generative agents: personas with observation, memory, reflection, and a simulation clock — the "believable agents" research direction, for simulation rather than production tasks.

In AgentVerse

  • app/coordination/camel/inception.py, adapter.py, termination.pyCAMEL role-play
  • app/coordination/generative/persona.py, observation.py, reflection.py, simulation_clock.pygenerative agents
  • app/api/coordination_camel.py, coordination_generative.pythe APIs

Worked example

CAMEL: "user" agent gives sub-tasks, "assistant" agent executes, dialogue
 continues until the termination condition → autonomous completion
generative: personas observe a simulated environment, form memories, reflect,
 and act on a simulation clock → a believable-behaviour sandbox

At production scale

Both are research-leaning. CAMEL's role-play can drive some autonomous tasks but is less controllable than plan-execute; generative agents are for simulation (testing how a population of agents behaves) rather than production work. They are included because they are real, distinct protocols in the platform — and because a complete map of coordination should name the experimental corners honestly, not just the production ones.

Failure modes

  • CAMEL non-termination. Role-play that never ends.
  • Generative drift. Personas behaving unpredictably.

Choose it when

  • CAMEL for dialogue-driven autonomous tasks; generative for simulation.
  • Not for controllable production work — use plan-execute or supervisor.

08Agent-to-agent (A2A) communication#

PartialProtocolImpl7/10Criticality6/10

The protocol for agents calling agents — across the same tenant or federated across platforms — with the security and dispatch machinery to make it safe.

Mechanism

A2A lets one agent invoke another as a capability, over MCP (chapter 20). Within a tenant it is a scoped call inheriting the caller's constraints; across platforms it is a federated call with its own security (a2a_security) and dispatch. It is how agents compose into larger systems — an agent using another agent as a tool — with the same validation and risk classification as any other tool call.

In AgentVerse

  • app/mcp/a2a.py, app/agent/tools/a2a_call.pyA2A over MCP
  • app/civilization/a2a_dispatch.py, a2a_repository.py, a2a_security.pydispatch and security
  • app/api/a2a.pythe API

Worked example

agent A needs a specialised analysis agent B provides
 A calls B via a2a_call (an MCP tool) with a scoped brief
 B runs as itself, within its own scope, returns a result
 the call is validated, risk-classified, and audited like any tool call

At production scale

A2A is how agents become composable building blocks — but it inherits every risk of tool calling plus the risk of an agent as an untrusted caller. Treat an A2A call like any external tool: validate, scope, classify risk, audit. Federated A2A (across platforms) needs its own trust model, which is why a2a_security is a distinct concern.

Failure modes

  • Unscoped A2A. A called agent exceeding the caller's scope.
  • A2A loops. Agents calling each other cyclically.
  • Federated trust gaps. Trusting a remote agent's output.

Choose it when

  • Agents compose into larger systems as capabilities.

What is missing here

  • Protocol selection guidance in the assembler. The pattern assembler picks single-agent patterns; choosing among coordination protocols for a multi-agent goal is more manual.
  • Cross-protocol composition. Running, say, a handoff inside a magentic session is possible but not a first-class composition.
  • Coordination eval. Individual agents and teams are evaluated; the effectiveness of a coordination protocol as such is not systematically measured.
  • Federated A2A trust framework. Cross-platform agent calls need a maturer trust and reputation model.
