Multi-model router

Per-role model selection under cost, latency, plan, and health.

Orientation

A production agent uses many models, not one — a planner, an executor, a verifier, a judge, an embedder, sometimes a vision or audio or reranker model — and the right choice for each is a different point on the cost/latency/quality surface. The model router is the component that makes that choice per role, per goal, under constraints, and reroutes when a provider fails.

Two ideas organise it. Role-based selection: the model that plans well is not necessarily the model that verifies cheaply, so choose per role. Constraint-aware routing: the choice is bounded by the tenant's plan, the goal's latency budget, and each provider's current health — so the same role can get different models on different goals.

Routing

01The model orchestrator#

ShippedCoreImpl8/10Criticality9/10

The component that binds a goal's pattern config to concrete models per role and hands the agent loop a set of ready, health-checked model clients.

Mechanism

At goal start, the orchestrator reads the pattern config (which named a model per role) and the routing signals, resolves each role to an actual model and provider, and constructs the clients — wrapped in circuit breakers and cost guards. It is where "the planner should be a strong model" becomes "the planner is this provider's this model, and here is the client".

In AgentVerse

  • app/ai_router/model_orchestrator.pyModelOrchestrator
  • app/ai_router/router.pyAIRouter — the routing decision
  • app/services/goal_service.py_make_agent_loop_for_tenant() constructs it per goal
  • app/agent/model_router.pyagent-side model routing

Worked example

pattern config  planner=large executor=large verifier=mid classifier=mini
goal signals    plan=enterprise · latency budget=relaxed · all providers ok
orchestrator    planner → anthropic/large · executor → anthropic/large
                verifier → openai/mid (cross-provider, for consensus)
                classifier → mini
                each client wrapped in a breaker + cost guard

At production scale

Constructing model clients per goal rather than globally is what lets routing be goal-specific and plan-aware. It is also where cross-provider verification is arranged — deliberately choosing a different provider for the verifier than the executor, so consensus is not two instances of the same blind spots (chapter 1).

Failure modes

  • Global model config. One model for every goal, chosen for the hardest case.
  • Same provider for actor and verifier. Correlated errors in consensus.

Choose it when

  • Any agent using more than one model role.

02Per-role model selection#

ShippedSelectionImpl8/10Criticality8/10

Planner, executor, verifier, judge — each has different requirements, and choosing per role is the largest cost lever in the platform without touching quality.

Mechanism

Each role is scored independently on quality, latency and cost against a measured table (chapter 9). The patterns that recur: verifiers and classifiers usually run well on cheaper models; executors on complex tool work usually need stronger ones; planners sit in between; judges must differ from the model they judge. The role policy encodes these and the router applies them per goal.

In AgentVerse

  • app/ai_router/role_policy.pyper-role selection policy
  • app/ai_router/complexity_scorer.pyscoring the goal's difficulty
  • app/evals/model_score.pythe measured per-role table
  • app/agent/pattern_config.pymodel_planner/executor/verifier/classifier fields

Worked example

role       requirement                     typical choice   cost share
planner    decomposition, judgement         strong           medium
executor   tool selection, reasoning        strong           high
verifier   check against a rubric            mid              low
judge      independent scoring              mid (diff vendor) low
classifier fast keyword+LLM tiebreak        mini             tiny
embedder   semantic quality                 small/medium     tiny
measuring per role typically finds 40-70% cost savings vs one global model

At production scale

The most common waste is a strong model on the verifier "to be safe". Verification is a rubric check — a task where a mid model matches a large one — and it runs on every step, so downgrading it is a large, quality-neutral saving. Measure per role rather than assuming; the answer shifts as models change.

Failure modes

  • One model for all roles. Overpaying on the cheap roles.
  • Judge = executor model. Self-preference in scoring.

Choose it when

  • Any multi-role agent — which is any production agent.

03Cost-, latency-, and plan-aware routing#

ShippedPolicyImpl8/10Criticality9/10

The same role gets a different model depending on what the goal can afford, how fast it must be, and what the tenant's plan permits.

Mechanism

A three-way policy: cost (route to a cheaper model when the budget is tight or the goal class does not justify the spend), latency (route to a faster model for interactive goals), and plan (a free tier gets the economy models, enterprise gets the frontier ones). These interact — an interactive enterprise goal optimises for latency within the enterprise model set — and the policy resolves the trade with a recorded reason.

In AgentVerse

  • app/ai_router/cost_latency_quality_policy.pythe three-way trade
  • app/tenancy/entitlements.py, limits.pyplan constraints
  • app/optimization/model_optimizer.py, latency_optimizer.py, cost_optimizer.pythe optimisers that tune it
  • app/routing_runtime/optimizer.py, model_router.pyruntime routing

Worked example

same role (executor), three goals
 interactive chat, enterprise  → fast enterprise model (latency wins)
 overnight batch, enterprise   → strong model (quality wins, latency free)
 chat, free tier               → economy model (plan caps the set)
each decision recorded: "executor=fast-enterprise, reason=latency<4s budget"

At production scale

Plan-aware routing is both a cost control and a product feature — it is how tiers are differentiated. The subtlety is not to optimise cost against a proxy: routing to a cheaper model that fails more often raises cost through extra iterations. Always evaluate a routing change on success and cost together (chapter 9).

Failure modes

  • Cost optimisation ignoring success. Cheaper model, more retries, higher net cost.
  • Plan not enforced in routing. Free tier reaching frontier models.
  • Latency ignored on interactive goals. A strong slow model on a chat path.

Choose it when

  • Multiple plans, or mixed interactive and batch workloads.

04Specialised model roles: embedding, vision, audio, reranker#

PartialSelectionImpl7/10Criticality7/10

Beyond the text roles, the platform routes to specialised models — an embedder per content type, a vision model for images, STT/TTS for voice, a cross-encoder for reranking — each selected on its own axis.

Mechanism

Each specialised role has its own selection logic. The embedding router chooses by content type and dimension compatibility (chapter 7). Vision routing picks a model that can read the image at acceptable cost. Voice routes to STT and TTS providers by language and latency (chapter 26). The reranker is selected by the retrieval pipeline (chapter 6). They share the router's constraint-awareness — plan, cost, health — but differ in what "quality" means for each.

In AgentVerse

  • app/embedding/router.py, app/routing_runtime/embedding_router.pyembedding selection
  • app/perception/multimodal.pyvision model use
  • app/voice/router.py, stt_engine.py, tts_engine.pyvoice model routing
  • app/rag_platform/reranker.pyreranker selection
  • app/routing_runtime/skill_router.py, tool_router.pythe same idea for skills and tools

Worked example

one goal touches four specialised roles
 embedder   code chunk → code model (1024) · prose → text model (3072)
 vision     invoice image → vision model for OCR fallback
 reranker   retrieval → cross-encoder, top 50
 (voice)    if voice channel → STT by language, TTS by latency
each selected on its own axis, all under the same plan/health constraints

At production scale

The specialised roles are where model diversity is highest and where a single hardcoded choice hurts most — an English STT model on German audio, a prose embedder on code. Route each by its own signal, and keep the selection recorded so a quality problem in one modality is traceable to the model that produced it.

Failure modes

  • One embedder for all content. Code and prose degrading each other.
  • Language-blind voice routing. Poor transcription on non-default languages.

Choose it when

  • Any workload spanning content types or modalities.

05Provider fallback and circuit breakers#

ShippedReliabilityImpl8/10Criticality10/10

Providers fail. A circuit breaker detects it, stops hammering the dead provider, and reroutes to a fallback — turning an outage into a degraded mode rather than a failure.

Mechanism

Each provider is fronted by a circuit breaker: after a threshold of failures the breaker opens and calls short-circuit to a fallback provider instead of timing out repeatedly. Fallback must respect constraints — a fallback model must be capable of the role, and for embedding it must match the index dimension (chapter 7). Provider health feeds back into routing so an unhealthy provider is deprioritised before the breaker even trips. When the breaker half-opens, a probe checks whether the provider has recovered.

In AgentVerse

  • app/providers/circuit_breaker.pyProviderCircuitBreaker, call_with_circuit_breaker()
  • app/ai_router/provider_health_policy.pyhealth feeds routing
  • app/providers/registry.pyresolve_provider(), fallback resolution
  • app/providers/fake.pythe ultimate fallback for tests/no-key
  • app/reliability/redis_circuit_breaker.pythe cross-replica breaker state

Worked example

primary provider returns 503s
 breaker after 5 failures → OPEN → calls short-circuit
 router reroutes executor to fallback provider (capable of the role)
 embedding role: fallback must match index dim → if none, queue, not reroute
 90s later → breaker HALF-OPEN → probe → recovered → CLOSE
users saw degraded latency for 90s, not an outage

At production scale

Cross-replica breaker state (in Redis) matters: without it, each replica discovers the provider is down independently, so the fleet keeps hammering a dead provider from every node. The breaker is also what makes cross-provider verification robust — if the verifier's provider is down, the system knows before it tries. Multi-provider capability is the whole reason the provider abstraction (chapter 20) must be genuinely vendor-neutral.

Failure modes

  • No breaker. A provider outage becoming your outage via retry storms.
  • Dimension-incompatible embedding fallback. Index corruption dressed as resilience.
  • Per-replica breaker state. The fleet not learning collectively.

Choose it when

  • Any dependency on an external model provider — so always.

06Shadow routing#

PartialImprovementImpl7/10Criticality6/10

Score a candidate model on real traffic without serving its output — the cheapest way to evaluate a new or cheaper model on your actual distribution before promoting it.

Mechanism

For a sampled fraction of goals, run both the incumbent (whose output is served) and a candidate (whose output is scored but discarded). Compare quality, latency and cost on identical inputs. Because the candidate never affects the user, shadow routing is safe to run on production traffic, and it answers the question benchmarks cannot: how does this model do on our goals?

In AgentVerse

  • app/ai_router/shadow_router.pyshadow routing
  • app/intelligence/experiment_registry.pyexperiment framing
  • app/evals/model_score.pyscoring both
  • app/optimization/ab_testing.pypromotion decision

Worked example

candidate: a new cheaper verifier model, shadowed on 5% of goals
 incumbent served, candidate scored on the same inputs
 over 3 days: candidate quality 0.93 vs 0.94, cost 0.004 vs 0.021
 → promote candidate; no user ever saw its output during evaluation

At production scale

Shadow routing is how you keep the per-role model table current as models and prices change (chapter 9). It de-risks model migration: you learn a candidate's real-world behaviour before it serves a single user, which is the difference between a confident promotion and a hopeful one. Budget the shadow cost — you are paying for a second inference on the sampled fraction.

Failure modes

  • Shadow output leaking to users. The one thing that must never happen.
  • Unbudgeted shadow cost. Doubling inference on the sample without accounting.

Choose it when

  • Evaluating a model change on real traffic before committing.

What is missing here

  • Learned routing. Selection uses hand-tuned policies over a measured table; a bandit over models per goal class would optimise success-per-dollar continuously.
  • Predictive complexity scoring. The complexity scorer runs before the goal; it cannot yet learn from how goals of a given shape actually turned out.
  • Cross-provider consensus automation. Consensus picks a second provider manually; routing does not automatically ensure verifier and executor providers differ.
  • Speculative multi-model execution. No support for racing two providers and taking the first acceptable answer under a tight latency budget.
