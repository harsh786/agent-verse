Workflow engine

Deterministic workflows, chat, and collaboration alongside the agent loop.

Orientation

The autonomous agent loop (chapter 1) is the platform's headline, but it is not the only execution model. Alongside it runs a deterministic workflow engine: a versioned DSL of typed steps that executes exactly as authored, with no model deciding control flow. The two are complementary — the agent loop for open-ended goals where the path is unknown, the workflow engine for known processes that must run the same way every time.

The distinction is the whole point. A goal like "investigate this incident" wants an agent; a process like "on every invoice: validate, screen for fraud, route for approval, file" wants a workflow — auditable, testable, versioned, and identical on run one and run ten thousand. A world-class platform needs both, and needs them to compose: workflow steps that invoke agents, agents that trigger workflows.

The engine

01The workflow DSL and definition#

ShippedDefinitionImpl8/10Criticality8/10

A workflow is authored as a versioned definition — a DAG of typed steps with a variable context — not written in code, so it can be created, reviewed, and changed without a deploy.

Mechanism

A WorkflowDefinition declares steps, their types, their inputs (including ${step.output} references resolved by an expression engine), and their dependencies. It is data — YAML or a stored definition — so a workflow is a configuration object with a version, not a function. That makes it reviewable by non-engineers, diffable across versions, and changeable at runtime.

In AgentVerse

  • app/workflow/dsl.pyWorkflowDefinition, StepDefinition
  • app/workflow/expression_engine.py, variables.py, context.pyvariable references and context
  • app/workflow/registry.pyStepTypeRegistry
  • app/db/models/workflow.pythe persisted Workflow model

Worked example

workflow "invoice-processing" v3
  steps
    parse:     tool  document_parser(input: ${trigger.file})
    validate:  code  check_totals(${parse.output})
    fraud:     rag   screen(${parse.output.vendor})       deps [validate]
    approve:   hitl  "approve payment ${parse.output.total}?"  deps [fraud]
    file:      tool  erp.create_payment(...)               deps [approve]
authored as data, versioned, reviewable — no code deploy to change it

At production scale

A DSL is what lets a compliance or operations team own a process without owning code. The variable context with explicit ${step.output} references is the detail that makes workflows composable and testable — every data flow is declared, so the compiler can validate it and a reviewer can read it. Versioning is non-negotiable: a running process must not change under a live run, and an audit must show which version executed.

Failure modes

  • Workflows as code. Every change a deploy, unreviewable by process owners.
  • Unversioned definitions. A process that changed mid-run, unauditable.
  • Implicit data flow. Undeclared dependencies the compiler cannot validate.

Choose it when

  • A process is known, repeatable, and must run identically every time.
  • Not for open-ended goals where the path is unknown — that is the agent loop.

02Compilation and testing#

ShippedValidationImpl8/10Criticality7/10

Before a workflow runs it is compiled — the DAG validated, variable references resolved, step types checked — and can be dry-run against test inputs, so a broken workflow fails at authoring, not at 3 a.m.

Mechanism

The compiler turns a definition into an executable form, validating that the DAG is acyclic, that every ${...} reference resolves to a real upstream output, that step types exist, and that required inputs are present. A test runner executes the compiled workflow against sample inputs with mocked side effects — the simulation discipline of chapter 31 applied to workflows — so it can be proven before it goes live.

In AgentVerse

  • app/workflow/compiler.pyWorkflowCompiler
  • app/workflow/test_runner.pydry-run against test inputs
  • app/workflow/security.pysecurity validation of a definition
  • app/workflow/state.py, storage.pycompiled state and storage

Worked example

compile "invoice-processing" v4
  DAG acyclic?            yes
  ${fraud.output.risk}    references a real fraud-step output?  yes
  step type "code"        registered?  yes
  approve step gated?     yes (hitl)
test run against 3 sample invoices (mocked ERP) → all pass → cleared to
publish; a v5 that referenced a deleted step would fail compilation

At production scale

Compilation catches the errors that would otherwise surface mid-run against real systems — a dangling reference, a cycle, a missing input. The test runner is the workflow equivalent of the certification gate (chapter 10): a workflow that touches money or files a return must be proven against sample data before it is allowed to run live. Security validation matters because a workflow with an http or code step is an execution surface.

Failure modes

  • No compile-time validation. A dangling reference discovered at runtime.
  • No dry-run. A workflow's first real run is its first test.
  • Unvalidated code/http steps. An execution surface with no security check.

Choose it when

  • Always, before a workflow serves production.

03Typed steps and the runner#

ShippedExecutionImpl8/10Criticality8/10

Fifteen step types — tool, LLM, RAG, HTTP, code, conditional, parallel, foreach, wait, set-var, transform, emit-event, HITL, sub-workflow, org — each a first-class auditable unit the runner executes against the variable context.

Mechanism

The runner walks the compiled DAG, executing each step by type: tool and http call out, llm and rag invoke the model and retrieval, code runs in the sandbox (chapter 25), conditional/parallel/foreach are control flow, hitl pauses for approval, sub-workflow composes, set-var/transform/emit-event manipulate state. Each step's execution is audited. The llm and agent-invoking steps are where determinism meets autonomy — a mostly-fixed process with one judgement step.

In AgentVerse

  • app/workflow/runner.pyWorkflowRunner (wired in create_app)
  • app/workflow/steps/*.pytool, llm, rag, http, code, conditional, parallel, foreach, wait, set_variable, transform, emit_event, hitl, sub_workflow, org steps
  • app/workflow/celery_tasks.pyexecute_workflow_run
  • app/workflow/audit_middleware.pyAutoAuditMiddleware — audits each step

Worked example

runner executes invoice-processing
  parse (tool)      → invoice fields                    audited
  validate (code)   → sandbox, totals consistent        audited
  fraud (rag)       → risk score 0.2                     audited
  approve (hitl)    → pause → human approves → resume    audited
  file (tool)       → ERP payment created                audited
foreach variant: process 200 invoices, parallel-bounded, one workflow run

At production scale

Typed steps are what make a workflow both expressive and governable — each step type has its own risk profile, audit shape, and failure handling, so the platform's controls (tool risk, sandbox, HITL, rollback) apply per step. The foreach and parallel steps bring the wave-execution benefit (chapter 1) to deterministic processes. The llm step is the seam that lets a workflow stay mostly deterministic while delegating the one genuinely-judgement step to a model or a full agent.

Failure modes

  • Untyped steps. Controls that cannot apply per step.
  • Unbounded foreach. A 10,000-item fan-out exhausting the pool (chapter 28).
  • Unaudited steps. A process no one can reconstruct.

Choose it when

  • Any repeatable multi-step process — the more regulated, the more this beats an agent.

04Versioning, HITL, and runs#

ShippedLifecycleImpl8/10Criticality8/10

Every workflow is versioned, every run records which version it executed, HITL steps pause durably like the agent loop, and templates ship proven processes (AML screening, KYC, invoice processing) ready to instantiate.

Mechanism

A workflow has versions; a run pins the version it executed, so an audit shows exactly what ran. HITL steps use the same durable-pause machinery as the agent loop (chapter 1) — the run checkpoints, releases its worker, and resumes on approval via callback. Templates package proven workflows with their steps, gates, and validation, so a tenant instantiates AML screening or invoice processing rather than authoring it. Runs are observable and replayable (chapter 11).

In AgentVerse

  • app/workflow/router_versions.py, router_runs.py, router_templates.py, router_hitl.pyversions, runs, templates, HITL routing
  • app/workflow/hitl_extension.py, steps/hitl_step.pyHITLWorkflowGateway — durable pause
  • app/workflow/template_store.py, templates/*.yamlaml-screening, kyc-automation, invoice-processing
  • app/workflow/nl_trigger.py, service.py, otel.pyNL triggering, service, tracing

Worked example

tenant instantiates the "kyc-automation" template
  comes with: document parse, identity extraction (OCR ch 21), sanctions
  screen, risk scoring, HITL gate for high-risk, audit on every step
run r-4471 pins workflow v3 → HITL pause at the high-risk gate → analyst
approves → resumes → completes; the audit shows v3 ran, who approved, when

At production scale

Versioning plus per-run version pinning is what makes workflows defensible to a regulator — "this exact process, this version, ran, and here is the audit". Templates are how vertical processes (KYC, AML, invoicing) become instantly available with governance baked in (chapter 20). The shared HITL machinery means a workflow's approval gate has the same durability and argument-hashing guarantees as an agent's (chapter 1). Together they make the deterministic engine as production-grade as the agent loop.

Failure modes

  • Runs not pinned to a version. An audit that cannot say what executed.
  • HITL blocking a worker. Use the durable pause, not a held thread (chapter 1).
  • Uncertified templates. A shared process that never passed its test runner.

Choose it when

  • Regulated, repeatable processes — and start from a template where one exists.

05Conversational and collaborative execution#

PartialAdjacentImpl7/10Criticality6/10

Two adjacent execution surfaces: a chat layer that runs goals conversationally with intent detection and streaming, and a collaboration runtime for multiple humans steering shared work in real time.

Mechanism

The chat layer wraps the agent loop in a conversation: it detects intent (a question, a command, a goal), maintains conversational context and session memory (chapter 3), and streams responses — the same goal engine, a conversational front door. The collaboration runtime adds real-time multi-human coordination over a WebSocket (chapter 23): shared goal views, clarification capture, human decision traces, and preference capture, so several operators can steer one piece of work.

In AgentVerse

  • app/chat/service.py, intent.py, execution.py, context.py, stream.pythe conversational layer
  • app/chat/memory_api.py, search.py, templates.pychat memory, search, templates
  • app/collab/agent_collab.py, store.pyagent collaboration
  • app/collaboration_runtime/clarification.py, human_decision_trace.py, preference_capture.py, missing_input_request.pyhuman-in-the-loop collaboration

Worked example

chat: "reconcile March payouts, then tell me the variance"
  intent → goal → agent loop runs → streams progress → answers in the thread
  follow-up "and file the amendment" → continues the session with context

collab: two analysts watch a KYC review; one requests clarification, the
  other approves the gate; both decisions recorded in the human decision trace

At production scale

The chat layer is how most users actually reach the platform — a conversation, not an API call — so it inherits every control (auth, scope, guardrails) while adding conversational context management, which is where multi-turn constraint persistence matters (chapter 10). The collaboration runtime is thinner (rated 7): real-time multi-operator steering with presence and conflict handling is an area a world-class platform would deepen — which is exactly the kind of gap the upgrade plan targets.

Failure modes

  • Chat losing constraints across turns. A stated constraint forgotten (chapter 10).
  • Collaboration without decision traces. No record of who steered what.
  • Session memory unbounded. Context overflow on long conversations (chapter 3).

Choose it when

  • Users interact conversationally, or multiple humans steer shared work.

What is missing here

  • Agent ⇄ workflow composition as first-class. An llm/agent step invokes an agent and an agent can trigger a workflow, but a seamless "escalate from deterministic to autonomous mid-process and back" is not fully first-class.
  • Workflow eval and certification parity. The test runner exists; a required certification gate for workflows matching the agent-side one (chapter 10) is thinner.
  • Real-time collaboration depth. Multi-operator steering with presence, cursors, and conflict resolution is early (chapter 23).
  • Conversational constraint persistence. Extracting stated constraints from chat into durable state, rather than trusting the transcript, is not fully wired (chapter 10).
