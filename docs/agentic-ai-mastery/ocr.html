OCR

Classify, extract, validate — document AI that has to be right.

Orientation

OCR in an agent platform is not "turn an image into text" — it is document understanding that has to be right, because the output feeds a filing, a payment, or a compliance decision. The difference from generic image captioning is that OCR here is structured extraction with validation: classify the document, extract typed fields with their locations, and validate each field against rules before anything downstream trusts it.

The three-stage shape — classify, extract, validate — is what separates document AI from a demo. A caption that is 90% right is useful; an invoice total that is 90% right is a liability, so the third stage exists to catch the 10%.

The OCR subsystem

01The OCR engine#

ShippedEngineImpl8/10Criticality8/10

Orchestrates the pipeline: OCR each page, classify the document, dispatch to the right extractor, and fall back to LLM vision OCR where classic OCR is weak.

Mechanism

The engine runs page-level OCR to get raw text and layout, classifies the document kind, and selects a kind-specific extractor via a factory. For low-quality scans or complex layouts where character-level OCR struggles, it escalates to LLM vision OCR — a vision model reading the image directly — which is more robust but more expensive, so it is a fallback rather than the default. The result is a typed OcrResult with fields and confidences.

In AgentVerse

  • app/ocr/engine.pyOcrEngine: extract(), _ocr_page(), _llm_vision_ocr(), the get_extractor factory + DocumentClassifier
  • app/ocr/models.pyOcrResult and field models
  • app/tools/ocr_tool.pyOCR exposed to agents as a tool
  • app/api/ocr.pythe API surface

Worked example

scan-invoice.pdf
 _ocr_page   raw text + word boxes, mean confidence 0.94
 classify    → invoice
 extractor   financial extractor → {vendor, invoice_no, total, tax, due}
 low-conf    "total" box confidence 0.61 → _llm_vision_ocr on that region
             → resolved to ₹41,200 at 0.97
 result      OcrResult with typed fields, each with a box and a confidence

At production scale

Reserve LLM vision OCR for the fields and pages classic OCR flags as low-confidence — running it on everything is expensive and usually unnecessary. The per-field confidence is what makes selective escalation possible: extract cheaply, escalate the uncertain 10%, and only then involve a human.

Failure modes

  • Vision OCR on everything. Cost with little marginal accuracy.
  • No per-field confidence. Cannot escalate selectively.
  • Silent low-confidence acceptance. A guessed total in a filing.

Choose it when

  • Any scanned or image-based document that feeds a decision.

02Document classification#

ShippedStageImpl8/10Criticality7/10

Decide what kind of document this is — invoice, ID, bank statement, contract — so the right extractor and the right validation rules apply.

Mechanism

Distinct from the content-type classifier of chapter 5 (which decides file format), this classifier decides business kind from the OCR'd content and layout. The kind determines everything downstream: which fields to extract, which rules to validate against, which retention and residency policy applies. A misread kind sends the document to the wrong extractor and produces confidently wrong fields.

In AgentVerse

  • app/ocr/classifier.pyDocumentClassifier — business kind
  • app/ocr/engine.pyuses it to select the extractor

Worked example

uploaded document
 layout + keywords → "invoice" (0.91) vs "purchase order" (0.06)
 → financial extractor, invoice validation rules, 7-year retention
misread as a receipt → wrong fields, wrong rules → wrong total downstream

At production scale

Kind classification errors are silent and expensive because everything downstream trusts the kind. Where confidence is low, route to a generic extractor plus human confirmation rather than committing to a wrong kind. Track the kind distribution — a shift signals a new document type nobody built an extractor for.

Failure modes

  • Confident misclassification. Wrong extractor, wrong fields.
  • No fallback for unknown kinds. New document types failing silently.

Choose it when

  • You process more than one kind of document.

03Kind-specific extractors#

ShippedStageImpl8/10Criticality8/10

Each document kind has an extractor that knows its fields: a financial extractor knows totals and tax, an ID extractor knows names and numbers, a general extractor handles the rest.

Mechanism

Extractors share an interface but encode kind-specific knowledge: the fields to look for, where they typically appear, and their expected types. A factory resolves the extractor from the classified kind. This specialisation is what makes extraction reliable — a general extractor guesses, a financial extractor knows an invoice has a total, a tax amount, and a due date, and where to find them.

In AgentVerse

  • app/ocr/extractors/base.pythe interface + get_extractor factory
  • app/ocr/extractors/financial.pyinvoices, statements, receipts
  • app/ocr/extractors/id_docs.pyidentity documents
  • app/ocr/extractors/general.pythe fallback extractor

Worked example

financial extractor on an invoice
 knows to find: vendor, invoice_no, line_items[], subtotal, tax, total, due
 locates each by layout + keyword + type → typed fields with boxes
 cross-field: subtotal + tax should equal total (a validation hook)

id_docs extractor on a passport
 knows: name, number, DOB, expiry, MRZ → and can checksum the MRZ

At production scale

Kind-specific extractors are where accuracy comes from, and they are worth building for the document kinds you process in volume. The general extractor is the honest fallback for the long tail — it extracts what it can and flags low confidence rather than pretending to understand a form it has no template for.

Failure modes

  • General extractor for everything. Guessed fields.
  • No cross-field checks. A total that does not match its line items, accepted.

Choose it when

  • You process specific document kinds in volume.

04Validation#

ShippedStageImpl8/10Criticality10/10

The stage that makes OCR trustworthy: check each field against format rules, checksums, and cross-field consistency, and escalate anything that fails rather than passing it downstream.

Mechanism

Validators apply deterministic rules: format (a date looks like a date, a GSTIN has 15 characters), checksums (Luhn for cards, MRZ check digits, GSTIN checksum), and cross-field consistency (subtotal + tax = total). A field that fails validation is not silently corrected — it is flagged for LLM vision re-read or human review. This is the difference between "we extracted a total" and "we extracted a total that is internally consistent and correctly formatted".

In AgentVerse

  • app/ocr/validators.pyformat, checksum, cross-field validation
  • app/ocr/engine.pyescalation on validation failure
  • app/governance/hitl.pyhuman review for unresolvable fields

Worked example

extracted invoice
 subtotal 38,200 · tax 3,000 · total 41,200 → 38,200+3,000=41,200 ✓
 GSTIN "27AAAPZ1234C1Z5" → checksum valid ✓
 due_date "31/13/2026" → invalid month → FLAG → re-read → "31/12/2026"
 total confidence 0.61 → below threshold → human confirms against the box
nothing with a failed check reaches the filing step

At production scale

Validation is the stage that lets you automate document workflows that touch money and compliance. The checksum and cross-field checks catch the errors that matter most — a transposed digit in a total passes an eyeball and fails arithmetic. Set confidence thresholds by field consequence: a total needs a higher bar than a memo line.

Failure modes

  • Silent correction. "Fixing" a field to what the validator expected, hiding an error.
  • No cross-field checks. Individually-plausible fields that do not add up.
  • Uniform confidence threshold. A memo line gated as strictly as a total.

Choose it when

  • Any OCR output that feeds an action that must be correct.

05OCR in the platform: ingestion, agents, and privacy#

PartialIntegrationImpl7/10Criticality7/10

OCR is both an ingestion stage (scanned documents become searchable) and an agent tool (extract fields on demand) — and its output is among the most sensitive data the platform handles.

Mechanism

In ingestion, scanned pages route to OCR at the parse stage and the extracted text joins the index (chapter 5). As a tool, an agent calls OCR to extract fields from a document mid-goal — "read this invoice and file it". Either way, the output is classified as sensitive by default: OCR'd documents are exactly the kind that contain personal and financial data, so redaction, retention, and residency all apply.

In AgentVerse

  • app/tools/ocr_tool.pyOCR as an agent tool
  • app/ingestion/parsers/pdf_parser.pythe ingestion path to OCR
  • app/data_classification/classifier.pyclassifying OCR output as sensitive
  • app/lifecycle/retention_policy.pyretention for extracted documents
  • agent-verse-frontend/src/features/ocrthe operator surface (a JARVIS page)

Worked example

agent goal "file the attached invoice"
 ocr_tool.extract(invoice.pdf) → validated fields
 → data classified confidential (contains vendor bank details)
 → PII redacted before any external tool call
 → original + extraction retained per the tenant's retention policy
 → filing step gated (write_high) with the extracted total hashed

At production scale

OCR sits at the intersection of the platform's most valuable and most sensitive workflows — automating invoice, ID, and statement processing — which is exactly why its output needs the full governance treatment. Classify originals as sensitive, apply short retention to raw scans, and keep the located spans so every extracted value can be audited against the source.

Failure modes

  • OCR output not classified. Financial data flowing without redaction.
  • Raw scans retained indefinitely. A compliance liability.
  • Extraction without verifiable spans. No audit path to the original.

Choose it when

  • Any document-processing workflow, especially financial or identity documents.

What is missing here

  • Handwriting and low-resource scripts. The extractors target printed documents in common scripts; handwriting and rare scripts are weaker.
  • Table extraction within documents. Field extraction is strong; complex nested tables inside scanned documents lean on the general path.
  • Confidence calibration per field type. Thresholds are set but not continuously calibrated against human-corrected outcomes.
  • Active-learning from corrections. Human corrections are not systematically fed back to improve extractor accuracy over time.
