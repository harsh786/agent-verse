Retrieval strategies

Vector, lexical, fusion, rerank — and how scores are made comparable.

Orientation

Chapter 2 was about retrieval architectures. This chapter is about the machinery underneath them: the four ways to find candidates, the three ways to combine incomparable scores, the one way to re-rank properly, and the question everybody skips — what do you do when retrieval returns nothing good?

The mental model that makes this tractable is a funnel with widening then narrowing stages. Cheap recall-oriented retrieval produces many candidates; expensive precision-oriented reranking cuts them down; a budget cuts them again. Getting the funnel widths right matters more than which algorithm sits in each stage.

Finding candidates

01Vector similarity#

ShippedRetrieverImpl9/10Criticality10/10

Rank by distance between the query embedding and chunk embeddings — the retriever that understands paraphrase and is blind to exact tokens.

Mechanism

Embed the query with the same model that embedded the corpus, then find nearest neighbours under the metric the model was trained for (usually cosine). Exact search is O(n); production uses an approximate index, which introduces a recall/latency dial — ef_search for HNSW, probe count for IVFFlat.

The parameter that actually decides your quality is not the metric but the candidate width: retrieving 20 and reranking to 6 caps your quality at whatever those 20 contain.

In AgentVerse

  • app/rag/store.py_cosine_similarity() in the memory path; pgvector operators in the DB path
  • app/embedding/vector_index_policy.pyindex and search parameters
  • app/rag/engine.pyRetrievalResult

Worked example

query "can I get my money back"
 0.81  "Refunds are accepted within 30 days of delivery"     ← paraphrase
 0.74  "Reimbursement requests must be filed via the portal"
 0.71  "Store credit is issued for opened items"
 0.31  "Invoice INV-2024-8891"                                ← exact-token
                                                                 query would
                                                                 have wanted this
recall at ef_search=40: 0.91 · at ef_search=200: 0.98 · latency 12ms → 34ms

At production scale

Measure recall against exact search on a sample. Most teams run default ANN parameters and never learn they are losing 8–15% of relevant documents — which then shows up as "the answer was in the corpus" complaints that get blamed on the model.

Retrieve wider than you need. Fetching 100–200 candidates and reranking is nearly always better than fetching 10 and trusting them, because reranking is cheap relative to being wrong.

Failure modes

  • Model mismatch. Query and corpus embedded with different models — results are noise that looks like results.
  • Exact-token blindness. Identifiers, codes, error strings. This is why hybrid exists.
  • Low ANN recall. Silent, systematic, and invisible without an exact-search baseline.
  • Filter interaction. A restrictive filter applied after the ANN limit returns almost nothing.

Choose it when

  • Always as one leg — never as the only leg.

02PostgreSQL full-text search#

ShippedRetrieverImpl9/10Criticality8/10

Stemmed, stop-worded, language-aware lexeme matching in the database — exact enough for terminology, cheap enough to run on every query.

Mechanism

Text is normalised to a tsvector of lexemes at index time using a language configuration; queries become tsquery expressions. Matching is on stems, so "refunding" finds "refund". ts_rank provides a relevance score weighted by lexeme position and frequency. A GIN index makes it fast.

Its virtue in this stack is proximity: it runs inside the same query as the vector search and the metadata filter, so a hybrid retrieval is one round trip.

In AgentVerse

  • app/rag/store.pyhybrid_search_db() — FTS leg
  • app/db/migrations/tsvector columns and GIN indexes

Worked example

query   "refunding damaged items"
tsquery 'refund' & 'damag' & 'item'
match   "Damaged items are refunded in full"  → stems align
miss    "Broken goods are reimbursed"          → different stems entirely
                                                  (vector search catches it)

At production scale

Language configuration per document, not per deployment. A multi-tenant platform will hold English, German and Hindi content, and one global english configuration silently degrades everything else. Store the detected language at ingest and choose the configuration per row.

Failure modes

  • Wrong language config. Poor stemming, silent quality loss.
  • No GIN index. Sequential scans on a large table.
  • Stop-word loss. Queries that are all stop words return nothing.

Choose it when

  • Any hybrid retrieval where the corpus is natural language.

03Trigram fuzzy search#

ShippedRetrieverImpl8/10Criticality8/10

Character-level similarity that survives typos and partial identifiers — the retriever that saves you when a user types INV-2024 or misspells a product name.

Mechanism

Break strings into overlapping three-character sequences and score by the overlap of the two sets. "invoice" and "invocie" share most of their trigrams; so do INV-2024 and INV-2024-8891. It is oblivious to meaning and excellent at surface form, which is precisely the gap the other two retrievers leave.

In AgentVerse

  • app/rag/store.py_trigram_score() in memory; pg_trgm similarity in the DB path
  • app/db/migrations/pg_trgm extension and GIN/GiST indexes

Worked example

query "Norhtwind" (typo)
 vector   0.42 — embedding of a misspelling is not close to the real name
 FTS      no match — 'norhtwind' is not a lexeme of 'northwind'
 trigram  0.71 — 6 of 9 trigrams shared → hit

query "INV-2024"
 trigram  0.83 against INV-2024-8891 → the invoice the user meant

At production scale

Enable trigram indexes on the fields where surface form matters — titles, identifiers, names — rather than on all content, because the indexes are large and slow writes. Bound the query too: trigram search over a million rows without an index is a table scan.

Failure modes

  • False positives. Short strings share trigrams accidentally; use a similarity floor.
  • Index bloat. Trigram indexes on long text columns are expensive.
  • Dominating the merge. High trigram scores on boilerplate crowding out semantic hits; cap its contribution.

Choose it when

  • Users type identifiers, names, or codes — which in enterprise search is most of the time.

04BM25#

ShippedRankingImpl8/10Criticality8/10

The ranking function that has outlived every generation of search technology: term frequency with saturation, inverse document frequency, and length normalisation.

Mechanism

Three ideas. Saturation: the tenth occurrence of a term adds less than the second, controlled by k1. IDF: rare terms discriminate, common terms do not. Length normalisation: a match in a 200-word document means more than one in a 20,000-word document, controlled by b. Together they explain why BM25 still beats naive embedding search on keyword-heavy queries.

In AgentVerse

  • app/rag/bm25.pyBM25Retriever
  • app/rag/store.pycalled as a leg of hybrid_search()

Worked example

query "pgbouncer pool exhaustion"

doc A  runbook, 180 words, "pgbouncer" ×3, "exhaustion" ×2
doc B  handbook, 24,000 words, "pgbouncer" ×3, "exhaustion" ×1
BM25   A ≫ B — same term counts, but B's length normalises them away
IDF    "pgbouncer" is rare in this corpus → high weight
       "pool" is common → low weight

At production scale

Compute IDF over the collection being searched, not globally. A term that is rare across the whole tenant may be ubiquitous in one collection, and using global statistics makes ranking within that collection wrong.

Default parameters (k1≈1.2, b≈0.75) are good. Tuning them is rarely the highest-value work available.

Failure modes

  • Wrong corpus statistics. Global IDF on a per-collection search.
  • Stale statistics. IDF computed once and never updated as the corpus grows.
  • Keyword stuffing. Documents that repeat terms; saturation limits but does not eliminate this.

Choose it when

  • Any lexical leg. It is the correct default ranking function for keyword matching.

05Metadata pre-filtering#

ShippedPrecisionImpl8/10Criticality9/10

The only stage that improves precision, latency and safety simultaneously — and it costs nothing but a well-designed metadata schema.

Mechanism

Apply hard constraints before scoring: tenant, collection set, jurisdiction, classification level, date range, document type, language. This shrinks the candidate space, which raises the effective recall of the ANN search (fewer irrelevant neighbours competing), reduces query latency, and enforces access rules at the index rather than in a post-filter.

The ordering rule from chapter 3 applies here too: filter, then score. Post-filtering means the restricted rows were read.

In AgentVerse

  • app/rag/store.pyfilters in the DB query
  • app/rag/gateway.pySQLCollectionAuthorizer — collection scope resolved before retrieval
  • app/db/rls.pytenant filter enforced by the database independently

Worked example

unfiltered   1.2M chunks → ANN top 200 → 14 relevant
filtered     tenant + collection[policies] + jurisdiction=DE + class≤internal
             → 6,400 chunks → ANN top 200 → 61 relevant
same model, same k, 4× better precision, 40% lower latency

At production scale

Index every field you filter on, and beware the ANN-plus-filter interaction: with a very selective filter, some index implementations return fewer than k rows or fall back to a scan. Test your selective-filter cases explicitly — they are the ones that behave differently in production than in staging.

Failure modes

  • Post-filtering. A leak and a performance bug in one.
  • Unindexed filter fields. Correct and unusably slow.
  • Over-filtering. Empty results; the agent then replans against nothing.

Choose it when

  • Always. It is the cheapest precision available.

Combining and re-ranking

06Hybrid scoring and normalisation#

ShippedFusionImpl8/10Criticality9/10

Four retrievers produce four incomparable numbers. You must either normalise them onto a common scale or discard the magnitudes and use ranks — but you cannot simply add them.

Mechanism

Cosine similarity lives in roughly [0,1] with a compressed useful range; BM25 is unbounded and corpus-dependent; trigram similarity is [0,1] with different semantics; ts_rank has its own scale. Three approaches:

  • Min-max normalisation per retriever per query — simple, but one outlier distorts the whole scale.
  • Z-score normalisation — more robust, needs enough candidates to estimate the distribution.
  • Rank fusion — ignore magnitudes entirely; this is why RRF is the usual answer.

Weighted sums of normalised scores are workable when you have an eval set to tune the weights on. Made up weights are worse than rank fusion.

In AgentVerse

  • app/rag/store.pyHybridSearchResult — the merged shape
  • app/rag/engine.pyhybrid_search / rerank_results
  • app/context/rerank_policy.pyper-source caps applied after merging

Worked example

raw scores for the same chunk set
 chunk  cosine  bm25   trigram
 c1     0.62    12.4   0.10
 c2     0.71     0.0   0.05
 c3     0.55     8.1   0.83

naive sum   c1 13.12 · c3 9.48 · c2 0.76   ← bm25 magnitude dominates entirely
min-max     c1 1.55  · c3 1.72 · c2 1.05   ← plausible
RRF         c3 ranked 1st by trigram and 2nd by bm25 → wins on consistency

At production scale

Start with RRF, because it requires no calibration and cannot be broken by a scale change in one retriever. Move to weighted normalised scores only when you have a labelled eval set and a measured reason. Whatever you choose, log the per-retriever scores — when a result looks wrong, the merge is the first place to look.

Failure modes

  • Adding raw scores. One retriever silently decides everything.
  • Normalising over too few candidates. Unstable scales query to query.
  • Double counting. The same chunk from two retrievers, counted twice.

Choose it when

  • Any time you run more than one retriever — so, always.

07Reciprocal rank fusion#

ShippedFusionImpl8/10Criticality8/10

Score each document by Σ 1/(k + rank) across result lists. No calibration, no tuning, robust to any number of heterogeneous retrievers — the default merge for a reason.

Mechanism

For each result list, a document at rank r contributes 1/(k + r) with k≈60. The constant flattens the top of the curve, so being 1st versus 3rd matters less than appearing in several lists at all. Documents found by multiple independent retrievers rise; documents found by one retriever with a suspiciously high score do not automatically win.

It works for merging retrievers, merging query variants (fusion RAG), and merging federated sources — anywhere scores are not comparable.

In AgentVerse

  • app/rag/agentic/patterns/fusion.pymulti-query fusion
  • app/knowledge/federated_search.pycross-source merge
  • app/rag/engine.pymerge in the retrieval path

Worked example

k = 60
doc   vector  bm25  trigram   RRF
c3      2      2      1       1/62 + 1/62 + 1/61 = 0.0486   ← consensus
c1      1      -      -       1/61                = 0.0164
c7      -      1      3       1/61 + 1/63         = 0.0323
ordering: c3, c7, c1 — not what any single retriever said

At production scale

RRF's weakness is the flip side of its strength: it discards magnitude, so a single retriever that is genuinely confident and correct can be outvoted. Where one retriever is known to be authoritative for a query class (exact identifier matches, for example), give it a rank bonus or short-circuit to it rather than fusing.

Failure modes

  • Correlated lists. Three retrievers that agree because they are similar, not because the document is right.
  • Losing a confident singleton. The exact-match document outvoted by three vague ones.
  • Wrong k. Very small k over-weights first place; very large k flattens everything.

Choose it when

  • Merging anything heterogeneous. Start here.

08Cross-encoder reranking#

ShippedPrecisionImpl8/10Criticality9/10

Score each (query, chunk) pair with a model that reads them together — far more accurate than comparing two independently-computed vectors, and affordable only on a small candidate set.

Mechanism

A bi-encoder embeds query and document separately, so it can never model their interaction. A cross-encoder takes the concatenation and outputs a relevance score, letting attention connect query terms to document terms directly. The cost is that it cannot be precomputed: every pair needs an inference. Hence the funnel — retrieve 200 cheaply, rerank those 200, keep the top 10.

Two engineering requirements make this production-safe: run inference off the event loop through a bounded executor (a synchronous model call in an async server stalls everything), and distinguish load failures from inference failures so a missing model degrades rather than erroring every query.

In AgentVerse

  • app/rag/cross_encoder.pyCrossEncoderReranker, _score_blocking(), cross_encode(), build_reranker()
  • app/rag_platform/reranker_contract.pyRerankerProtocol, BoundedAsyncExecutor, RerankerLoadError, RerankerInferenceError
  • app/rag_platform/reranker.pyCrossEncoderDocumentReranker
  • app/context/rerank_policy.pypolicy: what to rerank and how deep

The protocol-plus-bounded-executor design is the part worth copying: reranking is CPU-bound inference inside an IO-bound service, and that mismatch is the usual cause of mysterious latency spikes.

Worked example

query "does the warranty cover water damage?"

bi-encoder top 5 (by cosine)
 1  0.72  "Warranty terms and conditions"          generic
 2  0.70  "Water damage is excluded from coverage"  ← the answer
 3  0.69  "Warranty registration process"
cross-encoder rerank
 1  0.94  "Water damage is excluded from coverage"
 2  0.31  "Warranty terms and conditions"
 3  0.12  "Warranty registration process"
the answer moves from position 2 to 1, and the noise is clearly separated

At production scale

Rerank depth is a direct latency/quality dial: 200 candidates on a small cross-encoder is roughly 30–80ms on CPU, and grows linearly. Pick the depth from your latency budget, and cache rerank scores by (query hash, chunk id) — agents re-issue similar queries constantly within a goal.

If reranking is your latency bottleneck and quality still matters, that is the point at which late-interaction retrieval (ColBERT, chapter 2) starts to earn its index cost.

Failure modes

  • Blocking the event loop. Synchronous inference in an async handler — the bounded executor exists for this.
  • Reranking too shallow. Reranking 10 candidates cannot fix a recall problem.
  • Model not loaded. Treat as a readiness fact and delegate, not as a 500.
  • Domain mismatch. A general reranker on specialised jargon can be worse than the bi-encoder; measure.

Choose it when

  • Precision matters and you can afford tens of milliseconds.
  • Skip when candidates are already few and clearly correct.

09Score calibration and thresholds#

PartialPrecisionImpl6/10Criticality8/10

A relevance score is only useful if you know what "good" means. Calibration turns model outputs into a threshold you can act on — including the decision to return nothing.

Mechanism

Raw scores are not probabilities and are not comparable across models, corpora or query types. To act on them you need a mapping from score to expected relevance, built from labelled pairs: sample queries, have humans or a strong judge label the top results, then fit the threshold at your chosen precision/recall trade-off. Recalibrate whenever the embedding model, the reranker, or the corpus changes materially.

The payoff is the ability to say "nothing here is relevant" — which is the single most valuable behaviour a retrieval system can have and the one that requires a calibrated floor.

In AgentVerse

  • app/rag/evaluation.pyretrieval evaluation
  • app/evals/rag_score.pyretrieval scoring (chapter 10)
  • app/intelligence/verifier_calibration.pythe same discipline applied to verifier thresholds
  • app/rag/agentic/patterns/corrective.pythe consumer: a graded threshold decides the branch

Rated 6: evaluation and calibration machinery exist, but there is no continuous per-collection threshold calibration feeding the live retrieval path.

Worked example

labelled sample, 300 queries, cross-encoder scores
 score ≥ 0.80  precision 0.96  recall 0.41
 score ≥ 0.50  precision 0.87  recall 0.78
 score ≥ 0.30  precision 0.61  recall 0.93
choose 0.50 for general search, 0.80 for regulated answers
and "top score < 0.30" → return "not found", do not answer

At production scale

Per-collection thresholds beat one global threshold, because corpora differ in density and vocabulary. Store the threshold with the collection and revisit it when the collection changes shape.

The behaviour to protect above all: an honest "I could not find this in your documents". Every hallucination-mitigation technique downstream is more expensive than a calibrated floor upstream.

Failure modes

  • Uncalibrated thresholds. A number someone picked; either drops good results or admits junk.
  • Global threshold. Wrong for most collections.
  • Stale calibration. Model changed, threshold did not.
  • No floor at all. The system always answers, whatever it found.

Choose it when

  • Any system that must be able to say "not found" — which is any system used for real decisions.

Shaping what comes back

10Parent-child retrieval#

ShippedWindowImpl8/10Criticality8/10

Search small, return large: match on precise child chunks, then hand the model the parent section so it has enough context to answer.

Mechanism

Index fine-grained children (200–400 tokens) for precision, but store a parent reference on each. After ranking, replace or augment the matched children with their parents, deduplicating where several children of one parent matched. Citations should point at the child (precise) while the prompt carries the parent (complete).

This resolves the oldest tension in chunking: small chunks retrieve better, large chunks answer better.

In AgentVerse

  • app/rag/parent_child_chunker.pythe chunker
  • app/rag/store.py_expand_agentic_parent_citations()
  • app/context/context_budget.pyparents are bigger — the budget has to know

Worked example

matched children
  c#3 "The limit is 30 days from delivery."          0.88
  c#4 "Damaged goods are exempt."                     0.81
  c#9 (different parent) "Enterprise terms override." 0.74

expanded → parent §Refunds (1,100 tokens, contains c#1..c#6)
         + parent §Enterprise (600 tokens)
two coherent sections instead of three fragments; citations still name
c#3, c#4, c#9 so the user lands on the exact sentence

At production scale

Watch the budget: three matched children can expand into three 1,500-token parents and consume the whole context window. Cap parent expansion, deduplicate parents, and prefer expanding only the top few matches.

Failure modes

  • Budget explosion. Expansion without a cap.
  • Duplicate parents. The same section included three times.
  • Oversized parents. A parent that is the whole document defeats the purpose.

Choose it when

  • Documents have real sections and answers need surrounding context.
  • Skip for short, self-contained records (tickets, FAQ entries).

11Sentence-window retrieval#

ShippedWindowImpl8/10Criticality7/10

Index individual sentences for maximum precision, then return the n sentences either side — a sliding window instead of a fixed hierarchy.

Mechanism

Each sentence is a separately embedded unit, so matching is extremely precise. At return time, expand to a window of surrounding sentences to restore readability and pronoun resolution. Unlike parent-child, the window is symmetric and boundary-free, which suits flowing prose that has no clean section structure.

In AgentVerse

  • app/rag/sentence_window.pythe implementation
  • app/rag/chunker.pysentence splitting

Worked example

matched sentence  "It must be filed within 14 days."
window ±2
  "Amendments are permitted for the current quarter only.
   The form is available in the portal.
 → It must be filed within 14 days.
   Late filings incur a 2% penalty.
   The penalty is waived for first offences."
without the window, "it" and "within 14 days of what" are unanswerable

At production scale

Sentence-level indexing multiplies chunk count — a 40-chunk document becomes 400 sentences — which raises index size and embedding cost proportionally. It is worth it for dense reference material where precision is paramount, and wasteful for corpora where paragraph-level matching already works.

Failure modes

  • Index inflation. Ten times the vectors for a modest precision gain.
  • Bad sentence splitting. Abbreviations and decimals split mid-sentence.
  • Window crossing boundaries. A window that spans two unrelated sections.

Choose it when

  • Precision is critical and documents are flowing prose (legal, regulatory, contracts).
  • Avoid when index cost matters more than the last few points of precision.

12Query expansion#

ShippedQueryImpl8/10Criticality7/10

Add terms the user did not type — synonyms, abbreviation expansions, domain vocabulary — so lexical retrieval stops missing documents that say the same thing differently.

Mechanism

Three sources of expansion terms, in increasing cost: a curated synonym and abbreviation table (cheap, precise, tenant-specific), corpus co-occurrence statistics (free, noisy), and an LLM (flexible, metered). The best results come from the table for the terms you know and the model for the rest.

Expansion helps lexical retrieval most; vector search already handles paraphrase, so expanding a query before an embedding-only search often changes little.

In AgentVerse

  • app/rag/agentic/query_expander.pyexpansion
  • app/rag/agentic/query_reformulator.pyreformulation
  • app/rag/agentic/llm_query_transformer.pymodel-based transforms
  • app/rag/agentic/search_directive_parser.pystructured directives inside a query

Worked example

query "PTO policy"
table  PTO → "paid time off", "annual leave", "vacation"
expanded tsquery: ('pto' | 'paid time off' | 'annual leave' | 'vacation')
                  & 'policy'
effect  the German entity's "annual leave" handbook now matches, which the
        unexpanded lexical query missed entirely

At production scale

The tenant-specific abbreviation table is high-value manual data — every organisation has fifty acronyms that appear in no dictionary. Make it editable by support, seed it from frequent zero-result queries, and treat it as part of the knowledge base rather than as configuration.

Failure modes

  • Over-expansion. Precision collapses as the query matches everything.
  • Wrong-sense synonyms. "Charge" expanded to "fee" in a battery context.
  • Cost per query. An LLM expansion on every search, most of which did not need it.

Choose it when

  • Domain jargon and abbreviations are common, and lexical retrieval is a real leg.
  • Less useful for pure vector search.

13Multi-query retrieval#

ShippedQueryImpl8/10Criticality7/10

Issue several genuinely different queries instead of one — decomposition for compound questions, perspectives for ambiguous ones — then fuse.

Mechanism

Distinct from expansion (which adds terms to one query) and from fusion RAG (which rephrases the same intent): multi-query decomposes. "Compare our refund policy with our warranty policy" is two retrievals whose results should not be pooled by similarity but kept separate and then compared.

The implementation detail that matters: run the sub-queries concurrently, and keep their result sets labelled so the model can tell which evidence answers which part.

In AgentVerse

  • app/rag/agentic/query_reformulator.pydecomposition
  • app/rag_platform/query_planner.pyplans a multi-part retrieval
  • app/rag/agentic/patterns/fusion.pythe pooled-merge variant

Worked example

"how do our refund and warranty terms differ for enterprise customers?"
 q1  refund terms, enterprise      → 4 chunks  [A]
 q2  warranty terms, enterprise    → 3 chunks  [B]
 q3  enterprise contract overrides → 2 chunks  [C]
kept separate and labelled; the model compares A against B under C
pooling them by score would have returned 6 refund chunks and no warranty

At production scale

Compound questions are common and single-query retrieval handles them badly — usually returning everything about the dominant term. Detecting "this is two questions" is worth a cheap classifier, and the concurrency makes it nearly free in latency.

Failure modes

  • Bad decomposition. Sub-queries that do not cover the original.
  • Pooling when you should not. Comparison questions need separated evidence.
  • Budget multiplication. Three sub-queries × parent expansion overflows the window.

Choose it when

  • Questions contain conjunctions, comparisons, or several entities.

14Retrieval confidence and fallback paths#

PartialSafetyImpl7/10Criticality10/10

The most important behaviour in retrieval is knowing when it failed — and having an ordered set of alternatives that ends in an honest "not found" rather than an answer.

Mechanism

Compute a confidence signal from the result set: top score against the calibrated floor, score gap between first and fifth (a flat distribution means nothing stood out), candidate count after filtering, and coverage of the query's key terms. Below threshold, walk a fallback chain rather than answering:

  1. Relax the metadata filter (drop the date range, widen the collection set).
  2. Expand or reformulate the query.
  3. Try another strategy (hybrid → fusion → agentic).
  4. Try another source (a different collection, the graph, the web if permitted).
  5. Return "not found" with what was searched.

Each step must be recorded, so the trace explains why the answer took nine seconds or why it is empty.

In AgentVerse

  • app/rag/agentic/fallback_chain.pyFallbackChain
  • app/rag/agentic/context_gap_detector.pyGapReport — what is missing
  • app/rag/agentic/patterns/corrective.pygrading that drives the branch
  • app/agent/graph.pyrag_remediate — the agent-level fallback node
  • app/rag/gateway.pydelegation when a strategy is unavailable

Worked example

query "APAC revenue recognition policy"
attempt 1  hybrid, collection=policies, jurisdiction=APAC
           → 0 candidates after filter        (no APAC docs exist)
attempt 2  relax jurisdiction                  → 3 candidates, top score 0.28
                                                  → below floor 0.50
attempt 3  fusion with expansion               → top score 0.34, still below
attempt 4  graph: is there an owning team?     → yes, finance-apac
result     "No APAC revenue-recognition policy is indexed. The global policy
            (POL-204) may apply; the owning team is finance-apac. Searched:
            policies, finance, legal collections."

At production scale

This is the single highest-leverage feature for trust. Users forgive "I could not find it"; they do not forgive a confident wrong answer assembled from three irrelevant documents. Track the "not found" rate per collection — it is your knowledge-gap backlog, and it is more actionable than any satisfaction survey.

Bound the chain. Four attempts with reranking each can turn a 300ms query into four seconds; set a total retrieval deadline and return the honest answer when it expires.

Failure modes

  • No confidence signal. The system always answers.
  • Unbounded chains. Latency blowout on the queries that were never going to succeed.
  • Silent fallbacks. Nobody can explain the latency or the substitution.
  • Fallback to the web from a regulated collection. Policy must gate the chain, not just quality.

Choose it when

  • Always. This is the difference between a search feature and a trustworthy one.

15Retrieval tracing#

ShippedOperationsImpl8/10Criticality8/10

Every retrieval emits a structured trace: which strategy, which filters, how many candidates per retriever, what the scores were, what was cut and why.

Mechanism

A trace per retrieval with one leg per retrieval operation, capturing query text (or hash), strategy, filters applied, candidate counts, top scores, rerank deltas, and the final selection with reasons for exclusion. Attached to the goal and the request so a user complaint maps to an exact retrieval.

Without this, retrieval quality is unfalsifiable: you cannot tell a recall failure from a ranking failure from a budget cut, and all three feel identical to the user.

Worked example

trace for goal g-8891 step 2
 strategy   hybrid → rerank
 filters    tenant=acme, collections=[policies,legal], class≤internal
 legs       vector  200 candidates, top 0.71, 34ms
            bm25    140 candidates, top 11.2, 12ms
            trigram  60 candidates, top 0.44,  8ms
 merged     312 unique → RRF → top 50
 reranked   50 → top 8, cross-encoder 0.94…0.41, 62ms
 budget     8 → 6 (2 dropped: over 9k token cap)
 excluded   c#118 (0.39 below floor), c#204 (duplicate of c#201)

At production scale

Sample rather than store everything: full traces on 1–5% of traffic plus all failures gives you debuggability without a storage problem. Hash query text by default and store it in clear only where the tenant has consented — queries are user content and often contain personal data.

Failure modes

  • No trace. Quality complaints become unanswerable.
  • Traces without scores. You can see what was returned, not why.
  • PII in traces. Query text stored indefinitely in a log nobody classified.

Choose it when

  • Before you need it. Retrofitting traces during an incident is not fun.

What is missing here

  • Continuous threshold calibration. Thresholds are configured, not learned from ongoing labelled feedback per collection.
  • Learned fusion weights. RRF is untuned by design; a per-query-class weighting learned from click or acceptance signal would beat it.
  • Reranker distillation. Nothing feeds cross-encoder judgements back into the bi-encoder, which is the standard way to make cheap retrieval better over time.
  • Recall monitoring in production. ANN recall is measurable offline but not tracked continuously against an exact-search sample.
  • Query understanding as a first-class stage. Expansion, decomposition and filter inference are separate components rather than one query-understanding step with its own eval.
