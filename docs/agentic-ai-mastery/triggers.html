Triggers & event-driven agents

Cron, webhooks, IoT, data change — agents nobody typed a prompt into.

Orientation

Every goal so far started because a human asked. Triggers are the other half of an agent platform: goals that start because the world changed — a schedule fired, a webhook arrived, a metric crossed a threshold, a sensor reported, a row was inserted. This is what turns a request/response tool into an autonomous operator that watches and acts.

And it is where autonomy's risks concentrate. A trigger acts on behalf of someone who is not present, so the discipline is every trigger fires a normal, fully-governed goal — same auth, budget, approval gates, and audit — plus the trigger-specific controls (verification, rate-limiting, dedup, stale authorisation checks) that a request from a live user does not need.

Event-driven agents

01Natural-language scheduling#

ShippedSchedulingImpl8/10Criticality7/10

"Every weekday at 9am, summarise overnight incidents" becomes a trigger spec — cron and goal template parsed from plain language.

Mechanism

An NL scheduler parses a natural-language schedule into a TriggerSpec: a cron expression (via croniter), a goal template, and any parameters. It is the meta-agent idea (chapter 9) for schedules — a human describes what and when, the parser produces a governed, editable spec. The spec is stored and fired by beat.

In AgentVerse

  • app/triggers/nl_scheduler.pyparse() — NL → TriggerSpec
  • app/triggers/models.pyTriggerSpec, TriggerType
  • app/triggers/store.pyScheduleStore
  • app/scaling/tasks.pyfire_due_schedules, run_scheduled_goal

Worked example

"every weekday at 9am, summarise overnight incidents and post to #ops"
 → TriggerSpec(cron="0 9 * * 1-5", template="incident-summary", channel="#ops")
 stored → beat fires it at 9am on weekdays → submits a governed goal
editable and reviewable, not code

At production scale

NL scheduling makes autonomous work authorable by non-engineers, which is the point — but the resulting spec must be reviewable and editable, because "every weekday at 9am" parsed wrong is a goal firing at the wrong time indefinitely. Jitter scheduled goals (chapter 5) so a fleet of 9am triggers does not stampede.

Failure modes

  • Misparsed schedule. A trigger firing at the wrong time forever.
  • Unjittered fleet. A stampede at the top of the hour.

Choose it when

  • Recurring autonomous work authored by humans.

02Webhook triggers#

ShippedSourceImpl8/10Criticality8/10

An external event (a payment failed, a PR opened) submits a goal — with signature verification, secret rotation, and rate-limiting, because a webhook endpoint is an attacker-reachable front door.

Mechanism

A webhook arrives; the platform verifies its signature against the source's secret (which is rotated), parses the payload, and — if valid — submits a goal. Because the endpoint is public, it needs the full defence: signature verification (reject forgeries), rate-limiting (absorb floods), dedup (webhooks are often delivered more than once), and treating the payload as untrusted input (chapter 12).

In AgentVerse

  • app/triggers/webhooks/verifier.py, rotation.py, parsers.pyverification, secret rotation, parsing
  • app/triggers/dedup.py, rate_limiter.py, bulkhead.pydedup, rate-limit, bulkhead
  • app/triggers/dispatcher.pydispatch to a goal
  • app/gateway/channels/webhook.py, app/gateway/webhook_delivery.pythe channel

Worked example

Stripe webhook: payment.failed
 verify signature against the rotated secret → valid
 dedup: this event id seen before? no → proceed (webhooks retry)
 rate-limit: within bounds → dispatch a "triage failed payment" goal
 forged webhook → signature fails → rejected, logged

At production scale

The webhook endpoint is one of the few genuinely public, attacker-reachable surfaces. Signature verification is non-negotiable — without it, anyone can submit goals as any tenant. Dedup matters because webhook providers deliver at-least-once, so the same payment.failed can arrive three times and must fire one goal. Rate-limiting absorbs the flood when an upstream misbehaves.

Failure modes

  • Unverified webhooks. Attacker-submitted goals.
  • No dedup. One event firing three goals.
  • No rate-limit. An upstream flood becoming your outage.

Choose it when

  • External systems should drive agent actions.

03Data-change and IoT triggers#

PartialSourceImpl7/10Criticality6/10

Goals that fire when data changes or a sensor reports — a row inserted, a metric crossing a threshold, a geofence entered — with condition evaluation deciding whether the change warrants action.

Mechanism

Data-change triggers watch a source (a table, a stream) and fire when a condition matches. IoT triggers consume sensor and device signals — MQTT messages, geofence events, sensor thresholds. A condition evaluator decides whether a given change is significant enough to act on, so not every row insert or sensor reading becomes a goal. Monitoring triggers watch metrics and fire on threshold breaches.

In AgentVerse

  • app/triggers/data/consumers.pydata-change triggers
  • app/triggers/iot/mqtt.py, geofence.py, sensor.pyIoT sources
  • app/triggers/condition/evaluator.pycondition evaluation
  • app/triggers/monitoring/parsers.py, advanced/consumers.pymonitoring and advanced triggers

Worked example

data-change: a high-value order inserted
 condition: order.amount > ₹500,000 AND customer.risk = high → fire a
 fraud-review goal (most orders do not match → no goal)
IoT: a cold-storage sensor reports temperature > threshold for 5 min
 → fire an alert-and-remediate goal

At production scale

The condition evaluator is what keeps data and IoT triggers from firing constantly — the difference between "a goal per row insert" (unusable) and "a goal per significant change" (useful). Threshold and debounce logic (temperature over threshold for 5 minutes) prevents a flapping sensor from firing a hundred goals. These triggers make the platform reactive to the physical and data world.

Failure modes

  • Firing on every change. A goal per row insert.
  • Flapping sensors. No debounce, a hundred goals.
  • Missed significant changes. A condition too narrow.

Choose it when

  • Agents should react to data or physical-world changes.

04Dispatch, dead-letter, and trigger safety#

ShippedSafetyImpl8/10Criticality9/10

The controls that make autonomous triggers safe: re-check authorisation at fire time, rate-limit and bulkhead per tenant, quota-limit, and dead-letter failures — because a trigger acts without a human watching.

Mechanism

The dispatcher fires the goal but first applies the trigger-specific safety layer: re-check that the authorisation the trigger was created under is still valid (the user may have left), enforce per-tenant rate limits and bulkheads (a trigger must not stampede the fleet), enforce quotas, and dead-letter failures with backoff. A circuit breaker stops a repeatedly-failing trigger. State machines track trigger lifecycle; simulation lets a trigger be tested before it goes live.

In AgentVerse

  • app/triggers/dispatcher.py, state_machine.pydispatch and lifecycle
  • app/triggers/dlq.py, circuit_breaker.py, quota.pyDLQ, breaker, quota
  • app/triggers/rbac.py, events.py, metrics.pyauthorisation, events, metrics
  • app/triggers/simulation.py, consumers/hitl.py, consumers/chain.py, consumers/memory.pysimulation, HITL, chaining, memory consumers

Worked example

a scheduled trigger fires
 re-check auth: the creating user still has permission? → yes (or the
   trigger is disabled if they left)
 rate-limit + bulkhead: within the tenant's ceiling → proceed
 dispatch a normal governed goal
 [on repeated failure] → DLQ + backoff + breaker → stop retrying, alert

At production scale

The stale-authorisation check is the subtle, critical one: a trigger created by an employee who has since left must not keep acting on their authority — so authorisation is re-checked at fire time, not just at creation. Rate-limiting and bulkheading matter because an unbounded trigger is a self-inflicted load spike that no human requested. Simulation before go-live catches the trigger that would fire far more often than intended.

Failure modes

  • Stale authorisation. A trigger acting for a departed user.
  • Unbounded firing. A load spike nobody scheduled.
  • Unattended DLQ. Failed triggers silently dropped.
  • No simulation. A trigger that fires far too often, discovered live.

Choose it when

  • Always, for any trigger — this is the price of autonomy.

What is missing here

  • Trigger impact preview. Simulation tests behaviour, but a "this trigger would have fired N times last month" preview before activation is thin.
  • Cross-trigger coordination. Two triggers firing overlapping goals are not deduplicated at the goal level.
  • Prospective-memory integration. An agent setting its own future trigger (chapter 3) is a thinner path than externally-configured triggers.
  • Complex event processing. Conditions are per-event; correlating a pattern across multiple events over time is future work.
