Orientation

This chapter collects the cross-cutting infrastructure that the goal lifecycle depends on but that does not belong to any single step: the provider abstraction, the reliability primitives (bulkheads, breakers, dedup, rollback), the persistence and messaging layers, the schedulers, and the external integration boundaries. None of it is glamorous; all of it is the difference between a system that demos and one that stays up.

The recurring theme is isolation and idempotency: every shared resource is bounded per tenant so one cannot starve another, and every side-effecting operation is made safe to repeat so that retries — which are constant in a distributed agent system — do not double-charge, double-send, or double-file.

The primitives

01MCP registry and clients#

ShippedIntegrationImpl9/10Criticality9/10

The Model Context Protocol is the platform's device-driver layer: tools live in their own processes behind a uniform protocol, registered per tenant, so the tool surface is configuration and a bad connector cannot take the agent down.

Mechanism

A per-tenant registry holds connector definitions; the client discovers tools (tools/list) and executes them (call_tool) over HTTP or WebSocket, wrapped in circuit breakers, caches, and credential resolution. Connectors are certified before use, can be imported from OpenAPI specs, and support agent-to-agent (A2A) calls. The 325 built-in server modules cover common integrations; tenants add their own.

In AgentVerse

  • app/mcp/registry.py, client.py, ws_client.pyregistry and clients
  • app/mcp/catalog.py, capability_search.pydiscovery
  • app/mcp/certification.py, certification_manifest.pyconnector certification
  • app/mcp/openapi_importer.pyimport tools from an OpenAPI spec
  • app/mcp/a2a.py, app/agent/tools/a2a_call.pyagent-to-agent calls
  • app/mcp/servers/325 built-in server modules

Worked example

tenant adds a connector from an OpenAPI spec
 openapi_importer → tool definitions → certification (mocked probes)
 registered per tenant → discoverable by that tenant's agents only
 call_tool wraps each invocation in a breaker + cache + vault credential
one connector crashing affects only its own calls, not the agent process

At production scale

Process isolation per connector is the property that makes a large tool ecosystem safe: a connector with a memory leak, a hang, or a crash degrades only its own tool, and the breaker routes around it. Certification before use catches the connector that returns malformed results before an agent trusts it. Full treatment of the call path in chapter 19.

Failure modes

  • Uncertified connectors. Malformed results trusted by agents.
  • Cross-tenant tool visibility. One tenant's connector reachable by another.

Choose it when

  • Any agent that integrates with external systems.

02Provider abstraction#

ShippedAbstractionImpl9/10Criticality9/10

One interface for every LLM and embedding backend, resolved from env keys at startup, with a deterministic fake for tests — the abstraction that makes the platform genuinely vendor-neutral.

Mechanism

A common protocol (CompletionRequest, Message, EmbedRequest) covers completion and embedding; concrete providers implement it and are auto-detected from configured API keys. The registry resolves the right provider per request; the fake provider gives deterministic output with no keys. This is what lets cross-provider verification, provider fallback, and per-role routing exist at all — they all depend on the backends being interchangeable.

In AgentVerse

  • app/providers/base.pyCompletionRequest, Message (hub nodes), EmbedRequest, the protocol
  • app/providers/registry.pyresolve_provider() — auto-detection
  • app/providers/anthropic_provider.py, openai_compatible.py, gemini_provider.py, voyage_provider.py, ollama_provider.py, nvidia_nim_provider.py, openrouter_provider.pybackends
  • app/providers/fake.pyFakeProvider
  • app/providers/vault.pyencrypted credential store

Worked example

startup  ANTHROPIC_API_KEY and OPENAI_API_KEY set
 registry auto-detects both → available for routing
 no keys → FakeProvider only → the whole stack runs in CI deterministically
one CompletionRequest shape → any backend answers it → the router chooses
which, the loop does not know or care

At production scale

Vendor neutrality is not idealism here — it is the precondition for the reliability and cost features elsewhere in the book. Cross-provider consensus needs two real providers; fallback needs a second backend; per-role routing needs a choice. The deterministic fake is what makes the whole platform testable without keys or network. Full treatment in chapters 7 and 16.

Failure modes

  • Leaky abstraction. Vendor specifics reaching calling code.
  • No fake. Tests that need keys and network.

Choose it when

  • Always. Single-vendor deployments still need it for testing and fallback.

03Bulkheads, breakers, deduplication, idempotency#

ShippedReliabilityImpl8/10Criticality10/10

The four primitives that keep a distributed agent system from taking itself down: bounded per-tenant concurrency, breakers on flaky dependencies, dedup of repeated work, and idempotency so retries are safe.

Mechanism

Bulkhead: a per-tenant concurrency ceiling, so one tenant's fan-out cannot exhaust the shared worker pool or connection pool. Circuit breaker: after repeated failures on a dependency, stop calling it and fail fast (or serve stale) until it recovers. Deduplication: recognise a repeated request and return the prior result rather than re-doing it. Idempotency: derive a key from goal+step+arguments so a retried write is recognised as the same write, not a new one.

In AgentVerse

  • app/reliability/bulkhead.pyper-tenant concurrency
  • app/reliability/circuit_breaker.py, redis_circuit_breaker.pybreakers (in-process and cross-replica)
  • app/reliability/dedup.py, app/services/dedup.pydeduplication
  • app/reliability/idempotency.pyidempotency keys
  • app/reliability/result_processor.pysanitize/redact/truncate tool output

Worked example

bulkhead     acme capped at 50 concurrent tool calls → a 200-way fan-out
             queues rather than exhausting the pool → other tenants unaffected
breaker      the CRM connector fails 5× → open → fail fast for 60s → half-open
             probe → recovered → close
dedup        the same read issued twice in one goal → second served from cache
idempotency  a retried "create invoice" carries the same key → recognised,
             not duplicated → the customer is billed once

At production scale

These four are what separate a system that survives failure from one that amplifies it. Idempotency in particular is non-negotiable for an agent that writes — retries are constant, and without idempotency keys a retried "send invoice" sends three. The bulkhead is the ceiling that no amount of enthusiastic spawning (chapter 1) can breach. Full treatment in chapter 28.

Failure modes

  • Retry without idempotency. Duplicate side effects.
  • No bulkhead. One tenant's fan-out starving the fleet.
  • Per-replica breaker only. The fleet not learning a dependency is down.

Choose it when

  • Always. This is production reliability, not an add-on.

04Rollback and compensating actions#

ShippedReliabilityImpl8/10Criticality9/10

When a multi-step goal fails partway, the rollback engine applies registered inverses in LIFO order to undo the side effects — so a failed goal leaves no half-built state for a human to untangle.

Mechanism

For each executed tool that has a registered inverse (create→delete, grant→revoke, post→retract), the executed action and its inverse are recorded. On terminal failure, the rollback engine walks the executed actions in reverse order and applies each inverse. Actions with no inverse — you cannot un-send an email — are classified as irreversible and gated behind approval before they run (chapter 1).

In AgentVerse

  • app/reliability/rollback.pyRollbackEngine — LIFO compensation
  • app/reliability/tool_inverses.pythe inverse registry
  • app/memory/execution.pythe record of what was executed
  • app/recovery/*failure classification that triggers rollback

Worked example

goal fails at step 4
 executed  1 create epic  2 create sub-tasks  3 post to slack
 rollback (LIFO)  3 delete slack msg → 2 delete sub-tasks → 1 delete epic
 result   the goal failed cleanly; no orphaned records
step 3 had been "send external email" → no inverse → it would have been
gated behind approval before running

At production scale

Rollback is the feature most agent frameworks lack and the one that makes write-capable agents trustworthy. The pairing that matters: classify tools by compensability as well as risk, and put the irreversible ones behind HITL. A failed rollback (the inverse itself fails) is a human ticket, never a silent swallow. Full treatment in chapter 1.

Failure modes

  • Missing inverses. Nothing to compensate with.
  • Rollback failure swallowed. Half-undone state, unreported.
  • Irreversible actions ungated. Damage that cannot be undone.

Choose it when

  • Any agent that writes to systems of record.

05Postgres, pgvector, and RLS#

ShippedPersistenceImpl9/10Criticality10/10

One database is the filesystem, the vector store, and the tenant boundary at once — Postgres with pgvector holds documents, chunks, memory, goals, and audit, and row-level security enforces isolation underneath all of it.

Mechanism

SQLAlchemy 2 async over asyncpg, models per domain, migrations via Alembic (~44 revisions). Vectors live in pgvector columns alongside their metadata, so filtered vector search is one query. RLS policies filter every row by app.tenant_id. Keeping vectors, metadata, and relational data in one transactional store is what makes filtered retrieval, joins, and tenant isolation simple — the alternative (a separate vector database) turns every filtered query into a cross-system join.

In AgentVerse

  • app/db/models/one file per domain (24 model modules)
  • app/db/migrations/Alembic revisions
  • app/db/rls.pythe isolation enforcement
  • app/db/session.pyasync session factory
  • app/core/pools.pyconnection pooling (pgbouncer in the full stack)

Worked example

one query does isolation + scope + filter + ANN (chapter 6)
 SELECT ... WHERE tenant_id = current_setting('app.tenant_id')
   AND collection_id = ANY($1) AND metadata->>'jurisdiction' = 'DE'
   ORDER BY embedding <=> $2 LIMIT 50
no cross-system join, one transaction, RLS as the backstop

At production scale

The decision to keep everything in Postgres rather than adding a dedicated vector store is a deliberate simplification: transactions, joins, and RLS come for free, and pgvector is good enough for the scale most tenants reach. The migration discipline — never edit a deployed migration, always add a new one — is what keeps a 44-revision history deployable. Full treatment of the vector index in chapter 4.

Failure modes

  • Editing deployed migrations. Divergent schemas across environments.
  • Connection exhaustion. No pooling under fan-out load.
  • RLS bypassed by raw connections. A leak path (chapter 13).

Choose it when

  • The default persistence choice; revisit only at very large vector scale.

06Redis: pub/sub, cache, locks, checkpoints#

ShippedMessagingImpl9/10Criticality9/10

Redis is the platform's nervous system: it carries goal events across replicas, holds the cost counters and breaker state that must be shared, provides distributed locks, and backs the agent checkpointer.

Mechanism

Five distinct uses. Pub/sub delivers goal events from workers to the API for SSE. Cache holds semantic-cache and tool-result entries. Atomic counters hold cost budgets so accounting is accurate across replicas. Locks ensure one worker per goal. Checkpoints store agent state so goals survive worker restarts. Each is a case where the state must be shared across processes, which is exactly what Redis is for.

In AgentVerse

  • app/net/redis_factory.pyconnection management
  • app/services/goal_service.pypub/sub bridge
  • app/governance/cost.pyatomic cost counters
  • app/reliability/distributed_lock.py, redis_circuit_breaker.pylocks and shared breaker state
  • app/agent/graph.pyAsyncRedisSaver checkpointer

Worked example

one goal touches Redis five ways
 pub/sub    goal_events:acme:g-8891 → API → browser SSE
 cache      retrieval result served from semantic cache
 counter    INCRBY on cost:goal:g-8891 (atomic across workers)
 lock       lock:goal:g-8891 held by worker-4
 checkpoint agent state after each node → resume on restart

At production scale

Redis is what makes the platform horizontally scalable: workers are stateless because state lives in Redis and Postgres, so you add workers to add capacity. It is also a single point of failure to plan around — the checkpointer falls back to sync Redis then to in-memory, and the cost counters and locks need Redis to be highly available. Full treatment in chapters 11 (events) and 32 (scaling).

Failure modes

  • Redis as SPOF. Its outage stalling budgets, locks, and events.
  • Unbounded cache growth. No TTL or eviction.
  • Lock without expiry. A dead worker holding a goal forever.

Choose it when

  • Any multi-replica deployment.

07Celery and per-plan queues#

ShippedScalingImpl9/10Criticality9/10

The scheduler: goals, scheduled runs, and maintenance tasks run as Celery jobs, routed to per-plan queues so tenant tiers are isolated and enterprise tenants avoid noisy neighbours.

Mechanism

Celery workers pull from queues named by plan tier; a routing map sends each goal to its tenant's queue. Beat schedules periodic work — firing due triggers, ingestion syncs, memory consolidation, maintenance. A beat guard prevents duplicate beat schedulers. Task types cover goal execution, scheduled goals, and maintenance, each with its own concurrency and retry policy.

In AgentVerse

  • app/scaling/celery_app.pyPLAN_QUEUE_MAP, queue routing
  • app/scaling/tasks.pyrun_goal, run_scheduled_goal, fire_due_schedules, maintenance
  • app/scaling/beat_guard.pyone beat scheduler
  • app/scaling/priority_queue.py, parallel_executor.pypriority and parallelism

Worked example

PLAN_QUEUE_MAP  free→goals.free · starter→goals.starter · … · enterprise→…
 a free tenant submits 10,000 goals → they queue on goals.free
 an enterprise tenant's goal → goals.enterprise, drained by dedicated workers
 → the enterprise goal is not stuck behind the free backlog
beat fires due schedules, ingestion syncs, memory consolidation on cron

At production scale

Per-plan queue routing is the single most important multi-tenant scaling decision. Without it, tier differentiation is a lie — a premium tenant's latency is at the mercy of whoever submitted the biggest batch. With it, you scale workers per queue to match the SLA you sold. Full treatment in chapter 32.

Failure modes

  • Single queue. Noisy-neighbour latency.
  • Duplicate beat. Schedules firing twice.
  • No per-queue scaling. Workers idle on one tier, saturated on another.

Choose it when

  • Any multi-tenant async platform with tiers.

08Triggers and schedules#

ShippedSchedulingImpl8/10Criticality8/10

Agents that nobody typed a prompt into: cron schedules, webhooks, data-change events, and IoT signals that submit goals automatically, with natural-language scheduling on top.

Mechanism

A trigger is a source (cron, webhook, data change, IoT sensor, message queue) bound to a goal template. When it fires, it submits a goal on the tenant's behalf, subject to the same auth, budget, and governance as any other goal. Natural-language scheduling parses "every weekday at 9am, summarise overnight incidents" into a trigger spec. Webhooks are verified and rotated; triggers are rate-limited, deduplicated, and bulkheaded like any other work.

In AgentVerse

  • app/triggers/nl_scheduler.pyNL → TriggerSpec
  • app/triggers/store.py, models.pyScheduleStore, TriggerSpec, TriggerType
  • app/triggers/dispatcher.py, consumers/*dispatch and consumption
  • app/triggers/webhooks/verifier.py, rotation.pywebhook security
  • app/triggers/iot/*, data/consumers.pyIoT and data-change triggers
  • app/scaling/tasks.pyfire_due_schedules

Worked example

"every weekday at 9am, summarise overnight incidents and post to #ops"
 nl_scheduler → TriggerSpec(cron="0 9 * * 1-5", goal_template=..., channel=...)
 beat fires it → submits a goal as the tenant → runs the normal lifecycle
webhook trigger: a payment.failed webhook (verified) → submits a triage goal

At production scale

Triggers turn a request/response agent platform into an autonomous one, and they carry the same risks amplified: an unbounded trigger is a self-inflicted load spike, and a trigger that fires with stale authorisation acts on behalf of someone who may no longer be authorised. Rate-limit, deduplicate, and re-check authorisation at fire time. Full treatment in chapter 27.

Failure modes

  • Unbounded triggers. A load spike nobody scheduled.
  • Unverified webhooks. Attacker-submitted goals.
  • Stale authorisation. Firing on behalf of a departed user.

Choose it when

  • Any event-driven or scheduled autonomous work.

09Marketplace and templates#

PartialPlatformImpl7/10Criticality6/10

A gallery of goal templates, agent configurations, and workflows — so a tenant starts from a proven pattern (GST filing, AML screening, invoice processing) rather than a blank page.

Mechanism

Templates package a goal or workflow with its recommended patterns, tools, collections, and guardrails. The marketplace catalogs them by domain; a tenant instantiates one and customises it. This is how domain expertise is distributed — a template for GST return filing encodes the steps, the validation, and the HITL gates that a finance team would otherwise have to discover. Monetisation lets template authors be compensated.

In AgentVerse

  • app/enterprise/marketplace.py, marketplace_v2.pythe gallery
  • app/api/marketplace_monetization.pymonetisation
  • app/content/marketplace/the template content (insurance, banking, GST, government, cybersecurity…)
  • app/content/goal_templates/goal templates (HR, software, devops, sales, legal…)
  • app/workflow/templates/workflow templates (AML screening, KYC, invoice processing)

Worked example

tenant wants GST return filing
 instantiate the GST-filing template → comes with:
   plan pattern, gst.* tools, tax-policy collection, HSN validation,
   filing HITL gate, consensus for the filing action
 customise thresholds → run
weeks of setup replaced by a proven, governed starting point

At production scale

Templates are how a horizontal platform serves vertical needs: the 40+ marketplace domains and goal templates encode the workflows that make the platform immediately useful to a finance, HR, or security team. The governance is baked in — a template ships with the right gates — which is both a selling point and a safety property. Templates must be versioned and certified like any other configuration (chapter 10).

Failure modes

  • Uncertified templates. A shared config that has not passed evals.
  • Stale templates. Encoding a workflow the domain has since changed.

Choose it when

  • Serving common vertical workflows to non-expert tenants.

10RPA and browser automation#

PartialAutomationImpl7/10Criticality6/10

When a system has no API, drive its UI: an agent authenticates, navigates, and extracts using a real browser, with credentials injected out of the model's sight and every step captured for debugging.

Mechanism

A browser session (Playwright) authenticates with vault credentials injected at the browser layer, navigates via DOM analysis (falling back to vision), and acts. Sessions are managed and reused; successful selectors are remembered (visual memory, chapter 3); artifacts (screenshots, traces) are captured for debugging. It is brittle by nature, so it is instrumented heavily and reserved for systems with no API.

In AgentVerse

  • app/rpa/executor.py, runner.py, session.py, session_manager.pythe automation engine
  • app/rpa/credential_injector.pycredentials injected without model exposure
  • app/rpa/artifacts.pyscreenshots and traces
  • app/perception/browser_agent.py, page_analyzer.pypage analysis

Worked example

government tax portal, no API
 session authenticates (credentials injected at the browser, not the prompt)
 DOM analysis finds the filing form → fills → submits
 screenshots per step retained 7 days for debugging
 remembered selectors make the next run fast
UI change → extraction shape changes → alert, not a silent wrong result

At production scale

RPA is a bridge, not a strategy — it breaks whenever the target UI changes, so it is reserved for legacy and government systems with no other access. The credential-injection-at-the-browser-layer design is the security-critical part: the model drives the browser but never sees the password. Full treatment in chapter 5 (RPA extraction) and chapter 15 (screenshots).

Failure modes

  • UI change → silent wrong extraction. Validate the shape.
  • Credentials in the prompt or a screenshot. Inject at the browser, redact captures.

Choose it when

  • No API exists and the data matters. Never when an API does.

11External integration boundaries#

ShippedBoundaryImpl8/10Criticality9/10

Every point where the platform touches the outside world — connectors, webhooks, channels, egress — is a boundary that must authenticate, validate, rate-limit, and treat what comes back as untrusted.

Mechanism

The boundaries: outbound tool calls (MCP), inbound webhooks (verified and rate-limited), interaction channels (Slack, Teams, email, WhatsApp, Discord, Telegram, voice), and any HTTP egress (SSRF-guarded). Each applies the same discipline: authenticate the counterparty, validate the payload, rate-limit, and treat inbound content as untrusted data subject to injection scanning. The channels layer turns the platform into something reachable where users already are, not just an API.

In AgentVerse

  • app/gateway/channels/*slack, teams, email, whatsapp, discord, telegram, voice, webhook
  • app/gateway/webhook_delivery.py, router.pydelivery and routing
  • app/net/ssrf_guard.pyegress protection
  • app/integrations/slack/, zapier/, email/integration handlers
  • app/agent/exfil_guard.pyinbound content treated as untrusted

Worked example

inbound: a Slack message "reconcile March payouts"
 channel verifies the Slack signature → resolves the tenant + user
 → submits a goal (same auth, budget, governance as an API submission)
 → streams progress back to the thread
outbound: a web fetch → SSRF guard blocks internal addresses → content
 scanned for injection before it influences the agent

At production scale

The channels are how the platform meets users where they are — Slack and email are where work actually happens — and each is a new authentication and injection surface. The discipline is uniform: an inbound message is a goal submission subject to every control, and inbound content is untrusted. SSRF protection on every egress is the boundary that stops an agent being turned into a proxy into your own network.

Failure modes

  • Unverified inbound channels. Anyone submitting goals as anyone.
  • Egress without SSRF guard. The agent as an internal-network proxy.
  • Channel content trusted. Injection through a Slack message.

Choose it when

  • Any integration inbound or outbound — so all of them.

What is missing here

  • Connector health SLAs. Breakers protect against failure, but there is no per-connector SLA tracking that would let a tenant know a connector is chronically unreliable.
  • A vector-store abstraction. pgvector is assumed; very large deployments would benefit from a pluggable vector backend behind the same interface.
  • Template certification pipeline. Templates exist; a required "certified against evals before listing" gate is thinner than it should be (chapter 10).
  • Cross-region active-active. Redis and Postgres are assumed regional; a multi-region story for residency-split tenants is future work (chapter 32).
